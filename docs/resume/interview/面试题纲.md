## 正篇：Data Agent 业务题

---

### 一、业务背景

| 层级 | 面试官问法 | 第一句答题 |
|------|-----------|-----------|
| 宽问 | "介绍一下你在智能院的实习，做了什么项目？" | "我参与的是金融工商智能实验室自研的 Data Agent，核心是把自然语言转成 SQL 查询，让研究员不用写代码就能查数据库。" |
| 锥问 | "你在这项目里的具体职责是什么？" | "我负责智能问数这一块的体验优化，包括语义映射准确率提升、查询记忆复用、还有推荐问题。" |

**追问链：**

A. 用户与规模
1. 「简历说 500+ 名注册用户、日均 150 次查询——这 500+ 人包含哪些机构的？常驻和流动人员各占多少？日活大概多少？」
2. 「来自澳门大学、澳门科技大学、上外、中科院脑机所的用户——他们的研究方向差异很大，查询模式有没有明显不同？」
3. 「数据平台组有多少人？每个人的分工是怎样的？」
4. 「项目做了多久？你是在什么阶段加入的？」

B. 数据资产
4. 「实验室的数据库规模多大？200 多张表怎么组织的？」
5. 「为什么不直接让研究员写 SQL？用 Python/pandas 不也行吗？」

C. 技术全景
6. 「整个项目是单体还是分布式？后端是什么架构？」
7. 「Data Agent 整体链路是什么样的？你负责哪段？」
8. 「技术栈是什么？Java？Python？数据库用的什么？」

D. 业务价值与立项背景
9. 「实验室为什么要自研 Data Agent？外面现成的方案——Metabase、Superset、甚至是直接买 Tableau——为什么不行？」
10. 「这个项目在实验室里的"地位"是什么？是某个导师的课题？横向项目？还是实验室自己需要用的基础设施？」
11. 「你接手时，智能问数这块已经迭代到什么程度了？在你之前的版本，用户反馈最大的痛点是什么？」
12. 「有没有和竞品对标过？比如阿里的 Quick BI、百度的 Sugar BI，你们觉得自己差在哪、好在哪？」

E. 用户画像与真实使用场景
13. 「研究员最常查的三类问题是什么？举个例子，他们不会说"查一下表 A 的 B 字段"，他们问的是什么自然语言？」
14. 「有没有用户教不会、反复犯同样错误的情况？你怎么处理的？」
15. 「有没有研究员绕过 Data Agent，偷偷自己写 SQL？你知道的话怎么办？」

F. 运营与事故
16. 「系统出过生产事故吗？最严重的一次是什么？怎么排查的？」
17. 「LLM 有没有生成过完全错误的 SQL，导致研究员拿到了错的数据还信以为真？这种事发生过吗？怎么解决的？」
18. 「系统上线后，有没有用户因为体验太差而弃用？弃用率大概多少？」

G. 数据治理与质量
19. 「200 多张表，元数据怎么管理的？谁在维护？有没有字段名对不上、注释缺失的情况？」
20. 「跨表查询的时候，研究员用的字段名和数据库里的字段名对不上的情况怎么处理？比如用户说"市盈率"但数据库里字段叫 pe_ttm？」
21. 「数据更新频率是怎样的？实时？T+1？用户查到的数据可能已经过时了，这个你们怎么跟用户沟通的？」

H. 决策细节与替代方案（深水区）
22. 「你们选的向量库是什么？为什么没用 Elasticsearch 或者直接用 PostgreSQL 的 pgvector？是谁拍板的？」
23. 「项目开发过程中，有没有你提议过但被否决的方案？后来你回头看，觉得当时的判断对不对？」
24. 「你现在回头看这个项目，最大的遗憾是什么？如果重新做，你会改什么？」

### 二、智能问数体验优化

---

#### 2.1 SchemaMapper LLM 语义映射

| 层级 | 面试官问法 | 第一句答题 |
|------|-----------|-----------|
| 宽问 | "语义映射准确率你是怎么从 58% 提升到 81% 的，做了什么？" | "原 SchemaMapper 纯靠 BGE-M3 Embedding 向量匹配加规则过滤，短板在于语义相近的候选无法区分。我引入了 LLM 做两阶段精排——向量粗召回 Top-10，LLM 结合字段名、注释、数据类型、所在表名做消歧精选。" |
| 锥问 | "评测集怎么构造的？200 条够不够覆盖线上真实场景？" | "200 条人工标注，覆盖绿色经济、公司研究、经济研究三个主题域，简单单表 40%、多表关联 35%、复杂聚合 25%，模拟线上流量分布。" |
| 锥问 | "LLM 消歧的 prompt 传了什么上下文？候选的哪些字段一起给了？" | "每个候选传字段名、中文注释、数据类型、所在表名——四维信息。光传字段名 LLM 区分不了 total_profit 和 net_profit，加了注释才知道一个叫利润总额一个叫净利润。" |

**追问链：**

A. 数字深挖（面试官对简历数字的本能验证）
1. 「58% → 81%，+23 个百分点——这个提升是怎么测出来的？评测集怎么构造的？标注者和你有分歧吗？」

B. Pipeline 全链路（逼你画出完整流程）
2. 「从用户输入"查一下比亚迪去年的净利润"开始，到最终映射出表/字段，中间经过哪些步骤？LLM 是在哪个位置介入的——前置替代向量匹配，还是后置对候选集做重排序？」
4. 「向量粗召是怎么做的？BGE Embedding 对每个实体召回 Top-K 候选，K 是多少？为什么选这个 K？」
5. 「规则过滤了什么？举个例子——什么情况下向量召回的候选会被规则直接干掉？」

C. LLM 的角色定位（区分"调包侠"和"真做过"）
6. 「LLM 在这里具体做了什么——是选择题（给定 5 个候选，选一个）、排序题（排 Rank 1-5）、还是开放输出（让它自己猜字段名）？」
7. 「如果候选集里没有正确答案——向量召回漏掉了真正该匹配的字段——LLM 会怎么表现？它会随便选一个还是输出"找不到"？你怎么处理的？」
8. 「有没有让 LLM 输出 confidence score？低于某个阈值就拒绝映射？」

D. Prompt 工程细节
9. 「你的 prompt 里传了什么上下文？只是字段名，还是连字段注释、数据类型、所在表名一起传进去了？一行候选大概占多少 token？」
10. 「一轮调用传多少个候选？token 消耗和覆盖率之间怎么权衡的？」
11. 「用户 query 里包含多个实体——比如"查比亚迪和宁德时代去年的营收和净利润"——LLM 是一次调用处理所有实体，还是每个实体单独调一次？为什么？」

E. 顽固 case 与兜底
12. 「映射错误一般出在什么情况？有没有你印象特别深的一个错误 case？」
13. 「如果 LLM 也映射错了，有兜底方案吗？还是让后面的 SQL 生成直接炸？」

F. 与 SuperSonic 的对照（领域知识深水区）
14. 「SuperSonic 的 SchemaMapper 是纯 embedding 做的，跟你这套向量 + 规则 + LLM 的方案有什么差异？如果你现在去改 SuperSonic 的 SchemaMapper，会把这套方案搬过去吗？为什么能搬 / 不能搬？」

#### 2.2 查询记忆复用（向量库 + 评审）

| 层级 | 面试官问法 | 第一句答题 |
|------|-----------|-----------|
| 宽问 | "查询记忆复用是怎么做的？" | "LLM 对每条执行 SQL 从字段匹配度、结果合理性、时间范围正确性三维度评分——≥4/5 自动入库，3-4 分人工审核，<3 丢弃。记忆库累计 800+ 条，新查询召回 Top-3 相似历史拼进 prompt 做 few-shot。" |
| 锥问 | "你说的'成功执行的 SQL'，成功的标准是什么？SQL 没报错就算成功？" | "不算。SQL 不报错但返回 NULL 或者答非所问太常见了。所以我们用 LLM 从三个维度评分——字段匹配度（返回的列有没有覆盖用户要的指标）、结果合理性（数据量级是不是在预期范围）、时间范围正确性——综合 ≥ 4 分才叫成功。" |
| 锥问 | "87% 的端到端准确率是怎么定义的？是离线评测集还是线上抽样？" | "端到端——从用户自然语言到返回正确答案。用线上真实流量随机抽样的 300 条人工标注作为评测集。优化前 72%，加了记忆库到 87%，+15 个百分点。" |

**追问链：**

A. "成功"的定义（整个模块最核心的概念陷阱）
1. 「"成功执行的 SQL"——成功标准是什么？SQL 不报错就算成功？还是跑出来的结果经过了人工验证？」
2. 「SELECT 语句对数据库来说几乎不会报语法错——即使字段不存在也只会返回 NULL。你是怎么区分"技术成功"和"语义成功"的？」
3. 「这个区分是不是你引入 LLM 自动评审的动机？因为研究员不可能每条 SQL 都人工确认。」

B. 记忆库的数据结构（你到底存了什么东西）
4. 「一条记忆是怎么存储的？能不能举一个具体例子——一条用户查询从入库到被复用的完整生命周期？」
5. 「存到向量库里做 embedding 的对象是什么——用户的自然语言？SQL？还是两者拼接？对应的 SQL 是作为 payload 还是单独存？」
6. 「一条记忆记录包含哪些字段？除了 query embedding 和 SQL，有没有存元信息——用户、时间、评审状态、被复用次数？」

C. LLM 自动评审的工程细节（最"脏"的活儿）
7. 「LLM 自动评审评的是什么东西？你给它看的是 SQL 文本本身——还是把 SQL 的执行结果也传进去了？」
8. 「评审需要哪些输入？用户的原始问题、生成的 SQL、SQL 的执行结果预览——三个缺一个，LLM 就是盲猜。你传了哪些？」
9. 「评审的维度有哪些？有没有一个结构化的评分标准，还是就让 LLM 输出"好/坏"？」
10. 「LLM 评审的 prompt 你改过几版？最坑的一次误判是什么——比如 LLM 把什么情况判错了？」

D. 人工审核的真实运营
11. 「人工审核是谁在审？审一条大概多久？人请假或者某周特别忙怎么办？」
12. 「LLM 评审的判断和人审的判断，有过冲突吗？比如 LLM 说这条 SQL 很好，但你看了之后发现完全是错的——最典型的一个例子是什么？」
13. 「你审过的最离谱的一条错误 SQL 是什么样的？怎么发现的？」

E. 87% 准确率的拆解
14. 「87% 是用离线评测集测的还是线上真实流量抽样的？评测集有多少条？」
15. 「87% 是对比什么基线的？优化前是 72%——加上记忆库提升了 15 个百分点。这 15pp 里，记忆库有多少贡献，SchemaMapper 的优化有多少贡献？」
16. 「记忆库的增益在哪些类型的 query 上最明显？哪些类型上几乎没帮助？有没有做过按 query 类型的拆分分析？」
17. 「有没有记忆库反而帮倒忙的情况——召回了相似的错误 SQL 作为 few-shot，引导 LLM 也犯错？」

F. 技术债与诚实复盘
18. 「记忆库有没有淘汰机制？只进不出的话，错误的 SQL 怎么清理？」
19. 「有没有发生过记忆库里一条错误 SQL 被反复召回，污染了连续好几天的回答这种事？怎么发现的？怎么修的？」
20. 「你现在回头看，记忆复用这套方案最大的技术债是什么？」

#### 2.3 推荐问题

| 层级 | 面试官问法 | 第一句答题 |
|------|-----------|-----------|
| 宽问 | "为什么要做推荐问题？痛点是什么？" | "拆场景：行为实验助理反复查运维题——『未发报酬有哪些人』『校准失败多少人要补招』『场次男女比×厌恶风险比例』；绿色金融等靠内置引导开口（试验区碳面板、ESG×ROA 等）。内置 15%、相似 11%。" |
| 宽问 | "推荐问题是怎么实现的？" | "双通道——内置放绿色金融引导题 + 行为运维 FAQ（贡献日均查询 15%）；相似异步召回历史成功题（贡献日均查询约 11%）。两条都是 `source`/总查询，B 端不主报曝光 CTR。共用向量库，前端去重。" |
| 锥问 | "前两个模块都有量化指标，推荐问题有数据吗？" | "有——内置贡献 15%、相似贡献 11%，分母都是总查询次数：`count(source=preset|similar)/count(全部 query)`。异步召回用版本号防竞态错挂。" |
| 锥问 | "推荐问题的向量库和记忆复用的向量库是同一个吗？" | "是同一个底层向量库，但消费方式不同——记忆复用以 SQL 作为 payload 拼进 LLM prompt，同步调用、精度要求极高；推荐问题以自然语言问题作为展示文本，异步调用、允许一定容错。" |

**追问链：**

A. 数字与动机
1. 「痛点是全站『反复问』，还是主要在行为实验？金融侧推荐到底解决什么？」
2. 「内置 15%、相似 11%——是不是同分母？为什么不用曝光点击率？有没有按 Agent 拆过？」
3. 「内置推荐的列表是固定的还是动态更新的？金融引导题和行为运维 FAQ 怎么配？」
4. 「假设你只有 10 分钟给面试官讲你在 Data Agent 做的最有价值的一件事，你会选 SchemaMapper、记忆复用、还是推荐问题？为什么？」

B. 两种推荐模式的设计逻辑
5. 「内置（引导）和相似（反复查近邻）——为什么要两个通道？场景权重怎么分配？」
6. 「内置推荐和相似问题推荐——这两个在不同场景下分别触发，还是同一个界面同时展示？如果是后者，用户怎么区分它们？」
7. 「用户点了一个内置推荐查了"比亚迪去年营收"，出来相似推荐还是"比亚迪去年营收"的变体——这不就重复了？有没有做过去重？」
8. 「内置推荐被点过之后，会不会在相似推荐里降权？或者说两条逻辑完全没有联动？」

C. 与 2.2 记忆复用的关系（简历结构的核心疑点）
9. 「你的查询记忆复用里有一个向量库，推荐问题里也有一个向量库——这两个是同一个库还是两个独立的？如果是同一个，为什么简历要拆成两个模块写？」
10. 「如果是同一个底层向量库、两种消费方式——你能不能讲清楚：召回触发、召回内容、消费方、时效要求、精度要求，这五个维度上两者有什么区别？」
11. 「推荐问题的向量库和记忆复用的向量库，写入时机一样吗？是共享同一套入库逻辑，还是各自有一条写入链路？」

D. 异步召回的工程细节（简历里最容易被一笔带过的难点）
12. 「异步召回具体是怎么做的？简历说 <1.5s——这个时间是怎么测出来的？P50 还是 P99？」
13. 「用户快速连续输入多个 query——"比亚迪营收" → "宁德时代营收" → "宁德时代净利"——后台发起三次异步召回，返回顺序不可控。你说的版本号机制是怎么解决的？」
14. 「异步召回超时怎么处理？超时了是展示空状态还是回退到内置推荐？」
15. 「推荐结果回来了但用户已经进入下一个查询了——是静默丢弃还是预加载？」

E. 管理员预配置——不像工程师会提出的方案
16. 「内置推荐由管理员预配置——这个管理员是谁？是你？还是实验室的某个研究员？你给管理员看数据了吗？」
17. 「高频提问你怎么定义"高频"？管理员是凭感觉配的，还是你给了一个后台页面能看到过去一周的 Top 50 查询？」
18. 「你有没有想过应该做成自动化的——根据查询频率自动生成 Top 10，管理员只审核微调？为什么没做？」

F. 推荐问题的负作用（被忽略的暗面）
19. 「推荐会不会固化题型——金融侧只点引导例题、行为侧只点运维 FAQ，研究长尾更少被问？怎么权衡？」
20. 「金融数据场景下，错误解读可能影响研究结论——推荐系统会不会放大这个风险（把错误成功题传给更多同事）？」

### 三、深度研究（首条）—— 双层解读

| 层级 | 面试官问法 | 第一句答题 |
|------|-----------|-----------|
| 宽问 | "深度研究模块做了什么？" | "查询结果默认经 LLM 做描述性解读（<2s），深度研究作为可选项做多步联网交叉验证与归因分析，典型可观测耗时是数分钟级，临时超时建议 11 分钟；超时或最终报告不可用时静默回退，不阻断主链路。耗时口径仅来自 n=3 的运行时长下界，不是正式 SLA。在 GAIA-165 上整体 53%，Level 1 达 68%，Level 3 仅 19%——差距在复杂多步推理。" |
| 锥问 | "你在简历里专门写了 SOTA 是 80%。你为什么要把这个对比放进去？不担心面试官觉得 53% 太低了吗？" | "不担心。写 SOTA 是因为只看 53% 没法判断它到底算什么水平——GAIA leaderboard 上第一名 h2oGPTe 是 80%，说明 53% 在一个单人、业余时间做的系统里是一个真实的位置。Level 拆开看的话，简单问答 68% 还不错，多步推理确实是短板。" |

1. 「多租户怎么实现的？不同用户/研究组怎么隔离数据和元数据？」

   - 加分回答模板：Data Agent 不需要方言转换，但 SuperSonic 的 SemanticTranslator 在 S2SQL→物理 SQL 时，会根据数据源类型注入不同方言适配器——你注意到了吗？

4. 「API 设计层面——查询是同步还是异步？超时怎么处理？」

   - 深度研究异步：用户点"深入分析"后，分析需要 3 分钟——前端是轮询还是 WebSocket？轮询的间隔和最大次数？任务状态机（pending/running/success/failed）怎么设计的？用户关闭页面了，后台任务还在跑吗？

5. 「语义模型的元数据怎么管理？版本更新了怎么办？」

   - 如果是你：底表加新字段，语义模型怎么感知？手动更新还是自动发现？
   - 如果是研究员/DBA：改完了系统怎么知道？需要重启吗？热加载怎么做的？
   - 版本回滚：有人把"营收"定义改错了，能回滚吗？谁改的能查到吗？
   - 追：SuperSonic 有 MySQL binlog 做变更通知——你看过这部分实现吗？Data Agent 的元数据管理最大的坑是什么？

6. 「有没有做权限控制？表级/列级权限？」

1. 「多轮对话怎么处理的？用户的模糊引用（'上一条'、'那个公司'）怎么解析？」

2. 「上下文窗口有限，怎么管理长对话？」
   - 先做概念区分：你简历里"自适应压缩"是 Multi-Agent 深度研究的上下文（工具调用结果、子 Agent 报告），跟多轮对话上下文（用户交互历史）是两回事。你能讲清楚两者的管理策略有什么不同吗？
   - 多轮对话上下文：滑窗截断 + LLM 摘要，难点是截断时不能丢掉第一轮提到的公司名
   - Multi-Agent 深度研究上下文：结构化摘要（保留结论、丢弃原始 payload），难点是信息密集度远超对话
   - 追：如果把对话上下文和 Agent 执行上下文混在一起管理——会出什么问题？

3. 「对话改写 / query rewriting 做了吗？怎么做？」
   - 提出一个下游影响问题：假设给 Data Agent 加上多轮对话——用户第一轮"比亚迪去年营收"，第二轮"那净利呢"。QueryRewriter 改写后变成"比亚迪去年净利润是多少"。这个改写后的 query，能直接喂给你之前做的 SchemaMapper 吗？
   - 追：如果改写把"比亚迪"丢了，或者把"净利"翻成了 Embedding 召回不稳定的表达——你的 SchemaMapper 怎么兜底？这说明 QueryRewriter 的质量直接影响全链路——你认同吗？

4. 「用户输入错误（拼写错误、术语不准确）怎么处理？」
   - 用 Data Agent 场景：如果用户把"比亚迪"打成了"比亚笛"，你的 SchemaMapper 在这一步会怎样？BGE Embedding 对同音错字的鲁棒性好吗？LLM 消歧能自动纠错吗？
   - 诚实回答模板：如果 Data Agent 没做纠错——"实验室研究员输入质量很高，基本不会打错字，所以没有专门做。但我知道这是一个真实问题。"
   - 延伸到 SuperSonic：SuperSonic 的 SchemaMapper 是纯 embedding、没有 LLM 消歧——它对拼写错误的容错更差。你觉得拼写纠错应该放在 pipeline 的哪一步？QueryRewriter（改写阶段）还是 SchemaMapper（映射阶段）？为什么？

5. 「有没有做意图识别？用户说'帮我分析一下'和'直接给数据'要不要走不同路径？」
   - 连接你的简历：你的双层解读——描述性 vs 深度研究——是用户手动选的。你有没有想过根据用户原始 query 自动判断走哪条路径？
   - 可自动路由的信号：query 复杂度（涉及多少实体、是否跨表）、用户行为、意图词（"为什么"vs"查一下"）
   - 自动路由的风险：用户说"帮我分析一下"可能只需要描述性解读就够了——自动触发深度研究会浪费资源
   - 加分回答：描述性解读默认输出 + 底部动态插入引导语"想进一步了解原因？点击深入分析"——不替用户做决策
   - 追：SuperSonic 的 Chat 模块有意图路由吗？它的 Assistant 模式和你 Data Agent 的双层设计，你更认可哪个？为什么？
