### 0.2 产品定位

- **默认**：描述性解读（<2s）——只基于查数结果做结构化摘要 + 关键指标解释
- **可选**：深度研究——多步联网交叉验证 + 归因；失败/超时 → **静默回退**描述性解读，不阻断主链路
- **触发**：用户主动选（非默认全开）
- **通信**：独立 Python 微服务 ↔ Java 主链路（REST；深度研究偏异步长任务）

### 0.4 诚实边界

- 53% 是有参照的真实位置；短板在 Level 3 多步推理
- 价值在：跑通链路 + 工程化（追踪/熔断/断点续跑/不挡主链路），不是算法创新
- 这是 harness 工程；Prompt/评测有博士后建议

## 2. L1 追问链

### A. GAIA：53% 与 SOTA 对比

#### A1. Level 3 差到什么程度？典型失败是什么？

- **第一句：** Level 从 68% 降到 47%、再到 19%，衰减主要集中在需要多步工具调用、证据交叉验证和最终归纳的复杂题；典型情况是前一步检索偏了，后续推理继续放大偏差。
- **要点：**
  - L1 多为较短链路，68% 说明基础检索和回答链路可用；L2、L3 增加约束、工具跳数和证据冲突后，错误会累积。
  - 典型失败不是某一个工具完全不可用，而是多跳过程中选错信息源、漏掉约束，或没有完成跨来源一致性校验。
  - 面试时先讲失败模式，不虚构某道具体题；若要举例，可用「先定位实体 → 查多个来源 → 对齐时间口径 → 计算并归纳」这类链路说明。
- **易踩坑：** 把 L3 19% 包装成「模型偶尔波动」，或临场编造一个无法复盘的 GAIA 原题。
- **回看标本：** `main.py` 的 `common-benchmark` / `trace` 入口；`common_benchmark.py` 的 pass@k 尝试、判分和日志记录。

#### A2. 与 SOTA 80% 的差距在哪里？

- **第一句：** 差距不在单点功能，而在复杂任务上的系统能力：模型推理、工具选择、跨来源校验和编排纠错共同决定上限，Level 衰减说明多步链路是主要矛盾。
- **要点：**
  - 68% → 47% → 19% 表明任务越复杂，差距越明显；不能只归因于模型，也不能只归因于工具稳定性。
  - SOTA 约 80% 是定位坐标，不是宣称接近 SOTA；我的结果来自单人业余时间完成的工程实践，真实价值是跑通评测与服务链路。
  - 改进优先级是先增强失败可观测性和断点续跑，再基于错误样本优化工具选择、证据校验与 Prompt。
- **易踩坑：** 说成「换更强模型就能追平」，或把复习标本中的编排能力说成自己的算法发明。
- **回看标本：** `main.py` 用 `common-benchmark` 批量评测、用 `trace` 单题追踪；`common_benchmark.py` 记录每次 attempt 与 judge 结果，支持按错误样本复盘。

#### A3. GAIA 最常见的失败类型是什么？

- **第一句：** 我的排序是多跳推理失败最多，其次是工具链中断，再其次才是超时；超时阈值和端到端耗时要等实测后再给数字。
- **要点：**
  - 多跳推理失败包括漏约束、错误信息继续传播、多个来源无法对齐，以及计算或归纳阶段出错。
  - 工具链中断包括检索无结果、返回结构异常和中间调用失败；它与「答案推错」要分开统计。
  - 超时是结果状态，不等于根因；应结合 trace 判断卡在检索、工具调用还是推理循环。
  - 评测支持 pass@k，并扫描已有日志：已有完整答案和判分结果可直接复用；缺失或执行失败的 attempt 才重跑，实现断点续跑。
- **易踩坑：** 主动报未经实测的超时阈值，或把所有未完成任务都归为超时。
- **回看标本：** `common_benchmark.py` 的 `scan_latest_attempt()` 加载已有 log；`run_single_task()` 对 pending / run_failed 续跑，并在 pass@k 命中后提前停止。

### B. 语言切换：Java → Python

#### B4. 为什么 Agent 层改用 Python？

- **第一句：** 这是按边界选技术栈：LLM、MCP、多 Agent 编排和检索生态用 Python 集成成本更低；稳定的 Java 查数主链路不动，避免为追生态重写核心业务。
- **要点：**
  - Python 侧负责深度研究的编排运行时、工具接入、评测与服务化；Java 侧继续负责成熟的查数链路。
  - 独立微服务隔离依赖和故障域，深度研究失败时可回退描述性解读，不影响主请求。
  - 技术选型依据是生态成熟度、迭代效率和边界清晰度，不是「Python 天生比 Java 适合所有 AI 场景」。
- **易踩坑：** 贬低 Java 的 LLM 能力，或说成整个 Data Agent 都迁移到了 Python。
- **回看标本：** `server/app.py` 以 FastAPI 暴露产品服务；`server/bridge/runner.py` 将服务请求适配到 Agent pipeline。

#### B5. Java 与 Python 服务怎么通信？

- **第一句：** 查数结果走 REST 同步交接，深度研究按异步任务执行并回传进度；跨服务统一携带同一个 `traceId`，在 ELK 中串起 Java 主链路和 Python Agent 链路。
- **要点：**
  - REST 适合查数结果、上下文和任务参数的明确边界；深度研究耗时不稳定，不让 Java 请求线程同步等待完整研究过程。
  - 异步任务需要任务 ID、状态查询或流式事件、幂等启动和失败回退；产品层可用 WebSocket / SSE 展示进度，但它不是跨服务治理的唯一协议。
  - `traceId` 贯穿入口、任务、工具调用和回退日志，便于跨语言定位问题；日志字段与业务背景中的 ELK 叙事保持一致。
- **易踩坑：** 把标本的 WebSocket 产品交互直接说成 Java 与 Python 的唯一通信方式，或声称已采用未落地的消息队列。
- **回看标本：** `server/app.py` 接收 WebSocket `start` 后用 `asyncio.create_task()` 启动任务；`server/bridge/runner.py` 规范化 `task_id`、执行 pipeline 并流式发送报告片段。

#### B6. 技术栈切换是谁决策的？现在还会这样选吗？

- **第一句：** 我是深度研究服务的 0-1 owner，负责技术选型和落地；博士后主要咨询 Prompt 调优与评测方法。现在重选，我仍会保留 Java 主链路、Python Agent 微服务的边界。
- **要点：**
  - 我的职责覆盖编排运行时、工具接入、服务化、追踪和熔断；博士后提供 Prompt 与测评集方面的建议，不主导工程实现。
  - 继续选 Python 的前提是 Agent 生态和快速试验仍是主要矛盾；如果团队治理成本上升，会优先收紧 API 契约、部署和可观测性，而不是先重写语言。
  - 这套实现源于个人比赛实践后接入业务；标本用于对齐工程细节，不把 MiroFlow 或开源框架说成「我发明的」。
- **易踩坑：** 把咨询关系说成共同开发，或把个人技术选型描述为团队既定方案。
- **回看标本：** `server/app.py` 负责会话、异步任务和错误回传；`server/bridge/runner.py` 负责配置、pipeline 组件创建、执行与结果流式输出。
