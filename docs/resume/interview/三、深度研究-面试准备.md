### 0.2 产品定位

- **默认**：描述性解读（<2s）——只基于查数结果做结构化摘要 + 关键指标解释
- **可选**：深度研究——多步联网交叉验证 + 归因；失败/超时 → **静默回退**描述性解读，不阻断主链路
- **触发**：用户主动选（非默认全开）
- **通信**：独立 Python 微服务 ↔ Java 主链路（REST；深度研究偏异步长任务）

- 这是 harness 工程；Prompt/评测有博士后建议

## 2. L1 追问链

### A. GAIA：53% 与 SOTA 对比

#### A1. Level 3 差到什么程度？典型失败是什么？

- **第一句：** Level 从 68% 降到 47%、再到 19%，衰减主要集中在需要多步工具调用、证据交叉验证和最终归纳的复杂题；典型情况是前一步检索偏了，后续推理继续放大偏差。
- **要点：**
  - L1 多为较短链路，68% 说明基础检索和回答链路可用；L2、L3 增加约束、工具跳数和证据冲突后，错误会累积。
  - 典型失败不是某一个工具完全不可用，而是多跳过程中选错信息源、漏掉约束，或没有完成跨来源一致性校验。
  - 面试时先讲失败模式，不虚构某道具体题；若要举例，可用「先定位实体 → 查多个来源 → 对齐时间口径 → 计算并归纳」这类链路说明。
- **易踩坑：** 把 L3 19% 包装成「模型偶尔波动」，或临场编造一个无法复盘的 GAIA 原题。
- **回看标本：** `main.py` 的 `common-benchmark` / `trace` 入口；`common_benchmark.py` 的 pass@k 尝试、判分和日志记录。

#### A2. 与 SOTA 80% 的差距在哪里？

- **第一句：** 差距不在单点功能，而在复杂任务上的系统能力：模型推理、工具选择、跨来源校验和编排纠错共同决定上限，Level 衰减说明多步链路是主要矛盾。
- **要点：**
  - 68% → 47% → 19% 表明任务越复杂，差距越明显；不能只归因于模型，也不能只归因于工具稳定性。
  - SOTA 约 80% 是定位坐标，不是宣称接近 SOTA；我的结果来自单人业余时间完成的工程实践，真实价值是跑通评测与服务链路。
  - 改进优先级是先增强失败可观测性和断点续跑，再基于错误样本优化工具选择、证据校验与 Prompt。
- **易踩坑：** 说成「换更强模型就能追平」，或把复习标本中的编排能力说成自己的算法发明。
- **回看标本：** `main.py` 用 `common-benchmark` 批量评测、用 `trace` 单题追踪；`common_benchmark.py` 记录每次 attempt 与 judge 结果，支持按错误样本复盘。

#### A3. GAIA 最常见的失败类型是什么？

- **第一句：** 我的排序是多跳推理失败最多，其次是工具链中断，再其次才是超时；超时阈值和端到端耗时要等实测后再给数字。
- **要点：**
  - 多跳推理失败包括漏约束、错误信息继续传播、多个来源无法对齐，以及计算或归纳阶段出错。
  - 工具链中断包括检索无结果、返回结构异常和中间调用失败；它与「答案推错」要分开统计。
  - 超时是结果状态，不等于根因；应结合 trace 判断卡在检索、工具调用还是推理循环。
  - 评测支持 pass@k，并扫描已有日志：已有完整答案和判分结果可直接复用；缺失或执行失败的 attempt 才重跑，实现断点续跑。
- **易踩坑：** 主动报未经实测的超时阈值，或把所有未完成任务都归为超时。
- **回看标本：** `common_benchmark.py` 的 `scan_latest_attempt()` 加载已有 log；`run_single_task()` 对 pending / run_failed 续跑，并在 pass@k 命中后提前停止。

### B. 语言切换：Java → Python

#### B4. 为什么 Agent 层改用 Python？

- **第一句：** 这是按边界选技术栈：LLM、MCP、多 Agent 编排和检索生态用 Python 集成成本更低；稳定的 Java 查数主链路不动，避免为追生态重写核心业务。
- **要点：**
  - Python 侧负责深度研究的编排运行时、工具接入、评测与服务化；Java 侧继续负责成熟的查数链路。
  - 独立微服务隔离依赖和故障域，深度研究失败时可回退描述性解读，不影响主请求。
  - 技术选型依据是生态成熟度、迭代效率和边界清晰度，不是「Python 天生比 Java 适合所有 AI 场景」。
- **易踩坑：** 贬低 Java 的 LLM 能力，或说成整个 Data Agent 都迁移到了 Python。
- **回看标本：** `server/app.py` 以 FastAPI 暴露产品服务；`server/bridge/runner.py` 将服务请求适配到 Agent pipeline。

#### B5. Java 与 Python 服务怎么通信？

- **第一句：** 查数结果走 REST 同步交接，深度研究按异步任务执行并回传进度；跨服务统一携带同一个 `traceId`，在 ELK 中串起 Java 主链路和 Python Agent 链路。
- **要点：**
  - REST 适合查数结果、上下文和任务参数的明确边界；深度研究耗时不稳定，不让 Java 请求线程同步等待完整研究过程。
  - 异步任务需要任务 ID、状态查询或流式事件、幂等启动和失败回退；产品层可用 WebSocket / SSE 展示进度，但它不是跨服务治理的唯一协议。
  - `traceId` 贯穿入口、任务、工具调用和回退日志，便于跨语言定位问题；日志字段与业务背景中的 ELK 叙事保持一致。
- **易踩坑：** 把标本的 WebSocket 产品交互直接说成 Java 与 Python 的唯一通信方式，或声称已采用未落地的消息队列。
- **回看标本：** `server/app.py` 接收 WebSocket `start` 后用 `asyncio.create_task()` 启动任务；`server/bridge/runner.py` 规范化 `task_id`、执行 pipeline 并流式发送报告片段。

#### B6. 技术栈切换是谁决策的？现在还会这样选吗？

- **第一句：** 我是深度研究服务的 0-1 owner，负责技术选型和落地；博士后主要咨询 Prompt 调优与评测方法。现在重选，我仍会保留 Java 主链路、Python Agent 微服务的边界。
- **要点：**
  - 我的职责覆盖编排运行时、工具接入、服务化、追踪和熔断；博士后提供 Prompt 与测评集方面的建议，不主导工程实现。
  - 继续选 Python 的前提是 Agent 生态和快速试验仍是主要矛盾；如果团队治理成本上升，会优先收紧 API 契约、部署和可观测性，而不是先重写语言。
  - 这套实现源于个人比赛实践后接入业务；标本用于对齐工程细节，不把 MiroFlow 或开源框架说成「我发明的」。
- **易踩坑：** 把咨询关系说成共同开发，或把个人技术选型描述为团队既定方案。
- **回看标本：** `server/app.py` 负责会话、异步任务和错误回传；`server/bridge/runner.py` 负责配置、pipeline 组件创建、执行与结果流式输出。

### C. 双层解读的边界

#### C7. 同一份查询结果，两层分别输出什么？

- **第一句：** 描述性解读只回答表内「是什么」，把查询结果整理成趋势、对比和异常点；深度研究再引入外网与知识库证据做交叉验证，回答「为什么」，但会明确证据和不确定性。
- **要点：**
  - 以「比亚迪 2024 年净利润 300 亿」为例，描述性解读只基于结果表说明金额、同比变化、时间口径及与表内其他指标的关系，不自行补充原因。
  - 用户触发深度研究后，系统才会检索财报、行业资料、政策与知识库，核对数据口径，并从销量、价格、成本或政策等维度归因；没有证据支持的因素不写成确定结论。
  - 两层复用同一份查数结果作为事实起点，差异不在文案长短，而在证据范围与回答目标。
- **易踩坑：** 让描述性解读凭模型常识猜原因，或把深度研究说成「把基础摘要写得更长」。
- **回看标本：** `miro-flow-solution/src/core/pipeline.py` 的 `execute_task_pipeline()` 接收任务描述并产出最终报告；外部证据由 Agent 工具链补充，不改变上游查数结果。

#### C8. 这条边界为什么要由产品明确划定？

- **第一句：** 这是主动的产品决策：用默认描述性解读守住低延迟和高可用，再把联网、交叉验证与归因带来的延迟和失败面留给确实需要「为什么」的少数查询。
- **要点：**
  - 多数用户查完只需要快速确认「是什么」，没有必要为每次请求支付深度研究的等待和资源成本。
  - 深度研究增加联网搜索、知识库召回、多步工具调用和汇总，链路越长，延迟与失败面越大。
  - 明确边界还能约束答案可信度：表内事实和外部归因分层呈现，用户知道哪些来自数据、哪些来自外部证据。
- **易踩坑：** 引用未经验证的耗时、失败率或需求占比，或把双层设计解释成技术能力不足后的被动妥协。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 的主循环会经历多轮工具调用，并受 `max_turns` 约束，说明深度链路天然比表内摘要有更多延迟与失败节点。

#### C9. 用户如何触发？系统会不会自动开启？

- **第一句：** 深度研究由用户主动点击触发；系统可以在检测到归因意图时展示「进一步了解原因」的引导，但不会替用户自动启动高成本链路。
- **要点：**
  - 默认先交付描述性解读，让每次查数都有即时、可用的结果。
  - 对「为什么下降」「原因是什么」等意图，可在结果区增加引导点击，帮助用户发现能力，但点击前不创建深度任务。
  - 用户主动触发保留了对等待时间、资源消耗和答案深度的控制，也避免把一句模糊的「帮我分析」误判成深度研究。
- **易踩坑：** 把意图识别说成自动路由，或声称已有未经确认的具体按钮名称、页面位置和触发率。
- **回看标本：** `miro-flow-solution/server/app.py` 的产品服务接收显式 `start` 请求后创建异步任务，适合作为「用户确认后再启动」的工程参照。

### D. 失败回退

#### D10. 怎么定义失败？中间一步失败就整单失败吗？

- **第一句：** 失败看最终交付而不是单步状态：达到待实测的超时上限，或重试、换工具、汇总已有证据后仍没有可用的深度报告，才触发回退；中间一次工具或子任务失败不等于整单失败。
- **要点：**
  - 单步异常先在 Agent 内部消化：记录错误、尝试备选来源，其他子任务仍可继续，最终报告也可基于可验证的已有证据收束。
  - `max_turns` 到达代表停止继续扩张搜索，不是立刻丢弃所有结果；标本会转入 final summary，尝试把已有上下文汇总成最终答案。
  - 只有超时或最终报告为空、报错、缺少足够证据而不可用时，产品层才判定深度研究失败并回退。
- **易踩坑：** 把任一工具偶发失败等同于整单失败，或把超时阈值说成尚未实测的固定秒数。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 达到 `max_turns` 后标记 `task_failed` 并继续生成 final summary；`miro-flow-solution/src/core/pipeline.py` 在编排正常返回时标记 `completed`，在 `except Exception` 捕获异常时标记 `interrupted`，最终统一落盘。

#### D11. 回退后用户是否感知？为什么静默处理？

- **第一句：** 采用静默回退：用户始终保留已经拿到的描述性解读，不弹出阻断式失败提示；失败原因、阶段和 `traceId` 进入 ELK / 结构化日志，供内部复盘。
- **要点：**
  - 深度研究是查数后的增强项，失败不应把已经可用的基础答案变成红色错误，也不应阻断主链路。
  - 静默是指不打断用户，不是吞掉故障；内部仍记录超时、工具异常、汇总失败等原因，并可按阶段聚合定位。
  - 如果未来发现用户把描述性结果误认为深度报告，可改为弱提示，但当前优先保证答案连续性和操作负担最小。
- **易踩坑：** 把静默回退说成完全不记录失败，或在没有证据时声称用户一定察觉不到两层差异。
- **回看标本：** `miro-flow-solution/src/core/pipeline.py` 在 `finally` 中统一记录结束状态并保存 `TaskTracer`；异常路径同样写入错误详情，支持用户侧降级、内部可观测。

#### D12. 失败率和连续回退后的用户行为怎么看？

- **第一句：** 我不报没有线上统计支撑的失败率，也没有足够数据证明用户连续回退后的行为；能确认的产品取舍是，增强能力不稳定时优先交付可用的描述性答案，而不是让整次查数失败。
- **要点：**
  - 机制上，深度研究失败面来自联网、知识库、工具调用、轮次上限和最终汇总，日志应按失败阶段拆分，而不是只看一个总失败率。
  - 产品上，静默回退保障主任务完成，但也可能降低用户对深度能力状态的感知；需要结合后续的触发、完成、回退与再次触发数据再决定是否增加弱提示。
  - 若要评估连续回退影响，应先定义用户级漏斗和回退后的再次触发窗口，再用真实埋点回答，不能临场编造「第几次后放弃」。
- **易踩坑：** 交代未经核验的失败率，虚构连续三次回退后的用户行为，或用「用户无感」掩盖可靠性问题。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 记录工具失败、`max_turns` 与 summary 状态；`miro-flow-solution/src/core/pipeline.py` 统一保存任务结束日志，可为后续失败分层和用户漏斗关联提供基础。

### E. Main-Sub Agent 编排

#### E13. 子会话隔离具体怎么做？信息缺失怎么办？

- **第一句：** 主 Agent 不把完整对话历史复制给子 Agent，而是把子任务描述作为新会话的首条消息；每次调用都有独立的 session ID 和 message history，子 Agent 最终只把摘要报告回传主会话，从而控制上下文膨胀。
- **要点：**
  - 配置中的子 Agent 会先暴露成主 Agent 可调用的工具；主 Agent 选中后，`run_sub_agent()` 调用 `start_sub_agent_session()` 创建新会话，并以子任务描述初始化独立的 `message_history`。
  - `TaskTracer` 分开保存 `main_agent_message_history` 和按 session ID 索引的 `sub_agent_message_history_sessions`，既隔离推理上下文，也保留分会话追踪能力。
  - 隔离的代价是子 Agent 看不到主会话里的隐含条件。解决方式不是重新塞入全部历史，而是要求主 Agent 在委派时写全目标、范围、输入事实、输出要求和约束；若仍缺信息，再由主 Agent 补充描述后重派。
- **易踩坑：** 把隔离说成子 Agent 共享主 Agent 全量上下文，或只讲节省 Token、不承认任务描述不完整会导致误判。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 的 `run_sub_agent()` 初始化独立 `message_history`；`miro-flow-solution/src/logging/task_tracer.py` 的 `start_sub_agent_session()` 和 `sub_agent_message_history_sessions` 维护分会话记录。

#### E14. 子任务怎么分配？最多同时跑几个？

- **第一句：** 子任务由主 Agent 根据问题和可用子 Agent 的工具描述动态拆分、调度，不是把每类问题写死给固定角色；并发上限必须由运行配置和执行器共同约束，我不会把「每轮工具调用上限」直接当成「同时并发数」。
- **要点：**
  - `expose_sub_agents_as_tools()` 将每个子 Agent 的名称、能力描述和入参暴露给主 Agent，主 Agent 在推理过程中决定是否调用、调用哪个以及传入什么任务描述。
  - 主 Agent 可在一轮提出多个子任务，但标本的主循环当前对 tool call 逐个执行；因此它展示了 Main-Sub 调度边界，并不能证明这些调用已并行执行。业务侧若并发化，只应并行无依赖子任务，并设置全局并发、超时和异常隔离。
  - 上限分两层：`max_turns` 限制 Agent 循环深度，`max_tool_calls_per_turn` 限制单轮接收的工具调用数。以读过的 qwen37plus 示例为准，主 Agent `max_turns=20`、`max_tool_calls_per_turn=10`；后者是单轮调用上限，不是同时运行 10 个子 Agent。
- **易踩坑：** 临场编造固定并发数，把配置中的 `10` 说成并发度，或声称标本已用 `asyncio.gather()` 并行执行子 Agent。
- **回看标本：** `miro-flow-solution/src/utils/tool_utils.py` 的 `expose_sub_agents_as_tools()` 生成子 Agent 工具定义；`miro-flow-solution/src/core/orchestrator.py` 的主循环按工具调用动态调度且当前顺序执行；`miro-flow-solution/config/agent_llm_qwen37plus.yaml` 配置轮次和单轮工具调用上限。

#### E15. 主 Agent 如何汇总？子 Agent 质量差怎么办？

- **第一句：** 子 Agent 不把原始 tool dump 整包塞回主会话，而是在独立会话内先生成摘要报告，再作为一次工具结果回传；主 Agent 基于各报告的结论、证据和不确定性做二次汇总。
- **要点：**
  - 标本返回的是自然语言 summary，不是强制 JSON schema；工程上我更关注逻辑结构稳定，包括子任务结论、支持证据、来源、未解决冲突和置信度，而不是把所有中间调用细节复制给主 Agent。
  - 子 Agent 达到轮次上限或部分工具失败后仍会尝试基于已有上下文生成 summary，并在日志中保留失败状态；主 Agent 汇总时应区分「有证据的结论」和「未完成的候选」。
  - 如果报告答非所问、证据不足或彼此冲突，主 Agent 可以收紧任务描述后重派，或换子任务/工具补证；若预算或轮次不足，则保留不确定性并降低最终结论置信度，而不是强行拼成确定答案。
- **易踩坑：** 声称已有代码级 JSON 强校验或自动质量评分，或把低质量子报告未经核验直接写入最终结论。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 的 `run_sub_agent()` 先生成 `sub_agent_final_summary`，再将 `final_answer_text` 作为工具结果交回主循环；主 Agent 最后执行 final summary。

#### E16. 模块是谁做的？花了多久？

### F. Hybrid Search + MCP

#### F17. 什么情况走本地检索、联网检索或混合检索？

- **第一句：** 用户明确指定范围时服从指定；没有指定时，问附件、上传文档、合同或具体页码就优先查本地，问最新新闻、公告、政策或官网信息就优先联网，两类线索同时出现或意图不明确时默认混合检索。
- **要点：**
  - 如果当前任务没有可用的本地索引，即使问题提到附件，也不能假装查到了文件，直接转为联网检索，并在结果中保留路由原因。
  - 纯附件问题只查本地，纯时效问题只查 Web；例如「总结上传 PDF 第 5 页」走 local，「今天发布了什么行业政策」走 web，「结合附件研报和最新政策解释原因」走 hybrid。`route_query()` 只看 query 文本：须同时命中 local / web 两类 hint 才因关键词走 hybrid；仅含「近期」「政策」等 web hint 时走 web，两类 hint 都未命中则默认 hybrid。
  - 混合模式按配置给本地与 Web 结果加权，默认参考权重是 0.6 / 0.4；权重会先归一化，再统一按加权分数排序、按 URL 或来源与分块 ID 去重并截取 Top K。该数字是标本默认值，不包装成业务最优参数。
- **易踩坑：** 只背 `route_query()` 的条件分支，不用业务语言解释；附件与最新政策同时出现时只搜一边；没有本地索引仍声称引用了附件。
- **回看标本：** `miro-flow-solution/src/retrieval/router.py` 的 `route_query()` 处理强制模式、本地索引可用性、附件与时效线索及权重归一；`miro-flow-solution/src/retrieval/fusion.py` 负责加权排序、去重和 Top K 截断。

#### F18. MCP 工具调用成功率 98% 是怎么定义的？失败后怎么降级？

- **第一句：** 98% 指 MCP 工具请求返回了可解析、非空且满足调用目标的有效结果，不是深度研究任务有 98% 的成功率，更不代表最终结论有 98% 的准确率。
- **要点：**
  - 统计口径以单次工具调用为分母：成功要同时满足调用未超时、协议返回正常、结果非空、结构可解析且 Agent 可继续消费；连接成功但空召回、返回错误文本或 JSON 解析失败都不能记成功。
  - 常见失败分三类：连接或执行超时，检索完成但没有有效召回，以及工具返回结构异常、参数或结果解析失败。工具名挂错服务时，可先查找唯一拥有该工具的 MCP Server 并自动纠正；抓取失败时也可切换备用读取工具。
  - 降级顺序是「同工具限次重试或纠正参数 → 备选工具 / 备选来源 → 基于已有证据部分完成」。部分完成仍输出已验证结论，并明确缺失项与不确定性；只有最终报告不可用或达到总超时才回退到描述性解读。
  - 工具返回有效结果只证明调用层成功；深度研究还可能在多跳规划、证据冲突、计算和最终归纳阶段失败，因此工具成功率与任务成功率必须分开统计。
- **易踩坑：** 把 98% 说成 GAIA 任务成功率、深度研究完成率或答案准确率；把 MCP 进程启动成功就计为调用成功；某一步失败后丢弃全部已有证据。
- **回看标本：** `miro-flow-solution/src/tool/manager.py` 的 `execute_tool_call()` 统一处理超时、空内容、异常返回、Server 名纠错与备用读取；`miro-flow-solution/src/tool/mcp_servers/hybrid_search_mcp_server.py` 将路由、召回数量和融合结果封装为 MCP 工具返回值；`miro-flow-solution/config/tool/tool-hybrid-search.yaml` 注册工具命令与检索环境参数。

#### F19. 举一个金融研报与政策归因的 Hybrid Search 案例

- **第一句：** 我会用「结合上传的季度经营分析和近期公开政策，解释某业务指标为什么变化」作为案例：本地证据守住企业数据口径，联网证据补政策发布时间与适用范围，最后只输出两边都能支撑的归因。
- **案例骨架（示例可换成你真实项目名）：**
  1. 用户上传某上市公司的季度研报或经营分析表，再问「结合上传的季度经营分析，解释本季度毛利率变化；近期行业政策是否有影响」。问句同时含「上传」（local）与「近期」「政策」（web）两类 hint，因此走 hybrid。
  2. local 侧提取报告中的毛利率、销量、售价、成本和管理层解释，并记录报告期与页码；web 侧查询监管部门官网、政策原文及公司公开公告，核对发布日期、生效范围和适用对象。
  3. 融合时按来源与分块去重，优先保留原始研报、政府官网和公司公告。归因按「指标事实 → 内部经营因素 → 外部政策因素 → 证据强弱」组织，不把时间上相邻直接写成因果。
  4. 如果政策原文明确适用该行业，但研报没有披露量化影响，就表述为「可能的外部因素，当前证据不足以量化贡献」；如果 Web 检索失败，仍交付基于研报的经营归因，并明确政策部分未完成。
- **易踩坑：** 虚构公司内部经营数据或政策效果，把政策发布时间与指标变化的先后关系当作因果，或为了显得具体临场编造研报名称和页码。
- **回看标本：** `miro-flow-solution/src/retrieval/router.py` 对附件与政策线索选择 hybrid；`miro-flow-solution/src/retrieval/fusion.py` 融合两路证据；`miro-flow-solution/src/tool/mcp_servers/hybrid_search_mcp_server.py` 返回 route、mix、两路召回数和最终 results。

#### F20. 举一个行为科学相似研究的 Hybrid Search 案例

- **第一句：** 我会用「拿一份已有用户实验报告，寻找公开的相似行为科学研究，判断结论能否迁移」作为案例：本地检索还原实验设计，联网检索寻找相似机制和人群的公开证据，再比较边界条件，而不是只找标题相似的文章。
- **案例骨架（示例可换成你真实项目名）：**
  1. 用户上传一份关于「提醒频率是否影响任务完成率」的实验报告，再问「结合上传的实验报告，查找近期相似行为科学研究并评估能否用于产品策略」。问句同时含「上传」（local）与「近期」（web）两类 hint，因此走 hybrid。
  2. local 侧抽取样本、对照组、干预方式、观察周期、指标定义和局限；web 侧围绕提醒、注意力、习惯形成等机制检索高校、期刊或研究机构公开页面，不虚构具体论文标题。
  3. 相似性不只看关键词，而是比较干预机制、目标行为、样本人群、实验环境和指标口径；最终分成「直接可比」「机制相似但场景不同」「仅作背景」三档证据。
  4. 若公开研究与内部实验方向一致，也只说明外部证据增强了可解释性，不能替代本业务人群上的复验；若只召回弱相关材料，则输出本地实验结论与迁移风险，不强行给出推广建议。
- **易踩坑：** 编造论文标题、作者或显著性数字；把关键词相似等同于实验可比；忽略样本人群和指标口径差异，直接把学术结论外推到产品用户。
- **回看标本：** `miro-flow-solution/src/retrieval/router.py` 决定 local / web / hybrid；`miro-flow-solution/src/retrieval/fusion.py` 做证据融合与去重；`miro-flow-solution/config/tool/tool-hybrid-search.yaml` 提供自动路由和本地 / Web 权重配置。

### G. 工程化能力：追踪、并发、熔断与断点续跑

#### G21. 关键中间结果落盘后怎么回放？最复杂的一次 Bug 怎么排查？

- **第一句：** 每个任务用 `task_id` 关联一份结构化 trace，按 Agent turn 和时间顺序记录 LLM 响应、工具调用、子会话、状态与错误；排查时从最终异常状态反向定位到第一个偏离预期的 step，再结合该轮 message history 和 metadata 复现输入。
- **要点：**
  - `StepRecord` 包含 `step_name`、`message`、`timestamp`、`status` 和 `metadata`；`TaskTracer` 还保存任务输入、主 / 子 Agent message history、子会话 ID、最终答案、判分结果与错误。日志按 `task_id` 和 attempt 命名，可先定位任务，再按 step 时间线与会话边界回放。
  - pipeline 在执行中会阶段性 `save()`，并在 `finally` 统一写入 `completed` 或 `interrupted` 状态、错误栈和结束时间；即使任务异常，通常也能保留异常前的链路，而不是只剩一行报错。
  - 可用的排查例子是「某次工具返回结构异常，后续推理继续消费错误内容而跑偏」：先找最终答案开始偏离的 turn，再向前检查工具调用的名称、参数、返回状态和耗时，确认是调用失败、空结果、结构不可解析，还是 Agent 对正常结果理解错误。这里只说明标本字段支持的排查方法，不虚构具体生产事故和损失。
- **易踩坑：** 只说「有 ELK，所以能排查」，却讲不出 step、turn、session 和错误字段如何关联；或把标本中仅定义但未持续更新的 turn ID 字段说成已经完整驱动回放，实际还要结合 step 时间线与 message history。
- **回看标本：** `miro-flow-solution/src/logging/task_tracer.py` 的 `StepRecord`、`TaskTracer.log_step()` 与 `save()`；`miro-flow-solution/src/core/pipeline.py` 的运行状态更新、异常记录和 `finally` 落盘。

#### G22. 并发数一般设多少？一个任务挂了会影响其他任务吗？

- **第一句：** 并发数来自评测或服务运行配置，不把单轮工具调用上限当成并发度；批量评测用信号量限制同时运行的题数，并通过 `gather(return_exceptions=True)` 做单题异常隔离，一题失败会生成自己的失败结果，不取消其他题。
- **要点：**
  - 标本的 `run_parallel_inference()` 接收 `max_concurrent`，默认参数是 3，但真正运行时由 `benchmark.execution.max_concurrent` 传入；业务值要根据模型限流、工具容量、内存和任务耗时压测后确定，不能把默认值包装成生产最优值。
  - 每道题在独立的 `task_logging_context(task_id, ...)` 中执行，并各自生成 `BenchmarkResult` 和日志。并行收集结果时保留异常对象，再将异常转换为对应 task 的失败结果，因此单题异常不会让整批结果丢失。
  - 要区分两类「并发」：这里是评测多题并行；标本的单题内多个 tool call、子 Agent 调用当前主要是逐个执行，不能据此声称单题内子 Agent 已并行。若业务侧将无依赖子任务并行化，还需单独配置并发上限、超时和资源隔离。
- **易踩坑：** 把 `max_tool_calls_per_turn=10` 说成同时跑 10 个子 Agent，或把评测层的多题并行偷换成单题内工具并行。
- **回看标本：** `miro-flow-solution/common_benchmark.py` 的 `run_parallel_inference()`、`asyncio.Semaphore` 与 `asyncio.gather(return_exceptions=True)`；单题内顺序执行回看 `miro-flow-solution/src/core/orchestrator.py` 的 tool call 循环。

#### G23. `max_turns` 和 `max_tool_calls_per_turn` 怎么设？会截断正常任务吗？

- **第一句：** 熔断由两道预算共同组成：`max_turns` 限制 Agent 最多循环多少轮，`max_tool_calls_per_turn` 限制单轮最多消费多少个工具调用；读过的 qwen37plus 示例中主 Agent 是 20 / 10，但这是标本配置，不是未经实测就固定照搬的业务参数。
- **要点：**
  - `max_turns` 防止模型在搜索、纠错和重试之间无限循环；达到上限后停止继续扩张，并尝试基于已有上下文生成 final summary。
  - `max_tool_calls_per_turn` 防止模型单轮生成过多调用造成资源突刺；超出部分会被截断，只处理配置允许的前 N 个。它约束的是调用数量，不等于这些调用并行执行。
  - 参数过小确实可能截断正常长任务，例如需要多来源检索、逐步校验和计算的 Level 3 题。因此这是成本、延迟与任务完成度之间的 trade-off：先按任务复杂度分层设置，再用 trace 统计「触顶但仍未完成」的比例，避免只为降低耗时而牺牲正常任务。
  - 业务侧还需有独立的端到端超时和下游工具限流；`max_turns` / `max_tool_calls_per_turn` 控制 Agent 行为预算，不能替代所有超时、并发和配额治理。
- **易踩坑：** 把 20 / 10 说成线上已验证最优值，声称熔断绝不会误伤正常任务，或把达到轮次上限等同于立即丢弃已有证据。
- **回看标本：** `miro-flow-solution/config/agent_llm_qwen37plus.yaml` 的主 Agent `max_turns=20`、`max_tool_calls_per_turn=10`；具体截断与 summary 行为回看 `miro-flow-solution/src/core/orchestrator.py`。

#### G24. 怎么判断任务已经完成？断点续跑省了多少时间？

- **第一句：** 断点续跑以日志落盘状态判断：批量评测启动时按 `task_id + attempt` 扫描已有 log；已有 boxed answer 就加载回答，已有 judge result 就连判分一起复用，只有日志缺失、答案不完整或执行失败的 attempt 才重跑。
- **要点：**
  - `scan_latest_attempt()` 先将找到日志的 attempt 视为 `RUN_FAILED`，只有读到 `final_boxed_answer` 才提升为 `RUN_COMPLETED`；若同时存在 `judge_result`，再提升为 `RESULT_JUDGED`。因此「文件存在」本身不等于任务完成。
  - `run_single_task()` 对 `PENDING` / `RUN_FAILED` 重新执行，对已有答案但未判分的结果补 judge，对已有 judge 的结果直接复用；pass@k 任一 attempt 正确后提前停止，不再浪费后续调用。
  - 省时体感来自重跑评测集时跳过已完成题，尤其适合长任务中途被打断后的续跑。没有实测数据时不报「节省多少小时」或百分比，只说明节省量近似等于被复用 attempt 原本需要的推理、工具调用和判分时间，后续可从日志起止时间汇总。
- **易踩坑：** 只按日志文件是否存在判断完成，导致把半写入或异常日志误当成功；或没有统计依据就虚构具体节省时长。
- **回看标本：** `miro-flow-solution/common_benchmark.py` 的 `scan_latest_attempt()`、`run_single_task()`、已有 judge 加载和 pass@k 提前停止；落盘字段回看 `miro-flow-solution/src/logging/task_tracer.py`。
