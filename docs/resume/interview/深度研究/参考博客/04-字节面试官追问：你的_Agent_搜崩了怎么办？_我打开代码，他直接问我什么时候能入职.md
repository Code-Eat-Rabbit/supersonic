## 一、同样是"搜索"，RAG 和 Deep Research Agent 差在哪里

先用一个不那么技术的类比把这件事说清楚： **RAG 就像让你的助手去查字典** ——你问一个问题，他翻到对应词条，念给你听，完事。这对"词条型"的问题完全够用。

但如果你问的是"全球前五大新能源车企，在固态电池方向的研发投入和技术路线有什么差异"——这不是查字典能解决的，这需要助手去图书馆待一天，翻二十本书，交叉比对信息，然后给你写一份研究报告。

我们做的第一版系统就犯了这个错误。当时有个客户问了一个关于全球新能源政策比较的问题，我们的 RAG 系统查了一次，返回了三篇相关文章，生成了一段回答。客户直接说："这不就是搜索引擎加了个总结吗？"

他说的是对的。那个版本根本不是 Agent，只是 RAG。

真正的差距在这里：

| 问题类型   | 典型例子                       | 需要几轮检索 | 普通 RAG 能做吗 |
| ---------- | ------------------------------ | ------------ | --------------- |
| 单跳问答   | "等待期是多少天"               | 1 轮         | 完全够用        |
| 两跳推理   | "A 公司的 CEO 毕业于哪所大学"  | 2-3 轮       | 勉强应付        |
| 研究型问题 | "五大车企固态电池路线对比"     | 10-20 轮     | 无法处理        |
| 复杂分析   | "某政策对三个行业的差异化影响" | 20+ 轮       | 完全失效        |

研究型问题的关键特征是： **后面的搜索依赖前面的结果** 。你不知道要搜什么，直到你看到了前一步找到的信息。这种动态决策，RAG 的一次检索根本做不到。

所以 Deep Research Agent（深度研究 Agent）要做的事，只有三件：①动态决定下一步搜什么，②把多轮检索的信息整合在一起，③知道什么时候信息够用了、可以停下来。听起来简单，每一件做好都不容易。

**所以你应该先想清楚：你的问题是"词条型"还是"研究型"。** 如果用户的问题可以靠一次检索回答，用 RAG 就够了，不需要 Agent 的复杂度。只有确认需要多轮动态检索，才值得引入今天要讲的这套框架。

## 二、支撑 Deep Research Agent 的四根柱子

在跑第一行代码之前，先把全景看清楚——不是为了背概念，是因为后面遇到问题的时候，你需要知道问题出在哪个环节。

**第一根柱子是训练数据。** 模型没办法凭空学会做复杂研究，它需要看大量"有人做过这件事"的轨迹样本——从问题出发，一步一步搜索、判断、调整，直到拿到答案的完整过程。这些训练数据不是现成的，需要专门构造。我们系列的第6到第9篇会专门讲怎么做。

**第二根柱子是 Agent 框架。** 这是模型的"行动逻辑"——它按什么格式输出思考，按什么方式调用工具，工具结果回来之后怎么继续推理。最基础的框架叫 ReAct（推理与行动，Reasoning and Acting），今天我们就从这里开始。

**第三根柱子是训练系统。** 有了数据和框架定义，还需要通过 SFT（监督微调，Supervised Fine-Tuning）让模型学会基本格式，再通过 RL（强化学习，Reinforcement Learning）让它学会在不同情况下做出更好的策略选择。

**第四根柱子是工具集。** Agent 靠工具和外部世界交互，核心四件套是 Search（搜索引擎）、Visit（网页内容提取）、Scholar（学术文献检索）、Python（代码执行）。工具设计的好坏直接影响 Agent 的能力边界。

这四根柱子之间的关系是：训练数据决定了模型能学什么，训练系统把数据转化为模型参数里的能力，Agent 框架决定了这些能力怎么被激活和组织，工具集则是 Agent 和世界产生联系的接口。

今天我们只搭第二根柱子的最基础部分：让 ReAct 框架跑起来。

## 三、ReAct：把"想"和"做"交织在一起

ReAct 的核心思想只有三步，先把这三步搞清楚，代码就好理解了：

① **Thought（思考）** ：模型看着当前所有信息，先想一想：我现在知道什么，还缺什么，下一步应该干什么 ② **Action（行动）** ：根据思考结果，调用一个工具——搜索一个关键词，或者打开一个网址 ③ **Observation（观察）** ：工具执行完，把结果读进来，追加到对话历史，然后回到第①步

**就像你在解一道不会做的题：先想想思路（Thought）→ 去翻书查资料（Action）→ 把查到的内容记下来（Observation）→ 再想下一步** 。区别是 Agent 把这个过程完全自动化了，而且可以循环几十次。

下面是一个可以直接跑的 ReAct 最小实现，我把每个关键设计决定都注释出来了：

```
import json

 def react_loop(
     user_query: str,
     llm,
     tools: dict,
     max_steps: int = 10
 ) -> str:
     """
     最小 ReAct 执行循环。
     接任意支持 function calling 的 LLM（OpenAI/DeepSeek/Qwen 都行）。
     """

     # 初始化对话历史，包含系统提示和用户问题
     # 为什么要保留完整历史而不只保留最后几轮？
     # 因为 ReAct 要求模型每次都能看到完整的推理链——
     # 如果切掉早期的搜索结果，模型就不知道"这个信息我已经找到了"，
     # 会重复搜索完全相同的内容，浪费步数和 token
     messages = [
         {"role": "system", "content": SYSTEM_PROMPT},
         {"role": "user", "content": user_query}
     ]

     for step in range(max_steps):
         # 调用 LLM，让它在"生成最终答案"和"调用工具"之间自己做选择
         # tool_choice="auto" 的意思是：你自己判断，如果信息够了就直接回答，
         # 如果还需要查东西就调工具——不强制它必须调工具
         response = llm.chat(
             messages=messages,
             tools=list(tools.values()),   # 把工具定义传进去，让模型知道有什么可用
             tool_choice="auto"
         )

         # 模型选择调用工具（说明它认为信息还不够）
         if response.tool_calls:
             tool_call = response.tool_calls[0]
             tool_name  = tool_call.function.name
             tool_args  = json.loads(tool_call.function.arguments)

             print(f"[步骤 {step + 1}] {tool_name}({tool_args})")

             # 执行工具，拿到 Observation
             # 为什么要 try/except 而不是直接调？
             # 搜索引擎超时、网页 404、网络抖动——这些在生产里每天都会发生。
             # 不捕获的话，一个工具失败会导致整个 Agent 崩掉，
             # 而用户的问题只是因为一次网络问题就没了答案，体验很差
             try:
                 observation = tools[tool_name](**tool_args)
             except Exception as e:
                 # 工具失败时，告诉模型发生了什么，让它决定下一步
                 # 而不是直接抛错——模型可能会换个策略继续
                 observation = f"工具调用失败（{type(e).__name__}）：{e}。请尝试换一种方式。"

             # 把这一步的结果追加进对话历史
             # 为什么要严格按"assistant 消息 → tool 消息"的顺序追加？
             # 这是 OpenAI 格式的强制要求：tool 消息必须紧跟触发它的 assistant 消息，
             # 通过 tool_call_id 配对。顺序错了 API 会直接报错
             messages.append(response.to_message())   # Thought + Action
             messages.append({
                 "role":         "tool",
                 "tool_call_id": tool_call.id,
                 "content":      str(observation)      # Observation
             })

         # 模型没有调用工具——说明它判断信息已经够了，给出最终答案
         else:
             print(f"[完成] 执行了 {step + 1} 步")
             return response.content

     # 走到这里说明跑满了 max_steps 还没结束
     # 为什么不直接返回 None 或者报错？
     # 因为用户等了这么久，哪怕是不完整的答案也比什么都没有强，
     # 返回模型当前的最后一条输出，让用户知道系统在哪里卡住的
     last_content = next(
         (m["content"] for m in reversed(messages) if m["role"] == "assistant"),
         "已达到最大步数，未能生成完整答案。"
     )
     return f"[已达 {max_steps} 步上限] {last_content}"
```

这段代码今天就可以接上 OpenAI 或者 DeepSeek 的 API 跑起来。我们内测用的第一版代码和这个结构基本一样——当时还没加 try/except，第一次演示的时候搜索工具超时直接崩了，在客户面前很尴尬。加了错误捕获之后，工具失败的情况多了一条"换策略继续"的路，最终成功率从78%提升到了91%。

**所以你的 ReAct 框架里，工具调用的错误处理是第一优先级要做好的事。** 不是因为工具经常失败，是因为一旦失败、整个 Agent 崩掉的代价远比多写几行 try/except 要高。

## 四、你的第一个 Agent 能跑了——但很快会撞到这面墙

把上面的代码跑起来之后，处理简单问题完全没问题——搜个三四次就能给出答案，上下文不到一万 token，模型表现良好。

但当任务稍微复杂一点，问题就来了。

我们内测阶段有个用户问了一个关于全球新能源汽车政策的比较问题："欧盟、美国、中国三个市场的新能源补贴政策，在2024年各做了哪些调整，对不同车企的影响有什么差异？" Agent 跑了8步，最后给出的报告里，欧盟的补贴额度被安到了美国的政策里。

我们排查了将近两小时，最后在日志里发现：到第7步时，messages 里的 token数已经超过28000。搜索结果里欧盟、美国的数据都在，但模型对第一步找到的欧盟数据注意力明显下降，在生成报告的时候把两个来源混淆了。

这件事让我们意识到： **ReAct 的设计决定了它有一个天然的上限。**

长任务里 messages 随轮次线性增长——假设每步平均产生2500 token，跑10步就是25000 token，跑15步就是37500 token。在大部分模型的"舒适区"之外，注意力开始稀释，靠后的内容权重更高，靠前找到的关键信息越来越容易被忽视。

很多人以为上下文越长模型越聪明，实际上超过某个阈值之后，结果反而会变差。这不是模型的 bug，是注意力机制的物理特性。

除了上下文膨胀，还有第二个问题更难发现： **策略停滞** 。模型每次生成 Thought 的时候，要从几万 token 的历史里推理出"我还缺什么信息"。这个推理本身很容易出错——你会看到模型用几乎一样的关键词反复搜索，或者在同一个子问题上绕圈，因为它"看不见"前面几步已经找到答案了。

这两个问题，ReAct 框架本身解决不了。解法是引入一个固定大小的"研究摘要"——每轮执行完，不是把原始结果堆进上下文，而是更新一份结构化的摘要，记录"目前已知的信息"和"还没解决的子问题"。这个设计叫 IterResearch（迭代研究框架），我们下一篇专门来实现它。

今天先把眼前这个跑通，同时在你的系统里加一个监控： **每次 Agent 执行完，打印出 messages 的 token 总数** 。等你看到某类问题到第5步就已经过了两万 token，你就知道什么时候该上下一篇的方案了。

## 五、系统提示：让 ReAct 工作的隐藏关键

上面的代码里有一个 `SYSTEM_PROMPT` ，我没有展示它的内容。这里补上，因为系统提示写得好不好，直接决定了 ReAct 能不能按预期工作。

很多人觉得系统提示就是"介绍一下你是谁"。实际上在 Agent 里，系统提示需要做三件事： **定义 Agent 的角色** ， **规定输出格式** ， **设置行为边界** 。

```
SYSTEM_PROMPT = """你是一个专业的研究型 AI 助手，擅长通过多轮工具调用完成复杂信息检索任务。

 工作方式：
 - 遇到问题，先分析需要找哪些信息，再逐步检索
 - 每次工具调用之前，先想清楚：调这个工具是为了解决哪个具体的信息缺口
 - 拿到工具结果后，判断这个信息够不够用；不够用就继续搜，够用了就综合作答
 - 如果同一个搜索词搜了两次没有新信息，换一个角度重新搜，不要重复无效操作

 输出格式：
 - 调工具之前，先用一两句话说明你要做什么（Thought）
 - 工具结果回来后，先评估结果质量再决定下一步
 - 最终回答时，注明每个关键信息的来源

 边界：
 - 如果信息来源之间有矛盾，明确指出，不要自己"融合"矛盾的信息
 - 如果某个问题在现有检索结果里找不到答案，直接说找不到，不要编造
 """
```

注意最后两条边界规定，它们针对的就是我们前面说的"混淆欧盟和美国数据"这类问题。 **系统提示里明确告诉模型"矛盾的信息要指出来，不要融合"，可以降低一部分信息混淆的概率。** 不是万能的，但有明显效果——加了这两条之后，我们测试集上的信息混淆率从13%降到了6%。

一个好的系统提示不是写越多越好，是每一条都针对你在测试里看到的真实问题写的。 **所以你应该先跑起来，让 Agent 真实地出问题，然后有针对性地往系统提示里加约束。** 一开始就把系统提示写得很长，通常效果不好，模型会"读不进去"。

## 面试怎么答 Deep Research Agent 相关问题？

面试官问这类问题，通常不是在考你能不能背定义，是在看你有没有真的把系统跑到出过问题的地方，然后思考过为什么出问题。

**先说清楚 RAG 和 Deep Research Agent 的差距，用一个具体的对比说明（30秒）：**

不要上来就讲技术细节，先说你见过的真实失败案例： "我们第一版用的是 RAG，有个客户问了一个多市场政策比较的问题，系统返回了一段摘要，客户直接说'这不就是搜索引擎'。我们这才意识到，需要多轮动态检索的任务，RAG 的一次检索根本做不到。"

这比说"RAG 只能做单跳，Agent 可以多跳"有说服力得多。

**再说 ReAct 的工作方式，重点放在"消息历史是怎么构建的"（1分钟）：**

"ReAct 每步执行完，把 Thought + Action + Observation 追加进 messages，下一步的模型输入包含完整的历史链。我们在这里发现了一个问题：10轮之后，messages 里有三四万 token，模型对早期信息的注意力开始下降。我们内测的时候就因为这个，把欧盟的数据混进了美国的政策报告里，排查了两小时。"

有具体失败案例的回答，比泛泛说"上下文管理很重要"可信得多。

**然后说你是怎么处理工具失败的（30秒）：**

"工具调用失败是生产里很常见的情况，我们的处理方式是：失败时不崩，而是把错误信息写回 Observation，让模型自己决定换个策略继续。加了这个机制之后，成功率从78%提升到了91%。"

说出具体数字，说明你测过、你量过、这不是随便说的。

**最后如果面试官追问上下文溢出的解法（加分项）：**

"我们用了一个叫 IterResearch 的框架，不把原始搜索结果堆进上下文，而是每轮更新一份固定大小的研究摘要，记录'目前已知'和'还缺什么'。这样上下文大小保持常量，无论跑多少轮都不会溢出。"能说到这里的候选人很少，直接拉开差距。
