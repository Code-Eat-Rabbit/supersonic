## 为什么通用模型的工具调用"刚刚够用"

先说背景。现在主流的大模型（GPT-4o、DeepSeek V3、Qwen3）都原生支持 Function Calling，直接调用大多数情况下能跑通。那为什么还需要专门做 SFT 微调？

原因是"刚刚够用"和"生产可用"之间有一道坎。

通用模型的工具调用训练数据是泛化的——各行各业的工具调用场景都有，但没有哪个领域是深度训练的。当你的 Agent 需要处理金融行业的复杂查询，同时调用搜索、网页访问、Python 计算三个工具，并且工具的调用顺序有严格依赖关系时，通用模型的准确率通常在 65%-75% 之间。

65% 意味着什么？意味着三次工具调用里有一次是错的——选错了工具、参数格式不对、或者不该调用工具时调了。这个比例在 Demo 里还好，但在生产系统里，错误的工具调用会让 Agent 的整个推理链路跑偏，最终生成一个看起来完整但信息错误的报告。

我们在训练营的 DeepResearch 项目里实测过：基础模型（Qwen3-30B-A3B）不做微调，直接上线，工具调用准确率是 71%。做完 FC-SFT 之后，同一个模型在同样的测试集上准确率达到 94%。这 23 个百分点的提升，靠的不是换模型，是数据工程。

## 数据工程第一步：种子数据从哪来

SFT 的关键是训练数据质量，而不是数量。很多人在这里走弯路，以为堆数量就够了。

我们构造训练数据的起点是 **种子问题** ，一共约 200 条。种子问题来自两个渠道：

**渠道一：在线系统日志。** 如果系统已经有早期用户在用，从日志里提取真实的用户查询。这些是最有价值的种子——用户实际遇到的问题，代表了真实的分布，不是我们拍脑袋想出来的。

在我们的项目里，银行对公业务的真实查询里有这样的问题："某大型企业未来三年的债务到期分布和再融资风险分析"，这种复杂度是人工编写很难自然想到的。

**渠道二：专家人工编写。** 专家根据任务领域的特点，覆盖一些日志里天然出现频率低的场景：多跳推理、需要实时数据的查询、涉及交叉验证的研究任务。这部分大概占 40%。

200 条种子问题是不够训练的，需要扩充到 1200 条。扩充策略有三种：

**问题改写（1.5倍）** ：用 LLM 生成同一问题的不同表述。"XX 企业今年的营收怎么样" → "能帮我查一下 XX 企业 2024 年的营业收入吗" → "请分析 XX 公司最新财报的营收数据"。表述不同，但背后的工具调用模式相同。

**参数变化（2倍）** ：修改问题里的具体参数——时间、公司名、行业、数字。"查 2024 年的数据"改成"查 2023 年的数据"，同一问题覆盖更多的变体分布。

**组合扩展（1.5倍）** ：把单一问题组合成更复杂的追问。"查 A 公司的营收" + "再对比一下 B 公司" = 需要两次搜索 + 一次 Python 计算的组合任务。

三种策略叠加，从 200 条种子问题扩充到约 1200 条训练问题。

## 数据工程第二步：Teacher 模型生成轨迹

有了 1200 条问题，下一步是生成训练数据中的"轨迹"——每个问题对应的完整工具调用过程：Thought（推理）→ Action（工具调用）→ Observation（工具返回）→... → 最终答案。

我们用 DeepSeek V3 做 Teacher 模型来生成轨迹，原因是它的 Function Calling 能力在同级别开源模型里是最好的，同时成本相对可控。

Teacher 模型的 system_prompt 里明确定义了轨迹格式：

```
<think>
 [推理过程：分析任务，决定调用哪个工具，为什么]
 </think>

 <tool_call>
 {
     "name": "search",
     "arguments": {
         "query": "具体搜索词",
         "max_results": 5
     }
 }
 </tool_call>

 <observation>
 [工具返回结果]
 </observation>

 <think>
 [基于 observation 的进一步推理]
 </think>
 ...

 <final_answer>
 [综合所有信息后的最终答案]
 </final_answer>
```

这个格式有几个设计考量：

`<think>` 标签把推理过程显式化——训练完的模型不只是学会"调用什么工具"，还学会了"为什么调用这个工具"。这让模型在遇到 Teacher 模型没见过的新问题时，能通过推理链找到合适的工具。

工具调用用 JSON 格式——严格的结构让格式验证变得简单，解析失败的轨迹可以直接过滤掉。

`<observation>` 和 `<think>` 的交替——模型学会了"看了结果再想下一步"的模式，而不是一次性生成所有工具调用。

## 质量验证：不是所有 Teacher 模型生成的轨迹都可用

Teacher 模型生成 1200 条轨迹，但不是全部都能用。质量验证过滤掉了约 30% 的数据。

过滤规则分三类：

**格式验证（自动）** ：

- `<tool_call>`
  的 JSON 是否可以被解析
- 工具名是否在定义的工具集里
- 必填参数是否都有
- 不符合格式的直接丢弃

**逻辑验证（自动）** ：

- 轨迹步数是否合理（不少于 2 步、不多于 15 步）
- 最终答案是否有工具调用的支撑（不能凭空生成答案）
- 是否有重复调用同一工具的情况（Teacher 模型有时候也会循环）

**质量抽检（人工 10%）** ：

- 随机抽取 10% 的轨迹做人工检查
- 重点看"推理是否合理"——有些轨迹格式没问题，但 Teacher 模型的推理路径是绕远路的，这样的数据训练出来的模型也会学到低效的推理习惯

过滤完之后，1200 条问题对应约 840 条高质量轨迹数据。840 条不多，但质量高，这是 SFT 在这个量级里能做到的极限。

做到这里有一个容易踩的坑： **数据分布问题** 。如果 840 条数据里 70% 是搜索类工具调用，只有 10% 是 Python 代码执行，训练出来的模型会偏向用搜索，在应该用 Python 计算时也倾向于先搜索。解决方法是在种子数据构造阶段就控制分布，而不是等到训练完才发现。

## Claude Code 的 ExtractionCoordinator：另一种"自动积累知识"

说到这里，我想聊一个有趣的类比。

DeepResearch 的 SFT 冷启动解决的是这个问题：模型一开始不会高质量地调用工具，通过数据积累让它学会。

Claude Code 里有一个叫 `ExtractionCoordinator` 的组件，解决的是一个结构上类似的问题：Claude Code 一开始对一个新项目一无所知，通过使用过程中自动提取记忆，逐渐积累对项目的了解。

`ExtractionCoordinator` 的工作逻辑是这样的：每次对话结束时，后台会启动一个异步任务，分析这次对话里有没有值得持久化记忆的信息。如果有，把它写到 `MEMORY.md` 或者对应的主题记忆文件里。

```
# Claude Code 内部逻辑（简化）
 class ExtractionCoordinator:
     MIN_NEW_MESSAGES = 4  # 至少有 4 条新消息才触发提取

     async def maybe_extract(self, session: Session):
         """异步调用，不阻塞主流程"""
         new_messages = session.messages_since_last_extraction
         if len(new_messages) < self.MIN_NEW_MESSAGES:
             return  # 消息太少，不触发

         if self._is_running:
             self._dirty = True  # 标记"有新数据待提取"
             return  # 上一次提取还没完成，等等

         await self._run_extraction(session)

     async def _run_extraction(self, session: Session):
         self._is_running = True
         try:
             # 让模型判断这次对话有没有值得记住的内容
             memories = await self.model.extract_memories(session.recent_messages)
             if memories:
                 self.memory_writer.update(memories)
         finally:
             self._is_running = False
             if self._dirty:
                 self._dirty = False
                 await self._run_extraction(session)  # 处理积压的数据
```

注意 `MIN_NEW_MESSAGES = 4` 这个设计——不是每条消息都触发提取，而是积累到 4 条新消息才触发一次。这是在避免过于频繁的提取操作（每条消息都提取，大多数消息没有值得记忆的内容，浪费算力），同时保证信息不会积压太久。

这和 SFT 数据里的"质量门槛"是同一个工程思路：不是所有信息都值得进入训练/记忆，有门槛筛选的数据比无差别堆积的数据更有价值。

## 微调完成后：怎么知道这 23 个百分点是真实的？

SFT 做完，怎么验证提升是真实的？这是很多人忽视的步骤，也是面试官经常追问的地方。

评估的核心原则是 **测试集和训练集不能有重叠，测试场景要覆盖训练里没见过的分布** 。

我们构建的测试集有三层：

**层 1：标准测试集（100 条）** 。从种子数据里留出来的，没有参与训练。这一层测的是基础能力，主要验证微调没有崩掉基础。

**层 2：分布外测试（50 条）** 。覆盖训练数据里没有或者很少的场景——比如需要 4 个以上工具协同调用的复杂任务，或者工具返回了错误时的处理。这一层测的是泛化能力。

**层 3：对抗测试（30 条）** 。故意构造一些"看起来应该调工具但其实不应该"的问题，测试模型有没有被过拟合到"有问题就调工具"的模式里。比如"2 加 2 等于多少"——正确答案是直接回答 4，而不是调用 Python 工具去计算。

测试维度不只看"工具调用准确率"，还要看：

- **工具选择准确率**
  ：是否选了正确的工具
- **参数格式准确率**
  ：工具名选对了，但参数格式写错了的比例
- **调用顺序准确率**
  ：多工具任务里，顺序是否合理（不该先计算就先搜索）
- **遗忘率**
  ：微调后在非工具调用任务（普通问答）上的表现有没有明显下降

最后这一项很重要。SFT 有"遗忘"风险：专项微调做得太猛，模型会在专项任务上提升，但在其他任务上变差。控制遗忘的方法是在训练数据里混入 30% 的通用指令数据——不能全是工具调用样本，否则模型会"忘记"怎么做普通问答。这个数字（30%）是实验出来的，不是拍脑袋定的。

在我们的测试里，FC-SFT 5000 样本（我们做了更多轮迭代），工具调用准确率最终从 71% 提升到 94%，普通问答任务的退化在统计上不显著（MMLU 下降 0.3%，在误差范围内）。

## 面试怎么答"SFT 微调"这道题？

这道题考察的是你对整个数据工程流程的理解，而不是对微调原理的背诵。

**第一层：说问题（20 秒）** "通用模型的工具调用准确率大概在 65%-75%，对于复杂的多工具协同任务不够用。FC-SFT 的目标是在不换模型的情况下，用高质量的领域数据把准确率拉到生产可用的水平。"

**第二层：说流程（90 秒）** "我们的数据工程分四步：种子问题构造（在线日志 + 专家编写，约 200 条），三种策略扩充到 1200 条；用 Teacher 模型（DeepSeek V3）生成带轨迹的训练数据；质量验证过滤掉 30% 格式或逻辑有问题的数据；控制数据分布，工具类型平衡，混入 30% 通用指令数据防止遗忘。最终 840 条高质量训练数据，FC-SFT 完成。"

**第三层：说评估（30 秒）** "测试集分三层：标准测试、分布外测试、对抗测试。测试维度除了准确率，还有参数格式准确率、调用顺序准确率和遗忘率。最终结果：工具调用从 71% 到 94%，普通问答退化不显著。"

如果面试官追问"为什么要混入 30% 通用指令数据"——这是防遗忘的关键配比，纯工具调用数据会导致模型遗忘基础能力。这个数字是实验出来的，不是理论推导的，能说出这句话的人，面试官知道是真做过的。

## 总结

SFT 冷启动的本质是一句话： **让模型从"刚刚够用"变成"生产可用"，靠的是数据工程，不是调参魔法。**

数据质量 > 数据数量。840 条高质量轨迹比 5000 条粗糙数据有效得多。

分布是隐形的控制变量。工具类型分布不均衡、遗忘防护比例不对，都会让最终模型的行为偏离预期。

评估是闭环的保证。没有测试集，你不知道自己提升了多少；没有遗忘率监控，你不知道自己在哪里退步了。

Claude Code 的 `ExtractionCoordinator` 用的是另一种形式的同一个哲学：有门槛的选择性积累，比无差别的堆积更有价值。 `MIN_NEW_MESSAGES = 4` 是它的质量门槛，就像 SFT 里的质量验证过滤是训练数据的门槛一样。

两套系统，同一个设计哲学：选择比数量更重要。

今天这道题，只是 Deep Research Agent SFT 工程链路的一个切面。

真正的面试官不会只问这一问。他们会顺着你的回答追下去，追到你答不上来为止——判断的就是你到底做没做过这个系统。

背答案的人和真正做过的人，说话方式完全不一样。前者说"微调了工具调用"，后者说"FC-SFT 用 840 条高质量轨迹，混了 30% 通用指令防遗忘，对抗测试发现如果不混通用数据，模型会对'2 加 2'这种问题也去调用 Python 工具——这种过拟合只有真测过才能发现"。
