大家好，我是吴师兄。

**来个经典问题：Agent 的创建请求超时了，你再发一次，后台会返回原来的任务，还是多创建一条？**

做客服 Agent，这个问题得在项目里处理好。

因为客服点了“AI 处理”，页面一直没拿到任务编号，等了一会儿只能重试，可后端可能早就创建好了任务，丢的只是那条响应；再创建一次，同一张工单就可能被排进两次处理。

所以我会把“同一次处理被重复提交，只创建一条任务”写进验收要求，前端可以重试，后台得认得出这是刚才那次提交，客服不用猜上一次到底成功了没有。

为了检查这件事，我用两个独立的数据库连接跑了一次并发验证。先让两个请求都查到“没有任务”，再一起放行创建。没有唯一约束时，库里留下两条任务；加上约束并处理冲突后，两边拿回了同一个任务编号，库里也只有一条记录。

面试里可以顺着追问“请求超时了，怎么防止重复创建”。回答“创建前先查一下”很顺口，可再问一句“两个请求同时查空呢”，重复创建由谁拦住、重试又该返回什么，就得讲清楚了。

## 两个请求，为什么都觉得自己是第一次？

先把要做的事说清楚。客服收到工单 T-9527，顾客问包裹怎么还没到。点下“AI 处理”后，接口创建一条 Run，保存这次处理的输入，后台 Worker 再去查订单、查物流，生成回复建议。Run 就是这一次执行的记录，有自己的编号。

现在只看创建这一步。两个请求都带同一个 `idempotency_key` ，键是调用方给这次处理准备的标记。它跟着重试一起发，后端拿它查已有记录。测试里使用 `ticket:T-9527:handle:v1` ，实际使用时，同一次提交得一直保留这个键。

一口气连点几下按钮，很容易测出一个漂亮的结果：第一次已经建好，第二次才进来，查询当然能命中。可这样的先后顺序，正好绕开了我们想检查的空档。

我把等待点放在查询之后。每个线程查完，确认没找到记录，就停在同一个 Barrier 上；两个都到齐，才一起往后走。这样运行时不必猜机器快慢，也不用赌两个请求恰好挤在某一毫秒，测试直接安排它们带着同一个“查无记录”的结论去创建。

这次直接调用创建函数，返回值带着接口约定的状态码，先在数据库这一层检查结果，HTTP 服务和模型都不用启动。实验只保留我们要挤进去的那段空档。

测试入口里，安排等待点的是这几行：

PYTHON

```
# 吴师兄学大模型：wushixiongai.com barrier = threading.Barrier(2)# 每个线程都有独立连接。# after_missing 在 SELECT 查空之后调用。create_run(     db_path,     org_id="org_1",     key="ticket:T-9527:handle:v1",     input_json=ticket_input,     mode="naive",     after_missing=barrier.wait,)
```

等它们放行后，第一个请求写入自己的 Run，第二个请求也写入自己的 Run，两次生成的编号不同，任务编号的主键完全没有冲突，两个调用都正常结束了。再去查库，两条 Run 各带着一条创建事件，状态也都是 queued，Worker 随后去领任务时，面对的就是两份独立的处理请求。

这可没去重成功。

**两次查询都没错，错在拿旧的查询结果作了后面的保证。**

第二个请求真正写库时，第一个请求可能已经提交了。只是代码已经走过查询分支，手里那份“没有记录”的结果不会自己刷新，更不会替数据库拦住下一次插入。

这次验证用 SQLite，写事务本来就只能一个接一个执行。可两个写事务都正常提交了，重复记录照样出现。排队写入只安排了先后，表里还缺一条明确的规则，告诉数据库这两行只能留一个。

这里要盯住事务从哪里开始。我把查询放在自动提交模式下，取完结果才执行 `BEGIN IMMEDIATE` ，它包住后面的两次写入。第二个请求排队拿到写锁时，代码没有重新查询，继续沿用了排队前的判断。因此给插入套上事务，这个空档仍然在。

把查询也搬到取得写锁之后，再在锁里判断并创建，在 SQLite 上能让这段判断依次发生。但写锁占用的时间跟着变长，所有调用都得照着这条路走。我这里保留前置查询作为快捷入口，让唯一约束直接守住表，查询命中了就省一次插入，没命中也有后面的约束接着管。

拿写锁也可能等到超时。测试连接设置了十秒等待，这类失败仍按数据库错误处理，调用方下次带原键重试。只有拿到了明确的原任务，接口才返回那个编号。

## 加了唯一约束，另一个请求该回什么？

缺的规则放在组织编号和幂等键上。我们把一次处理限定在当前组织内，同一个组织里的同一个键，只允许对应一条 Run。

表里与这条规则有关的字段如下，其他执行字段先略去：

SQL

```
-- 吴师兄学大模型：wushixiongai.com org_id          TEXTNOTNULL, idempotency_key TEXTNOTNULL, input_hash      TEXTNOTNULL, UNIQUE (org_id, idempotency_key)
```

这里不能只给 `run_id` 加唯一约束。重复请求每次都能生成一个新编号，数据库会把它们当成两行合法数据。组织编号和幂等键这两个值相同，才是这次要挡住的重复。

把约束加上，再跑刚才的并发安排，两个请求仍然都先查空。随后第一个成功写入并提交，第二个插入时，数据库发现相同的组织和键已经占着位置，抛出了唯一约束异常。

任务只剩一条。

但站在客服这边，这轮还没处理好。第一次响应可能已经丢了，第二次又收到错误，页面仍然不知道该去查哪条任务。有人忍不住再点“重新处理”，又生成一个新键，系统便会认真地创建第二次执行。

所以按钮置灰也只管得住界面上的那一下。你在一个页面里禁用了按钮，另一个标签页仍可能提交，网络层也可能重发请求。这些请求到了后台，创建接口还是得按同一个约定处理。前端减少误触，后端接受重试，两边都得把自己的那段接好。

我希望正常重试回到原来的 Run 上。所以唯一冲突出现后，代码先回滚当前事务，再用同一组组织编号和键查询已经提交的记录。输入一致，就把那个编号交回去，用 200 表示这次复用了已有资源。

创建分支依然返回 201。两边的编号相同，前端往后查询的是同一次执行。

这里还有个很容易改过头的地方。Python 的 `IntegrityError` 包含多种数据约束错误，主键重复、外键出错也可能进这个分支。把它们统统翻译成“你已经提交过了”，就会把真正的写入故障盖住。

所以我在 SQLite 这份代码里，只认具体那一条组织和幂等键的唯一冲突。下面是回滚后的处理分支，前面的创建事务已经把 Run 和创建事件放在一起写：

PYTHON

```

```

这次本机运行是 Python 3.13.3、SQLite 3.49.1。换数据库驱动时，我会把这段识别改成对应的约束名或错误字段。需要识别的是那一条幂等约束，不能只认一个笼统的“数据库报错”。

回读也可能没有拿到记录，代码里专门保留了失败出口。此时连原来的 Run 都找不到，接口就没有依据给调用方发一个成功编号，继续查原因才是正事。

## 同一个键，输入变了，听哪一次的？

找到旧任务后，还有一次比对。否则只要键相同，第二个请求里改过的内容就会被悄悄丢掉。

比如客服把工单里的订单号从 ORD-10086 改成了 ORD-99999，却沿用了原先的幂等键。直接返回旧 Run，页面可能显示“已提交”，后台实际还在按第一个订单处理。接口没有多建任务，却把客服这次想做的事接错了。

所以创建 Run 时，我会一起保存 `input_hash` 。收到同键请求后，将当前输入的哈希跟库里那份比对。一致才返回原任务，不一致就返回 409，并带上 `IDEMPOTENCY_CONFLICT` 。

PYTHON

```
# 吴师兄学大模型：wushixiongai.comdefresponse_for_existing(row, request_hash):if row["input_hash"]!= request_hash:return{"status_code":409,"error":{"code":"IDEMPOTENCY_CONFLICT"},}return{"status_code":200,"run_id": row["run_id"],"status": row["status"],}
```

这里的哈希从校验后的输入计算。这个例子只允许客服处理一种任务，输入中的工单号、订单号和消息都要求是非空字符串，JSON 对象的键排序后再序列化。这样同一份输入换了字段顺序，仍会得到同一份哈希。

PYTHON

```
# 吴师兄学大模型：wushixiongai.com canonical = json.dumps(     validated_input,     sort_keys=True,     ensure_ascii=False,     separators=(",",":"),) request_hash = hashlib.sha256(     canonical.encode("utf-8")).hexdigest()
```

但字符串里的内容我没有顺手清理。顾客补了一句话、客服换了订单号，输入就确实变了。接口不替调用方猜“这个改动应该不重要”，碰到冲突，把问题明白地交回去。

这也影响前端接下来怎么做。409 之后先确认这次是不是新的处理意图；确认重新处理，就生成新键。网络重试仍保留旧键和原输入，别在重试拦截器里一遇到错误就换键，那样每次失败都可能启动一次新任务。

为了检查并发时也能守住这个约定，我又让两个请求带同一个键、不同的订单号，同时停在查空的位置。放行后，一边返回 201，另一边返回 409。最后只有一条 Run，保存的是成功创建那一边的输入，后来的内容没有把它覆盖掉。

这里没有预先指定哪边获胜。线程先后由调度决定，验收检查的是成功的一边留下什么、冲突的一边收到什么，不能把“永远按第一个启动的线程处理”写进断言。

顺着这个场景，再把两个请求放到不同组织里，同一个键就各建各的。组织范围来自登录身份，不能拿请求体里随便填的组织号直接当权限。回读时也带上这个范围，否则第二个组织可能拿到第一个组织的任务。

于是键的职责就很清楚了。它标记一次提交意图；输入哈希检查这次重试有没有改内容。顾客后来又要生成一版回复，可以用新键重新处理，没必要让一张工单从此只能运行一次。

也正因为如此，我没有直接拿输入哈希当幂等键。你第一次生成的回复不满意，原样提交，想再生成一份，输入可以完全相同，处理意图却已经是新的一次。只按输入去重，这个“重新生成”就会一直拿回旧结果。测试里我给相同输入换了一个新键，确认库里确实增加了一条新 Run，避免把正常操作也挡掉。

## Run 写进去了，创建事件没写进去呢？

前面的冲突回读有一个前提：被找到的旧记录，是一次完整提交留下来的。

这份实现除了 `runs` ，还有一张 `events` 表。创建任务时，先插入 Run，再追加 `run.created` 事件，记录它以 `queued` 状态进入等待。两次写入都完成，事务才提交，随后才返回 201。

为什么连事件也放进去？因为重试会把这条已存在的 Run 当成原任务返回。只写完一半就提交，下一次请求很可能命中这份半成品，接口回了 200，排查记录却从第一条就缺了一截。

我用数据库触发器专门阻止创建事件写入。运行到第二次插入时，SQLite 抛出异常，随后事务回滚。再查数据库，Run 是零条，事件也是零条，前面已经执行过的 Run 插入没有单独留下来。

这次错误也没有被当成幂等冲突。触发器报错原样向上抛出，调用方得知创建失败，后续仍可以带原键重试。

记录没留下，键也就没占住。下一次请求可以重新尝试创建，成功后再把 Run 和它的第一条事件一起交出来；要是先把键单独标成“已处理”，剩余写入又失败，重试反而会被自己留下的标记堵住。

这正好检验了前面那段异常判断。处理得太宽，事件写入失败就可能被包装成正常重复；只围着唯一键打补丁，漏掉创建事务，又可能留下一个能查到、却没有完整创建记录的任务。

因此这次补全的顺序很具体。正常路径把两次写入一起提交，重复路径只回读已提交的旧任务。前面快查命中也好，后面插入撞上唯一约束也好，最终返回的都得是同样完整的一条记录。

我也没有把查物流塞进这段事务。这里只登记任务，后台执行还没开始。占着 SQLite 的写事务等待外部接口，会让其他创建请求跟着等，前面费力修好的重试体验又被拖回去了。

## 怎么确认挡住的，确实是并发重试？

到这里，再看测试结果，比只盯着“一共一条 Run”多了几层判断。下面三个实现都把 Run 和事件放进同一个写事务，差别只在唯一约束和冲突处理：

| 实现                     | 两个调用的结果     | Run 数量 | 创建事件数量 |
| ------------------------ | ------------------ | -------- | ------------ |
| 先查再建，没有唯一约束   | 201、201，编号不同 | 2        | 2            |
| 加唯一约束，异常直接抛出 | 201、唯一约束异常  | 1        | 1            |
| 加约束，并在冲突后回读   | 201、200，编号相同 | 1        | 1            |

这张表后面，我还留了每个连接的执行顺序。日志会检查两次查空都发生在任何一次写事务之前，免得测试悄悄退回了顺序重试。行数是最后的结果，时间顺序则说明这轮到底有没有测到那个空档。

为了确认重试依赖的是库里的记录，我还做了两次接续检查。一次创建已经提交，我把返回值丢弃，随后用原键重新调用，拿回原来的编号；另一次直接启动新的 Python 进程再调用，拿回的还是那条 Run。重试路径没有依赖上一次函数还留在内存里的对象。

加上不同输入竞争、组织范围和回滚检查，这轮共跑了九组测试，全部满足各自断言。前两个错误实现也在里面，测试通过的意思是成功复现了它们的问题，可别把那两行绿色结果当成“实现没毛病”。

有一点得在面试里答准。我们守住的是 **同一组织、同一幂等键只创建一条 Run** 。Worker 拿到它以后，查物流的工具超时重试，仍可能发出第二次外部请求。创建记录和后续工具调用，各有自己的重试位置，验收时分别去查。

所以被问到“两个请求同时到，创建前查一下够不够”，我会把刚才那两次查询画出来。它们都可能查空，唯一约束负责挡住第二次插入，冲突处理再去取回同一条 Run。接着跑一次，让编号和数据库里的行数对上。

你也可以直接在自己的创建接口里找那个位置：查询刚结束，写入还没开始。把两个请求都停在那里，再一起放行。这个来回跑完，接口能不能接住一次并发重试，就有了具体答案。
