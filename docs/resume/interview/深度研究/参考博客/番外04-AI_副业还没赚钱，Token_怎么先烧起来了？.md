进而想到，如果作为一个个人开发者或者用 AI 搞副业，这些 Token 得多少钱？比如准备做个客服助手，让用户提交问题，后台自动查资料、查物流，最后生成回复。界面上只有一次提交，后面却可能连续调用模型。用户还在等答案，调用消耗已经发生了。

如果把这样的助手作为副业，做出第一版之后，我会先检查：一张工单最多允许花多少？几个任务同时跑，谁来决定下一次调用还能不能发出去？

我为这个问题做了一个小实验。预算设为 100 个演示额度，两个任务各申请 60。先查余额再执行，两个都通过，合计占用了 120；把检查和预占放到同一次数据库更新里，只通过一个，另一个没有进入模拟调用。

差别就出在花钱之前的那一步。

## 用户点了一次，模型为什么要跑好几轮？

先用一个简化任务说明。顾客问包裹什么时候送到，客服希望助手根据订单与物流记录生成一份回复建议。后台为这次处理保存一条 Run，也就是一次执行记录；Worker 负责拿着这条记录继续做事。

模型读到问题，决定查询订单。程序执行订单工具，把结果交回来；模型再决定查询物流，拿到物流信息后，组织最后的回复。按这个安排，已经有三次模型调用。工具执行还可能有独立费用，这里先只算模型部分。

三轮读到的内容也可能越来越多。如果每轮都保留之前的对话和工具结果，最初的问题会再次进入输入，新增的订单、物流信息也会跟着进入后续请求。计算一次任务的输入消耗，需要把各轮实际送进去的内容加起来。

举个纯算术的例子。三轮输入分别是 2000、4000、6000 个 Token，输入合计就是 12000。最后一轮看到的 6000，只描述了那一轮，不能拿来代替整个任务的累计量。缓存命中会影响费用，结算时还得按服务商的分类拆开。

工具出错，又会改变这条路径。订单服务暂时超时，程序可能重试查询；如果把错误交回模型，请它重新决定怎么做，就会增加模型调用。再套一层“任务失败就重新执行”，前面已经成功的步骤也可能被跑一遍。

所以我会把调用明细关联到同一个 `run_id` ，这个编号指向刚才那张工单的一次处理。每次真正发出的模型请求再有自己的 `attempt_id` 。同一 Run 下，第一次调用、超时后的新调用分别记账，才能看出费用到底在哪一轮增加。

重试结算同一次调用，沿用原来的尝试编号；重新向模型发一次请求，创建新的编号。两个动作都叫“重试”，但前者要防重复记账，后者必须重新申请额度。

## 给每次调用留一笔额度

循环最多执行五轮，确实能挡住无限往返。但同样五轮，一次带两千字的资料，一次带整份长文，消耗可能差很多。再增加同时处理的任务数，总消耗还会继续上升。

我会在后台同时保留单次 Run 的预算和组织预算。单次预算约束一张工单，组织预算约束这个客户当前结算周期内的所有任务。两边都允许，本次调用才有资格继续。对于自己运营的小产品，组织可以先理解成自己的应用账户。

预算要约束费用，就先统一记账单位。我会用足够细的整数金额单位，避免浮点累加误差；下面实验用无币种的整数额度，只验证准入逻辑。实际接模型时，按所用模型的计费项目，把 usage 换算到同一种内部单位，并记录采用的价格版本。

输入、输出、缓存读取，以及模型适用时的缓存写入，要按对应口径计算。不能把彼此包含的统计字段再加一遍。原始 usage 也要保留，之后调整价格配置、发现统计错误，才有依据重新核算。

这种明细表能回答已经用了多少，执行端还需要知道尚未结算的调用占了多少。模型请求发出以后，要过一会儿才返回 usage；在这段时间里，只看已结算金额，会把正在消耗的部分漏掉。

于是预算表里要再加一个数： **已预占额度** 。每次调用之前，先为它留出额度；结果回来，再按实际消耗结算。此时允许分给下一次调用的余额，才是总预算减去已结算金额，再减去已预占额度。

这也解释了为什么关掉入口仍可能继续产生消耗。刚才已经进入队列的工单，还会被 Worker 取走执行。把预算检查放到每次模型调用之前，才能约束这些已经排队的工作。

检查的位置也要统一。如果生成回复经过了预算函数，另一条“补充检索后再分析”的路径却直接调用模型，账户上的限制就有了缺口。我会让这些路径都经过同一个模型调用入口，由后端根据任务记录确定组织身份。客户端传来的预算数字只作请求参数，不能自行扩大后台配置的上限。

调用封装里还有一层要看清。有些客户端会在内部自动重试，应用只调用一次函数，外面实际发出了多次请求。若每笔预占只覆盖一次请求，就要把重试交给能逐次申请额度的执行层；若保留内部重试，则必须将允许的全部尝试计入预占上界，并汇总其用量。不能让隐藏的请求从记账路径旁边溜过去。

## 两笔 60 的并发申请，我用代码跑了一遍

把事情缩小到最容易看见的程度。账户预算是 100，已结算和已预占都是零，两个 Worker 分别处理一张工单，各自需要为下一次调用申请 60。

第一个 Worker 查询，得到余额 100。它还没有占用这笔额度，第二个也查询，仍然得到 100。两边各自判断“够用”，然后把自己的申请写入数据库。每一步单独看都没报错，合起来却允许了 120 的调用。

我在实验里专门放了一个等待点：两个线程都查完余额，才允许它们继续。这样就固定了发生竞争的位置，不用靠快速点击按钮碰运气。两个线程各用一个数据库连接，调用模型的位置只做计数，整个实验不会请求外部服务。

下面这段可以直接复制成 `budget_race.py` ，用 Python 3 运行。它只依赖标准库，数据库建在临时目录，结束后自动清理。 `held` 表示已经预占的额度， `cap` 是预算上限。

PYTHON

```
# 吴师兄学大模型：wushixiongai.com# 预算准入教学实验，无真实扣费。import sqlite3 import tempfile from concurrent.futures import ThreadPoolExecutor from pathlib import Path from threading import Barrier  defrace(guarded):with tempfile.TemporaryDirectory()as folder:         path =str(Path(folder)/'budget.db')with sqlite3.connect(path)as db:             db.execute('CREATE TABLE budget (cap INT, held INT)')             db.execute('INSERT INTO budget VALUES (100, 0)')         gate =Barrier(2)defworker(_):             db = sqlite3.connect(path, timeout=10, isolation_level=None)try:                 left = db.execute('SELECT cap-held FROM budget').fetchone()[0]                 gate.wait(timeout=10)if guarded:                     cur = db.execute('UPDATE budget SET held=held+60 ''WHERE cap-held>=60')                     admitted = cur.rowcount ==1else:                     admitted = left >=60if admitted:                         db.execute('UPDATE budget SET held=held+60')returnint(admitted)# 通过后，才进入模拟调用。finally:                 db.close()withThreadPoolExecutor(max_workers=2)as pool:             calls =sum(pool.map(worker,range(2)))with sqlite3.connect(path)as db:             held = db.execute('SELECT held FROM budget').fetchone()[0]return calls, held  for guarded in(False,True):print(('guarded'if guarded else'naive'),*race(guarded))
```


后两列分别是进入模拟调用的次数，以及合计预占额度。第一行放行了两次；第二行只放行一次，留下 40 的可用余额。

第二行起作用的地方，是把余额条件放进了 `UPDATE` 。数据库执行更新时，只有余额仍然够用，才把 60 加到预占里。在这个 SQLite 实验中，写操作被串行执行，后执行的更新会面对前一次写入后的数据。它发现只剩 40，更新零行，程序随即拒绝调用。

实际预算表有多个账户时，还必须带上准确的账户条件，并检查影响行数恰好为一。实验只有一行，省去了账户筛选；拿到多租户系统里，这个条件可不能省。

## 预占之后，额度怎么流转？

现在允许一个请求出去了。预占是 60。结果回来后，按 usage 算出的实际消耗是 40。结算需要同时把预占减去 60，把已结算增加 40。账户剩余可用额度恢复到 60，多留出的 20 又能分给后续请求。

组织和 Run 两层预算也要一起变动。我会把它们放在同一个数据库事务里：两层都预占成功，才提交；有一层额度不足，整笔回滚。否则组织额度可能已经占住，Run 却没有通过，任务没开始，账上先少了一块可用余额。

我补做的结算检查里，组织总额为 100，单次 Run 总额为 80。先预占 60，再按实际 40 结算。之后申请 50，组织还剩 60，本来允许；Run 只剩 40，拒绝。检查数据库，组织那笔预占也已经回滚，两边都保持已结算 40、预占零。

这个事务还得保存一条调用记录，把尝试编号、预占量和状态关联起来。收到结算消息时，根据同一个尝试编号更新。只有尚未结算的记录可以推进到已结算，并在同一事务里更新两层金额；重复收到消息，直接返回已有结果。

我也检查了重复结算：同一次调用的 40 再结算一遍，账上仍然是 40。正式实现中，调用记录的状态判断也需要锁或条件更新，避免两个结算者同时通过。演示的重复结算检查是顺序执行，不能拿它证明并发结算已经覆盖。

数据库事务只包住这些短暂的记账动作。预占提交后，再向模型发请求，别让事务一直等着模型生成。否则一次耗时调用占着数据库锁，其他工单连申请额度都可能被拖住。

预占数得覆盖这次调用可能产生的费用。若只是拿历史平均值估个数，某次输入变长、输出变多，实际消耗就可能超过预占，前面的并发检查再正确也管不住这部分差额。

调用的计费规则明确、输入输出也可约束时，可以按允许的最大输入、最大输出及相关计费项计算保守上界。模型切换或参数改变后重新计算，不能继续沿用旧额度。拿不准缓存是否命中时，也别提前把折扣当成必然结果。

上界取得越保守，同时能放行的请求可能越少。比如每个请求预占 60，实际经常只用 10，余额 100 时仍然只能先放一个。它换来了更可控的支出，也带来了等待。后面可以通过限制资料长度、压低输出上限改善利用率，但需要保留任务质量检查。

### 拿不到用量，就先保留这笔预占

预占解决了并发争用，调用超时又会带来一个空档。请求已经发到模型服务，客户端没有收到完整响应，也没有拿到 usage。模型究竟处理了多少，当前这条连接交代不了。

这时把消耗填成零，再释放全部预占，后续任务就能继续使用这笔额度。如果前一个请求已经产生费用，系统会在账面上反复“有钱”，外部消耗却越积越多。

我会把这次尝试保留为用量待确认，继续占住额度。能根据服务商的请求编号查回结果，就补齐实际用量再结算；需要等账单或人工核对，就把这个状态明确留下。单纯到了超时时间，没有证据说明请求未产生费用，不能据此自动退款。

为了检查这条分支，我在演示里保留一条尚未提供实际用量的预占记录，检查它仍然占用额度。模拟取得“未产生费用”的确认后，才以零结算并释放预占。若实际值超过预占，检查程序会报告上界失效，并保留原预占等待核对，后续要修正金额和准入策略。

这会牺牲一些可用额度。服务商长期不提供可核对结果时，账户甚至可能被未决记录占满。产品上需要让维护者看见是哪几次调用卡住，提供核对和处理入口；不能在后台悄悄清零，然后继续把新的请求放出去。

进程崩溃也按这条思路处理。预占已经提交，发请求前进程退出，可能一分钱都没花；请求已发出、来不及保存结果时退出，又可能已经产生费用。只看数据库里一条长期未更新的记录，无法区分这两个窗口。恢复流程要结合发送记录和外部查询证据处理，证据不足就继续留作未决，不能把进程重启当成退回额度的理由。

如果决定再次调用模型，新尝试还要单独预占，旧尝试保持待确认。单个任务也要有最大尝试次数和总时长，避免不断申请、不断失败。限流约束一段时间内的调用速率，预算约束累计允许花出的额度，两项检查都放在真正发请求的路径上。

## 预算拒绝之后，怎么结束这张工单？

回到那张物流工单。订单已经查到，准备生成回复时额度不够了。后台既然决定不再调用模型，前端就该结束无休止的加载，告诉客服当前处理停在哪里，并保留已经取得的订单信息。

我会把“预算不足”作为明确的停止原因记录下来，页面用现成文案提示：“本次自动处理已停止，可查看已有结果或转人工处理。”为了生成这句提示，再额外调一次模型，只会让预算出口多出一个例外。

是否允许恢复，由产品规则决定。允许恢复时，先确认预算确实增加或原预占已经完成核对，再继续申请下一次调用。普通的自动重试遇到预算拒绝就结束，不能靠不断重投队列等待某次侥幸通过。

做第一版时，可以先按这篇的参数做一次检查：余额 100，同时申请两笔 60，外部调用入口只能进入一次。然后把获准的调用停在结果未知的位置，确认额度还被占着；拿到实际用量后重复提交结算，确认金额没有被记两次。

这几步检查完，才轮到分析哪些调用值得优化。把单次成本和任务结果放在一起看：便宜的调用如果一直失败，仍然解决不了工单；消耗更高的路径如果能完成必要工作，也有保留的理由。用同一组任务比较修改前后的结果和费用，才能知道省掉的是重复工作，还是回答所需的信息。

开头那张 193.3 亿的面板，记录了我的使用情况。轮到自己做产品，我更关心下一次请求：它准备花多少？谁已经占住额度？结果没回来时，这笔账由谁保管？

**模型可以继续提出下一步，执行程序要先确认这一步有预算。**
