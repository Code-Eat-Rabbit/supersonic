# 深度研究功能集成设计（SuperSonic × miro-flow-solution）

> 目标：在 SuperSonic 问数成功并完成描述性解读后，引导用户触发 Python 深度研究 Agent（miro-flow-solution），产出归因报告并回挂到当前 `queryId`。
> 输入文档：`docs/resume/interview/三、深度研究-面试准备.md` 的 B5 / C9 章节。
> 状态：设计定稿，待编写实现计划（writing-plans 阶段）。
> 协议契约原则：**协议先就绪、实现可渐进**——Demo 阶段每项只做最小实现，但字段和抽象接口先留好，未来演进无损。

---

## 1. 项目背景

### 1.1 B5 文档描述的产品形态

- 用户问数成功并完成描述性解读后，结果区展示「想要对结果做深度研究吗？」
- 用户点击 = 启动深度研究，前端只传当前 `queryId`
- Java 按该 `queryId` 取出原问题、`textResult`/`textSummary`、维度/指标，截断后拼成 `task + context`
- Java `POST` Python `/v1/research/jobs`，立即 `202` 返回 `jobId`，**不**在 execute 线程同步等待
- 前端轮询/订阅 Java 取终态；成功写入短报告字段；失败静默保留 `textSummary`

### 1.2 双方代码现状落差

| 维度 | 现状 | 差距 |
|------|------|------|
| Python 任务执行通道 | 仅 WebSocket `/ws`（session 1:1 task，纯内存） | 需新增 REST `/v1/research/jobs` 异步 job 契约 |
| Python 任务状态持久化 | 无（仅 TaskTracer JSON 日志，无 load 入口） | 需新增 SQLite job store + 启动恢复 |
| Java 异步 job 框架 | 无（仅 textSummary 伪流式轮询） | 需新建 `s2_chat_research_job` 表 + 网关层 |
| 前端轮询/推送 | ChatItem 500ms 轮询 `getExecuteSummary` | 新增 SSE 推送通道 |
| traceId | Java MDC + LogInterceptor，链路完整 | 需 HTTP header 透传到 Python |

### 1.3 实现目标

**端到端跑通 Demo**：Java 网关 + Python REST + 前端 SSE，三个本地进程能从点击按钮看到深度报告产出。

## 3. 整体架构

### 3.1 数据流总览

```
[用户] 在 ChatItem 结果区点击"深度研究"
   │
   ▼  POST /api/chat/research/query/{queryId}        (前端 → Java)
[Java 网关]
   - UserHolder.findUser() 拿当前用户
   - permissionChecker.check(user)  ← 权限+配额+并发
   - 从 ChatQueryDO 取 question + textResult + textSummary + 维度/指标
   - 截断拼成 task + context
   - 生成 jobId = UUID，拿 traceId
   - 写 s2_chat_research_job(PENDING)
   - @Async 调 Python（带 Authorization + X-Trace-Id header）
   - 返回 {jobId, status:PENDING}
   │
   │                                              ────►  [Python miro-flow]
   │                                                     FastAPI dependency 验 service token
   │                                                     IntentClassifier 分类（1 次 LLM 调用）
   │                                                     TypeToConfig 映射
   │                                                     写 SQLite(PENDING)
   │                                                     asyncio.create_task 执行 pipeline
   │                                                     立即返回 202 + job_id
   │
   ▼  EventSource 订阅 /api/chat/research/{jobId}/stream
[前端]                                          [Python pipeline 运行]
   - 先 GET 当前状态                                - execute_task_pipeline
   - 终态则关闭                                     - 长度控制（句子边界截断）
   - 订阅 SSE                                       - 写 outputs/{tenant}/research_jobs/{job_id}.json
   - onerror 3 秒重连                               - 更新 SQLite(COMPLETED)
                                                       │
[Java @Scheduled fixedDelay=2000]                       │
   - 扫 s2_chat_research_job WHERE status IN (PENDING, RUNNING)
   - 对每条记录 GET /v1/research/jobs/{jobId}
   - 状态变化 → 更新本地表 + 推 SSE
   - 超时（15min）→ 标 FAILED
```

### 3.2 两个独立方向（关键澄清）

| 方向 | 机制 | 频率 |
|------|------|------|
| Python 状态 → Java 表 | Java `@Scheduled` 主动拉 Python | 每 2 秒 |
| Java 表 → 前端 UI | Java SSE 推送 + GET fallback（首次/重连） | 事件驱动 |

**关键设计**：Java→Python 流量与前端用户数解耦。100 个用户同时轮询，Java 仍然每 2 秒一次固定频率向 Python 发请求。

### 3.3 Python 内部处理流（意图识别 → 分发 → 执行）

Python 服务接到 POST 后**内部**的处理链路（详细 ASCII 图见 §7.0）：

```
POST /v1/research/jobs 接到请求
   │
   ▼  同步路径（立即返回 202）
[FastAPI middleware] → trace_id 注入 contextvar
   │
   ▼
[deps.verify_service_token] → 401 失败
   │
   ▼
[routes.create_job]
   │
   ├─ IntentClassifier.classify(task, context)
   │    └─ 单次 LLM 调用 → JSON {research_type, data_domain}
   │       （启动时扫描 domains/*.md frontmatter 动态构建取值清单）
   │
   ├─ JobStore.create(... status=PENDING)   ← SQLite 写入
   │
   ├─ BackgroundTasks.add_task(run_pipeline_async, ...)
   │
   └─ return 202 {job_id, status:PENDING}

            ─── 异步路径（asyncio background task）───

run_pipeline_async(job_id, research_type, data_domain, ...)
   │
   ▼
[幂等守卫] 已终态则直接 return
   │
   ▼
[QueryRewriter.rewrite]
   └─ default：prepend 通用归因约束
   └─ financial_analyst/academic：原样返回
   │
   ▼
[ResearchDirective.compose_task]
   ├─ 加载核心模板：research_prompts/{type}.md
   ├─ 加载领域片段（仅 financial_analyst）：domains/{domain}.md
   └─ 拼成 <research_directive>...</research_directive>
   │
   ▼
[asyncio.wait_for(execute_task_pipeline, timeout=14min)]
   │
   ├─ Main Agent 多轮工具调用（MCP + sub-agents + max_turns）
   ├─ 超时 → PipelineTimeoutError
   └─ 产出：final_answer + boxed_answer
   │
   ▼
[enforce_length_budget] 句子边界截断
   │
   ▼
[ReportStore.save] → outputs/{tenant}/research_jobs/{job_id}.json
   │
   ▼
[JobStore.update(status=COMPLETED, summary, uri)]   ← 终态不可变守卫
```

**Python 内部三层职责**（§7.4/§7.5/§7.6 详述）：

| 层 | 组件 | 职责 |
|----|------|------|
| 路由层 | IntentClassifier | 判断研究方法论 + 数据领域 |
| 改写层 | QueryRewriter | 仅 `default` 加通用约束，其他原样 |
| 指导层 | ResearchDirective | 拼接核心 prompt + 可插拔领域片段 |

**与 Java 侧的边界**：Java 只看到 HTTP；所有路由、prompt 拼接、pipeline 执行、状态迁移都在 Python 内部完成。Java 通过 @Scheduler 拉 SQLite 状态，是"观察者"不是"参与者"。


Response 200:

### 4.2 REST 契约（前端 ↔ Java · 外部）

| 方法 | 路径 | 响应 |
|------|------|------|
| POST | `/api/chat/research/query/{queryId}` | `200 {jobId, status:PENDING}` / `400`（无 textSummary）/ `403`（无权限）/ `429`（配额）/ `409`（并发） |
| GET | `/api/chat/research/{jobId}` | `200 {jobId, queryId, status, reportSummary?, reportFull?, errorMsg?}` |
| GET | `/api/chat/research/{jobId}/stream` | `SseEmitter`（`text/event-stream`，状态变化推送） |

### 4.3 状态机

```
            ┌──────────────────────────────────────┐
            │                                      │
PENDING ──► RUNNING ──► COMPLETED                  │
   │           │                                  │
   │           └──► FAILED（Python 异常 / 超时）   │
   │                                              │
   └──► FAILED（Python 启动恢复扫到 RUNNING）◄────┘
```

**状态迁移规则**：

| 迁移 | 触发时机 | 实现位置 |
|------|----------|----------|
| → PENDING | POST `/v1/research/jobs` 收到请求 | `routes.py` create_job |
| → RUNNING | `run_pipeline_async` 开始执行 | `pipeline_adapter.py` 入口 |
| → COMPLETED | `execute_task_pipeline` 正常返回（含 max_turns 到顶但有 final summary） | `pipeline_adapter.py` try 块末尾 |
| → FAILED | pipeline 抛异常 / Python 14min 硬超时 / Python 启动恢复扫到 / Java 15min 兜底 | `pipeline_adapter.py` except / `asyncio.wait_for` / `recover_stale_jobs` / `ResearchSyncScheduler` |

**终态不可变约束**（消除 Java/Python 状态分叉）：

- 一旦 job 进入 `COMPLETED` 或 `FAILED`，**任何后续状态写入都被拒绝**
- Python `job_store.update()` 校验当前状态：若已终态，跳过更新并记录 warning
- Java `mergeStatus()` 同样校验：若本地表已终态，拒绝 Python 回包覆盖
- 这是评审 #6 的根本修复——防止「Java 超时标 FAILED → Python 后完成标 COMPLETED」造成永久分叉

### 4.4 关键设计决策（7 条）

1. **jobId 由 Java 生成**（UUID）——Java 控制命名空间，Python 不自创 task_id
2. **traceId 从 Java MDC 透传到 Python**——HTTP header `X-Trace-Id`，便于事后排查
3. **路由由 Python 全权决策**——IntentClassifier 判断类型 → ResearchDirective 选 prompt，Java 只传 `task + context`，不感知业务
4. **前端永远不直连 Python**——所有调用过 Java 网关
5. **Python 是超时唯一权威**（评审 #6 修复）——Python `asyncio.wait_for` 硬超时 14 分钟，保证 Python 永远在 14min 内进入终态；Java 15 分钟仅作兜底（Python 进程崩溃、网络分区等极端情况）
6. **终态不可变**（评审 #6 修复）——COMPLETED/FAILED 一旦写入，任何反向覆盖都被拒绝；消除双写一致性问题
7. **超时时钟统一用 `started_at`**——`started_at` 为 Python 标 RUNNING 时 Java 表更新的时间；若仍为 null（PENDING 卡住）则 fallback 到 `created_at`

### 5.4 `useResearchJobStream` hook

```typescript
// hooks/useResearchJobStream.ts
import { useEffect, useState } from 'react';
import { getResearchStatus } from '../service';

export type JobStatus = 'PENDING' | 'RUNNING' | 'COMPLETED' | 'FAILED';

export interface ResearchState {
    status: JobStatus | null;
    report: { summary: string; full?: string } | null;
    errorMsg: string | null;
}

export function useResearchJobStream(jobId: string | null): ResearchState {
    const [state, setState] = useState<ResearchState>({
        status: null, report: null, errorMsg: null,
    });

    useEffect(() => {
        if (!jobId) return;

        let eventSource: EventSource | null = null;
        let reconnectTimer: ReturnType<typeof setTimeout> | null = null;
        let closed = false;

        const connect = async () => {
            if (closed) return;

            try {
                // 1. 先 GET 当前状态（避免 SSE 不推当前状态的问题）
                const current = await getResearchStatus(jobId);
                setState({
                    status: current.status,
                    report: current.reportSummary
                        ? { summary: current.reportSummary, full: current.reportFull }
                        : null,
                    errorMsg: current.errorMsg,
                });

                // 已终态：不订阅
                if (current.status === 'COMPLETED' || current.status === 'FAILED') {
                    return;
                }

                // 2. 订阅 SSE
                eventSource = new EventSource(`/api/chat/research/${jobId}/stream`);

                eventSource.onmessage = (e) => {
                    const data = JSON.parse(e.data);
                    setState({
                        status: data.status,
                        report: data.reportSummary
                            ? { summary: data.reportSummary, full: data.reportFull }
                            : null,
                        errorMsg: data.errorMsg,
                    });
                    if (data.status === 'COMPLETED' || data.status === 'FAILED') {
                        eventSource?.close();
                    }
                };

                eventSource.onerror = () => {
                    eventSource?.close();
                    if (!closed) {
                        reconnectTimer = setTimeout(connect, 3000);   // 3 秒重连
                    }
                };
            } catch (err) {
                if (!closed) {
                    reconnectTimer = setTimeout(connect, 3000);
                }
            }
        };

        connect();

        return () => {
            closed = true;
            eventSource?.close();
            if (reconnectTimer) clearTimeout(reconnectTimer);
        };
    }, [jobId]);

    return state;
}
```

### 5.5 ResearchItem 容器

```tsx
// components/ChatItem/ResearchItem/index.tsx
import { useState } from 'react';
import { useResearchJobStream } from '../../../hooks/useResearchJobStream';
import { createResearchJob } from '../../../service';
import ResearchTrigger from './ResearchTrigger';
import ResearchProgress from './ResearchProgress';
import ResearchReport from './ResearchReport';

interface Props {
    queryId: number;
    researchFeature: {
        enabled: boolean;
        remainingToday: number;
        runningJobId: string | null;
    };
}

export default function ResearchItem({ queryId, researchFeature }: Props) {
    // jobId 初始化：优先用 runningJobId（页面刷新后继续订阅）
    const [jobId, setJobId] = useState<string | null>(
        researchFeature.runningJobId
    );
    const { status, report, errorMsg } = useResearchJobStream(jobId);

    const handleStart = async () => {
        try {
            const res = await createResearchJob(queryId);
            setJobId(res.jobId);
        } catch (err) {
            // 静默失败（权限/配额/并发已在 service 层抛出）
            console.warn('[research] start failed', err);
        }
    };

    // ✗ FAILED：不渲染（静默保留 textSummary）
    if (status === 'FAILED') {
        return null;
    }

    // 进行中
    if (status === 'PENDING' || status === 'RUNNING') {
        return <ResearchProgress status={status} />;
    }

    // 完成
    if (status === 'COMPLETED' && report) {
        return (
            <ResearchReport
                summary={report.summary}
                fullReport={report.full}
            />
        );
    }

    // 默认：启动按钮
    return (
        <ResearchTrigger
            remainingToday={researchFeature.remainingToday}
            runningJobId={researchFeature.runningJobId}
            onStart={handleStart}
        />
    );
}
```

### 5.7 关键交互细节

**场景 1：页面刷新后继续订阅**
- `queryResult.researchFeature.runningJobId` 不为 null（Java 表里 RUNNING job）
- ResearchItem 初始 jobId 即 `runningJobId`，自动续订 SSE
- 用户体验：刷新后看到"正在深度研究中..."

**场景 2：用户离开页面后回来**
- EventSource 在组件 mount 时重新建立
- `useResearchJobStream` 先 GET 拿当前状态，可能直接是 COMPLETED → 跳过 SSE 订阅

**场景 3：深度研究失败**
- SSE 收到 `{status: 'FAILED', errorMsg: '...'}`
- ResearchItem 返回 `null`，不渲染任何东西
- 用户只看到原表格 + textSummary
- 失败原因在浏览器 console + Java logback 日志里

**场景 4：Python 服务挂了**
- SSE 连接失败 → `onerror` → 3 秒重连
- 重连期间 UI 显示 RUNNING（保持上次状态）
- 如果 Python 一直不响应，Java @Scheduler 15 分钟后标 FAILED → 推送 → UI 静默隐藏

### 5.8 与现有轮询模式的关系

**两条独立的状态获取路径**：

| 数据 | 获取方式 | 管理者 |
|------|----------|--------|
| `textSummary`（描述性解读） | 500ms 轮询 `getExecuteSummary` | `ChatItem/index.tsx` 现有逻辑 |
| 深度研究状态 | SSE 推送 | `ResearchItem` + `useResearchJobStream` |

**互不干扰**：textSummary 轮询失败不影响深度研究 SSE；深度研究挂了不影响 textSummary 展示。

### 5.9 前端不做的事

- 取消按钮（Demo 范围）
- 进度条/百分比（PENDING/RUNNING 两态够）
- 历史报告列表
- 报告导出按钮
- 用户反馈/评分
- toast 提示（静默失败原则）

```java
@Service
public class ResearchJobServiceImpl implements ResearchJobService {

    @Autowired private ChatQueryService chatQueryService;
    @Autowired private ResearchPermissionChecker permissionChecker;
    @Autowired private PythonResearchClient pythonClient;
    @Autowired private ResearchJobMapper jobMapper;
    @Autowired private ResearchSseRegistry sseRegistry;

    @Override
    public CreateJobResponse createResearch(User user, Long queryId) {

        ChatQueryDO query = chatQueryService.getChatQuery(queryId);
        if (query == null || StringUtils.isEmpty(query.getTextSummary())) {
            throw new ResearchBadRequestException(
                "查询结果不存在或无描述性解读");
        }

        // 2. 权限 + 配额 + 并发校验
        permissionChecker.check(user);

        // 3. 组装 task + context（截断到 ≤ 4000 字）
        String task = query.getQuestion();
        String context = buildContext(query);

        // 4. 生成 jobId + 拿 traceId
        String jobId = UUID.randomUUID().toString();
        String traceId = TraceIdUtil.getTraceId();

        // 5. 写 Java 表（PENDING）
        ResearchJobDO job = new ResearchJobDO();
        job.setJobId(jobId);
        job.setQueryId(queryId);
        job.setTenantId("default");
        job.setTraceId(traceId);
        job.setCreatedBy(user.getId());
        job.setAgentId(query.getAgentId());
        job.setTask(task);
        job.setPythonStatus("PENDING");
        job.setCreatedAt(new Date());
        jobMapper.insert(job);

        // 6. 异步调 Python（不阻塞响应）
        pythonClient.createJobAsync(jobId, traceId, task, context);

        return new CreateJobResponse(jobId, "PENDING");
    }

    private String buildContext(ChatQueryDO query) {
        // textResult + textSummary + 维度 + 指标，总长度 ≤ 4000 字
        StringBuilder sb = new StringBuilder();
        if (query.getTextResult() != null) {
            sb.append("## 查询结果\n").append(truncate(query.getTextResult(), 2000)).append("\n\n");
        }
        if (query.getTextSummary() != null) {
            sb.append("## 描述性解读\n").append(truncate(query.getTextSummary(), 1000)).append("\n\n");
        }
        // Demo 范围内只取 textResult + textSummary；维度/指标列表留作扩展
        // 未来从 ParseContext.getParsedS2SQL() 提取 metrics/dimensions 字段追加到 context
        return sb.toString();
```

#### 6.3.3 `ResearchPermissionChecker` · 权限校验

```java
@Component
public class ResearchPermissionChecker {

    @Value("${research.enabled-admin-only:true}")
    private boolean adminOnly;

    @Value("${research.enabled-users:}")
    private Set<String> whitelist;

    @Value("${research.daily-quota:10}")
    private int dailyQuota;

    @Value("${research.max-concurrent-per-user:1}")
    private int maxConcurrent;

    @Autowired private ResearchJobMapper jobMapper;

    public void check(User user) {
        // 1. 功能权限（内测期：admin OR 白名单）
        boolean permitted = false;
        if (adminOnly && Integer.valueOf(1).equals(user.getIsAdmin())) {
            permitted = true;
        }
        if (whitelist.contains(user.getName())) {
            permitted = true;
        }
        if (!permitted) {
            throw new ResearchPermissionException(
                "深度研究功能内测中，仅对管理员开放");
        }

        // 2. 配额（每用户每日）
        int todayCount = jobMapper.countByUserAndDate(user.getId(), today());
        if (todayCount >= dailyQuota) {
            throw new ResearchQuotaExceededException("今日深度研究次数已用完");
        }

        // 3. 并发（每用户 max_concurrent 个 RUNNING）
        int runningCount = jobMapper.countByUserAndStatus(user.getId(), "RUNNING");
        if (runningCount >= maxConcurrent) {
            throw new ResearchConcurrentException("已有深度研究进行中");
        }
    }

    public boolean isPermitted(User user) {
        // 轻量判断（不抛异常），用于 queryResult.researchFeature.enabled
        if (adminOnly && Integer.valueOf(1).equals(user.getIsAdmin())) return true;
        return whitelist.contains(user.getName());
    }

    public int remainingQuota(User user) {
        return Math.max(0, dailyQuota - jobMapper.countByUserAndDate(user.getId(), today()));
    }
}
```

#### 6.3.5 `ResearchSyncScheduler` · @Scheduled 同步（评审 #6 修复）

**核心改动**（对比原版）：
1. **isTimeout 用 `started_at`，fallback `created_at`**（对齐 §4.4 决策 #7）
2. **`mergeStatus` 内置终态不可变校验**：本地已终态则拒绝 Python 回包覆盖
3. **拉 Python 状态分两阶段**：先不带 full 拉状态；变 COMPLETED 后单独拉一次 full（修复评审 #10 的 `include_full` 恒 true bug）
4. **区分 404 与网络抖动**：404 立即标 FAILED（清理孤儿），网络抖动跳过下次重试（修复评审 #18）

```java
@Component
public class ResearchSyncScheduler {

    private static final Logger log = LoggerFactory.getLogger(ResearchSyncScheduler.class);
    private static final Set<String> TERMINAL = Set.of("COMPLETED", "FAILED");

    @Value("${research.timeout-minutes:15}")
    private int timeoutMinutes;

    @Autowired private ResearchJobMapper mapper;
    @Autowired private PythonResearchClient pythonClient;
    @Autowired private ResearchSseRegistry sseRegistry;

    @Scheduled(fixedDelayString = "${research.sync-interval-ms:2000}")
    public void syncRunningJobs() {
        List<ResearchJobDO> active = mapper.selectByStatusIn(
            Arrays.asList("PENDING", "RUNNING"));

        for (ResearchJobDO job : active) {
            try {
                // 1. 超时兜底（Python 崩溃 / 网络分区）
                if (isTimeout(job, timeoutMinutes)) {
                    flipToFailed(job, "java-side timeout after " + timeoutMinutes + " min");
                    continue;
                }

                // 2. 拉 Python 状态（不带 full，避免大字段每 2s 拉）
                PythonJobStatus p = pythonClient.getStatus(job.getJobId(), false);

                // 3. Python 已终态，但本地仍 RUNNING → 合并
                if (!job.getPythonStatus().equals(p.getStatus())) {
                    // COMPLETED 时单独拉一次 full（评审 #10 修复）
                    if ("COMPLETED".equals(p.getStatus())) {
                        PythonJobStatus full = pythonClient.getStatus(job.getJobId(), true);
                        p.setReportFull(full.getReportFull());
                    }
                    mergeStatus(job, p);   // 内置终态不可变校验
                }
            } catch (HttpClientErrorException.NotFound e) {
                // Python 返回 404：孤儿记录（Python 重启清库），立即 FAILED（评审 #18）
                flipToFailed(job, "python reports job not found (orphan record)");
            } catch (Exception e) {
                // 网络抖动：跳过本次，下次再试（评审 #18）
                log.debug("[research] sync failed jobId={} will retry: {}",
                    job.getJobId(), e.getMessage());
            }
        }
    }

    /** 终态不可变合并：本地已 COMPLETED/FAILED 则拒绝 Python 回包覆盖（评审 #6 修复） */
    private void mergeStatus(ResearchJobDO job, PythonJobStatus p) {
        if (TERMINAL.contains(job.getPythonStatus())) {
            log.warn("[research] reject terminal flip jobId={} local={} remote={}",
                job.getJobId(), job.getPythonStatus(), p.getStatus());
            return;
        }
        job.setPythonStatus(p.getStatus());
        if (p.getStatus().equals("COMPLETED")) {
            job.setReportSummary(p.getReportSummary());
            job.setReportFull(p.getReportFull());
            job.setCompletedAt(new Date());
        } else if (p.getStatus().equals("FAILED")) {
            job.setErrorMsg(p.getErrorMsg());
            job.setCompletedAt(new Date());
        }
        mapper.updateById(job);
        sseRegistry.send(job.getJobId(), buildEvent(job));
        log.info("[research] status change jobId={} -> {}",
            job.getJobId(), p.getStatus());
    }

    /** 标 FAILED 并推 SSE；若本地已终态则跳过（幂等） */
    private void flipToFailed(ResearchJobDO job, String reason) {
        if (TERMINAL.contains(job.getPythonStatus())) {
            return;   // 已终态，跳过（评审 #6）
        }
        job.setPythonStatus("FAILED");
        job.setErrorMsg(reason);
        job.setCompletedAt(new Date());
        mapper.updateById(job);
        sseRegistry.send(job.getJobId(), buildEvent(job));
        log.warn("[research] timeout jobId={} traceId={}",
            job.getJobId(), job.getTraceId());
    }

    /** 超时时钟：优先 started_at，fallback created_at（评审 #6 + §4.4 #7） */
    private boolean isTimeout(ResearchJobDO job, int minutes) {
        Date clock = job.getStartedAt() != null ? job.getStartedAt() : job.getCreatedAt();
        long elapsed = System.currentTimeMillis() - clock.getTime();
        return elapsed > minutes * 60_000L;
    }
}
```

### 6.4 `ResearchSseRegistry` · SSE 推送（评审 #4 + #11 修复）

**核心改动**：
1. **`SseEmitter` 设有限超时**（20 分钟，略大于 job 15min 超时）——防资源耗尽（评审 #4c）
2. **终态推完后 `complete()`**——释放 emitter 资源（评审 #14）
3. **register 前归属校验已在 Controller 完成**——这里只信任已校验的调用方
4. **SSE 只推 summary，不推 full**——避免大字段重复推送（评审 #11）

```java
@Component
public class ResearchSseRegistry {

    private static final long SSE_TIMEOUT_MS = 20L * 60 * 1000;   // 20min，略大于 job 超时
    private static final Set<String> TERMINAL = Set.of("COMPLETED", "FAILED");

    @Autowired private ResearchJobMapper mapper;

    private final Map<String, List<SseEmitter>> emitters = new ConcurrentHashMap<>();

    public SseEmitter register(String jobId) {
        // 有限超时（评审 #4c 修复）
        SseEmitter emitter = new SseEmitter(SSE_TIMEOUT_MS);
        emitters.computeIfAbsent(jobId, k -> new CopyOnWriteArrayList<>())
                .add(emitter);

        emitter.onCompletion(() -> remove(jobId, emitter));
        emitter.onTimeout(() -> {
            remove(jobId, emitter);
            log.debug("[research] SSE timeout jobId={}", jobId);
        });
        emitter.onError(e -> remove(jobId, emitter));

        // 首次连接立即推当前状态（避免新连接看不到状态）
        ResearchJobDO current = mapper.selectById(jobId);
        if (current != null) {
            try {
                emitter.send(SseEmitter.event().data(buildEvent(current)));
                // 已终态立即 complete，释放资源（评审 #14）
                if (TERMINAL.contains(current.getPythonStatus())) {
                    emitter.complete();
                }
            } catch (IOException ignored) {}
        }
        return emitter;
    }

    public void send(String jobId, Object event) {
        List<SseEmitter> list = emitters.get(jobId);
        if (list == null) return;
        for (SseEmitter e : list) {
            try {
                e.send(SseEmitter.event().data(event));
                // 推送终态后 complete（评审 #14）
                if (event instanceof JobStatusResponse rs
                        && TERMINAL.contains(rs.getStatus())) {
                    e.complete();
                }
            } catch (IOException ex) {
                remove(jobId, e);
            }
        }
    }

    private void remove(String jobId, SseEmitter emitter) {
        emitters.computeIfPresent(jobId, (k, v) -> {
            v.remove(emitter);
            return v.isEmpty() ? null : v;
        });
    }

    /** SSE 推送 payload：只含 summary，full 走按需 GET（评审 #11 修复） */
    private JobStatusResponse buildEvent(ResearchJobDO job) {
        return new JobStatusResponse(
            job.getJobId(), job.getQueryId(),
            job.getPythonStatus(),
            job.getReportSummary(),   // 只 summary，不带 full
            null,                      // full 走独立 GET ?include_full=true
            job.getErrorMsg()
        );
    }
}
```

```java
    rf.setRunningJobId(runningJob != null ? runningJob.getJobId() : null);

    return rf;
}
```

### 7.3 ReportStore 抽象（演进锚点 #1）

```python
# server/rest/report_store.py
from pathlib import Path
import json
from typing import Protocol

class ReportStore(Protocol):
    def save(self, job_id: str, tenant_id: str, payload: dict) -> str: ...
    def get(self, job_id: str, tenant_id: str = "default") -> dict | None: ...
    def delete(self, job_id: str, tenant_id: str = "default") -> None: ...

class FileSystemReportStore:
    """当前实现：JSON 文件存到 outputs/{tenant_id}/research_jobs/{job_id}.json

    设计动机：
    - JSON 含结构化字段（report_markdown + boxed_answer + metadata），未来迁移 MongoDB/PostgreSQL JSONB 格式不变
    - 按 tenant 分目录，未来多租户自然隔离
    - 开发者可直接打开 JSON 文件调试
    """

    def __init__(self, base_dir: str = "outputs"):
        self.base_dir = Path(base_dir)

    def _path_for(self, tenant_id: str, job_id: str) -> Path:
        return self.base_dir / tenant_id / "research_jobs" / f"{job_id}.json"

    def save(self, job_id: str, tenant_id: str, payload: dict) -> str:
        path = self._path_for(tenant_id, job_id)
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(
            json.dumps(payload, ensure_ascii=False, indent=2),
            encoding="utf-8"
        )
        return f"fs://{path}"

    def get(self, job_id: str, tenant_id: str = "default") -> dict | None:
        path = self._path_for(tenant_id, job_id)
        if not path.exists():
            return None
        return json.loads(path.read_text(encoding="utf-8"))

    def delete(self, job_id: str, tenant_id: str = "default") -> None:
        path = self._path_for(tenant_id, job_id)
        if path.exists():
            path.unlink()
```

### 7.4 IntentClassifier（路由分类 · 演进锚点 #2）

**职责**：单次 LLM 调用输出**结构化 JSON**，同时判断 `research_type`（研究方法论）和 `data_domain`（数据领域）。失败统一 fallback `("default", "unknown")`。

**type 与 data_domain 的关系**：
- `research_type` 决定**研究方法论**（用什么套路做研究）→ 选核心 prompt 模板
- `data_domain` 决定**领域知识**（哪些驱动因素、口径注意）→ 拼接可插拔 domain 片段

**取值清单**：

| 字段 | 取值 | 说明 |
|------|------|------|
| `research_type` | `financial_analyst` / `academic` / `default` | 决定核心 prompt 模板 |
| `data_domain` | **动态扫描** `domains/*.md` 目录，从 frontmatter 读取 | 决定可插拔 domain 片段 |

**核心设计：零代码扩展**（用户反馈）：IntentClassifier 不再硬编码 domain 清单——启动时**扫描 `domains/*.md` 目录**，解析每个文件的 frontmatter 自动构建：

- `VALID_DOMAINS`（合法 domain 清单）
- `PROMPT` 中的取值说明（动态注入）

**新增数据域的工作量**：在 `domains/` 目录加一个带 frontmatter 的 `.md` 文件即可，**零代码改动**。

#### Domain 文件 frontmatter 规范

`domains/green_economy.md` 示例：

```markdown
---
name: green_economy
description: 碳排放/碳价/ESG/绿色债券/新能源
trigger_keywords: [碳, ESG, 绿色, 新能源, 可持续]
priority: 10
---

本次研究的查询数据属于**绿色经济**领域。除核心四步法外，重点关注：
...（domain 片段正文）
```

| frontmatter 字段 | 必填 | 说明 |
|-----------------|------|------|
| `name` | ✓ | domain 标识符（与文件名一致） |
| `description` | ✓ | 简短描述（注入 IntentClassifier prompt） |
| `trigger_keywords` | 可选 | 触发关键词（增强分类准确性） |
| `priority` | 可选 | 排序权重（多个 domain 时影响注入顺序） |

**以 `_` 开头的文件**（如 `_template.md`）会被扫描跳过——是开发者文档不是领域定义。

#### IntentClassifier 实现

```python
# server/rest/intent.py
import json
import pathlib
import re
from dataclasses import dataclass
from functools import lru_cache

DOMAIN_DIR = pathlib.Path(__file__).parent / "research_prompts" / "domains"

@dataclass(frozen=True)
class DomainMeta:
    name: str
    description: str
    trigger_keywords: tuple[str, ...] = ()
    priority: int = 0

    def prompt_line(self) -> str:
        """生成 PROMPT 中的取值说明行"""
        keywords = "/".join(self.trigger_keywords[:3]) if self.trigger_keywords else ""
        suffix = f"（关键词：{keywords}）" if keywords else ""
        return f"- {self.name}：{self.description}{suffix}"


@lru_cache(maxsize=1)
def _scan_domains() -> dict[str, DomainMeta]:
    """启动时扫描 domains/ 目录，自动加载所有 domain 元数据

    新增数据域 = 在 domains/ 目录加一个带 frontmatter 的 .md 文件
    零代码改动，重启即生效（Demo 期不做热加载）
    """
    domains: dict[str, DomainMeta] = {}
    if not DOMAIN_DIR.exists():
        return domains

    for md_file in sorted(DOMAIN_DIR.glob("*.md")):
        # 跳过 _template.md 等以下划线开头的文档文件
        if md_file.name.startswith("_"):
            continue
        meta = _parse_frontmatter(md_file)
        if meta and meta.name:
            domains[meta.name] = meta

    # 按 priority 排序（高优先级先注入 prompt）
    return dict(sorted(domains.items(), key=lambda x: -x[1].priority))


def _parse_frontmatter(path: pathlib.Path) -> DomainMeta | None:
    """解析 frontmatter（YAML between --- and ---）

    使用 stdlib 简单解析，不引入 PyYAML 依赖。
    支持基本类型：str / [list]。
    """
    text = path.read_text(encoding="utf-8")
    match = re.match(r"^---\n(.*?)\n---", text, re.DOTALL)
    if not match:
        return None

    frontmatter: dict = {}
    for line in match.group(1).split("\n"):
        if ":" not in line:
            continue
        k, v = line.split(":", 1)
        k = k.strip()
        v = v.strip().strip('"').strip("'")
        # 简单 list 解析：[a, b, c] -> tuple
        if v.startswith("[") and v.endswith("]"):
            v = tuple(
                x.strip().strip('"').strip("'")
                for x in v[1:-1].split(",")
                if x.strip()
            )
        frontmatter[k] = v

    return DomainMeta(
        name=frontmatter.get("name", path.stem),
        description=frontmatter.get("description", ""),
        trigger_keywords=tuple(frontmatter.get("trigger_keywords", ())),
        priority=int(frontmatter.get("priority", 0)),
    )


class IntentClassifier:
    """研究任务路由分类器

    启动时扫描 domains/ 目录自动加载领域清单，新增数据域零代码改动。
    """

    PROMPT_TEMPLATE = """判断研究任务的类型和数据域，只返回一行 JSON：
{{
  "research_type": "financial_analyst" | "academic" | "default",
  "data_domain": {domain_options}
}}

分类规则：
- research_type=financial_analyst 时，data_domain 必须明确（除 unknown 外）
- research_type=academic 时，data_domain 可选（辅助文献检索策略）
- research_type=default 时，data_domain 必为 unknown

data_domain 取值含义：
{domain_list}
- unknown：无法识别

任务：{task}
上下文：{context_head}

JSON："""

    VALID_TYPES = frozenset({"financial_analyst", "academic", "default"})

    def __init__(self, llm_client):
        self.llm_client = llm_client
        self.domains = _scan_domains()
        self.VALID_DOMAINS = frozenset(self.domains.keys()) | {"unknown"}

    def _build_prompt(self, task: str, context: str) -> str:
        domain_list = "\n".join(
            d.prompt_line() for d in self.domains.values()
        )
        domain_options = " | ".join(
            f'"{d}"' for d in self.VALID_DOMAINS
        )
        return self.PROMPT_TEMPLATE.format(
            domain_options=domain_options,
            domain_list=domain_list,
            task=task,
            context_head=context[:500],
        )

    async def classify(self, task: str, context: str) -> tuple[str, str]:
        """返回 (research_type, data_domain)；失败统一 fallback ("default", "unknown")"""
        try:
            prompt = self._build_prompt(task, context)
            resp = await self.llm_client.complete(prompt)
            data = json.loads(resp.strip())
            rtype = data.get("research_type", "default")
            ddomain = data.get("data_domain", "unknown")
            rtype = rtype if rtype in self.VALID_TYPES else "default"
            ddomain = ddomain if ddomain in self.VALID_DOMAINS else "unknown"
            # default type 强制 unknown domain
            if rtype == "default":
                ddomain = "unknown"
            return rtype, ddomain
        except Exception:
            return "default", "unknown"   # 双字段 fallback
```

**关键设计点**：

1. **`_scan_domains` 用 `lru_cache(maxsize=1)`**：启动后只扫描一次，后续调用直接命中缓存。Demo 期不做热加载（改了 domain 文件需重启 Python），未来可加 watchdog 实现热加载
2. **frontmatter 解析不引入 PyYAML**：用 stdlib 手写简单解析器，避免新增依赖；只支持 str 和 list 两种类型够用
3. **以 `_` 开头的文件被跳过**：`_template.md` 是文档，不是领域定义
4. **priority 字段**：当 domains 多了之后控制 prompt 注入顺序（高 priority 先注入）
5. **`trigger_keywords` 注入 prompt**：增强分类准确性（LLM 看到关键词提示更准）

**为什么单次 LLM 调用**：分两次（先 research_type 后 data_domain）多一次 LLM 往返 +2s 延迟。一次 JSON 输出失败时统一 fallback，对调用方无感。

**为什么分类和改写分离**：单一职责。IntentClassifier 失败只 fallback type/domain，不污染 query；ResearchDirective 失败只退回 default prompt，不污染分类。两条失败路径独立，日志可追溯。

**为什么用 `financial_analyst` 而不是 `industry`**（用户反馈）：原 `industry` 命名过窄——实际覆盖场景包括财报分析、估值建模、宏观政策、投资决策等，远超"行业研究"。改名为 `financial_analyst` 准确表达"金融分析师视角"的角色定位。

### 7.5 ResearchDirective（type-specific 研究指导 prompt）

**职责**：根据 IntentClassifier 输出的 type，加载对应的 Markdown 提示词模板，作为**研究指导**拼到 task description 前面。原 query 保持不变——这是"加约束"而非"改意图"。

**为什么不直接改写 query**：
- 改写会改变用户意图（"比亚迪 2024 净利润"被改成"比亚迪 2024 净利润 行业对比"已经偏题）
- 不同风格的差异本质是"Agent 关注点不同"，不是"用户问题不同"
- 用 ResearchDirective 指导 Agent 怎么研究，比改用户问题更稳

**模板文件位置**：`server/rest/research_prompts/{type}.md`

#### `financial_analyst.md`（金融分析师核心框架 · 四步归因法）

**定位说明**（面试讲解用）：本文件只保留**通用金融分析核心框架**——四步归因法 + 证据强度 + 报告结构。所有领域特有内容（公司估值、宏观周期、绿色政策等）已抽离到 `domains/*.md` 可插拔片段，由 ResearchDirective 按 `data_domain` 动态拼接。加新数据域 = 新增一个 domain 文件，**不动本文件**。

```markdown
你是一名**金融分析师**（兼具金融经济研究、财报分析、宏观归因视角）。
本研究的核心目标：**对查询结果做深度归因与预测**——不只是描述数据，
要回答"为什么是这个值"、"接下来会怎样"。

## 分析四步法（任何数据都必须完整走）

### 第一步：数据描述（是什么）
- 报告核心数字 + 时间口径（年报 / 季报 / 月度）
- 横向锚定：同比 / 环比 / 与同行 / 与行业平均 / 与历史区间
- 结构分解：按业务线 / 区域 / 客户群 / 产品类别
- **不要堆数据**——提炼**关键变化点**（什么涨了、什么跌了、什么反常）

### 第二步：归因分析（为什么）—— 核心能力，篇幅最大
列出所有可能的驱动因素，**每个因素标注证据强度**：

- **业务驱动**：销量 / 价格 / 成本 / 结构调整 / 一次性事件
- **行业驱动**：周期位置 / 供需变化 / 技术变革 / 竞争格局
- **宏观驱动**：GDP / 利率 / 汇率 / 政策 / 国际环境
- **领域特有驱动**：见下方"数据领域"片段（如有）

**证据强度标注**（强制）：
- **[已验证]**：查询结果或公开数据直接支持
- **[推断]**：行业逻辑或类比推导，未直接验证
- **[推测]**：合理假设但缺证据，必须明确假设条件

### 第三步：预测分析（会怎样）
- **短期（下一报告期）**：基于动量、基数、已知事件
- **中期（1-3 年）**：基于核心驱动因素的持续性判断
- **情景分析**：base / bull / bear 三种情景的关键假设与概率权重
- **不强行给精确目标值**——预测的核心是**展示驱动逻辑与假设敏感度**

### 第四步：不确定性与风险
- 数据口径限制（未经审计、口径变更、样本偏倚）
- 归因置信度（哪些驱动是高把握，哪些是低把握）
- 预测的关键假设（哪些假设变化会颠覆结论）
- **反面证据**（不支持当前归因的数据，必须列出，不选择性忽略）

## 何时不做估值（强制约束）

**只有当"数据领域片段"显式启用估值方法时**，才使用 DCF / 可比公司等。
默认情况下（无领域片段，或片段未启用估值）**严禁套估值模型**——
归因分析 + 预测分析才是核心。

## 数据与时间口径（不可违反）

- 每个数字必须能链回数据源：查询结果 / 财报原文 / Wind / Bloomberg / 国家统计局 / 行业协会
- **严禁编造数据**：找不到就写"未公开披露"或"估算（注明假设）"
- 时间口径必须明确：年报 / 季报 / 业绩预告 / 业绩快报 / 月度 / 季度 不能混用
- 同比 / 环比要说明基数

## 报告结构（强制，适配任何数据域）

```
1. 数据要点（核心数字 + 关键变化点，一页内）
2. 归因分析（驱动因素 + 证据强度标注）         ← 篇幅最大，至少占全文 40%
3. 预测与情景（短期 / 中期 + base / bull / bear）
4. 不确定性与风险（含反面证据）
5. 结论（基于证据强度的整体判断）
```

## 禁止行为

- ❌ 编造数据或引用未公开披露数字
- ❌ **强行套估值模型**（数据领域片段未显式启用时）
- ❌ 归因不标证据强度
- ❌ 预测不给假设条件
- ❌ **只描述不归因**（"营收增长 20%"远远不够，必须回答"为什么增长 20%"）
- ❌ 隐藏不确定性或反面证据
- ❌ 对推测性结论不标注置信度
```

```markdown
你正在开展**学术研究**。核心原则：**证据可核验、结论标置信、矛盾不掩盖、不编造文献**。

## 研究流程（必须完整执行）

### 1. 中英双语来源检索（强制）
- 每个关键论点必须检索中文（CNKI / 万方 / 知网）和英文（Google Scholar / SciVerse / ArXiv）来源
- **不得只依赖单一语种**
- 每个研究维度至少 3 条独立来源

### 2. 来源真实性核验
- **严禁编造引用**：作者、年份、期刊 / 会议名称必须可核验
- 优先引用经同行评审的论文；预印本（arXiv / SSRN）必须明确标注"未经过同行评审"
- DOI / URL 必须真实存在，不要生成看似合理的假链接
- 找不到真实来源就写"未检索到相关公开发表"，不要补编

### 3. 证据等级与置信度（每条结论必标）
- **[高]**：多个独立同行评审研究支持，效应量稳定，样本足够
- **[中]**：单一研究或少数相关性研究支持，需更多验证
- **[低]**：理论推测、个案、或作者个人观点

### 4. 矛盾保留（不得强行统一）
- 不同研究结论矛盾时，**分别列出**各方证据、样本、方法论差异
- 让读者看到争议本身，不要为了叙述流畅而掩盖分歧

### 5. 红队自批判（内部审查，不写入正文）
撰写前对每个核心论点做反向质疑：
- 样本是否偏倚？（selection bias / survivorship bias）
- 方法论是否有 confounder？
- 结论是否外推过度？（external validity）
- 是否有反面证据被选择性忽略？

内部审查发现问题，要么修正结论，要么在"研究限制"中明确说明。

## 报告结构（强制）

```
1. 研究问题（明确边界，不泛化）
2. 文献综述（按主题组织，不按作者罗列）
3. 方法论（本研究综合证据的方法与标准）
4. 实证分析（分论点 + 证据 + 置信度）
5. 矛盾与争议（保留不同观点，不强行统一）
6. 研究限制（样本 / 时间窗口 / 外推性）
7. 结论（标注整体置信度）
8. 参考文献（[作者, 年份] 文内引用 + 文末清单，含 DOI/URL）
```

## 禁止行为

- ❌ 编造作者、年份、期刊名、DOI

- ❌ 把相关性研究说成因果性结论
- ❌ 删除不利证据或选择性引用
- ❌ 对推测性结论不标注置信度
- ❌ 用"多数研究认为"代替具体引用
```

**research_directive.py 实现**（支持核心模板 + 可插拔领域片段）：

```python
# server/rest/research_directive.py
import pathlib
from functools import lru_cache

PROMPT_DIR = pathlib.Path(__file__).parent / "research_prompts"
DOMAIN_DIR = PROMPT_DIR / "domains"

@lru_cache(maxsize=8)
def _load_template(type_name: str) -> str:
    """加载核心 prompt 模板，失败 fallback default.md"""
    path = PROMPT_DIR / f"{type_name}.md"
    if not path.exists():
        path = PROMPT_DIR / "default.md"
    return path.read_text(encoding="utf-8").strip()

@lru_cache(maxsize=16)
def _load_domain_template(domain_name: str) -> str | None:
    """加载领域片段；不存在返回 None（不拼）"""
    if domain_name in ("", "unknown", None):
        return None
    path = DOMAIN_DIR / f"{domain_name}.md"
    if not path.exists():
        return None
    return path.read_text(encoding="utf-8").strip()

class ResearchDirective:
    """根据 (research_type, data_domain) 产出研究指导 prompt

    拼接逻辑：
    1. 加载核心模板（按 research_type）
    2. 如果 financial_analyst 且 data_domain 有对应片段，拼接领域片段
    3. 包裹在 <research_directive> 标签内
    """

    def build_directive(self, research_type: str, data_domain: str = "unknown") -> str:
        core = _load_template(research_type)

        # 领域片段拼接（仅 financial_analyst 默认拼，academic 可选）
        domain_section = ""
        if research_type == "financial_analyst":
            domain_tpl = _load_domain_template(data_domain)
            if domain_tpl:
                domain_section = f"\n\n## 数据领域：{data_domain}\n{domain_tpl}"

        return f"<research_directive>\n{core}{domain_section}\n</research_directive>"

    def compose_task(
        self,
        research_type: str,
        data_domain: str,
        user_task: str,
        context: str,
        length_budget: int,
    ) -> str:
        directive = self.build_directive(research_type, data_domain)
        return (
            f"{directive}\n\n"
            f"## 研究任务\n{user_task}\n\n"
            f"## Context\n{context}\n\n"
            f"## 输出长度\n请在 {length_budget} 字以内完成报告。"
        )
```

**提示词方法论参考**：
- `financial_analyst.md` 基于 [CFA Institute Equity Valuation Concepts](https://www.cfainstitute.org/insights/professional-learning/refresher-readings/2026/equity-valuation-concepts-basic-tools)、[CFRA Equity Research Methodology](https://www.juliusbaer.com/fileadmin/legal/cfra-qualitative-equity-research-methodology.pdf)、中国注册估值师（CVA）实务
- `academic.md` 参考 [jefeerzhang/tri-research-skill](https://github.com/jefeerzhang/tri-research-skill) 的"状态机门禁 + 双语强制 + 报告验证器 + 红队自批判"方法论

### 7.6 QueryRewriter（按 type 分发，default 补通用约束）

**设计决策**（用户反馈）：只有 `default` 需要 rewriting——因为 `financial_analyst` 和 `academic` 已有专门的 prompt 模板指导 Agent，不需要改 query；而 `default` 无专门模板，需要 prepend 一段通用约束让 Agent 知道"做归因分析"。

**Demo 期不做 LLM 改写**：`default` 分支只是 prepend 一段硬编码的通用约束（不调 LLM），避免增加延迟和失败面。

```python
# server/rest/query_rewriter.py
class QueryRewriter:
    """按 research_type 分发：default 加通用约束；其他 type 原样返回

    设计依据：
    - financial_analyst / academic 有专门 prompt 模板指导，不改 query
    - default 无专门模板，需要 prepend 通用归因约束
    """

    DEFAULT_CONSTRAINT = (
        "\n\n## 通用研究约束\n"
        "请对查询数据做归因分析：\n"
        "1. 数据描述（核心数字 + 横向锚定）\n"
        "2. 归因分析（驱动因素 + 证据强度）\n"
        "3. 预测与情景（短期 / 中期 + base / bull / bear）\n"
        "4. 不确定性与风险（含反面证据）\n"
        "证据强度标注：[已验证] / [推断] / [推测]。"
    )

    async def rewrite(self, task: str, research_type: str) -> str:
        if research_type == "default":
            return task + self.DEFAULT_CONSTRAINT
        # financial_analyst / academic：原样返回，由 ResearchDirective 拼 prompt
        return task
```

**为什么 `default` 不调 LLM 改写**：
- Demo 期分类正确性不可观测，LLM 改写增加延迟（~2s）和失败面
- 硬编码约束已能引导 Agent 走归因路径
- 未来若发现 query 表达问题（口语化、指代不清），可在这一层加 LLM 调用

**演进路径**（未来扩展）：
- `default` 启用 LLM 改写：识别新兴数据域并补充领域关键词
- 加新 type（如 `consumer`）：走 `financial_analyst` 同模式（有专门模板不改写）
- 改写可观测性：`rewritten_task` 字段写入 ReportStore JSON，便于事后审计

### 7.7 长度控制（三层级联）

```python
# server/rest/length_control.py
import re

SENTENCE_BOUNDARY = re.compile(r'(?<=[。！？\n])')

def enforce_length_budget(report: str, budget: int = 900) -> str:
    """句子边界感知截断

    设计原则：
    - Prompt 软引导（task description 内已要求 length_budget 字数）
    - 产出后硬兜底（此处）：按句子边界截断，不破坏内容
    - 允许 20% 浮动，避免勉强
    """
    if len(report) <= int(budget * 1.2):
        return report

    parts = SENTENCE_BOUNDARY.split(report)
    result, total = [], 0
    for p in parts:
        if total + len(p) > budget:
            break
        result.append(p)
        total += len(p)

    summary = "".join(result).rstrip()
    if len(summary) < len(report):
        summary += "\n\n…（已省略部分细节，完整报告见 report_full）"
    return summary
```

### 7.8 pipeline_adapter.py · 异步执行包装（含路由后处理 + 硬超时）

```python
# server/rest/pipeline_adapter.py
import asyncio
import logging
import pathlib
from datetime import datetime, timezone
from .job_store import JobStore
from .report_store import FileSystemReportStore
from .length_control import enforce_length_budget
from .research_directive import ResearchDirective

from ..bridge.config_loader import compose_config, create_pipeline_components
from src.core.pipeline import execute_task_pipeline

logger = logging.getLogger("server.rest.pipeline_adapter")
report_store = FileSystemReportStore()
directive = ResearchDirective()
rewriter = QueryRewriter()

# Python 硬超时（评审 #6 修复）：必须早于 Java 15min 兜底
PIPELINE_HARD_TIMEOUT_S = 14 * 60   # 14 分钟

async def run_pipeline_async(
    job_id: str, task: str, context: str,
    research_type: str, data_domain: str, config_name: str, trace_id: str,
    tenant_id: str, length_budget: int,
    job_store: JobStore, llm_client,
):
    from .logging_config import set_trace_id
    set_trace_id(trace_id)

    # 幂等保护：若 Job 已终态（如启动恢复标过 FAILED），直接返回
    current = job_store.get(job_id)
    if current and current.status in {"COMPLETED", "FAILED"}:
        logger.warning(f"job {job_id} already terminal, skip",
                       extra={"trace_id": trace_id})
        return

    job_store.update(job_id,
        status="RUNNING",
        started_at=datetime.now(timezone.utc).isoformat(),
    )

    try:
        # 1. QueryRewriter：default 加通用约束，其他 type 原样
        rewritten_task = await rewriter.rewrite(task, research_type)

        # 2. ResearchDirective：按 type + domain 拼研究指导 prompt（核心 + 领域片段）
        full_task = directive.compose_task(
            research_type=research_type,
            data_domain=data_domain,
            user_task=rewritten_task,
            context=context,
            length_budget=length_budget,
        )

        # 3. 调用现有 execute_task_pipeline（用 asyncio.wait_for 包装硬超时）
        cfg = compose_config(config_name)
        components = create_pipeline_components(cfg)

        final_answer, boxed_answer, log_path = await run_with_timeout(
            execute_task_pipeline(
                cfg=cfg,
                task_name=job_id,
                task_id=job_id,
                task_description=full_task,
                task_file_name=None,
                main_agent_tool_manager=components[0],
                sub_agent_tool_managers=components[1],
                output_formatter=components[2],
                log_path=pathlib.Path("logs") / f"{job_id}.json",
                ground_truth=None,
                metadata={"trace_id": trace_id, "source": "rest_api",
                          "research_type": research_type},
                event_sink=None,
                human_interaction=None,
            ),
            timeout_s=PIPELINE_HARD_TIMEOUT_S,
            job_id=job_id,
        )

        # 4. 长度控制：句子边界截断
        summary = enforce_length_budget(final_answer, budget=length_budget)

        # 5. 完整报告写 JSON 文件
        report_uri = report_store.save(job_id, tenant_id, {
            "job_id": job_id,
            "trace_id": trace_id,
            "task": task,                 # 原始 task，不是 rewritten/full_task
            "research_type": research_type,
            "data_domain": data_domain,   # 数据领域（用于审计 + 未来按领域检索）
            "rewritten_task": rewritten_task if rewritten_task != task else None,
            "report_markdown": final_answer,
            "boxed_answer": boxed_answer,
            "metadata": {
                "config_file_name": config_name,
                "model_used": cfg.get("main_agent", {}).get("model", "unknown"),
            },
            "created_at": datetime.now(timezone.utc).isoformat(),
            "completed_at": datetime.now(timezone.utc).isoformat(),
        })

        # 6. SQLite 只存 summary + URI（终态不可变校验在 job_store.update 内）
        job_store.update(job_id,
            status="COMPLETED",
            report_summary=summary,
            report_uri=report_uri,
            completed_at=datetime.now(timezone.utc).isoformat(),
        )
        logger.info(f"job {job_id} completed type={research_type}",
                    extra={"trace_id": trace_id})

    except PipelineTimeoutError as e:
        job_store.update(job_id,
            status="FAILED",
            error_msg=f"python hard timeout after {PIPELINE_HARD_TIMEOUT_S}s",
            completed_at=datetime.now(timezone.utc).isoformat(),
        )
        logger.warning(f"job {job_id} timeout", extra={"trace_id": trace_id})

    except asyncio.CancelledError:
        # 启动恢复 / 显式 cancel 时进入此分支；不覆盖已终态状态
        current = job_store.get(job_id)
        if not current or current.status not in {"COMPLETED", "FAILED"}:
            job_store.update(job_id,
                status="FAILED",
                error_msg="task cancelled",
                completed_at=datetime.now(timezone.utc).isoformat(),
            )
        raise   # propagate

    except Exception as e:
        job_store.update(job_id,
            status="FAILED",
            error_msg=f"{type(e).__name__}: {str(e)[:500]}",
            completed_at=datetime.now(timezone.utc).isoformat(),
        )
        logger.exception(f"job {job_id} failed", extra={"trace_id": trace_id})
```

**`pipeline_timeout.py` 实现**：

```python
# server/rest/pipeline_timeout.py
import asyncio
from typing import Awaitable, TypeVar

T = TypeVar("T")

class PipelineTimeoutError(Exception):
    """Pipeline 硬超时，Python 侧权威超时信号"""

async def run_with_timeout(
    coro: Awaitable[T], timeout_s: int, job_id: str,
) -> T:
    task = asyncio.ensure_future(coro)
    try:
        return await asyncio.wait_for(task, timeout=timeout_s)
    except asyncio.TimeoutError:
        task.cancel()
        try:
            await task   # let cleanup run
        except (asyncio.CancelledError, Exception):
            pass
        raise PipelineTimeoutError(f"{job_id} exceeded {timeout_s}s")
```

**关键设计点**：

1. **ResearchDirective 调用在 try 外**：若 prompt 模板加载失败，不应进入 RUNNING 状态——但实际通过 `lru_cache + default fallback` 已避免
2. **`rewritten_task` 写入 report JSON**：审计可追溯，区分原 task 和实际执行的 task
3. **`except PipelineTimeoutError` 单独分支**：error_msg 明确"python hard timeout"，与 Java 兜底区分
4. **`except asyncio.CancelledError` 幂等**：不覆盖已终态，符合 §4.3 终态不可变约束

### 7.9 启动恢复 + 终态不可变校验

```python
# server/rest/job_store.py
from datetime import datetime, timezone

TERMINAL_STATUSES = frozenset({"COMPLETED", "FAILED"})

class JobStore:
    def __init__(self, db_path: str):
        self.db_path = db_path
        self._init_schema()

    def update(self, job_id: str, status: str | None = None, **fields):
        """终态不可变校验：COMPLETED/FAILED 一旦写入，任何 status 覆盖都被拒绝

        评审 #6 修复：防止 Java 超时标 FAILED 后 Python 回包 COMPLETED 造成永久分叉。
        业务字段（如 report_summary/error_msg）更新允许，但 status 不可反向迁移。
        """
        if status is not None:
            current = self.get(job_id)
            if current and current.status in TERMINAL_STATUSES and status != current.status:
                logger.warning(
                    f"reject status flip job={job_id} "
                    f"{current.status} -> {status}",
                    extra={"trace_id": current.trace_id},
                )
                return False   # 调用方可记录，但视为成功幂等
        # 执行真实 UPDATE（带 status 守卫的 SQL）
        return self._do_update(job_id, status=status, **fields)

    def recover_stale_jobs(self):
        """启动时调用：把所有 PENDING/RUNNING 标 FAILED"""
        stale = self.list_by_status_in(["PENDING", "RUNNING"])
        for job in stale:
            # 启动恢复绕过终态校验（stale 的不会是终态，但显式标记以防 race）
            self._do_update(job.job_id,
                status="FAILED",
                error_msg="runner restarted (process crashed or restarted)",
                completed_at=datetime.now(timezone.utc).isoformat(),
            )
            logger.warning(
                f"recovered stale job {job.job_id}",
                extra={"trace_id": job.trace_id},
            )
```

### 7.10 Service Token 验证（独立 token，不复用 SuperSonic JWT）

### 8.1 设计原则

**权限完全在 Java，Python 不感知用户**：

## 9. 错误处理 + 可观测性 + 测试

### 9.1 错误处理矩阵（13 种失败场景，对齐评审 #6 / #18 修复）

| # | 失败点 | Python 状态 | Java 响应 | 前端表现 |
|---|--------|------------|-----------|---------|
| 1 | Python 服务进程挂了 | 无响应 | GET 失败，保持 RUNNING；15min 兜底标 FAILED | 继续 loading → 最终静默隐藏 |
| 2 | pipeline 抛异常 | FAILED + error_msg | `mergeStatus` 标 FAILED + 推 SSE | return null（静默） |
| 3 | IntentClassifier 失败 | fallback `default` | 正常 RUNNING | 正常完成 |
| 4 | LLM 调用失败 | pipeline 抛异常 → FAILED | 同 #2 | 静默 |
| 5 | 报告文件写入失败 | pipeline 抛异常 → FAILED | 同 #2 | 静默 |
| 6 | SQLite 写入失败 | HTTP 500 | Java 标 FAILED + error_msg | 静默 |
| 7 | Java→Python 网络抖动 | - | GET 抛非 404，**跳过本次，下次再试**（评审 #18） | 继续 loading（用户无感） |
| 8 | Service token 不匹配 | HTTP 401 | Java 标 FAILED + 严重告警 | 静默（但日志 ERROR） |
| 9 | Job 不存在（Python 重启清库） | HTTP 404 | `HttpClientErrorException.NotFound` → 立即 FAILED（评审 #18） | 静默 |
| 10 | Python 重启过程中 | 启动时扫 RUNNING 标 FAILED | Java 拉到 FAILED，推 SSE | 静默 |
| 11 | **Python 硬超时（14min）**（评审 #6） | `asyncio.wait_for` 触发，标 FAILED error_msg="python hard timeout" | 拉到 FAILED，推 SSE | 静默 |
| 12 | **Java 兜底超时（15min）**（评审 #6） | Python 已 COMPLETED 但 Java 未拉到 | `flipToFailed` 标 FAILED；后续 Python 回包**被拒绝**（终态不可变） | 静默 |
| 13 | **越权访问 jobId**（评审 #4） | 正常返回 | `ResearchOwnershipChecker` 抛 `ResearchNotFoundException`（不泄露存在性） | 前端显示"未找到" |

**核心原则**（对齐 B5）：
- 所有失败路径 → 前端 `return null`（保留 textSummary）
- 失败原因**永远**写日志（带 traceId）
- 不弹 toast、不重试请求、不覆盖 textSummary
- **终态不可变**（评审 #6）：一旦 COMPLETED/FAILED，任何反向状态迁移都被拒绝（Python `JobStore.update` + Java `mergeStatus` + SQL `WHERE python_status NOT IN (...)` 三层守卫）

### 9.2 traceId 完整链路

```
[Java 入口] TraceIdUtil.getTraceId()（从 MDC，或 LogInterceptor 生成）
    │
    ▼  HTTP header: X-Trace-Id: supersonic_<UUID>
[Python FastAPI middleware]
    │
    ▼  set_trace_id(...) → contextvar
[Python pipeline 执行]
    │
    ├── logging filter 带 trace_id
    ├── TaskTracer JSON 写 trace_id 字段
    └── ReportStore JSON 含 trace_id
    │
    ▼  HTTP response header: X-Trace-Id: <原值回传>
[Java 接收] 校验 traceId 一致性
    │
    ▼  写入 s2_chat_research_job.trace_id
[Java 日志] logback pattern `%X{traceId}` 自动带
```

## 10. 三个演进锚点

整个设计的核心原则：**协议先就绪、实现可渐进**。三个关键演进锚点：

### 10.1 路由 + 数据域

- **协议就绪**：POST body 不传 research_type / data_domain，Python 全权决策
- **当前实现**：
  - IntentClassifier 单次 LLM 调用输出 JSON `{research_type, data_domain}`
  - 三类 research_type（financial_analyst/academic/default）都 fallback 到 `agent_llm_gpt5`
  - data_domain 触发可插拔领域片段拼接（`domains/{domain}.md`）
  - **IntentClassifier 启动时扫描 `domains/*.md` frontmatter，动态构建取值清单**
- **演进触发**：
  - 加新研究风格（如 medical）→ 加 `medical.md` 核心模板 + IntentClassifier 加 `VALID_TYPES`
  - **加新数据域（如 consumer）→ 只在 `domains/` 加一个带 frontmatter 的 `.md` 文件**
- **演进成本**：
  - 新数据域：**新增 1 个 .md 文件，零代码改动**（IntentClassifier 自动扫描感知）
  - **不动核心 financial_analyst.md**
  - **不动 IntentClassifier 代码**
  - 不动协议、Java、前端
- **未来扩展**：
  - data_domain 支持多领域（如 `["green_economy", "industry_analysis"]`），ResearchDirective 拼接多个片段。Demo 期只输出主要领域
  - domains/ 目录加 watchdog，实现热加载（改文件不重启即生效）

### 10.2 报告存储

- **协议就绪**：`report_uri` 字段通用（`fs://` / `mongo://` / `pg://`）
- **当前实现**：`FileSystemReportStore` 存 JSON 到 `outputs/{tenant}/research_jobs/{job_id}.json`
- **演进触发**：生产化部署时
- **演进成本**：换实现类（`MongoReportStore` / `PgJsonbReportStore`），序列化格式（JSON）不变，URI scheme 换掉

### 10.3 多租户

- **协议就绪**：`tenant_id` 进 schema 和 REST 协议，缺省 `"default"`
- **当前实现**：所有 job 属 `"default"`，不实现隔离逻辑（按 `job_id` 主键查天然隔离）
- **演进触发**：加列表查询接口或真实多租户部署时
- **演进成本**：Java 把 agentId 映射到 tenant_id；Python GET 加 `WHERE tenant_id = ?` 过滤；ReportStore 已按 tenant 分目录

**三者共同的设计原则**：Demo 阶段每项只做最小实现，但字段和抽象接口先留好，未来演进无损。

## 12. 面试讲解话术（整合）

### 12.1 整体架构

> "Java 是网关，Python 是研究中心。Java 负责权限、组装上下文、异步调度；Python 负责意图识别、执行 pipeline、产出报告。两个独立方向设计：Java→Python 用 @Scheduled 主动拉，流量与用户数解耦；Java→前端用 SSE 推送，避免无效轮询。"

### 12.2 三个演进锚点

> "协议先就绪、实现可渐进：
>
> 1. **路由**：Python IntentClassifier 全权分类，加新研究类型不动协议
> 2. **报告存储**：ReportStore Protocol 抽象，当前 FileSystemReportStore，未来换 MongoDB 或 PostgreSQL JSONB 不动协议
> 3. **多租户**：tenant_id 字段进 schema 和协议，当前 Demo 不实现隔离（按 jobId 主键查天然隔离），未来加列表接口时补 WHERE 过滤
>
> 三者共同的设计原则是 Demo 阶段每项只做最小实现，但字段和抽象接口先留好。"

### 12.3 权限边界

> "权限完全在 Java 网关——Python 不感知用户体系。Java 在 POST 之前做三层校验：功能开关（JWT 的 isAdmin 字段 + 白名单）、每日配额、并发数。校验通过才调 Python，并在 Authorization header 带 service token。
>
> **不复用 SuperSonic 的 user JWT**：payload 含密码哈希会泄漏给 Python，密钥耦合，语义错位（user token vs service token）。Python 侧 FastAPI dependency 验证独立 service token，不知道也不需要知道调用方是谁的用户体系。"

### 12.4 失败处理

> "失败的核心契约是'静默保留 textSummary'——10 种失败场景（Python 异常、Python 重启、网络抖动、配额耗尽、权限拒绝、token 错、SSE 断线等）全部走相同路径：前端 return null，不渲染任何东西；失败原因进日志（带 traceId）。
>
> Python 侧 SQLite job store + 启动恢复——进程重启时扫 RUNNING 标 FAILED，Java 下次轮询秒级感知，用户从等待 15 分钟降到秒级。Java 侧 15 分钟超时兜底防 Python 假死。"

### 12.5 可观测性

> "三层可观测性：
>
> 1. **结构化日志**：Java logback + Python logging，统一带 trace_id（HTTP header 透传），事后用单条 grep 命令串起完整调用链
> 2. **TaskTracer JSON**：Python 侧已有，每次 LLM 调用前后写完整 message_history 到文件，调试时直接打开看
> 3. **业务状态表**：Java `s2_chat_research_job` 是事实来源，任何状态机变化都落表
>
> 测试三层：单测（JUnit/pytest/Jest）+ 集成（SpringBootTest + FastAPI TestClient）+ E2E（Puppeteer，可选）。"
