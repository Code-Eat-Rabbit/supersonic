# SuperSonic × miro-flow 深度研究集成设计 — 评审报告

> 评审对象：`docs/resume/interview/深度研究/02-集成设计.md`
> 评审日期：2026-08-05
> 评审维度：架构合理性 / 跨服务契约 / 一致性与并发 / 安全 / 可靠性与可观测性 / 与现有代码落差 / Demo→生产演进
> 交叉验证：SuperSonic（`ChatQueryDO` / `ResultData` / Token 鉴权 / `@EnableAsync`）+ miro-flow（`server/app.py` StaticFiles、`bridge/runner.py`、`execute_task_pipeline`）
> 结论：**有条件通过** — 架构骨架可保留，修完关键项后再进入 writing-plans

---

## 整体评价

这份规格在**分层职责和解耦洞察上是合格的**：Java 网关 / Python 研究中心切分干净，「Java→Python 定频拉取」与「Java→前端事件推送」两个方向解耦是正确的关键洞察；独立 service token、权限信息 vs 审计信息、SQLite 不存大字段只存 `report_uri` 等决策都经得起推敲。范围边界（§2.3 YAGNI）和失败静默契约也清晰。

但规格声称的「现状」与两边代码库存在多处**硬性冲突**——最核心的 `ChatQueryDO` 取数字段、`bridge/config_loader.py`、`Result<T>` 等在实现时会直接编译/导入失败。更严重的是三类**设计级**缺陷：报告落在无鉴权公开静态目录、research 接口缺归属校验（IDOR）、Java 单边超时导致与 Python 永久状态分叉且算力泄漏。在这些问题落地前，不宜直接进入 writing-plans。

---

## 值得学习的地方

1. **§3.2 两个独立方向**：把「Java↔Python 同步频率」与「前端订阅数」彻底分开，避免 100 个前端 = 100 倍 Python 压力——这是本设计最有价值的部分。
2. **§8.5 权限信息 vs 审计信息**：内测期不建权限表、用 `isAdmin + 白名单 + 从审计表聚合配额`，YAGNI 判断准确，演进不改 Python 协议。
3. **§5.8 拒绝复用 SuperSonic user JWT**：经代码验证属实——`UserConstants.TOKEN_USER_PASSWORD` 把密码哈希放进 JWT claims；独立 service token 决策正确。
4. **§5.2 不存 `report_full` 只存 `report_uri`**：避免高频状态查询读 overflow pages，存储层理解到位。
5. **§9.1 十种失败场景矩阵**：覆盖面好于多数设计文档；「静默保留 textSummary」作为统一失败契约清晰。
6. **§2.3 明确不做清单**：边界画得清楚，避免范围蔓延。

## 主要问题

### [必须修复] 1. §6.3.2 核心取数 API 与 `ChatQueryDO` 现状不符

**位置**：§1.1、§6.3.2（约第 714–763 行）

规格写 `query.getQuestion()` / `getTextResult()` / `getTextSummary()` / `getChatQuery(queryId)`。实际 `ChatQueryDO` 字段为：

```java
// chat/server/.../ChatQueryDO.java
private Long questionId;      // 非 queryId
private String queryText;     // 非 question
private String queryResult;   // JSON 序列化的 QueryResult，非 textResult/textSummary
```

`textResult` / `textSummary` 存在于反序列化后的 `QueryResult` DTO 中；查单条方法在 `ChatManageService.getChatQuery(Long)`，不在 `ChatQueryService`。

**影响**：`buildContext()` 与整个 `createResearch()` 流程需重写，并引入新失败模式（`query_result` 反序列化失败 / `textSummary` 尚未写入）。

**建议**：改为：

```java
ChatQueryDO do = chatManageService.getChatQuery(queryId);
QueryResult qr = JsonUtil.toObject(do.getQueryResult(), QueryResult.class);
```

并显式定义 `queryResult == null` / 反序列化失败 / `textSummary` 为空 三种返回；同步修正 §1.1 的产品描述。

---

### [必须修复] 2. §5.6 pipeline 适配层建立在不存在的模块上

**位置**：§5.6（约第 417–458 行）

```python
from ..bridge.config_loader import compose_config, create_pipeline_components  # 文件不存在
```

实际情况：
- `server/bridge/config_loader.py` 全仓库不存在
- `compose_config` 是 `StreamingTaskRunner._compose_config` 私有方法（`server/bridge/runner.py`）
- `create_pipeline_components` 在 `src/core/pipeline.py`
- `execute_task_pipeline` 真实签名含 `event_sink` / `human_interaction` / `ground_truth` 等，规格遗漏

**影响**：Python 侧适配层核心代码是伪代码；实现阶段必须重新设计「如何从 runner 抽取 config 组装」这一非平凡重构。

**建议**：新增明确重构步骤——把 `_compose_config` 提升为 `server/bridge/config_loader.py` 模块级函数（WebSocket 路径同步改用），并在 §5.6 显式写 `human_interaction=None, event_sink=None`。

---

### [必须修复] 3. 报告文件落在无鉴权公开静态目录

**位置**：§5.3 FileSystemReportStore（`base_dir="outputs"`）

现有代码已挂载：

```python
# server/app.py
app.mount("/outputs", StaticFiles(directory=str(outputs_dir)), name="outputs")
```

**影响**：任何能访问 Python 端口的人，只要知道（或枚举）`job_id`，即可 `GET /outputs/default/research_jobs/{job_id}.json` 拿到完整业务报告，绕过 Java 权限、配额与 service token。§8.1「Python 只验证 service token（防内部直连）」在当前代码下不成立。

**建议**：报告存储换到 `data/research_reports/` 等未挂载目录，规格明确「该目录不得被 StaticFiles 挂载」；补充部署约束：Python 端口仅对 Java 网段开放。

---

### [必须修复] 4. research 接口缺归属校验（IDOR）+ SSE 资源耗尽面

**位置**：§6.3.1 Controller

`getStatus(jobId)` / `streamStatus(jobId)` 不取 `User`、不校验 `created_by`；`createResearch` 也不校验查询是否属于当前用户；`register(jobId)` 不检查 job 是否存在，配合 `new SseEmitter(0L)`（永不超时）。

**影响**：
- (a) 已知 jobId 可读他人报告
- (b) 白名单用户可对他人 queryId 发起研究
- (c) 随机 UUID 无限注册 emitter，占满异步请求容量

**建议**：三接口统一加 `created_by == user.getId()`（或 admin 放行）；`register()` 先查 job 存在且属当前用户，否则 404；`SseEmitter` 设有限超时（如 20 分钟，略大于 job 超时）。

---

### [必须修复] 5. 并发校验漏掉 PENDING，双击可绕过

**位置**：§6.3.3（约第 808–811 行）

```java
int runningCount = jobMapper.countByUserAndStatus(user.getId(), "RUNNING");
```

新建 job 初始为 `PENDING`，要等 Scheduler 拉到 Python 的 RUNNING 才变。两次快速点击之间两个 job 都是 PENDING，`max-concurrent-per-user: 1` 失效。同一 queryId 也无去重。

**影响**：配额/并发形同虚设；双击烧两倍 LLM 成本。

**建议**：
1. 并发计数改为 `status IN ('PENDING','RUNNING')`
2. 校验与 insert 同事务（或约束关掉 TOCTOU）
3. queryId 级去重——已有 COMPLETED/进行中 job 时返回既有 jobId

---

### [必须修复] 6. Java 超时标 FAILED 后与 Python 永久状态分叉

**位置**：§4.4 决策 #5、§6.3.5、§2.3（不做取消接口）

Java 15 分钟标 FAILED 后不再轮询该 job；Python pipeline 仍可继续跑并在稍后 COMPLETED。§4.4 写「以 `started_at` 判超时」，§6.3.5 `isTimeout()` 实际用 `getCreatedAt()`——两处也矛盾。

**影响**：表与 SQLite 永久不一致；用户配额已扣且静默失败，但报告实际存在无法访问；孤儿文件堆积；被判超时的 job 继续烧 token 至 max_turns。

**建议**：至少三选一写进规格——
1. **推荐**：Python 侧 `asyncio.wait_for` 硬超时（如 14 分钟，早于 Java 15 分钟），让 Python 成为超时唯一权威
2. 加极简 `DELETE /v1/research/jobs/{job_id}` 做 `task.cancel()`
3. 定义「终态不可变」+ Java 对账查询

并统一超时时钟字段为 `started_at` 或 `created_at`。

---

### [必须修复] 7. EventSource 无法携带 JWT，鉴权开启后 SSE 必挂

**位置**：§7.4 `useResearchJobStream`

SuperSonic token 只从 `Authorization` header 读（`TokenService.getClaims`）；拦截器 `includePath` 默认 `/api`。浏览器原生 `EventSource` **无法设置自定义 header**；代码库无 EventSource + token 先例。

**影响**：`s2.authentication.enable=false`（当前默认）时 Demo 能跑；一旦开启鉴权 SSE 全挂——与「协议先就绪」自相矛盾。

**建议**：现在就定方案并写进 §7.4。可选：
1. query param 传 token（简单，进 access log，拦截器需改）
2. **推荐**：`@AuthenticationIgnore` + 一次性签名 stream token
3. `fetch` + `ReadableStream` 手写 SSE（能带 header，需自实现重连）

---

### [必须修复] 8. `@Async("researchExecutor")` Bean 不存在 + RestTemplate 无超时

**位置**：§6.3.4、§11.2 文件清单

`ThreadPoolExecutorMdcWrapper` 类存在于 `common/`，但从未注册为 Bean；现有执行器为 `eventExecutor` / `chatExecutor` 等裸 `ThreadPoolExecutor`。`@EnableAsync` 仅在 `StandaloneLauncher`，`ChatLauncher` 没有。每次 `new RestTemplate()` 且无 connect/read timeout。

**影响**：启动 `NoSuchBeanDefinitionException`；chat-only 部署下 `@Async` 可能静默降级为同步；Python 假死时 POST 线程挂死。

**建议**：文件清单增加 `researchExecutor` Bean 配置类；RestTemplate 注入单例并设 connect/read timeout（如 3s/5s）。

---

### [必须修复] 9. `enabled-admin-only` 语义与实现相反

**位置**：§6.3.3、§6.6、§8.2

配置名直觉：`false` = 开放所有人。实现却是「`adminOnly=true` 时管理员放行」——设为 `false` 反而关掉管理员，只剩白名单。`@Value("${research.enabled-users:}")` 绑 `Set<String>` 时，空串可能变成 `[""]`。

**影响**：内测转公测改开关会导致含管理员在内全员被拒。

**建议**：改为枚举 `research.access-mode: ADMIN_AND_WHITELIST | WHITELIST_ONLY | ALL`。

---

### [必须修复] 10. `includeFull` 判断恒为 true，与 §4.1 契约矛盾

**位置**：§6.3.5（约第 926–927 行）

```java
boolean includeFull = "COMPLETED".equals(oldStatus) == false;
```

`oldStatus` 来自 `selectByStatusIn(["PENDING","RUNNING"])`，永不可能是 COMPLETED，故 `includeFull` 恒 true。§4.1 声称「COMPLETED 时拉一次」，实际每 2 秒对每个在跑 job 都请求完整报告。

**建议**：先不带 `include_full` 拉状态，变为 COMPLETED 后再单独拉一次 full。

---

### [建议修改] 11. SSE 推送携带 `report_full`，体积过大

**位置**：§6.4 `buildEvent`

完整 markdown 常 20–50KB，每次重连、每个订阅者都推一遍。建议 SSE 只推 `{jobId, status, reportSummary, errorMsg}`，完整报告走按需 GET。

---

### [建议修改] 12. Java 侧 `report_full TEXT` 与 Python「不存大字段」原则自相矛盾

**位置**：§6.2 vs §5.2

MySQL `TEXT` 上限 64KB，报告易静默截断。建议改 `MEDIUMTEXT`，或更进一步：Java 也只存 summary + uri，完整报告由 Java 代理 Python `include_full`。

---

### [建议修改] 13. DDL 路径与方言不符合项目现状

**位置**：§6.2

项目无 Flyway/Liquibase，实际用 `spring.sql.init.schema-locations` 指向 `launchers/standalone/.../db/schema-{h2,mysql,postgres}.sql`。内联 `INDEX idx_x (col)` 语法 PostgreSQL 不支持。

**建议**：写明需维护三份 DDL，去掉误导性的 `V20260804__` Flyway 命名。

---

### [建议修改] 14. SSE 无心跳、终态不 `complete()`，多实例必丢事件

**位置**：§6.4、§6.6

`SseEmitter(0L)` + `request-timeout: -1`，nginx 默认 60s 会断连；终态后若不 `emitter.complete()`，客户端异常退出时 emitter 可永久驻留。多实例下进程内 `ConcurrentHashMap` + 无 ShedLock 的 `@Scheduled` → 事件投递到错误实例、重复扫 job。

**建议**：Demo 明确「单实例部署」约束；加 20s SSE comment 心跳；终态 `complete()`；演进路径补 ShedLock + Redis Pub/Sub。

---

### [建议修改] 15. Python 无全局并发上限；多 worker 下 `recover_stale_jobs` 误杀

**位置**：§5.7

每个 pipeline 会 spawn MCP stdio 子进程；10 用户并发即可膨胀。uvicorn `--workers N` 时每个 worker 启动都会把其他 worker 在跑 job 标 FAILED。

**建议**：写死「Python 单进程单 worker」；加全局 `asyncio.Semaphore`；SQLite 启用 WAL + `busy_timeout`。

---

### [建议修改] 16. `BackgroundTasks` 与 `asyncio.create_task` 前后不一致

**位置**：§3.1 vs §5.8

`BackgroundTasks` 异常被吞、优雅关闭会等长任务；`asyncio.create_task` 需强引用防 GC。建议统一为 `create_task` + task 集合 + `done_callback`。

---

### [建议修改] 17. IntentClassifier 依赖不存在的 LLM 接口，且 Demo 零业务价值

**位置**：§5.4

`llm_client.complete(prompt)` 在 miro-flow 中不存在；实际为 `create_message(...)`。三类 `TYPE_TO_CONFIG` 全指向 `agent_llm_gpt5`——额外 LLM 调用只增延迟/成本，分类正确性不可观测。

**建议**：补薄 wrapper；或 Demo 直接 stub 返回 `default`，接口保留；或让三个 config 至少有可观测差异（不同 system prompt）。

---

### [建议修改] 18. §9.1 错误矩阵与实现代码矛盾

**位置**：§9.1 #8/#9 vs §6.3.4/#6.3.5

矩阵声称 Service token 错 / Job 不存在时「Java 标 FAILED + 告警」，但 `createJobAsync` 吞掉 POST 失败，Scheduler catch-all 不区分 404 与网络抖动。

**建议**：对齐实现——POST 失败立即标 FAILED；Scheduler 对 404 立即 FAILED，对网络抖动重试。

---

### [仅供参考] 19. `Result<T>` 不存在，且不必手动包装

实际为 `ResultData<T>`；`ResponseAdvice` 已自动包装 `@RestController` 返回值。§6.3.1 应直接返回 DTO。`ResearchExceptionHandler` 返回裸 `ErrorBody` 会绕过全局信封，前端 `res.code === 200` 判断失效——建议用 `ResultData.fail(...)`。

## 需作者澄清

### [问题] Q1. 页面刷新后已完成报告能否恢复？

§6.5 `findRunningByQueryId` 只返回进行中 job；COMPLETED 后 `runningJobId` 为 null，刷新回到 IDLE，「已产出报告消失」。这与开篇「回挂到当前 queryId」冲突。Demo 接受缺失，还是改为 `findLatestByQueryId`？

### [问题] Q2. `config_file_name` / `retrieval_mode` 是预留忽略还是应生效？

POST 契约有字段，`routes.py` 不消费。若 Java 传入 `agent_server`（human clarify 全开），headless 会阻塞约 900 秒。需标注 `ignored` 或显式拒绝非白名单 config。

### [问题] Q3. Prompt 注入立场？

`full_task` 把用户问题与查询结果拼进具备联网/代码执行能力的 Agent。是否记录为已知风险？

### [问题] Q4. 数据保留 / TTL？

`outputs/`、`logs/{job_id}.json`、两边 job 表均无清理策略——有意省略还是遗漏？

### [问题] Q5. 15 分钟超时依据？

UI 写「预计 3–10 分钟」。若 P90≈12 分钟，15 分钟会造成大量假失败。是否有实测耗时分布？
