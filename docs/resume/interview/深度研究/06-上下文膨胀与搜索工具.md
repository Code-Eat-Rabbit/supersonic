## §0 使用说明与口径红线

**考前 30 秒红线**（其余诚实边界细则已并入各节）：

1. 博客数字开口前带"业界案例"或"博客实测"；本地数字带"我跑了 15 条轨迹实测的，字符数除以 4 估的 token"。
2. "我们做了"清单：**Tavily 主搜索 + 自建三段式（Serper+Jina+MarkItDown）降级**、超时指数退避、硬错（参数错/无权限）拒绝重试、**空结果不重试返回 hint**（"当前搜索无结果，请换个角度或将问题拆分成子问题后再搜索"）、**事前预防（域名黑名单 + 404/登录墙/付费页排除）**、**正文去模板（剥侧边栏/导航/评论）**、**三重指纹内容去重（标题>0.8 ∧ MinHash>0.7 ∧ SimHash≤3，毫秒级零 embedding）**、**规则制资料打分（来源权威度/子问题相关度/时效性——用于去重组内保留与候选排序）**、**prompt 层核验指令（结论性事实双独立来源交叉验证 + 矛盾信息保留并核实）**、Main-Sub 隔离、两道预算闸、**滑动窗口清理工具结果（保留首条 + 最近 N 条，占位替换——零 LLM 规则裁剪，别冒"压缩"的名）**、爆仓蒸馏（兜底，0 次触发）、三级抓取降级链、900s 硬超时、工具名自动纠错、反作弊屏蔽、URL 规范化、hybrid 融合去重、prompt cache、TaskTracer 全量落盘。
3. 其余一切（**重复 query 过滤、降级链正文切块/分档截断与状态透出（口子二）、机制层信息源核验（可信度分层/独立性粗筛——prompt 层核验已上线）、query 去重阈值标定、停止信号、结果缓存**）——只能讲"我判断的演进方向"，并备好"为什么现在没做"的答案：上线前三类失败处理与批级 QC 已覆盖日常绝大多数场景，两个口子和核验是上线后/复盘后才看清的。**ReSum、IterResearch 演进报告不在这份演进清单里**——上下文方案是设计时定的，排除理由见 §1.1；被问到不要答成"还没来得及做"。

## §1 重难点一：上下文膨胀——设计时就得定的架构选型

### 1.1 故事线（完整版 ≈ 2 分钟，五幕）

**第一幕：这道题在架构设计时定。**

"上下文膨胀是架构选型，设计时就要定下来：上下文按什么形态活着，后面的轮次、工具结果、子任务回传都得顺着这个形态走。候选我看过三条。一条是 ReSum，水位到了就让模型把历史压成摘要。一条是 IterResearch，用一份演进报告替换线性历史，每步重写。我们选的是第三条：**Main-Sub 主子会话隔离，加上滑动窗口替换工具结果。**两道闸卡死上限，Main 20 轮、Sub 50 轮，一条任务最多 20×50 轮。"

**第二幕：选中的方案保什么、丢什么。**

"隔离做的是换工作空间。子代理开独立会话，网页原文、长抓取都堆在子会话里；回给主代理的是加工后的摘要，不是原始信息堆。主会话因此不承接网页原文。

滑动窗口做的是在各自会话里替换工具原文。保留第一条 user/tool 和最近 N 条，更早的工具结果改成占位，assistant 的思考轨迹不动。零额外 LLM 调用。它丢的是工具返回的原文，不是结论——结论在模型的思考里，子代理侧还在回传的摘要里，原文在 TaskTracer 里能回放。

这两层叠在一起，按现在的轮次总量不用再做语义压缩。主代理最多 20 轮，看到的已经是摘要；子代理 50 轮里真正占体积的是工具原文，按条替换就够。爆仓蒸馏只是换小窗口时的兜底，不是这条选型的主路径。"

**第三幕：为什么不选 ReSum。**

"ReSum 是设计时排除的，三条理由。

第一，**信息损耗大于只替换工具结果。**滑动窗口只改工具消息的 content，assistant 的思考和 tool_calls 全留。ReSum 是让模型把一段历史合成「已确认事实」，思考链和证据出处一起被改写；触发多次就是摘要的摘要，失真会累积。

第二，**当前轮次总量用不着压缩。**Main 20、Sub 50，再乘上隔离——子会话的大块原文进不了主会话。模型是 1M 窗口，这个上限不是为了先付一次有损压缩才撑得住。

第三，**子代理回给主代理的已经是摘要。**主会话里再跑一轮 ReSum，是在摘要上再压一次。损耗加在已经提炼过的内容上，不是加在网页原文上。"

**第四幕：为什么不选 IterResearch。**

"演进报告也是设计时排除的，同样三条。

第一，**太重，实现是换一套状态机。**它不是在 provider 层加一条规则，而是每步 extract_findings、维护 Facts/Gaps、下一步只喂报告快照。报告结构要单独设计，更新质量还依赖模型会「改报告」——这不是一条可单测的规则。这个重量，我判断更适合**单 Main、20 轮以上、原始观察还堆在同一条历史里**的方案。我们的 Main 被闸在 20 轮，长轨迹在 Sub，Main 本身不堆原文。

第二，**反复改、反复读，既占上下文，又拉长时间。**每步多一次报告更新，下一步还得把整份报告重新读进去——上下文里多一块常驻报告，墙钟时间也每步加一次调用。博客自己的口径是 15 步以上准确率能抬，但那是用常驻的额外调用换来的。我们没有把这个开销放进主路径。

第三，**它要替换的工作空间，和我们已经拆开的不是同一件事。**IterResearch 成立的前提，是单代理把每步原始观察堆进同一条历史，所以才用一份有上限的报告把这条历史换掉；下一步的输入是「当前报告 + 这一步的原始工具结果」。我们的原始观察在子会话，主会话只收摘要；子会话里该丢的是工具原文，占位替换的损耗边界是确定的，思考还在，trace 能回放。演进报告是模型每步重写中央记忆，漏抽或者结构过度会静默丢细节，上一版也不再作为工作记忆存在。这不是更高级的滑动窗口。"

**第五幕：收束。**

"所以这道选型题的答案是：主子隔离负责让原文别进主会话，滑动窗口负责在会话内部只替换工具原文，容量按 20×50 配。ReSum 损的是思考和证据链，而且还要在主会话里把子摘要再压一次；演进报告换的是整套工作空间，重量和时延都落在「单 Main 长跑」那种形态上。当前的回传形态和轮次总量，用不上这两条。"

**30 秒版（被问"简短说说"时用）：**

"上下文方案是设计时定的。我们选 Main-Sub 隔离加滑动窗口：子会话独立，只回传摘要；各自会话里保留首条和最近 N 条工具结果，更早的原文换成占位，思考不动。两道闸是 Main 20 轮、Sub 50 轮，最多 20×50。没选 ReSum：语义摘要的损耗大于只替换工具原文，这个轮次总量用不着压缩，而且子代理回传的已经是摘要，主会话不用再压一次。没选 IterResearch：它适合 20 轮以上、单 Main 还在堆原始观察的方案，实现是换状态机；每步重写报告再整份重读，既占上下文又加时延；我们的原文已经隔在子会话里，不必再用一份模型改写的报告替换工作空间。"

### 1.3 追问详解（H25–H30）

#### H25. "那为什么不直接换个更大的窗口模型？"

- **第一句**：换大窗口只多给容量，不改变上下文的形态。我们是 1M 窗口，本地 15 条轨迹 ContextLimitError 是 0，选型已经按「装得下」来做了——隔离加滑动窗口，不是再换一个更大的窗口。
- **要点**：NoLiMa 显示 32k 起注意力显著折扣，窗口标称值 ≠ 有效注意力（Lost in the Middle 的 U 形曲线：中部信息利用率最低）；Agent 每步重读全史，窗口越大每步越贵，Anthropic 口径 4×/15×；我们输入缓存命中 82%，换模型等于打破缓存重新烧钱。注意力衰减用结果侧减量处理（大网页别整篇进来），不用 ReSum 去重写历史。
- **易踩坑**：不能说"窗口够大所以不用管上下文"；也不能吹"我们做了注意力优化"——没做。管上下文的手段是隔离和替换工具原文，见 §1.1。
- **回看标本**：01 册 §2.3；本册 §1.1。

#### H26. "你们为什么没做阈值触发的主动压缩？"

- **第一句**：不是没来得及，是设计时就没选 ReSum。滑动窗口只替换工具原文；ReSum 让模型重写一段历史，损耗更大。Main 20 × Sub 50 这个轮次总量，再加上子回传已经是摘要，主会话里没有再压缩一次的位置。
- **要点**：三条和 §1.1 第三幕同一套——① 损耗边界：窗口只改 tool 的 content，assistant 的思考和 `tool_calls` 全留；ReSum 把历史合成「已确认事实」，思考链和证据出处一起被改写，多次触发就是摘要的摘要。② 轮次总量：两道闸把一条任务卡在 20×50，1M 窗口下这不是装不下，用不着先付一次有损压缩。③ 主会话的输入已经是子摘要，再跑 ReSum 损的是提炼结果，不是网页原文。爆仓蒸馏是换到小窗口（比如 128k 的 deepseek 配置）时的兜底，本地 0/15 触发，不是主路径。标本里 `max_context_length` 读了没用、`_estimate_tokens` 零调用，只说明水位监测没接线，不能说成「差一步就要上 ReSum」。
- **易踩坑**：不要答成短板认错、再许诺下一档上 ReSum；不能把滑动窗口说成"我们做了语义压缩"；被追问"窗口具体怎么裁、为什么不直接删消息"——转到 H30，两个能打的点是占位替换保配对、发送侧副本不落盘。
- **回看标本**：`provider_client_base.py:54/115/254`（水位配置读而未用 / 占位替换 / 尾部截断兜底）、`orchestrator.py:192/294`（调用前全量落盘 / 蒸馏）；本册 §1.1 第三幕、H30。

#### H27. "子代理隔离有什么代价？"

- **第一句**：隔离不白给——业界的说法叫四项并行税：重复认路、依赖链串行、共享状态冲突、汇总验收；最阴的是汇总税，子代理要是回传详细结果，隔离省下的上下文在汇总时连本带利还回去。
- **要点**：主代理只拿摘要，细节得在派单时写全（目标/范围/输入/约束/期望输出）——正确解法是任务描述写全，不是把全 history 塞过去；每个子代理从零重建认知，短任务反而更贵（简单查证 1 个 agent + 3–10 次调用就够）；我们的取向：一次只跑一个子代理、顺序执行——牺牲并行收益换掉冲突面和汇总税，这是当前规模的理性选择不是能力缺陷；隔离的真实收益是上下文管理不是速度（Anthropic 那个 90.2% 是质量分不是提速）。
- **易踩坑**：不能说"我们并行跑子代理所以快"；也别把顺序执行说成丢人事。
- **回看标本**：03 册 §6/§9；番外02。

#### H28. "演进报告怎么防止自己变成新的线性历史？"（问的是没选的那套方案本身，不是我们的落点）

- **第一句**：先收一句：这套我们没选，理由在 §1.1。若问机制，三道保险——报告本身设 token 上限、同话题事实强制合并、矛盾信息两条都保留进缺口清单；让报告"越写越好"而不是"越写越长"。
- **要点**：上限 2000–3000 token，逼近就触发 LLM 压缩；Confirmed Facts 只留最近 20 条、Open Questions ≤10——上限是设计约束不是巧合；同话题 >5 条触发语义合并（两条营收合成一条带同比的），按语义合并不按条数硬砍；矛盾双保留 + 标"需核实"，不让一个版本悄悄消失——报告可以暂时错，不能静默改写历史；更本质的防退化：报告更新是主动选择留存，和摘要的有损压缩是两码事。
- **易踩坑**：只答"设上限"不给另外两道保险；漏说"报告更新动作由模型做，提示词要专门约束"。
- **回看标本**：本册 §1.2-L3；博客05/07；arXiv 2509.13309。

#### H29. "怎么判断该停？max_steps 不够吗？"

- **第一句**：max_steps 是预算不是停止条件——它回答"最多花多少"，不回答"是否做完了"；真正的停止条件是三个可计算信号，而且要放在循环外的守卫代码里，不能指望模型自觉。
- **要点**：三信号（增益连续 3 步 <8%、双独立来源覆盖八成、硬顶 40 步+成本上限）落地后平均 31→19 步，砍的全是空转；到顶要"收敛"不要"截断"——收敛模式锁死 query 范围、只许补单源的第二来源、两轮补不上就标"未验证"，交付边界清楚的半成品；另有三指纹（动作/观察/状态差）抓"话都对但一步没往前走"，注意幂等重试是合法重复不能误杀；我们现在的停止就是两道轮次闸（Main 20 / Sub 50）加上触顶后的 final summary，增益衰减是另一条演进，不拿它反过来改上下文选型。
- **易踩坑**：不能说"我们实现了增益检测"；8%/40 步是业界值，落地要按任务族重标。
- **回看标本**：05 册 §3.3；番外01/03。

#### H30. "上下文管理为什么选'隔离 + 滑动窗口'，而不是博客推荐的 ReSum 或 IterResearch？"（选型题）

- **第一句**：选的是 Main-Sub 隔离加滑动窗口，容量 Main 20 × Sub 50。ReSum 和 IterResearch 是设计时排除的，不是还没排上的下一档。
- **要点**（和 §1.1 同一套，追问时按这个顺序说）：
  - **不选 ReSum，三条。** ① 信息损耗更大：窗口只替换工具结果的原文，思考和 `tool_calls` 还在；ReSum 把一段历史合成摘要，思考链和证据出处一起被改写，多次触发是摘要的摘要。② 当前轮次总量用不着压缩：20×50，再加隔离，子会话的大块原文进不了主会话。③ 子代理回传的已经是摘要，主会话里再压一次，损的是提炼结果。
  - **不选 IterResearch，三条。** ① 太重：每步 extract_findings、维护报告结构、下一步只喂快照，是换编排层的状态机，更新质量还依赖模型会改报告；这个重量更适合单 Main、20 轮以上、原始观察还堆在同一条历史里的方案。我们的 Main 卡在 20 轮，长轨迹在 Sub，Main 不堆原文。② 反复改、反复读：每步多一次报告更新，下一步把整份报告重新读回去，既多占一块常驻上下文，又每步加一次调用的时延。③ 它要替换的工作空间和我们已经拆开的不是同一件事：演进报告的前提是单代理把原始观察堆进同一条历史；我们的原文在子会话，主会话只收摘要，子会话里用占位替换就能定界，trace 还能回放。报告是模型重写中央记忆，漏抽会静默丢，上一版也不再留在工作记忆里。
  - **选中方案的损耗边界（被追问"那你们丢了什么"时用）。** 丢的是窗口外的工具原文，不是结论。结论在思考里、在子摘要里；原文在 TaskTracer。占位文案留着"这里有过结果"。
- **机制细节**（被追问"窗口具体怎么裁"时展开。每次 LLM 调用前在 provider 层执行，不动编排。入口是 `create_message`，`:177`）：
  - **两层，主力在第二层。** ① `_filter_message_history`（`:254`，注释自评 "For now, simply..."）是简化兜底：`-1` 原样返回；`N>0` 且历史条数超过 N 时，**所有角色**整表取尾部 N 条。② `_remove_tool_result_from_messages`（`:115–175`）才是主机制：占位替换。同一个 N 在两层语义不同——兜底按总条数砍，占位层只数 user/tool。
  - **生效开关。** `keep_tool_result >= 0` 才处理，`-1` 直接跳过。标本所有 yaml 都是 `-1`，这条路径历史上从未生效；产品口径启用为 N。
  - **窗口只圈 user 和 tool。** 这两类是大块头（tool 就是工具返回，实测中位 2.2k 字符、最大 10 万）；assistant 永远不动——思考轨迹和 `tool_calls` 全留。这是"保 think 弃 observation"的规则版。
  - **保留集合 = 首条 + 尾部 N 条。** 列表里第一条 user/tool 永远留（任务定义不能丢）；`num_to_keep = min(N, 条数-1)`，减 1 是防首条被尾部重复计入；N=0 只留首条。N=3 时形如：`[u0 任务✓] [a] [t→占位] [a] [t→占位] [a] [t✓] [a] [t✓] [a] [t✓]`——assistant 全留，窗口外的 tool 原文换成占位。
  - **占位替换，保配对。** 窗口外的 user/tool 只改 `content`，换成固定文案 `"Tool result is omitted to save tokens."`（约 40 字符，字符÷4 不到 10 token）。条数、顺序、角色全不变。删消息不行：OpenAI 格式要求 tool 消息紧跟带对应 `tool_calls` 的 assistant，`call_id` 必须配对，删掉就报错。副产品是模型看见占位符，知道"这里有过结果、已省略"，assistant 的动作叙述还在（"我搜过 X"）——留"做过什么"，丢原文。
  - **发送侧副本，存储侧全量。** 函数第一行 `messages_copy = [m.copy() for m in messages]`，替换只作用在本次 API 请求的副本上；编排器在调用前就把原件写入 TaskTracer（`orchestrator.py:192–203`）。裁掉的原文永远能从 trace 回放——上面"裁原文不裁结论"落在这里。
  - **缓存友好。** 每条消息只翻转一次"原文→占位"，翻转后永久稳定。对 prompt 前缀缓存的破坏是一次性、可预测的；摘要式压缩每步都可能重写中段。
  - **按条数，不按 token 水位。** 一条 10 万字符的新结果只要落在最近 N 条里，照样全量进窗口。这一档用结果侧截断处理（单条正文的形态，见 §2 口子二），不改成 ReSum 的语义压缩。另外，兜底层按总条数砍尾，会先把真正的首条任务定义整条切掉，"保首条"只对占位层收到的那份列表成立。产品启用时以占位层为准，兜底层保持注释里的临时语义。
- **易踩坑**：不要把「没上 ReSum / IterResearch」说成进度问题，也不要说成它们不好——排除理由是损耗边界、轮次总量、工作空间是不是已经被隔离拆开；别把滑动窗口说成"压缩"——零 LLM 参与的规则裁剪；被追问"为什么不直接删旧消息"——答"删了 `call_id` 对不上，API 报错；占位替换保条数、保顺序、保配对"；被追问"裁掉的原文要回看怎么办"——答"trace 里有全量，TaskTracer 在调用前落的是原件，替换只发生在发送副本上"。
- **回看标本**：`provider_client_base.py:115–175`（占位替换）、`:254`（尾部截断兜底）、`gpt_openai_client.py:89`（provider 侧调用点）；`orchestrator.py:192–203`（调用前全量落盘）；本册 §1.1、§1.2-L2。

## §2 重难点二：搜索工具——"上线后遇到过什么问题"：交家底，再交两个口子

### 2.1 故事线（完整版 ≈ 2 分钟，四幕）

**第一幕：先交家底——"上线后遇到过什么问题"这道题的答法。**

"这道题面试官几乎必问，我先交家底：上线前工具层的失败处理我们做了三类——网络抖动、超时这类可自愈的失败走指数退避；参数错误、无权限这类硬错误直接拒绝不重试，重试也没意义；空结果不硬塞给模型，返回带 hint 的提示，比如'当前搜索无结果，请换个角度或将问题拆分成子问题后再搜索'。当时觉得这套已经挺稳了。上线后真正打脸的，是两个我们没料到的口子：一个是空结果之后模型的'假换角度'；另一个我先一句话剧透——主路径 Tavily 降级到自建链时，单条正文的形态没人管——细节放在质量把控那幕一起讲。"

**第二幕：口子一——空结果之后，模型学会了"假换角度"。**

"第一个口子出在我们最得意的那条 hint 上。'请换个角度'——模型确实听了，但它对'换角度'的理解是微调关键词：'苹果财报'搜不到，就试'苹果财务报告'，再试'apple 财报 PDF'——三个 query 意思一模一样，方向一点没变。没有程序化的重复 query 检测，这种循环每一步都是真金白银的预算。业界有个一模一样的案例：日志拉出来，Agent 17 步里第 7 到 14 步全在搜同一件事的不同说法。"

"业界的解法是把'换角度'这件事工程化，核心是**向量相似度 + 滑动窗口**两件套：

- **向量相似度匹配**：每条 query 过一遍 embedding，新 query 与历史 query 两两算余弦，**阈值 0.88** 判重复。这个数不是拍的，是拿两个 badcase 夹出来的：低了会把'固态电池'和'锂电池'误判成重复，高了漏掉'苹果财报 PDF'和'Apple annual report'这种中英变体。
- **滑动窗口**：不做全量历史比较——新 query 只和**最近 5 条**比，历史队列只保留**最近 20 条**。两个理由：成本上，每步只算 5 次余弦，增量 O(1)；语义上，'绕圈'是近期行为，隔了三十步重搜同一个词，可能是信息缺口变了之后的合理回访，不该拦。所以这层管的是'近重复、是否原地打转'；远期的'是不是同一篇文章'交给内容层的三重指纹去管——两层分工，互不越界。
- **命中之后 hint 升级**：不能只说'你重复了'，要带上上次失败的原因——上次空结果，就说'上次这个方向搜不到，从对立面、上位概念或案例来源切入'；上次是付费墙，就说'直接访问官网或权威媒体 URL'。只说'你重复了'，模型的反应只会是再微调一次关键词。
- **两个工程细节**：一是只对 search 工具做检测——Visit 重访同一 URL 可能是合理的加载重试，不能误杀；二是命中重复时**不执行工具**，把 hint 作为 tool 消息注入——省一次真实调用。

加了这套，业界数据有效步骤从 73% 提到 91%。我们缺的就是这一层，演进清单第一位——而且 0.88 是英文的经验值，中文 query 得拿我们自己的轨迹回放重新标定，我正好有 91 条现成的。"

**第三幕：质量把控——事前预防、三重指纹去重、还没做的核验（口子二在这幕收尾）。**

"质量把控我们按三段组织：**先拦在门外、再洗进来、最后验真伪**。

**第一段：事前预防（拦在门外）。**

- 域名黑名单：已知低质来源直接不取；
- 页面级排除：404、登录墙、付费页——登录页最典型，模型拿去只会开始研究'怎么绕过登录'；
- 特点：零成本零延迟，第一道闸。

**第二段：爬取结果的处理（洗进来）。**

- ① 去模板：侧边栏、导航、评论区剥掉，只留正文；
- ② 三重指纹去重，**与门判重**——三个条件同时满足才算重复：
  - 标题相似度：编辑距离 + 余弦，**>0.8**——抓标题变体；
  - 正文重合度：MinHash 估计的 Jaccard，**>0.7**——抓转载改写，长文本词集重叠它算得最快；
  - 语义相似度：SimHash 64 位指纹汉明距离 **≤3**——抓表达不同但核心内容相同的；
- ③ 量级口径：一次搜索返回 10 篇上下、筛 5 篇；一轮任务累计待去重 **50–150 篇**；
- ④ 不用逐段 embedding 的理由，时间账：指纹侧——标题微秒级、MinHash 128 排列每篇 1–2ms、SimHash 亚毫秒，**单批 10 篇 20–50ms、累计 150 篇半秒以内**（工程估算）；embedding 侧——每篇正文向量化 20ms 起步、API 批量 500ms 级，逐段再乘段数——高频路径这笔钱不该花；
- ⑤ 生产手段：MinHash 走 LSH 分桶、SimHash 分桶先出**候选对**，候选对再跑三重确认——避免 O(n²) 全对比较；指纹库增量存，新文章只与历史指纹比；
- ⑥ 判重后保留谁：组内**规则打分取最高**——来源权威度（域名名单、机构站加分）+ 与当前子问题的相关度（标题摘要命中）+ 时效性（近两年加分，新闻类权重更高）；同分留发布最早（原始来源，溯源信息保留）。'一律留最早'的两类翻车：预印本 vs 期刊定稿（晚的更权威）、滚动报道 vs 首发快讯（新的更全）；
- ⑦ 这把打分尺子复用于候选排序：分高的先进上下文，低分降权不丢弃。

**学术源单独一套取法。**

- 不能按引用量挑——Attention is All You Need 引用十万级，但你问'改进方法'它一个字不讲：引用高=奠基工作，不等于对你的问题相关；
- 按相关性排序：标题命中为主、摘要命中为辅，时效（近两年）和开放全文加分；**取十筛三**——学术摘要两三百字，三篇 700–1200 字，够用不撑上下文；
- 元数据透传：年份、venue、被引数**原样带上**——工具不替模型下'哪篇可信'的结论，掂量的材料给够，判断留给模型和核验层。

**口子二在这段收尾：降级链的正文形态。**

- 主路径 Tavily 一次调用搜索、抽取、切块全做完，质量是买来的；降级到自建链（Serper+Jina）后，上面这套批级 QC——黑名单、去模板、去重——都还在管，但**单条正文没有定长切块、没有分档截断：正文再干净，十万字还是十万字**；
- 实测证据：91 条工具结果里 12% 超一万字符，最大一条顶满十万截断上限，约两万五 token——上下文膨胀的大头就是这类结果贡献的（标本/降级链口径）；
- 更隐蔽的是降级发生时系统'活着但变笨'，上层分不清结果切过块没有。要补两样：**切块/分档截断 + 降级状态透出**（结果里标清楚'本次为降级结果，未经切块'）。

**第三段：信息源核验——prompt 层已上线，机制层还没做。**

- **prompt 层（已上线，两条指令）**：一是**结论性事实双独立来源交叉验证**——搜索过程自带信源核实任务：凡是写进结论的数字、时间、因果，必须再找一个独立来源佐证，单源只能标'待核实'；二是**矛盾信息保留并核实**——搜到的信息观点打架时不许静默融合、不许悄悄取舍，两条都保留、在报告里标注分歧待核实。这类 prompt 纪律的效果有业界数字支撑：系统提示加'矛盾信息要指出不许融合、找不到就说找不到'两条后，信息混淆率从 13% 降到 6%【业界参考值】——是降幻觉最便宜的一层；
- **机制层（还没做）**：prompt 管得住模型的行为，管不住模型看不见的东西——三篇互相抄袭的文章，模型只看得到三个不同域名，会被当成'三源确认'；内容农场和权威媒体的域名分差，也得机制层给。演进 B3 补的就是这个：域名名单 → 信号特征打分 → 来源独立性粗筛（域名/发布时间/正文相似度）；
- 杀手锏问题留给机制层：同一篇稿子四个 URL——去重发现'同一篇'，prompt 让模型去找第二个来源，但'两个来源是不是互抄'模型自己看不出来；
- 分层逻辑一句话：**prompt 层核验降幻觉的行为面，机制层核验补认知盲区**——Tavily 切块、学术元数据、prompt 指令都不解决'互抄假独立'，那是质量侧演进清单的下一项（业界完整分层做到幻觉率 14%→3%【业界参考值】）。"

**第四幕：收尾——演进按口子排。**

"所以'上线后遇到什么问题'我的完整答案：上线前的三类失败处理加批级 QC 加 prompt 层核验——退避、硬错拒绝重试、空结果带 hint、黑名单、去模板、三重指纹去重、结论性事实双来源交叉与矛盾保留核实——扛住了日常绝大多数场景；真正漏进来的是两个口子和半个核验：空结果后的重复 query 循环、降级链的正文形态没人管、核验的机制层还没做。对应的演进也就清楚了：先补 query 去重加差异化 hint，再补降级链的切块、截断和状态透出，然后是核验机制层（可信度分层、独立性粗筛），缓存并行殿后。选型哲学始终一句：**主路径把质量买成品（Tavily），降级路径的质量自己补——把贵的方案留给真正需要它的场景。**"

**30 秒版：**

### 2.3 追问详解（I30–I35）

#### I30. "空结果为什么不重试？hint 给出去之后呢？"

- **第一句**：空结果不重试是对的——它是引擎明确说"这方向没有"，重发同一个词纯烧预算，这一点我们上线前就做了：空结果不硬塞，返回带 hint 的提示；真正的坑在 hint 之后——模型收到"请换个角度"，它的执行是微调关键词，转一圈又回到原地。
- **要点**：失败四类分级的哲学一句带过（超时退避/硬错跳过/空结果转 hint/垃圾过滤）；我们现有 hint 是"半成品"——只给了动作（换角度/拆子问题）没给原因（这方向搜不到），模型缺换搜索空间的算子（接 I33）；业界验证：重复 query 检测 + 差异化 hint 之后有效步骤 73%→91%；防反问"万一是引擎抖动呢"——单次短退避可接受，连续空结果必须转升级版 hint，用 hint 命中率兜不是用次数兜。
- **易踩坑**：不能把标本仓库的"无差别 5 次退避"说成产品现状——产品层已分级，标本代码是历史实现（§0 差异注记）；也别把现有 hint 说成已含差异化逻辑——它是 B1 的升级对象。
- **回看标本**：产品口径为主；标本历史实现 `searching_mcp_server.py:143-170`；博客02。

#### I31. "URL 去重为什么不够？你们的内容去重怎么做的？"

- **第一句**：URL 去重抓的是"同一条链接"，抓不住"同一篇稿子的四个转载"——所以内容层我们上的是**三重指纹门控**：标题相似度大于 0.8、MinHash 正文 Jaccard 大于 0.7、SimHash 64 位汉明距离小于等于 3，**三个同时满足才判重**。
- **要点**：三个指纹各管一段——标题（编辑距离+余弦，0.8）抓标题变体；MinHash（3-gram shingle、128 排列，0.7）抓转载改写，转载通常删改 5–20% 还掺站点元素，纯 Jaccard 天然被拉低，所以阈值比业界博客的 0.8 放宽到 0.7；SimHash（64 位，≤3）抓"同文不同述"；**为什么 0.7 敢比业界松：三重与门兜住了误杀**——单指纹放宽偏向召回，漏检比误杀贵（重复文章进上下文烧 token，误杀最多损失一篇候选）；量级与时间：单批 10 篇、任务累计 50–150 篇，单批全流程 20–50ms、累计半秒以内（工程估算）；生产手段：MinHash LSH 分桶 + SimHash 汉明分桶先出候选对，避免 O(n²) 全对比较，指纹库增量存、新文章只与历史比；业界对照：博客06 是 URL→MinHash(0.8)→语义 embedding(0.92) 漏斗，150→52【业界】——我们用 SimHash 替掉 embedding 层，代价是语义召回略弱，换来零 embedding 调用的成本和延迟；**保留策略：组内规则打分取最高——来源权威度 + 与当前子问题的相关度 + 时效性，同分才留发布最早的（原始来源，溯源信息保留）**；"一律留最早"的两类翻车：预印本 vs 期刊定稿（晚的更权威）、滚动报道 vs 首发快讯（新的更全）；这把资料打分的尺子同时用于候选排序——分高的先进上下文，低分降权不丢弃（呼应业界 <0.35 降权不删的思想）。
- **易踩坑**：三重是"与门"不是"或门"——说成任一满足就判重会放大误杀；保留策略别说成"留发布最早的"——那是同分优先级，主策略是组内打分取最高；时间数字是工程估算口径，落地以实测复核；别把博客的 150→52 说成我们的数据。
- **回看标本**：本册 §2.1 第三幕、§2.2-R3；博客06（业界对照）；标本仅 hybrid 融合层有 URL 级 `_dedupe`（`fusion.py:4`，04 册 §3.6 有其副作用注记）。

#### I32. "标题 0.8、正文 0.7、语义汉明 3——三个阈值差这么远，怎么标定的？"

- **第一句**：因为三个指纹比的东西不一样、量纲也不一样，数字不能直接比大小——标题比短文本字面（转载标题常只改个别词，0.8 抓变体）；正文比长文本词集重合（转载删改加站点元素天然拉低 Jaccard，放到 0.7）；SimHash 比 64 位指纹的位差（汉明距离 3 ≈ 4.7% 的位差异，业界惯例 3–6，越小越严）。
- **要点**：标定方法和业界 query 去重 0.88 一样，是拿 badcase 夹出来的——标题改一两个词的转载对（不能漏）和同话题不同文章对（不能误杀）两边一夹；0.7 的额外逻辑是系统性的：三重与门已控住误杀，单指纹可以偏向召回——漏检比误杀贵，重复文章进上下文烧 token，误杀最多损失一篇候选；query 去重的 0.88 是业界英文经验值（固态电池 vs 锂电池=误报下界；苹果财报 vs Apple annual report ≈0.86=漏报上界），我们落地要拿 91 条轨迹回放重标中文；被追问"为什么不用 embedding 逐段匹配"——回到时间账：指纹毫秒级、零调用成本，embedding 每篇 20–50ms 起步、API 批量 500ms 级，高频路径上"贵的方案留给真正需要的场景"。
- **易踩坑**：0.8 的余弦、0.7 的 Jaccard、汉明 3 是三种量纲，直接比大小就是露怯；只会背数不会答"0.75 行不行"——要能答"行，但误杀率升，得看与门里另外两道能不能兜住"。
- **回看标本**：本册 §2.1 第三幕、§2.2-R3；博客02/06（业界对照）。

#### I33. "为什么 hint 不能只说'请换个角度'？"（拿我们自己的 hint 开刀）

- **第一句**：因为模型对"换角度"的执行就是微调关键词——苹果财报→苹果财务报告，方向一点没变；我们现有的空结果 hint 是个"半成品"：给了动作（换角度/拆子问题），没给原因（上次这方向搜不到）——模型缺的是换搜索空间的算子，不是再来一句叮嘱。
- **要点**：升级版差异化 hint 三型——空结果给新搜索空间（对立面/上位概念/案例来源）、垃圾给新工具选择（直达可信 URL）、一般给新问题分解（从子问题出发）；hint 以 tool 消息注入且不执行工具，省一次真实调用；这套"执行器引导 LLM 自愈"我们已经在用同族设计——工具名写错自动纠错并注明 `[Auto-corrected]`、Jina 422 提示换沙箱、失败文案自包含，都是把"怎么修"喂回去而不是只报错；缺口就是把同样的设计补到空结果 hint 上（演进 B1），由重复 query 检测触发。
- **易踩坑**：不能说现有 hint 已含差异化逻辑——它是升级对象不是成果；也别把它说成纯 prompt 问题——检测（embedding 0.88）和 hint 升级是一体的，缺检测就不知道"上次为什么失败"。
- **回看标本**：`manager.py:276-307`、`smart_request.py:44-69`；博客02。

#### I34. "你们 hybrid 的 web 检索没有重试，主搜索路径却有指数退避，为什么不对称？"（主动亮短板题）

- **第一句**：这是真实短板，我直说——hybrid 链路里的 `web_retriever` 是一次性请求，失败或没 key 就静默返回空列表，和主搜索路径的退避策略完全不对称；它是检索融合链路里最薄的一环。
- **要点**：代码事实（`web_retriever.py:17-28`）；设计意图能理解——web 路权只有 0.4，本地 0.6 兜底，"Web 空召回≠Hybrid 失败"的降级哲学没错，**但静默空列表让上层分不清"没搜到"和"搜挂了"**；危害链：空列表→web_hits=0→本地也没命中时 Agent 拿到全空还以为"真没有"，正是我们 01 册问题清单里"空检索被当成有效证据"的形态，最后靠 `hybrid_search_observability` 的 route/web_hits 元数据才排查得动；修法三步：对齐退避（tenacity 3 次就够，0.4 的路权不值得更多）、返回带状态码把"空召回"和"失败"分开、将来双路并行化时统一重试与超时预算。
- **易踩坑**：别辩护"静默返回是优雅降级"——降级可以，状态要诚实；这题答好的标志是主动给修法和优先级。
- **回看标本**：`web_retriever.py:13-28`；04 册 §3.4；01 册 P7。

#### I35. "搜索为什么用 Tavily 不自建到底？主路径挂了怎么办？"（选型题）

- **第一句**：我们已经就是这么选的——**搜索主路径 Tavily，自建三段式（Serper+Jina+MarkItDown）做降级**；道理一句话：主路径把质量买成品，降级能力留手里。至于主路径挂了会怎样，正是我们上线后暴露的口子二——降级链的质量真空。
- **要点**：
  - 加工程度光谱一句话：DDG 免费但把工程债留给你（非官方接口、IP 级 429 限流、Bing 系索引弱中文）；Serper/SerpAPI 把引擎的债买断（CAPTCHA/代理/改版归供应商，还带 knowledge graph、answer box 这类一步直答元素）但给的仍是"结果页"不是"内容"；Tavily 连抽取和切块一起买断——AI 应用要的不是链接是带引用的答案。
  - 为什么 Tavily 做主路径：链路短一半 = 失败面少一半；预切定长块 = 把 L1 前置减量外包给供应商；官方 MCP 支持。
  - 为什么自建链不扔：① 成本对冲——Tavily 按 credit 计费，Agent 自主跑起来账单会咬人，自建链是天然的预算降级档；② 控制力——分档截断这类策略只有自建层能调；③ 供应商故障兜底——和三级抓取降级链同构，等于把降级思想从工具内部上移到供应商层面。
  - 这套选型的软肋要主动交代：主路径的质量是买来的，**降级发生时质量没人管**——"活着但变笨"比挂掉更隐蔽，所以演进 B2（降级链质量把控）是这套架构的配套件不是可选项。
  - 收束话术："DDG 到 Serper 到 Tavily 是加工程度的光谱——免费接口留债给你，SERP API 买断引擎债，LLM 定制 API 连抽取切块一起买断。我的选型是主路径买成品、降级留自建，两头的便宜都占——但降级的质量得自己补。"
- **易踩坑**：别说"我们自建搜索为主"（现状是 Tavily 主路径）；别把自建链说成包袱——它是降级资产；也别踩 DDG——生产不适合，但原型零成本起步仍是它的场景。

## §3 演进优先级（怎么讲"如果给你两周你先做什么"）

排序判据三条：改动面小（不动主循环优先）、直击实测瓶颈（重尾 scrape）、可离线验证（15 条轨迹 + 91 条工具结果就是现成回放集）。上下文方案本身不在这张演进表里——Main-Sub 隔离 + 滑动窗口是设计时定的，ReSum / IterResearch 的排除理由见 §1.1。

**主题 A（上下文）**：

| 优先级 | 演进项 | 改动面 | 一句话理由 | 验收 |
| --- | --- | --- | --- | --- |
| A1 | scrape 分档截断 + `strip_markdown_links` 接线 | `io_utils.py` 一处 + 复活死代码 | 滑动窗口按条数保留最近 N 条，一条落在窗口内的 10 万字符结果仍会全量进去。12% 的大结果是体积来源（降级链口径，§0 注记）；这一档是结果侧截断，不是改上下文方案。与 B2 是同一改动的上下文侧视角 | 回放 n=15，>10k 字符的工具结果条数和会话峰值下降；GAIA 子集准确率不降 |

**主题 B（搜索工具）**——现状：主路径 Tavily + 自建链降级、批级 QC（黑名单/去模板/三重指纹去重）已上线；演进按"两个口子 + 一个核验"排：

| 优先级 | 演进项 | 改动面 | 一句话理由 | 验收 |
| --- | --- | --- | --- | --- |
| B1 | **重复 query 过滤 + 差异化 hint（口子一）** | 执行器层 | 空结果 hint 之后模型"假换角度"微调关键词，近似 query 循环纯烧预算；业界 73%→91% | 91 条轨迹离线回放标定中文阈值；有效步骤比例 |
| B2 | **降级链正文形态把控（口子二）：定长切块 + 分档截断 + 状态透出** | 降级链（Serper/Jina）出口 + `io_utils` | 事前预防与去重已覆盖批级质量，缺的是单条结果进上下文的形态——"正文再干净，十万字还是十万字"；与 A1 是同一改动的工具侧视角 | 回放 n=15：>10k 字符大结果条数显著下降；降级结果带"未经切块"状态标注 |
