## §1 重难点一：上下文膨胀的工程解法

### 1.1 问题本质：从"装不下"到"看不见、买不起、收不住"

讲这道题的第一句，先分清两个语境，否则后面所有参数都是错的：

**语境一：博客语境（32k 级小窗口）。** messages 随轮次线性膨胀：每步约 2500 token，10 步 25000、15 步 37500【业界·博客01】；一步"搜索 + 访问"喂进上下文 8k–12k token【业界·番外01】。三大症状：① 注意力稀释导致信息混淆——经典事故是第 7 步 messages 超 28000 token 时，模型把欧盟补贴额度安到美国政策上（排查 2 小时）；② 策略停滞——模型从几万 token 历史里推"我还缺什么"极易出错，导致近似关键词反复搜；③ 截断丢早期关键背景——截掉的恰是最初任务定义和早期核心结论【业界·博客01/05】。

**语境二：本项目语境（1M 大窗口）——"装不下"不是主要矛盾。** 标本模型 qwen3.7-plus 上下文窗口 **1M**、最大输出 131,072，配置实际 `max_tokens: 8192`（`config/agent_llm_qwen37plus.yaml`；模型规格见阿里云文档）。本地 n=15 轨迹里 **ContextLimitError 触发 0 次**——"爆仓蒸馏"（见 L2）是设计兜底，不是实测路径。窗口大了，问题变成三个：

- **看不见**：注意力衰减不因窗口变大而豁免。Lost in the Middle（arXiv 2307.03172，TACL 2024）给出 U 形曲线——相关信息在上下文中部时性能显著下降；NoLiMa（arXiv 2502.05167，ICML 2025）显示 **32k 起各模型性能即显著折扣**。结论：有效注意力远小于标称窗口，1M 窗口 ≈ "装得下"≠"看得进"。
- **买不起**：单题 total usage 14 万–76 万 token（n=3，01 册 §2.3）；Agent 多轮重复读前缀，Cached/Input ≈ 82%——缓存命中决定成本。Anthropic 官方口径：Agent 单任务 token ≈ 普通对话 **4 倍**，多智能体研究系统 ≈ **15 倍**（出处：Anthropic《How we built our multi-agent research system》，2025-06）。
- **收不住**：失败题 c61d22de（01 册 P1 失败模式）——单个 agent-worker 会话 25 条消息累计 **405.9k 字符（≈10 万 token，仅占 1M 窗口约 10%）**，43 个 step，单 Sub usage 74.6 万 token，最终无 final answer。死因是步数预算和收束失败，不是窗口溢出——**上下文堆得越厚，收束越难**。

**语境三：本地实测——膨胀是重尾的，不是均匀的。** n=15 轨迹、91 条工具结果：

| 指标 | 中位 | 均值 | p90 | 最大 |
| --- | --- | --- | --- | --- |
| 单条工具结果（字符） | 2.2k | 8.9k | 17k | **100,023**（3 条顶满 100k 截断上限 ≈ 25k token/条） |
| 每轮会话增长（字符） | 613 | 9.6k | 22.9k | 101.9k（单轮含一次满额 scrape） |

12% 的工具结果超过 10k 字符。**结论：本项目的膨胀主要由少数大 scrape 驱动**，不是博客"每步均匀 2500 token"的模型。这个差异直接决定演进优先级（§3）：对标本而言，L1 前置减量（正文过滤、分档截断）的 ROI 高于均匀的历史压缩。

> **第一句话术**："上下文膨胀要分语境：小窗口场景的问题是'装不下'，我们标本是 1M 窗口，装得下，但问题变成'看不见、买不起、收不住'——注意力衰减 32k 就开始（NoLiMa），单题成本 14 万到 76 万 token，最厚的一个失败会话 40 万字符还没溢出就先收不住场了。所以我的答案是一套四层防线，重心从'腾空间'移到'提信噪比、控总量'。"

### 1.3 逐层展开

#### L1 前置减量——"输入端的质量控制，比 Prompt 优化更根本"【业界·博客06】

**业界谱系**（出处：博客03、06）：

- **条数控制**：search 取 10 筛 5（前 5 条覆盖九成有效信息，条数多让模型分心）；scholar 取 10 筛 3（学术摘要 250–400 字 ×3 恰好）。**校准注**：1M 窗口下条数不是瓶颈，"筛 5"的理由从小窗口的"装不下"变为"看得清 + 省钱"。
- **正文抽取去模板**：去掉 nav/footer/header/aside/评论/推荐位；优先 `article/main/[role=main]` 语义容器，降级取 >50 字的 `<p>`。反模式："BeautifulSoup 抓了正文啊"——5000 字网页里 3000 字是侧边栏和评论区噪声，模型顺着评论区观点偏了 4 步【业界·博客03】。
- **段落级相关性过滤**：Visit 的 `query` 设为**必填**（工具必须知道"为什么访问这个页面"才知道留哪段）；两阶段处理——先去模板再做段落级打分（查询词重叠 + 前 3 段 0.3 位置加权，选满 `max_chars=2000` 后**按原文顺序重排**）；40 道多页深读题任务完成率 **55%→76%**【业界·博客03】。明确不用 embedding：Visit 高频调用（一次研究十几个页面 × 几十段），关键词重叠的延迟成本远低；失效场景是跨语言，此时才升级。"把贵的方案留给真正需要它的场景。"
- **三层去重**（150 条原始结果抽样 50 条，19 条高度重叠 ≈ 40% 全逃过 URL 去重）：① URL 去重 150→130；② **MinHash 内容指纹**（字符级 3-gram shingle 抗标题改写、num_perm=128、Jaccard 阈值 **0.8**——转载通常改 5–20%，设 1.0 漏报、0.5 误删独立文章；MinHashLSH 分桶近似 O(n) 可线上实时）130→75；③ **语义去重**（snippet embedding 余弦 **≥0.92** 判重——同话题不同文章天然 0.8–0.85，阈值须更高；组内保留发布最早一篇 = 原始来源）最终 45–52 条。**150 进 52 出，数量减 2/3，信息量几乎无损**【业界·博客06】。流水线并行化后 2.3s→0.8s（打分与 MinHash 并行、批量 Embedding、LLM 交叉验证不可并行）。
- **可信度三层**：域名黑白名单（.gov/.edu/reuters/nature→0.92，已知农场→0.05，零成本零延迟）→ 信号特征 + LightGBM（域名年龄 <1 年、外链 <50、无署名、广告密度 >30%、日更 50 篇+ 聚合站特征；**<0.35 降权不丢弃**，不作核心论据）→ LLM 交叉验证（结论性事实 **≥2 个独立来源**才写入报告，单源标"待核实"）。幻觉率 **14%→3%**（人工抽标 100 份报告）【业界·博客06】。
- **独立性陷阱**：三篇互抄会被交叉验证误当"三源确认"——独立性判断至少做域名/发布时间/正文相似度粗筛，同源只算一票【业界·番外01】。

**项目落点**：

- 【已落地】hybrid_search 融合层 `_dedupe()` 按 URL（或 source:chunk_id）去重（`src/retrieval/fusion.py:4`）；本地检索 snippet 截 500 字符（`src/retrieval/local_index.py:68`）；chunk 800/overlap 120（`src/retrieval/local_index.py:9`）。
- 【已落地·弱】主搜索路径（google_search）原样透传 Serper organic 结果，无去重无重排；富结果裁剪靠 env 开关（`REMOVE_SNIPPETS/KNOWLEDGE_GRAPH/ANSWER_BOX`，默认 false，`searching_mcp_server.py:45-85`）。
- 【半落地】`strip_markdown_links()`（去链接/图片压缩 markdown）已实现但**无人调用**（`src/tool/mcp_servers/utils/url_unquote.py:60`）——"准备了但没接线"。
- 【演进】scrape 结果分位数分档截断（见 §3 演进 A1：直击重尾源头）；MinHash/语义去重（中英混合源的 0.8/0.92 阈值需重标定）。

#### L2 运行时预算——"在'溢出前'处理，不是'溢出后'"【业界·博客02】

**业界谱系**（出处：博客02、07）：

- **token 三档**：上限 28000（不是 32000——留 4000 给最终答案生成）；<65% normal（observation 截 3000 字符）、65%–85% compact（截 1500）、≥85% compress（截 800 + 触发历史压缩）。复杂任务成功率 **61%→78%**【业界·博客02】。
- **历史压缩的取舍**：压缩时**保留 think、压缩 observation**——思考轨迹比原始结果对后续决策更重要；用 LLM 把全部 tool 消息合成"已确认的事实 + 尚未解决的子问题"结构化摘要后重建 messages【业界·博客02】。
- **ReSum**：上下文使用率 >80%（128k×0.8=102400）触发结构化摘要，保留 system + 最近 5 条，丢弃 Observation 原文；40+ 步任务上下文占用从接近溢出降到平均 **65%**，准确率无明显下降【业界·博客07】。与 Claude Code `/compact` 的区别：compact 单次手动，ReSum 持续监控自动触发。
- **选型逻辑**：<10 步 ReAct；10–20 步 ReSum（改动最小的线性历史上加摘要触发）；>20 步 IterResearch；准确率极高要求用 Research-Synthesis（并行验证）【业界·博客05】。

**项目落点**：

- 【已落地】两道闸：`max_turns`（Main 20 / Sub 50，防"无限想—调—再想"与上下文膨胀）+ `max_tool_calls_per_turn`（10，防单轮调用爆炸）——详见 05 册 §3。
- 【半落地】`keep_tool_result` 历史裁剪机制存在（`src/llm/provider_client_base.py:115`，保留首条 user + 最近 N 条，其余替换为 "Tool result is omitted to save tokens."）但**所有配置均为 -1（不裁剪）**，靠模型长上下文硬扛。
- 【已落地·被动】爆仓蒸馏：`ContextLimitError`（8 种 "context length" 错误文案识别 + `finish_reason=="length"`，`claude_openrouter_client.py:161-202`）→ `_handle_summary_with_context_limit_retry()`（`orchestrator.py:294`）——把长历史一次性蒸馏成 FINAL ANSWER + 结构化报告；仍超限则逐对弹出最近 assistant/user 消息重试（`:376-382`）。**本地 n=15 触发 0 次**：是兜底保险，不是日常路径。
- 【演进】虚拟工作区 + 阈值主动压缩（见 §3 演进 A2）。**校准注**：博客的 28000/65%/85% 是 32k 窗口的换算，照搬到 1M 窗口 = 99 万预算毫无意义；按 NoLiMa 的注意力折扣，建议把"虚拟工作区"设在 **~10 万 token（窗口的 10%）**量级，且阈值以**工具结果累计**为主要触发依据（本项目的膨胀源头是重尾 scrape，不是均匀步数）。

#### L3 架构根治——"把上下文从'越来越长的对话'变成'越来越好的研究报告'"【业界·博客05】

**业界谱系**（出处：博客05、07、番外02；论文 arXiv 2509.13309）：

- **IterResearch / 演进报告**：论文出处为阿里通义 WebResearcher（arXiv 2509.13309，2025-09）——把深度研究建模为 MDP，agent 周期性把发现整合进 **evolving report** 并维护 **focused workspace**，治的是 mono-contextual 方案的 **context suffocation 与 noise contamination**；6 个 benchmark SOTA。博客的可操作化版本：
  - **报告四模块**：Confirmed Facts（带来源与步骤号，只取最近 20 条）/ Open Questions（≤10 条）/ Information Gaps / Current Focus【博客05】；另一模板五模块（研究目标 / 已确认事实 |来源|置信度 / 待验证假设 / 信息缺口 / 结论草稿）【博客07】——结构化的价值是强迫显式分类（"待验证"不当"已确认"用），信息缺口成为下一轮搜索的驱动引擎。
  - **循环**：报告快照 + 当前焦点 → 决策 → 执行 → `extract_findings`（每步额外一次 LLM 调用，把 Observation 解析成结构化新发现）→ 更新报告 → 无未解决子问题则停。性质：**输入规模 = 报告大小 + 单步工具结果，不随步数增长**。
  - **防退化三条**：报告上限 **2000–3000 token**（超限触发 LLM 压缩合并）；同话题事实 >5 条合并（两条营收数据合成一条带同比的）；矛盾信息**两条都保留**并在 Gaps 记"需核实"，不让一个版本悄悄消失【博客05/07】。
  - **效果口径**：15 步以上任务准确率比 ReAct 高 18 个百分点、总 token 反而更少（避免重复搜索）——此为**博客自测参考值**；10 步以内 ReAct 更快更省【博客05】。
  - **缺口驱动搜索**：下轮 query 必须从"信息缺口"里选 + prompt 列出已有事实注明"不要搜索以下已有信息"，搜索重复率 **23%→6%**【博客07】。
- **子代理隔离与汇总税**：隔离省的是主对话的注意力（番外02："多开 subagent 首先是上下文管理手段，不是性能优化手段"）；但有**四项并行税**——重复认路 × 人头数、依赖链串行化、共享文件冲突、主 agent 汇总验收（回传详细结果会把主上下文重新吃满，"用隔离省下的上下文在汇总时连本带利还回去"）。规模参考：简单查证 1 agent + 3–10 次调用；对比类 2–4 subagent × 10–15 次；复杂研究才上 10+；Anthropic 内部评测多智能体比单 agent 好 90.2%（质量分不是速度）。
- **外置存储 + 悲观信任**：类比 Claude Code Memory——MEMORY.md 注入 system prompt 且硬限 **200 行**（≈3000–4000 token，超限截断显示 `[MEMORY TRUNCATED]`），其余按需读取；设计哲学"记忆是线索不是事实"，用前必须验证——与演进报告里"待验证假设"同一思路【博客07】。

**项目落点**：

- 【已落地】Main-Sub 隔离四件套（详解见 03 册 §6 / E13）：`run_sub_agent()` 新建独立 `message_history`（`orchestrator.py:595`，不复制主 history）、独立 ToolManager、独立 LLM client、独立用量统计；**主代理只接收子代理最终摘要文本**（`orchestrator.py:884`）——这就是"信息压缩边界"。委派时把 subtask 写全（目标/范围/输入/约束/期望输出），而不是把 Main 全 history 塞给 Sub（破坏隔离、扩大上下文、引入无关信息）。
- 【已落地·诚实点】无并行 fan-out：主代理一次只 await 一个工具/子代理（`orchestrator.py:1124` 顺序循环），prompt 明文"每轮只允许一个 tool call"（`sub_worker.py:89`）——"架构可并行 ≠ 标本已并行"（05 册口径）。这恰好**回避了汇总税**，但也没吃到并行收益。
- 【演进】演进报告：在 L3/多跳失败题子集试点（对照 01 册 P1"信息到了、收束没完成"的失败模式，演进报告的 Confirmed Facts/Gaps 结构正是对"收不住"的针对性解法）；代价是每步多一次 extract_findings 调用（成本 +10–20% 量级估计，需实测）。

#### L4 总量开关——"一个不设停止条件的系统，是把最贵的决策外包给运气"【业界·番外01】

**业界谱系**（出处：番外01、03）：

- **三个可计算停止信号**（全部放在**循环外的守卫代码**，提示词中从不出现"你自己判断要不要停"）：① 信息增益衰减——连续 3 步新信息占比 **<8%** 触发收敛（15% 太激进误伤慢热题、5% 太保守；新实体只算系统名+版本号/具体数字/机制名词，形容词不算）；② 子问题覆盖率——"两个独立来源确认"占比八成且其余连续无进展；③ 预算水位——90% 任务 35 步内无增量 → 硬顶 40 步 + 成本上限。实测平均步数 **31→19**，子问题覆盖 5→4+（掉的是本来就查不到的）。
- **到顶"收敛"而非"截断"**：收敛 = 强制收尾模式——已确认写成结论、未验证标注、未覆盖标注，交付"边界清楚的半成品"；截断 = 断在半截。收敛模式三规则：新搜索方向一律不放行；query 锁死在"未确认"清单；只许给单源子问题补第二个独立来源，补两轮不成直接标"未验证"。翻车细节：模型在收敛模式输出"我注意到一个新的有趣方向"，被守卫直接拦下。
- **无进展检测**（番外03）：`max_steps` 只是硬预算，回答"最多花多少"，不回答"是否完成"；等轮数跑满才停，中间的钱和延迟已花掉。三信号：**动作指纹**（参数大小写/空白/排序/默认值归一化后取哈希）、**观察指纹**（结果集稳定摘要，排除抓取时间/请求 ID/排序抖动）、**状态差**（evidence_count/open_gaps 前后对比——模型自己改 scratchpad 不算进展，只有权威工具的状态转移才能关闭缺口）。注意：完全相同的调用不一定是坏循环（幂等键重试、等索引刷新是合理恢复），"看到重复就停"会误伤。
- **软停止状态分型**：completed / 连续无进展 / needs_input / risk_gate / no_progress（输出已确认事实 + 缺口 + 停止原因）/"带证据降级"，不能全压成 failed。

**项目落点**：

- 【已落地】`max_turns` 触顶不硬掐死：`max_turns_reached` → `task_failed=True` → 仍走 final summary 带证据收束（05 册 §3.3）；到达上限返回最后 assistant 输出而非报错。
- 【演进】信息增益衰减检测：标本只有步数硬顶，没有"增量"维度——c61d22de 失败题正是"步数没用完但已无增量"的形态（43 步无答案）。落地面：在执行器层对新 Observation 与 Confirmed Facts 做增量打分（轻量：实体抽取 + 与已有事实重叠度），连续 N 步低于阈值转收敛模式。

### 1.4 口头答案（定时模板 ≈ 95 秒）

**先讲问题本质（20s）**：
"上下文膨胀要分语境。小窗口场景是真'装不下'——业界数据是每步 2500 token、10 步就 2 万 5。我们标本是 qwen3.7-plus 一百万窗口，本地 15 条轨迹里上下文溢出零次，所以我们的问题不是装不下，是三个：看不见——NoLiMa 这类评测显示 32k 起注意力就显著折扣，窗口大不豁免；买不起——单题 14 万到 76 万 token；收不住——我们有个失败案例，单个子代理会话堆到 40 万字符、烧了 74 万 token，最后没交出答案。"

**再讲核心思路（30s）**：
"我的解法是一套四层防线：L1 前置减量——垃圾不进上下文，正文抽取、三层去重；L2 运行时预算——token 三档、溢出前压缩；L3 架构根治——子代理隔离、演进报告，把上下文从'越来越长的对话'变成'越来越好的研究报告'；L4 总量开关——停止信号和无进展检测。重心从小窗口的'腾空间'移到我们这种大窗口的'提信噪比、控总量'。"

**然后讲实现细节（30s）**：
"标本里已经落地的是：Main-Sub 隔离，子代理独立会话、只回传摘要，主代理上下文不被子代理的原始工具结果污染；两道预算闸，max_turns 20/50 加单轮工具调用上限；上下文超限的兜底是强制蒸馏——把长历史一次性压成结构化报告再交答案；检索侧做了 URL 去重和 snippet 截断。我实测过本地轨迹的膨胀分布——中位数每轮只涨 600 字符，但百分之十二的工具结果超过一万字符、最大顶满十万截断，膨胀是少数大网页抓取驱动的重尾分布——所以我判断下一步 ROI 最高的是抓取结果分档过滤，而不是均匀压缩。"

**最后说选型逻辑（15s）**：
"方案选型看任务长度：十步以内 ReAct 够用，十到二十步上滚动摘要，二十步以上该上演进报告——WebResearcher 论文就是这么治 context suffocation 的。我们标本在'隔离 + 熔断 + 被动蒸馏'这个档位，演进路线是主动压缩和演进报告。"

### 1.5 追问详解（H25–H29）

#### H25. 为什么不直接加大上下文窗口 / 换长上下文模型？

- **第一句**：加大窗口只解决"装不下"，解决不了"看不见、买不起"——我们 1M 窗口零次溢出，问题反而更集中在注意力和成本上。
- **要点**：
  - 注意力衰减是机制性的：Lost in the Middle（TACL 2024）U 形曲线，中部信息利用率显著低；NoLiMa（ICML 2025）32k 起各模型显著折扣——窗口标称值 ≠ 有效注意力。
  - 成本随前缀线性重复计费：Agent 每步重读全部历史，单题 14 万–76 万 token；Anthropic 口径 Agent ≈ 对话 4 倍、多智能体 ≈ 15 倍。换更大窗口只会更贵。
  - 缓存是生命线：我们实测 Cached/Input ≈ 82%，换模型/频繁改前缀会打破缓存命中。
- **易踩坑**：不能说"窗口够大所以不需要上下文管理"；也不能反过来虚标"我们做了注意力优化"——标本没做，答案落在"所以更要减量"。
- **回看标本**：01 册 §2.3 Token 实测；本册 §1.1 语境二。

#### H26. 你们为什么没做阈值触发的主动压缩？（诚实答 + 引出演进）

- **第一句**：坦率说这是标本当前的短板——压缩是"爆仓后被动蒸馏"，不是"阈值前主动压缩"，而且本地 15 条轨迹一次都没触发过，说明它只是兜底。
- **要点**：
  - 现状三件事：`max_context_length` 配置被读取但从未使用（`provider_client_base.py:54`）；`_estimate_tokens`（tiktoken）在 4 个 provider client 里定义但**零调用**；`keep_tool_result` 裁剪机制存在但全配置 -1 关闭。
  - 为什么当时没做：qwen3.7-plus 1M 窗口下溢出不是主要矛盾（0 次），先把工程预算花在隔离和降级链上。
  - 为什么现在该做：注意力衰减与成本跟窗口无关；实测膨胀是重尾的（12% 的大 scrape），主动压缩的对象应该先是**单条工具结果**而不是全历史。
  - 演进方案：虚拟工作区 ~10 万 token（窗口 10%）+ 三档阈值作用于工具结果累计；tiktoken 已在依赖里，接线成本小（§3 演进 A2）。
- **易踩坑**：不能说"我们做了压缩"；被问到"为什么 0 次还设计这个兜底"——答"防御性设计，服务端换小模型配置（如 deepseek 128k）时它就是主路径"。
- **回看标本**：`miro-flow-solution/src/llm/provider_client_base.py:115`（裁剪）、`src/core/orchestrator.py:294`（爆仓蒸馏）；本册 §1.3-L2。

#### H27. 子代理隔离的代价是什么？

- **第一句**：隔离不是免费的——业界的说法是"四项并行税"：重复认路、依赖链串行化、共享状态冲突、汇总验收；其中汇总税最隐蔽，子代理回传详细结果会把主上下文重新吃满。
- **要点**：
  - 信息损耗是定向的：主代理只拿到摘要，细节问题要么在 subtask 里预先写全（目标/范围/输入/约束/期望输出），要么隔离就变成信息断层——正确解法是 Main 把任务描述写全，**不是**把全 history 塞给 Sub。
  - 每个子代理从零重建认知（重读系统提示、重摸工具集），短任务反而更贵；简单查证类 1 个 agent + 3–10 次调用就够，2–4 个 subagent 是对比类任务的配置。
  - 标本的取向：一次只跑一个子代理、顺序执行——牺牲并行收益，换来没有汇总税和冲突面；这是"架构可并行 ≠ 标本已并行"的诚实口径（05 册）。
  - 隔离的真实收益是**上下文管理**而不是速度（番外02 核心论点）——多智能体质量分高 90.2% 是 Anthropic 内部研究评测口径，不是提速承诺。
- **易踩坑**：不能说"我们并行跑子代理所以快 5 倍"；也不能把"顺序执行"说成缺陷——它是当前规模下的理性选择。
- **回看标本**：03 册 §6（run_sub_agent 四层隔离）、§9（顺序 vs 并发）；番外02。

#### H28. 演进报告怎么防止退化成新的线性历史？

- **第一句**：三道保险——报告本身设 token 上限、同话题事实强制合并、矛盾信息双保留进缺口清单，让报告"越写越好"而不是"越写越长"。
- **要点**：
  - 上限 2000–3000 token，逼近即触发 LLM 压缩（合并相似事实、删久无进展的假设）；Confirmed Facts 只取最近 20 条、Open Questions ≤10 条——上限本身就是设计约束，防止"事实列表"无限增长。
  - 同话题事实 >5 条触发合并：两条营收数据合成一条带同比的——合并规则按语义不按条数硬砍。
  - 矛盾双保留 + Gaps 记"需核实"：不让一个版本悄悄消失，这是防"报告自嗨"的关键——报告可以暂时错，不可以静默改写历史。
  - 深层防退化：报告更新是"主动选择留存"而非"被动压缩"，每步 extract_findings 决定什么进报告——这跟 ReSum 摘要的有损压缩是本质区别（博客05 的对比论证）。
- **易踩坑**：不能只答"设上限"——上限只是三道保险之一；也不能漏说"报告更新动作由模型做，训练/提示要专门约束"这条工程细节。
- **回看标本**：本册 §1.3-L3；博客05/07；arXiv 2509.13309（机制出处）。

#### H29. 怎么判断该停止研究？max_steps 够不够？

- **第一句**：max_steps 只是硬预算，回答"最多花多少"，不回答"是否完成"；真正的停止条件是三个可计算信号——信息增益衰减、子问题覆盖率、预算水位，而且要放在循环外的守卫代码里，不交给模型自觉。
- **要点**：
  - 三信号参数【业界·番外01】：连续 3 步新信息占比 <8% 收敛；"两个独立来源确认"覆盖八成；硬顶 40 步 + 成本上限。实测平均步数 31→19，砍掉的是空转。
  - 到顶行为分"收敛"与"截断"：收敛 = 强制收尾模式（新方向不放行、query 锁死未确认清单、单源补证两轮不成标"未验证"），交付边界清楚的半成品；截断 = 断在半截——我们标本的 max_turns 触顶走 final summary 带证据收束，方向一致但没有收敛模式的 query 管控。
  - 无进展检测三指纹（动作/观察/状态差）抓的是"话都对但一步没往前走"；注意幂等重试是合法重复，不能误杀。
  - 标本差距的实证：失败题 c61d22de 步数没用完但 43 步无答案——正是"没有增量维度停止条件"的形态。
- **易踩坑**：不能说"我们实现了增益衰减检测"；参数 8%/40 步是业界值，落地要按任务族重标定。
- **回看标本**：05 册 §3.3（触顶收束）；本册 §1.3-L4；番外01/03。

## §2 重难点二：搜索工具的稳健与效率

### 2.1 问题本质

- 第一句："工具能调通是 Demo，工具调稳才是产品"【业界·博客02】。Deep Research 的门槛不在那个循环，在循环外面的所有东西【业界·合集】。
- 标本现状口径（链 04 册 F18）：MCP 单次调用成功率 **~98%**——定义为"未超时 + 有可解析、非空、能进下一轮 LLM 的内容"，≠ 任务做完率、≠ 答案准确率；剩余约 2% 归因外部源偶发（联网/scrape/索引超时）+ 模型写错 server_name/tool_name/参数。
- 反模式三连（面试官的下马威，全来自博客翻车现场）【业界】：
  1. "搜索偶尔超时？我们加了重试"——被三连追问击穿：重试几次？间隔多久？空结果也重试吗？死循环有监控吗？（博客02）
  2. "用 BeautifulSoup 抓了正文啊"——5000 字网页 3000 字噪声（侧边栏 + 评论 + 推荐），模型被评论区带偏 4 步（博客03）
  3. "做了 URL 去重"——同一篇稿子 36kr/知乎/公众号/爬虫站四个 URL 各一份，Agent 以为有 4 个独立来源；抽样 40% 内容重叠全逃过 URL 去重（博客06）
- 与主题 A 的接口：工具层是上下文的进水口——**工具最重要的职责不是"取回信息"，是"过滤噪声"**【业界·博客03】；"把每一次工具调用的结果都当成可能是垃圾的，直到你验证了它不是"【业界·博客02】。

### 2.3 逐环展开

#### R1 query 层（前置：搜什么、防重复）

**业界谱系**（出处：博客02、07、番外01/03）：

- **LoopDetector 重复搜索检测**：embedding 余弦相似度，window=5、threshold=**0.88**、历史只留最近 20 条；只对 search 工具检测（Visit/Python 不检测）。阈值是经验值：太低误报（"固态电池"vs"锂电池"被判重）、太高漏报（"苹果2023财报 PDF"vs"Apple annual report 2023"≈0.86）。效果：有效步骤比例 **73%→91%**【业界·博客02】。
- **差异化 hint（命中重复后不执行工具，把提示作为 tool 消息注入）**：按上次 `result_quality` 分三型——空结果 → "从对立面、上位概念或案例来源切入"；垃圾内容 → "直接访问官网/权威媒体 URL"；一般 → "从子问题出发设计搜索词"。设计洞察：**只说"你重复了"，模型倾向微调关键词；告知"上次这方向搜不到"，模型才真正换角度**【业界·博客02】。
- **query 归一化指纹**：大小写/空白/排序/默认值归一化后取哈希，抓"字符串变了状态没变"的变体循环（`"agent memory update"` vs `"agent  memory update"`）【业界·番外03】。
- **query 与信息缺口绑定**：query 只能从"未确认/缺口"清单生成 + prompt 列出已有事实禁重搜，重复率 **23%→6%**【业界·博客07】；收敛模式下新方向一律不放行【业界·番外01】。

**项目落点**：

- 【已落地】hint 文案自愈一族：server/tool 名写错时自动纠错路由（`_find_servers_with_tool` 全局找唯一含该 tool 的 server 代执行，结果加 `[Auto-corrected]` 前缀，`manager.py:276-307`）；同名 tool 多处提供时不猜、返回候选列表；YouTube/文件类 URL 附 `[NOTE]` 引导换工具（`smart_request.py:44-69`）；Wayback 结果附 "Hint: You can use the scrape_website tool..."（`searching_mcp_server.py:432`）；搜索失败文案自包含（`[ERROR]: google_search tool execution failed after 5 attempts: ...`）便于 LLM 下轮自行调整。
- 【弱落地】query 层去重只有 prompt 约束（"Avoid broad, vague, or speculative queries"，`sub_worker.py:305`），无程序化检测——同一/近似 query 重复搜索不会被拦截。
- 【演进】LoopDetector 级别的程序化去重 + 差异化 hint（§3 演进 B2）。**校准注**：0.88 是英文 query 的经验值，中文 query 的 embedding 分布不同，阈值需重标定——本地 91 条工具调用轨迹可直接做离线回放验证集。

#### R2 失败分级（中间：调不动怎么办）

**业界谱系**（出处：博客01、02、03）：

- **失败分级四类**：① 超时/网络异常 → 指数退避重试 **1s/3s/9s 最多 3 次**（单次 timeout=10s；理由：固定间隔会在服务器高压期继续打压）；② 非超时硬错误 → **不重试**直接 skip；③ 空结果（strip 后 <50 字符）→ **不重试**，返回"换表述或拆子问题"提示——"空结果重试同一个词纯属浪费步数"；④ 垃圾内容（登录墙信号词 / 正文 <100 字符 / URL 数占比 >0.15 广告页）→ 主动过滤不传给模型。垃圾导致推理跑偏的比例 **11%→3%**【业界·博客02】。
- **失败写回 Observation**：try/except 不崩，错误信息作为 Observation 写回让模型换策略，成功率 **78%→91%**【业界·博客01】；tool 消息必须紧跟 assistant 消息（OpenAI 格式硬性要求）。
- **Visit 状态对**：返回 `[访问超时]/[访问失败]` 或状态对（ok/paywall/empty/error），执行器按状态决策不 raise【业界·博客02/03】。
- 翻车案例（开场故事）：登录页被当正文塞进 Observation，模型开始推理"怎么绕过登录"，第 7–14 步 8 步里 6 步在搜"PDF 下载"变体，18 步超时报告胡说八道【业界·博客02】。

**项目落点**：

- 【已落地】搜索重试：google_search `max_retries=5`、`sleep(min(2**retry_count, 60))`（`searching_mcp_server.py:143-170`）；Serper 请求层 tenacity 3 次指数退避、只对 ConnectionError/Timeout/HTTPError 重试（`miroapi_serper_mcp_server.py:42-48`）。
- 【已落地】抓取降级链（标本最有话说的一段，详解 04 册 §2.5）：Jina Reader → Serper scrape → requests+MarkItDown 三级 fallback（`smart_request.py:57-105`）+ 外层 3 次整体重试；Jina 422 特判提示"URL 可能是文件，请用其它工具/沙箱"；scrape 报 unhandled errors 时 MarkItDown 兜底（`manager.py:485-510`）。
- 【已落地】硬超时：单次工具执行 `@with_timeout(900)`（`manager.py:254`），超时抛 TimeoutError 写回对话。
- 【演进】失败分类——现状是**无差别指数退避**（空结果也会重试 5 次），博客的分级哲学（空结果不重试、垃圾主动过滤）未实现（§3 演进 B1）。

#### R3 内容质量（中间：回来的能用吗）

**业界谱系**（出处：博客03、06）：

- **域名黑名单**：百度知道/搜狗问问/360 问答/贴吧/公众号（公众号抓不到原文），垃圾来源访问率 **18%→5%**；黑名单需持续养，垂直场景（只搜学术库）不必上【业界·博客03】。
- **snippet 打分**：<50 字符 0.1 分、营销词（"点击查看/立即购买"）0.2、含数字 +0.1、技术词（"方案/实现/研究/数据"）每个 +0.05 上限 +0.3、**<0.3 丢弃**；返回自然语言结构化文本而非原始 JSON（省 token 且模型读得顺）【业界·博客03】。
- **三层去重与可信度**：见 §1.3-L1（同一批手段，此处不重复）——150→52 条、幻觉率 14%→3%。
- **Scholar 排序**：按相关性不按引用数（反直觉点：Attention is All You Need 引用最高但不讲"改进方法"）；打分 = 标题命中 ×0.5 + 摘要命中 ×0.3 + 近 2 年 +0.15/近 5 年 +0.05 + 开放全文 +0.05；**带上年份/venue/被引数**，工具不替模型下可信结论，摆元数据让模型自己掂量【业界·博客03】。
- **返回格式工程**：Python 工具错误只回 stderr 最后 5 行（完整堆栈会把模型带偏，只回 5 行改代码成功率反而高）；输出截断 2000 字符【业界·博客03】。

**项目落点**：

- 【已落地】反作弊屏蔽：HuggingFace datasets/spaces 一律拒绝（搜索结果剔除 `miroapi_server.py:58-66`、scrape 前置 `manager.py:93-104`、事后结果替换 `manager.py:395-396`）——这是防 benchmark 数据泄漏的质检手段；URL 规范化 `decode_http_urls_in_dict`（safe_unquote 保护保留编码，`url_unquote.py:36`）。
- 【已落地·弱】富结果裁剪（REMOVE_SNIPPETS 等 env 开关，默认 false）；正文抽取后**无智能压缩**——`scrape_website` 全文进上下文，只靠 `OutputFormatter` 100k 字符硬截断（`io_utils.py:119-136`，注释自评 ≈25k token）；wiki 全文分支留着 `# TODO: Context Engineering Needed`（`searching_mcp_server.py:220-221`）。
- 【演进】段落级相关性过滤 + 三层去重 + 可信度分层（§3 演进 A1/B3）。

#### R4 效率（后置：少花钱多办事）

**业界谱系**（出处：博客06、11、番外02）：

- **过滤流水线并行化**：2.3s→0.8s（可信度打分与 MinHash 并行、语义去重批量 Embedding、LLM 交叉验证不可并行）；各步耗时表：URL <10ms、MinHash 320ms、可信度 410ms、语义 580ms、交叉验证 980ms【业界·博客06】。
- **轻量打分替代 LLM Judge**：BoN 打分用启发式（答案长度/引用数/步数/完成状态），打分零 token 成本【业界·博客11】；给不同采样不同搜索约束制造多样性（第 2 个必须先用 Scholar）。
- **防重复就是省钱**：有效步骤 73%→91%（R1）、重复率 23%→6%（L3 缺口驱动）、平均步数 31→19（L4 停止信号）——三处数字同一逻辑：空转步是纯烧钱（8k–12k token/步）。
- **并发规模参考**：subagent 并发上限 20 超限报错不排队；简单事实查证 1 agent + 3–10 次调用；对比类 2–4 subagent × 10–15 次；复杂研究才上 10+【业界·番外02】。

**项目落点**：

- 【已落地】prompt cache + 防跨会话缓存污染：Anthropic ephemeral cache 打在 system + 末条 user（`claude_openrouter_client.py:373`）；同时每条 user 消息加随机 `[msg_xxx]` 前缀防跨会话缓存命中（评测公平性，`orchestrator.py:172-190`）。
- 【已落地·评测侧】多题并发 `Semaphore + gather(return_exceptions=True)`（`common_benchmark.py:377`；`max_concurrent` 按 benchmark 配置浮动：default 5 / gaia-validation 10 / text-only 3——05 册"默认 3"是 text-only 口径）；**Agent 内工具执行串行**（`orchestrator.py:1124` 顺序 await）。
- 【演进】结果缓存（同 URL 重复 scrape 会重新请求——标本无任何结果层缓存）；hybrid 双路并行融合（现为顺序执行）。

#### R5 执行控制（取消 / 幂等 / 终态一致性）

**业界谱系**（出处：番外05、06、03）：

- **取消协议**：反模式——接口把状态改成 `cancelled` 就返回"已取消"，执行线程读不到字段继续跑，最后一条 UPDATE 把 cancelled 覆盖回 succeeded。正解：`cancel_requested_at` 标记 + 事件同事务；页面显示"**正在停止**"，Worker 在**工具调用前、返回后各设检查点**，确认后才写"已取消"；已发出的远端调用无法凭字段中断，承诺只能是"尽快停止后续处理"；终态竞争用 `BEGIN IMMEDIATE` 写事务 + 取锁后重读再决定；验证指标看调用计数（取消后回复生成 0 次）而非状态字段。
- **幂等创建**：反模式——"创建前先查一下"在并发下双双查空建两条任务（Barrier 实验证实）。正解：`UNIQUE(org_id, idempotency_key)` 唯一约束兜底 + 冲突后回滚回读返回原 run_id；`input_hash` 二次校验（同键不同输入返 409——客服改了订单号却沿用旧键）；**不拿输入哈希当幂等键**（同输入重生成是新的提交意图）；Run 与 created 事件同事务。
- **分工**：循环检测管停滞，幂等键管重复副作用，缺一不可；相同调用可能是合法重试不能误杀【业界·番外03/06】。
- **无进展状态分型**：completed / needs_input / risk_gate / no_progress / 带证据降级——不全压成 failed（详见 §1.3-L4）。

**项目落点**：

- 【部分落地】会话级取消：WebSocket 断开 cancel `running_task`（`server/session.py:29-37`）；评测并发用 Semaphore；无显式幂等键（`call_id` 只做 tool result 配对，`orchestrator.py:1199`）。
- 【演进】工具调用前后检查点式取消确认、任务级幂等键——产品化（Java 网关建任务）时幂等创建是必答题（02 册集成设计的服务端语境正好用得上番外06 的方案）。

### 2.4 口头答案（定时模板 ≈ 100 秒）

**先说失败分级（30s）**：
"工具稳健性的第一步是把失败分类，不能一句'加了重试'。业界成熟做法分四类：超时用指数退避 1、3、9 秒最多三次——固定间隔会在服务器高压期继续打压；硬错误不重试直接跳过；空结果不重试——重试同一个词纯属浪费步数，直接提示模型换表述；最隐蔽的第四类是工具成功返回但内容是垃圾，登录墙、广告页，必须主动检测过滤，不然模型把垃圾当信息。我们标本落地的是搜索五次指数退避、抓取三级降级链 Jina、Serper、requests 兜底、单次工具九百秒硬超时，MCP 单次调用成功率百分之九十八。"

**再说检测了什么（30s）**：
"第二道是 query 层的防重复：embedding 相似度检测重复搜索，阈值零点八八，业界数据是有效步骤从七成三提到九成一。关键是命中后不能只说'你重复了'——要按上次失败原因给差异化提示：上次空结果就从对立面、上位概念切入，上次是付费墙就直接访问可信 URL。我们标本在这一层落地的是自动纠错——模型写错工具名，harness 全局查找唯一匹配代执行并注明 Auto-corrected；失败文案自包含，让模型下一轮自己调整。程序化去重是演进项。"

**然后说内容质量与效率（30s）**：
"第三道是内容质量：URL 去重不够——同一篇稿子四个 URL 各一份，业界做法三层去重：URL、MinHash 内容指纹阈值零点八、语义向量零点九二，一百五十条筛到五十二条信息量近无损；再加可信度三层——域名名单、信号特征模型、双独立来源交叉验证，幻觉率从百分之十四压到三。效率上过滤流水线并行化，两秒三压到零点八秒。我们标本落地了反作弊屏蔽和 URL 规范化，正文过滤和语义去重是演进方向——我实测过，膨胀主要是少数大网页抓取驱动的，所以正文过滤优先级最高。"

**最后说选型逻辑（15s）**：
"工具设计四个原则：简单、可靠、确定性、可观测。方案轻重看调用频率——高频的正文过滤用关键词重叠就够，跨语言才升级 embedding；把贵的方案留给真正需要它的场景。"

### 2.5 追问详解（I30–I34）

#### I30. 空结果为什么不重试？重试策略到底怎么分级？

- **第一句**：重试只对"可自愈的失败"有意义——超时和网络抖动重试有意义；空结果是搜索引擎明确告诉你"这个方向没有"，重试同一个词只会再烧一步预算。
- **要点**：
  - 分级表：超时 → 指数退避（1s/3s/9s×3，退避理由是避免高压期继续打压）；硬错误（认证失败/参数错）→ skip 不重试；空结果（<50 字符）→ 不重试 + hint"换表述或拆子问题"；垃圾内容 → 过滤 + hint"直接访问可信 URL"。
  - 空结果的正确响应是**改 query**而不是重发——这把 R2 和 R1（差异化 hint）连起来了。
  - 标本现状的诚实口径：google_search 是无差别 5 次退避（空结果也重试），分级是演进项 B1——改在 MCP server 内部，不动主循环。
- **易踩坑**：不能说"我们做了失败分级"；也要防反问"空结果会不会是引擎抖动"——答"短退避一次可以接受，但连续空结果必须转 hint，用 hint 成功率而不是重试次数兜"。
- **回看标本**：`searching_mcp_server.py:143-170`；博客02 §一。

#### I31. URL 去重为什么不够？MinHash 阈值 0.8 怎么定的？

- **第一句**：URL 去重只能抓"同一条链接"，抓不住"同一篇内容的四个转载 URL"——抽样里 40% 的内容重叠全部逃过 URL 去重，Agent 误以为有四个独立来源。
- **要点**：
  - MinHash 细节：字符级 3-gram shingle（抗标题改写）、num_perm=128（精度/成本业界经验点）、MinHashLSH 分桶近似 O(n) 可线上实时；Jaccard 阈值 0.8 的依据：转载稿通常有 5–20% 修改，设 1.0 漏报、0.5 会误删独立文章——0.8 是这两类错误的平衡点。
  - 三层是递进的：URL（零成本）→ MinHash（抓转载）→ 语义 embedding（抓改写），150→130→75→52。
  - 保留策略：同组保留发布时间最早的一篇（原始来源）——去重同时把"溯源"做了。
  - 标本现状：仅 hybrid 融合层有 URL 级 `_dedupe`（`fusion.py:4`），主搜索路径无内容级去重【演进】。
- **易踩坑**：阈值是英文网页经验值，中英混合源需重标定；不能把"去重后剩多少"说成本项目数据。
- **回看标本**：04 册 §3.6（_dedupe 副作用：本地多 chunk 共用 source_uri 会撞车只剩 1 条）；博客06。

#### I32. 为什么 query 去重阈值 0.88、语义去重 0.92，两个数不一样？

- **第一句**：因为比的对象不同——query 去重比的是"意图"，要容忍同义改写（阈值低些防漏报）；内容去重比的是"同一篇文章"，同话题不同文章天然就有 0.8–0.85 的相似度，阈值必须更高防误杀。
- **要点**：
  - 0.88 的标定逻辑（博客02）：太低误报——"固态电池"vs"锂电池"被判重；太高漏报——"苹果2023财报PDF"vs"Apple annual report 2023"只有约 0.86。window=5 + 历史只留 20 条，控制的是"近重复"不是全局去重。
  - 0.92 的标定逻辑（博客06）：同话题不同文章的 embedding 基线 0.8–0.85，低于 0.9 的阈值会把"同话题的独立视角"删掉——去重的目标是"删转载保视角"。
  - 方法论：阈值不是拍脑袋，是拿 badcase 对标定的——两个 badcase 一左一右夹出阈值。我们落地时应该拿本地 91 条工具调用轨迹做同样的离线回放标定（中文 query 的分布和英文不同）。
- **易踩坑**：不能背数字不背理由——面试官追问"0.87 行不行"要能答"行，但会多漏报 X 类 case，这是精确率/召回率的取舍"。
- **回看标本**：本册 §2.3-R1；博客02/06。

#### I33. hint 为什么不能只说"你重复了"？

- **第一句**：因为模型听到"你重复了"的第一反应是微调关键词——把"苹果财报"改成"苹果财务报告"，方向没变；hint 必须携带"上次为什么失败"的信息，模型才会真正换角度。
- **要点**：
  - 差异化 hint 三型的本质是给模型一个"新的搜索算子"：空结果 → 从对立面/上位概念/案例来源切入（改变搜索空间）；垃圾 → 直接访问可信 URL（改变工具选择）；一般 → 从子问题出发重新设计（改变问题分解）。
  - 这是"执行器引导 LLM 自愈"的通用模式，标本里同族设计：server 名写错自动纠错路由（Auto-corrected 注记让模型知道发生了代执行）、Jina 422 提示"用其它工具/沙箱"、失败文案自包含带完整错误上下文——都是把"怎么修"的信息喂回给模型，而不是只报错。
  - hint 放 tool 消息注入、不执行工具——省一次真实调用。
- **易踩坑**：不能说"我们实现了 LoopDetector 的差异化 hint"——标本落地的是纠错/引导类 hint，重复检测类是演进项。
- **回看标本**：`manager.py:276-307`（auto-correct）；博客02 §二。

#### I34. 你们 web_retriever 没有重试，google_search 却有 5 次，为什么不对称？（短板题）

- **第一句**：这是真实的薄弱点，我直说——`web_retriever.search_web` 是一次性请求，无 key 或异常一律静默返回空列表，和 google_search 的五次退避不对称；它是 hybrid 链路的短板。
- **要点**：
  - 代码事实：`web_retriever.py:17-28` 一次请求失败返回 `[]`，无重试；设计意图是"Web 空召回 ≠ 整次 Hybrid 失败"（本地路权 0.6 兜底），降级哲学没错，但**静默空列表**让上层分不清"没搜到"和"搜挂了"。
  - 危害链路：空列表进融合层 → web_hits=0 → 若本地也无命中，Agent 拿到全空结果还以为"真没有信息"——这正是 01 册 P7"空检索被当成有效证据"的形态之一；靠 `hybrid_search_observability` 的 route/web_hits metadata 才能排查出来。
  - 修法（演进）：a) 对齐 google_search 的退避（tenacity 三次就够，web 路权 0.4 不值得五次）；b) 返回结果带状态码/原因，空召回与失败分开（对应博客02 的状态对思想）；c) 长期看 hybrid 双路并行化时重试和超时预算统一设计。
- **易踩坑**：不要辩护"静默返回 [] 是优雅降级"——降级可以，但**状态要诚实**；这道题答好的标志是主动给出修法和优先级。
- **回看标本**：`src/retrieval/web_retriever.py:13-28`；04 册 §3.4（Web 空召回口径）；01 册 P7。

排序判据三条：① 改动面小（不动主循环优先）；② 直击实测瓶颈（重尾 scrape、收束失败）；③ 可离线验证（本地 15 条轨迹 + 91 条工具结果可做回放集）。

### 3.1 主题 A 演进路线（上下文）

| 优先级 | 演进项 | 改动面 | 为什么是它 | 验收 |

### 3.2 主题 B 演进路线（搜索工具）

| 优先级 | 演进项 | 改动面 | 为什么是它 | 验收 |
| --- | --- | --- | --- | --- |
