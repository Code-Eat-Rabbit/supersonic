## 0. L0 事实库（一处定义）

### 0.1 职责与来源

| 项 | 口径 |
|----|------|
| Owner | 我从 0-1 搭建深度研究服务（工程 harness：编排运行时、工具接入、服务化、追踪与熔断） |
| 算法博士后 | **咨询**：Prompt 调优建议、测评集怎么选/怎么跑——不主导实现 |
| 起源 | 业余阿里云 Research Agent 比赛 → 魔改接入 Data Agent（双层解读、对接 Java 查数主链路、领域知识库） |
| 复习标本 | `miro-flow-solution`：把工程细节摸熟；面试不主动对比 MiroFlow，也不把开源框架说成「我发明的」 |

### 0.2 产品定位

- **默认**：描述性解读（<2s）——Java `DataInterpretProcessor` 基于查数结果写 `textSummary`
- **可选**：深度研究——多步联网交叉验证 + 归因；失败/超时 → **静默回退**描述性解读，不阻断主链路
- **触发**：有 `textSummary` 后，结果区引导「想要对结果做深度研究吗？」；用户点击才启动（非默认全开、非自动路由）
- **通信**：Java 为网关——前端只传当前 `queryId`；Java 组装上下文后 REST 调 Python 异步 job；前端轮询 Java 取终态；成功短报告落库挂同 `queryId`

### 0.3 硬指标

| 指标 | 取值 | 说明 |
|------|------|------|
| GAIA-165 | 整体 53%（L1 68% / L2 47% / L3 19%）；SOTA ~80% | 简历已写 |
| MCP 工具调用成功率 | ~98% | 简历已写；定义见 L1-F |
| 超时上限 | **临时建议 660 秒（11 分钟）** | 最慢可观测样本 × 1.2 后向上取整；`n=3`，非正式 P95 / SLA |
| 端到端耗时（当前可观测下界） | **约 ≥138 / ≥262 / ≥545 秒；中位约 ≥262 秒（4.4 分钟）** | 历史样本 `n=3`，均缺少可信完成标记；只能说明典型可观测耗时为数分钟级 |
| 失败/回退率 | **不写入、不主动交代** | 被追问只讲机制 |

### 0.4 诚实边界

- 53% 是有参照的真实位置；短板在 Level 3 多步推理
- 价值在：跑通链路 + 工程化（追踪/熔断/断点续跑/不挡主链路），不是算法创新
- 这是 harness 工程；Prompt/评测有博士后建议

## 2. L1 追问链

### A. GAIA：53% 与 SOTA 对比

#### A1. Level 3 差到什么程度？典型失败是什么？

- **第一句：** Level 从 68% 降到 47%、再到 19%，衰减主要集中在需要多步工具调用、证据交叉验证和最终归纳的复杂题；典型情况是前一步检索偏了，后续推理继续放大偏差。
- **要点：**
  - L1 多为较短链路，68% 说明基础检索和回答链路可用；L2、L3 增加约束、工具跳数和证据冲突后，错误会累积。
  - 典型失败不是某一个工具完全不可用，而是多跳过程中选错信息源、漏掉约束，或没有完成跨来源一致性校验。
  - 面试时先讲失败模式，不虚构某道具体题；若要举例，可用「先定位实体 → 查多个来源 → 对齐时间口径 → 计算并归纳」这类链路说明。
- **易踩坑：** 把 L3 19% 包装成「模型偶尔波动」，或临场编造一个无法复盘的 GAIA 原题。
- **回看标本：** `miro-flow-solution/main.py` 的 `common-benchmark` / `trace` 入口；`miro-flow-solution/common_benchmark.py` 的 pass@k 尝试、判分和日志记录。

#### A2. 与 SOTA 80% 的差距在哪里？

- **第一句：** 差距不在单点功能，而在复杂任务上的系统能力：模型推理、工具选择、跨来源校验和编排纠错共同决定上限，Level 衰减说明多步链路是主要矛盾。
- **要点：**
  - 68% → 47% → 19% 表明任务越复杂，差距越明显；不能只归因于模型，也不能只归因于工具稳定性。
  - SOTA 约 80% 是定位坐标，不是宣称接近 SOTA；我的结果来自单人业余时间完成的工程实践，真实价值是跑通评测与服务链路。
  - 改进优先级是先增强失败可观测性和断点续跑，再基于错误样本优化工具选择、证据校验与 Prompt。
- **易踩坑：** 说成「换更强模型就能追平」，或把复习标本中的编排能力说成自己的算法发明。
- **回看标本：** `miro-flow-solution/main.py` 用 `common-benchmark` 批量评测、用 `trace` 单题追踪；`miro-flow-solution/common_benchmark.py` 记录每次 attempt 与 judge 结果，支持按错误样本复盘。

#### A3. GAIA 最常见的失败类型是什么？

- **第一句：** 我的排序是多跳推理失败最多，其次是工具链中断，再其次才是超时；历史 `n=3` 样本只能观察到约 ≥138 / ≥262 / ≥545 秒的运行时长下界，因此当前临时超时建议是 660 秒，而不是正式 SLA。
- **要点：**
  - 多跳推理失败包括漏约束、错误信息继续传播、多个来源无法对齐，以及计算或归纳阶段出错。
  - 工具链中断包括检索无结果、返回结构异常和中间调用失败；它与「答案推错」要分开统计。
  - 超时是结果状态，不等于根因；应结合 trace 判断卡在检索、工具调用还是推理循环。
  - 评测支持 pass@k，并扫描已有日志：已有完整答案和判分结果可直接复用；缺失或执行失败的 attempt 才重跑，实现断点续跑。
- **易踩坑：** 主动报未经实测的超时阈值，或把所有未完成任务都归为超时。
- **回看标本：** `miro-flow-solution/common_benchmark.py` 的 `scan_latest_attempt()` 加载已有 log；`run_single_task()` 对 pending / run_failed 续跑，并在 pass@k 命中后提前停止。

### B. 语言切换：Java → Python

#### B4. 为什么 Agent 层改用 Python？

- **第一句：** 这是按边界选技术栈：LLM、MCP、多 Agent 编排和检索生态用 Python 集成成本更低；稳定的 Java 查数主链路不动，避免为追生态重写核心业务。
- **要点：**
  - Python 侧负责深度研究的编排运行时、工具接入、评测与服务化；Java 侧继续负责成熟的查数链路。
  - 独立微服务隔离依赖和故障域，深度研究失败时可回退描述性解读，不影响主请求。
  - 技术选型依据是生态成熟度、迭代效率和边界清晰度，不是「Python 天生比 Java 适合所有 AI 场景」。
- **易踩坑：** 贬低 Java 的 LLM 能力，或说成整个 Data Agent 都迁移到了 Python。
- **回看标本：** `miro-flow-solution/server/app.py` 以 FastAPI 暴露产品服务；`miro-flow-solution/server/bridge/runner.py` 将服务请求适配到 Agent pipeline。

#### B5. Java 与 Python 服务怎么通信？

- **第一句：** 描述性解读在 Java execute 后由 `DataInterpretProcessor` 写出 `textSummary`；深度研究在有总结后由结果区引导触发，前端只传当前 `queryId`，Java 组装上下文经 REST 把异步 job 交给 Python，前端轮询 Java 取终态；成功则控字数的短报告落库挂同 `queryId`，失败静默保留原总结。
- **要点：**
  - **触发：** 问数成功并完成描述性解读后，结果区展示「想要对结果做深度研究吗？」。用户点击 = 启动深度研究，而不是输入栏默认模式、也不是系统自动开。
  - **组装 message（服务端为准）：** 前端不传大表，只传 `queryId`（+ chatId/agentId/`traceId`）。Java 按该 `queryId`（当前这条结果，不是会话里模糊的「随便最近一次」）从 `ChatQueryDO` 取出原问题、`textResult`/`textSummary`、指标与维度，截断后拼成发给 Python 的 `task` + `context`。
  - **跨服务 REST：** Java `POST` Python `/v1/research/jobs`，等 Python **SQLite `INSERT PENDING`（落库即入队）**后回 `200` + `jobId`；**不**在 execute 请求线程里同步等待数分钟。独立 worker 扫表跑 Main-Sub Agent；Java 作为网关持有 `queryId↔jobId`。
  - **回传：** 前端轮询 Java（如 `GET /api/chat/research/{jobId}`），心智对齐现有 `getExecuteSummary` 伪流式轮询。进行中仍展示表格 + `textSummary`；成功写入短报告字段（控字数，可进主表）；失败/超时不覆盖 `textSummary`，原因进 ELK（同 `traceId`）。
  - **和标本的关系：** `miro-flow-solution` 的 WebSocket 是人对 Research UI 的产品入口；**Java↔Python 主协议是 REST 任务 API**，不要把 WebSocket 说成跨语言唯一通信方式。
- **易踩坑：** 说前端把整表 POST 给 Python；说 execute 线程同步 await 深度研究；把标本 WebSocket 说成 Java-Python 主通道；失败时覆盖已有 `textSummary`。
- **回看标本：** SuperSonic `DataInterpretProcessor`（`textSummary` + `getExecuteSummary` 轮询）；`ChatQueryServiceImpl.execute()` 的 Processor 链；`miro-flow-solution/server/bridge/runner.py`（任务执行与结果产出，对接时改为 REST job 契约）。

#### B6. 技术栈切换是谁决策的？现在还会这样选吗？

- **第一句：** 我是深度研究服务的 0-1 owner，负责技术选型和落地；博士后主要咨询 Prompt 调优与评测方法。现在重选，我仍会保留 Java 主链路、Python Agent 微服务的边界。
- **要点：**
  - 我的职责覆盖编排运行时、工具接入、服务化、追踪和熔断；博士后提供 Prompt 与测评集方面的建议，不主导工程实现。
  - 继续选 Python 的前提是 Agent 生态和快速试验仍是主要矛盾；如果团队治理成本上升，会优先收紧 API 契约、部署和可观测性，而不是先重写语言。
  - 这套实现源于个人比赛实践后接入业务；标本用于对齐工程细节，不把 MiroFlow 或开源框架说成「我发明的」。
- **易踩坑：** 把咨询关系说成共同开发，或把个人技术选型描述为团队既定方案。
- **回看标本：** `miro-flow-solution/server/app.py` 负责会话、异步任务和错误回传；`miro-flow-solution/server/bridge/runner.py` 负责配置、pipeline 组件创建、执行与结果流式输出。

### C. 双层解读的边界

#### C7. 同一份查询结果，两层分别输出什么？

- **第一句：** 描述性解读只回答表内「是什么」，把查询结果整理成趋势、对比和异常点；深度研究再引入外网与知识库证据做交叉验证，回答「为什么」，但会明确证据和不确定性。
- **要点：**
  - 以「比亚迪 2024 年净利润 300 亿」为例，描述性解读只基于结果表说明金额、同比变化、时间口径及与表内其他指标的关系，不自行补充原因。
  - 用户触发深度研究后，系统才会检索财报、行业资料、政策与知识库，核对数据口径，并从销量、价格、成本或政策等维度归因；没有证据支持的因素不写成确定结论。
  - 两层复用同一份查数结果作为事实起点，差异不在文案长短，而在证据范围与回答目标。
- **易踩坑：** 让描述性解读凭模型常识猜原因，或把深度研究说成「把基础摘要写得更长」。
- **回看标本：** `miro-flow-solution/src/core/pipeline.py` 的 `execute_task_pipeline()` 接收任务描述并产出最终报告；外部证据由 Agent 工具链补充，不改变上游查数结果。

#### C8. 这条边界为什么要由产品明确划定？

- **第一句：** 这是主动的产品决策：用默认描述性解读守住低延迟和高可用，再把联网、交叉验证与归因带来的延迟和失败面留给确实需要「为什么」的少数查询。
- **要点：**
  - 多数用户查完只需要快速确认「是什么」，没有必要为每次请求支付深度研究的等待和资源成本。
  - 深度研究增加联网搜索、知识库召回、多步工具调用和汇总，链路越长，延迟与失败面越大。
  - 明确边界还能约束答案可信度：表内事实和外部归因分层呈现，用户知道哪些来自数据、哪些来自外部证据。
- **易踩坑：** 引用未经验证的耗时、失败率或需求占比，或把双层设计解释成技术能力不足后的被动妥协。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 的主循环会经历多轮工具调用，并受 `max_turns` 约束，说明深度链路天然比表内摘要有更多延迟与失败节点。

#### C9. 用户如何触发？系统会不会自动开启？

- **第一句：** 不会自动开。有 `textSummary` 之后，在结果解读区放引导「想要对结果做深度研究吗？」；用户点击后，才按当前 `queryId` 组装上下文并 REST 启动 Python 深度研究。
- **要点：**
  - 默认先交付表格 + 描述性解读，保证每次查数都有即时可用答案。
  - 引导出现在**总结下方**，绑定**当前这条**结果的 `queryId`，避免挂到会话里错误的「最近一次」。
  - 点击即「确认启动」：前端只传触发信号，Java 负责取数组装与创建 job；不把模糊的「帮我分析」自动路由成高成本 Agent。
  - 输入栏常驻「深度研究」模式更适合开放域调研（可选二期）；**结果归因**以本引导为主入口。
- **易踩坑：** 说成意图识别自动开深度研究；说前端自己拼长 message 直打 Python；把引导按钮和输入栏模式混成同一条链路却讲不清绑定哪次查数。
- **回看标本：** SuperSonic `DataInterpretProcessor` / `ExecuteItem` 的 `textSummary` 展示位；B5 中的 Java 网关 + 轮询契约；`miro-flow-solution` 仅作 Agent 执行侧参照。

### D. 失败回退

#### D10. 怎么定义失败？中间一步失败就整单失败吗？

- **第一句：** 失败看最终交付而不是单步状态：当前达到临时建议的 660 秒（11 分钟）上限，或重试、换工具、汇总已有证据后仍没有可用的深度报告，才触发回退；中间一次工具或子任务失败不等于整单失败。660 秒仅依据 `n=3` 的可观测时长下界保守估算，不是正式 P95 / SLA。
- **要点：**
  - 单步异常先在 Agent 内部消化：记录错误、尝试备选来源，其他子任务仍可继续，最终报告也可基于可验证的已有证据收束。
  - `max_turns` 到达代表停止继续扩张搜索，不是立刻丢弃所有结果；标本会转入 final summary，尝试把已有上下文汇总成最终答案。
  - 只有超时或最终报告为空、报错、缺少足够证据而不可用时，产品层才判定深度研究失败并回退。
- **易踩坑：** 把任一工具偶发失败等同于整单失败，或把 660 秒临时建议说成已经稳定验证的正式 SLA。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 达到 `max_turns` 后标记 `task_failed` 并继续生成 final summary；`miro-flow-solution/src/core/pipeline.py` 在编排正常返回时标记 `completed`，在 `except Exception` 捕获异常时标记 `interrupted`，最终统一落盘。

#### D11. 回退后用户是否感知？为什么静默处理？

- **第一句：** 采用静默回退：用户始终保留已经拿到的描述性解读，不弹出阻断式失败提示；成功时才把控字数的短报告落库挂同 `queryId`，失败不写大段正文覆盖 `textSummary`；原因、阶段和 `traceId` 进 ELK。
- **要点：**
  - 深度研究是查数后的增强项，失败不应把已经可用的基础答案变成红色错误，也不应阻断主链路。
  - 静默是指不打断用户，不是吞掉故障；内部仍记录超时、工具异常、汇总失败等原因，并可按阶段聚合定位。
  - 存储策略：成功短报告与 `textSummary` 并列持久化，便于刷新回看；报告控字数，可直接进主表字段。
  - 如果未来发现用户把描述性结果误认为深度报告，可改为弱提示，但当前优先保证答案连续性和操作负担最小。
- **易踩坑：** 把静默回退说成完全不记录失败，或在没有证据时声称用户一定察觉不到两层差异。
- **回看标本：** `miro-flow-solution/src/core/pipeline.py` 在 `finally` 中统一记录结束状态并保存 `TaskTracer`；异常路径同样写入错误详情，支持用户侧降级、内部可观测。

#### D12. 失败率和连续回退后的用户行为怎么看？

- **第一句：** 我不报没有线上统计支撑的失败率，也没有足够数据证明用户连续回退后的行为；能确认的产品取舍是，增强能力不稳定时优先交付可用的描述性答案，而不是让整次查数失败。
- **要点：**
  - 机制上，深度研究失败面来自联网、知识库、工具调用、轮次上限和最终汇总，日志应按失败阶段拆分，而不是只看一个总失败率。
  - 产品上，静默回退保障主任务完成，但也可能降低用户对深度能力状态的感知；需要结合后续的触发、完成、回退与再次触发数据再决定是否增加弱提示。
  - 若要评估连续回退影响，应先定义用户级漏斗和回退后的再次触发窗口，再用真实埋点回答，不能临场编造「第几次后放弃」。
- **易踩坑：** 交代未经核验的失败率，虚构连续三次回退后的用户行为，或用「用户无感」掩盖可靠性问题。
- **回看标本：** `miro-flow-solution/src/core/orchestrator.py` 记录工具失败、`max_turns` 与 summary 状态；`miro-flow-solution/src/core/pipeline.py` 统一保存任务结束日志，可为后续失败分层和用户漏斗关联提供基础。

## 3. L2 速查

<a id="l2-model"></a>
### 3.1 模型选型与效果对比（题纲模型 B4–B6、C7–C8）

| 追问 | 速答 |
|------|------|
| **模型 B4：主 / 子 Agent 是否可用不同模型？** | 可以，配置层本来就把 `main_agent.llm` 与 `sub_agents.*.llm` 分开。主 Agent 更依赖任务拆解、跨来源取舍和最终汇总，可优先强 reasoning；子 Agent 多做检索、阅读和局部归纳，可按任务难度换更便宜、吞吐更高的模型。当前读过的 GAIA 配置为保证变量可控，通常主 / 子使用同一模型；「支持异构」不等于「已经在线上异构部署」。 |
| **模型 B5：GAIA 用过哪些模型，谁最好？** | 标本保留了 Qwen（`qwen3.7-plus`）、DeepSeek（`deepseek-chat-v3.1`）、Claude（`claude-3.7-sonnet`）和 GPT（`gpt-5`）四个模型族的 GAIA 配置。未拿到同一题集、同一工具、同一预算下的完整对照结果前，不给「谁最好」的伪排名；53% 只绑定实际评测口径，不挪给其他配置。 |
| **模型 B6：reasoning 模型一定更好吗？** | 复杂多跳题通常更受益于 reasoning，但收益要用 Level 分层准确率验证，同时计入 reasoning token、延迟和超时；链路短的 L1 题可能不值得支付同样成本。应做同配置消融，而不是凭模型标签下结论。 |
| **模型 C7：三类模型怎么选？** | Embedding 看召回与领域覆盖，Chat-BI LLM 看低延迟、结构化输出和成本，Research Agent LLM 看复杂推理、工具调用稳定性和长上下文；三者目标函数不同，不能用一个榜单统一决定。 |
| **模型 C8：预算变化怎么调？** | 预算翻倍先升级主 Agent 或只给 L2 / L3 难题启用强 reasoning；预算砍半先下调可并行的子 Agent、简单任务模型或 pass@k 次数，保留主 Agent 的拆解与最终证据校验能力。 |

**性价比一句话：** 不追求全链路堆最强模型，而是「强模型守主 Agent 和难题上限，便宜模型承接可验证的子任务」；Qwen / DashScope 可作为低接入成本基线，但没有同口径价格—效果数据时不宣称它是性价比冠军。
