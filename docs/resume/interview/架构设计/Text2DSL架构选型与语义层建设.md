## 一、为什么选择 Text2DSL，而不是其他架构

Text2DSL 选择的理由可以收成一句：企业问数的主要失败，是业务口径没有被编译成可执行约定，而不是模型不会写 SQL 语法。让模型直接产出物理 SQL，等于让它每次重新发明指标、关联和权限；Text2DSL 把这三件事挪到语义层，模型只负责把自然语言映射到已治理的指标、维度、时间和筛选。

### 1.1 问题出在 SQL 生成之前

「上季度华东区重点客户的净销售额」在语法上是完整的，在组织里却是一组未说出口的约定：季度按自然年还是财年，华东按注册地还是销售归属，重点客户按合同分级还是手工名单，净销售额扣不扣退货和返利。这些约定不在大模型的训练数据里，散落在指标文档、ETL、报表和人口述中。

因此会出现一种比系统崩溃更麻烦的结果：SQL 能执行、行数看起来合理、图表也能画出来，口径却是错的。材料里把失败大致拆成 schema 选错约 40%、业务口径错误约 25%、SQL 结构错误约 20%、方言与权限等工程问题约 10%。前两项都是知识没有精确交给模型。Text2SQL 继续优化提示词和推理，改善的是「给定 schema 之后怎么写」；Text2DSL 改变的是模型被允许写出什么。

### 1.2 其他路线各自解决哪一层，以及停在哪里

| 路线 | 模型做什么 | 适合什么 | 企业问数里停在哪里 |
| --- | --- | --- | --- |
| 规则槽填充 | 关键词命中预置模板 | 问法封闭、指标很少 | 覆盖随问法和表数线性膨胀；同义词、缩写、部门黑话都要手写规则 |
| Seq2Seq Text2SQL | 把问句翻译成 SQL | WikiSQL 这类单表 | Spider 上长期约 50%–60% EX。学到的是问句模式和 SQL 模式的统计关联，schema 一脏（`revenue` 变成 `c_rev_x7`）关联就断 |
| 朴素 LLM Text2SQL | 一次看完 schema 并写出 SQL | 单表、小宽表、口径简单；使用者是懂表的分析师 | 三个天花板：几百张表塞不进上下文；JOIN / 聚合能执行但语义错；「销售额」含税与否从表名推不出来 |
| Schema Linking + Few-shot + 自校正 | 先缩 schema，再模仿样例，再按执行结果改 | 学术库和中等规模分析 | 仍由模型产出物理 SQL。样例和当前 schema 版本不一致时，范文会教错 |
| 多 Agent Text2SQL | Selector、Decomposer、Refiner 或多种候选再投票 | 复杂 SQL、需要探索和验证 | 提高的是生成质量，调用次数和延迟成倍增加。它没有回答「为什么必须让模型写 SQL」 |
| Text2DSL / Text2Metric | 选出指标、维度、时间、筛选、排序、TopN | 多部门共用、口径必须一致的 KPI 和报表 | 覆盖限于已建模的指标和维度；临时比值、全新关系要另开长尾链路 |
| 语义层 + 本体 / 图谱 | 意图映射到对象、关系和证据，计算交给引擎 | 跨系统、要消歧、归因和溯源 | 建模成本最高。指标层回答「怎么算」，本体回答「谁和谁」，证据层回答「依据在哪」 |
| Agentic 行动 | 问数之后触发任务、通知、报告 | 指标异常要变成动作 | 前提是指标、对象、负责人、动作契约和审计都已经可信。Skill 和 Memory 只是能力表达层 |

规则时代的准确率在预定义范围内可以很高，维护成本却随 schema 涨。Seq2Seq 到 RESDSQL，是先做 schema linking 再生成骨架，Spider dev 上 EM 80.5%、EX 84.1%，但这是小而干净的 schema。DIN-SQL 把 linking、难度分类、分步生成和自纠错串起来，Spider test 85.3% EX，随后仍撞上规模、静默错误和业务语义三块天花板。CHASE-SQL、XiYan-SQL、MAC-SQL、Arctic-Text2SQL-R1 把候选、投票和执行奖励做深了，BIRD 上可以到 70% 以上，交互延迟也上去了。Agent 是执行引擎，不是意义来源。

### 1.3 Text2DSL 改的是解空间

Text2DSL 的链路是：

```text
用户问题
  → 意图解析
  → 指标 / 维度 / 时间 / 筛选 / 排序 / TopN / 对比
  → 语义查询 DSL（MQL、SMQ 等）
  → 语义层或 BI 引擎编译成 SQL / DAX / LookML / SemQL
  → 执行，并带回口径说明
```

[SMQ](https://arxiv.org/abs/2606.31041) 把这件事写成两层。上层 LLM 看到的是指标、维度和度量，输出例如 `metrics: [return_rate]`、`region = 华东`、`time = LAST_MONTH`。下层编译器从指标库展开物理表达式（如 `SUM(return_amount) / SUM(sales_amount)`），从 join 图注入关联，生成方言正确的 SQL。表名、列名和 JOIN 条件来自编译器，不来自模型采样。幻觉列名这一类错误被从解空间里拿掉，这不是换一代模型就能自动得到的。

材料里和这条机制相关的数字要分开读：

- Spider2-snow（547 个任务）上，SMQ 模式 94.15% EX，官方榜单第三；同一榜单上裸 schema 的 DAIL-SQL + GPT-4o 是 2.2%。材料写明：基座模型有代差，四十多倍不能全记在架构上。能记在架构上的，是物理标识符不再由模型发明。
- dbt 2026 年内部基准：原始 schema 上直接 Text2SQL 整体 64.5%，接入语义层后 72.7%，语义层覆盖到的子集 98%–100%。更重要的是失败模式。语义层失败是答不出；Text2SQL 失败经常是一个看起来对的错数字。对企业决策，后者破坏更大。
- EntSQL（1,066 个中英文对齐样例，约 96% 需要问题和 schema 之外的企业知识）里，英文且提供长文档时最好 15.9%。它说明：库结构正确，甚至塞进长文档，仍不等于口径已经可执行。语义层要接入指标说明、报送规则和部门词典，否则只是一层薄翻译。

已有数仓时，这条路线也更顺。事实表、维度表、主题域、统一维度编码里，对象关系已经写过一遍：订单事实关联客户维，销售事实关联产品维。语义层是把这些关系收成公共词典，而不是再猜一遍 JOIN。

### 1.4 选择它，同时保留另外两条链路

千表规模下，没有材料支持「一个语义空间吃下全部表」。Snowflake Cortex Analyst 建议单空间不超过约 10 张表、50–100 列；Databricks Genie 硬上限 30 张表、推荐不超过 5 张；Uber QueryGPT 按约 12 个业务域切 workspace。1000 张表大约是这些上限的一个数量级以上，选型的第一步是按业务域拆开。

查询分布本身也是斜的：企业数仓里约 94.5% 的查询是重复的，约一半能在历史里找到模板。所以架构是三层，不是一条流水线：

1. **确定性语义层**承接高频、可预期的 BI。命中就出数，未覆盖就明确报错。
2. **路由和缓存**判断走快车道还是慢车道。命中已定义指标走 DSL；未命中才升级。缓存必须 fail-closed：宁可不命中，也不能把「2024 年 Q1 的 MAU」当成「2025 年 Q1 的 MAU」。
3. **长尾 Agent**承接探索式问题，做域内检索、SQL 生成和执行验证，接受更低的准确率。重复出现的长尾再晋升进语义层。

跨部门、要回答「这个对象是谁、依据在哪一份文档」时，再在语义层之外加本体和证据层。Agent 负责规划、探索和触发动作，动作是否允许，由指标、对象、权限和审计契约决定。

语义层自己的成本材料没有回避：指标要人建模，口径一漂移，编译出来的确定性就是过时的确定性。SMQ 的讨论也写了两点：语义层质量决定上限；语义中介在换取 grounding 的同时，有过拟合已建模域的风险。Text2DSL 是治理查询的主路径，不是所有问句的唯一路径。

## 二、语义层如何构建：从设计到实施

语义层不是数据字典。数据字典回答「这列是什么类型」；语义层回答「销售额怎么算、活跃用户怎么定义、这两个数能不能比、谁能看」。LLM 先把自然语言映射到语义查询，引擎再确定性编译成 SQL。不确定的是意图，确定的是编译。

### 2.1 设计原则

先定边界，再填指标。

- **不推倒物理数仓。** 逻辑 schema 是给模型看的接口。底层数据和关系语义保持不变，表结构变更时只改映射。
- **先小后全。** dbt、Cube、衡石的建议是先做 10–30 个 Tier-0 指标。落地顺序是先盘点约 20 个高频且易混的问题：指标定义、字段映射、权限边界、责任人。业务负责人确认「这个词在我们部门指什么」，这一步不写 SQL，但决定语义上限。
- **按域切分，而不是做一个千表空间。** 一个数据集 / workspace / Topic 对应一个业务域。域内几十张表，域间靠路由。
- **口径是公共词典，变体要显式建节点。** 「销售额」若在披露、经营、考核里是三套 SQL，就建成三个指标或一个权威节点下的变体，不能合成一个含糊名字。
- **关联只封装反复出现、语义明确的路径。** 把所有表 JOIN 成一张宽表会改变结果：多余 INNER JOIN 会滤掉关联键为空的行。
- **权限在编译期注入。** 行级、列级条件由编译器写入 SQL，使越权查询在语法上拼不出来，而不是靠提示词叮嘱模型。
- **范文和逻辑 schema 同步。** 提供了新视图或新指标名，示例仍在教旧的多表 JOIN，模型就不会用新结构。改写后的示例只保留执行结果与原 SQL 等价的那些。
- **未覆盖要拒答或追问。** 缺时间条件时静默补一个默认日期，是在替用户做未声明的约定。低置信度应澄清，而不是硬答。

### 2.2 语义模型里要有什么

一个可编译的语义层至少有五块。再往企业对象和证据走，才加本体。

| 对象 | 设计时要写清的内容 | 编译时怎么用 |
| --- | --- | --- |
| 指标 | 聚合公式、默认过滤、口径说明、时间粒度、依赖指标、刷新频率 | 展开为 SELECT 中的表达式，不让模型重写公式 |
| 维度 | 层级（天/周/月，省/市）、属性、可筛选值 | 展开为 GROUP BY、筛选列和时间函数 |
| Join 图 | 哪些表以什么键关联、1:1 还是 1:N、是否经桥接表、行粒度 | 按本次用到的指标和维度自动补 JOIN |
| 同义词 | 「用户 / 客户 / 会员 / 买家」落到同一指标或维度 | 意图解析只做名称对齐，不做口径猜测 |
| 权限 | 行级、列级策略，以及策略作用在哪个维度或字段 | 编译 SQL 时注入 WHERE / 列裁剪 |

指标图谱是其中的子图。以材料里的 GMV 为例：权威定义是 `SUM(t_order.amount) WHERE status = 'completed'`；含退款、净额、含税是变体；客单价、退款率是依赖指标；时间、区域、产品线、客户等级是可用维度。改一个底层字段时，沿依赖边找出受影响的指标，而不是等报表数字对不上再查。

若同一企业还要回答「VIP 客户是谁、退货率的依据写在哪份制度里」，本体再补这些类型和关系：

```text
实体：Database、Schema、Table、Column、BusinessConcept、Metric、Dimension、Domain、SQLPattern
关系：CONTAINS、REFERENCES、MAPS_TO、DEFINES_AS、BELONGS_TO、REQUIRES、ALIAS_OF、CONSTRAINS
```

指标语义层回答怎么算，对象本体回答谁是谁，证据层回答依据来自哪份文档和当前状态。Text2DSL 的最小闭环是前一层；后两层按跨系统程度加，不作为第一期的门槛。

逻辑 schema 还可以做三种不改变物理库的变换，对应模型读 schema 时的三个困难（[论文](https://arxiv.org/abs/2606.03145)）：

- **+R 重命名**：`molecule.label` 这类名字换成 `carcinogenic_flag`，并保留「逻辑名 → 物理列」的可逆映射。名称要能区分近义指标，例如净利、归母净利、扣非净利，而不是都叫 `profit`。
- **+A 抽象**：从历史 SQL 的表集合里挖频繁共现，生成逻辑视图；用执行结果等价来验收改写。视图是加给模型选的，不必藏掉原表。没有历史查询时，可按当前问题识别到的表按需生成并缓存。
- **+P 分区**：按查询把 schema 收成局部区域。示例从同一区域的历史查询里取，使范文和本轮可见的表是同一套。裁剪必须留下本题需要的表、列和关系。

这三件事和语义层兼容：名称对应同义词和指标名，视图对应受验证的关联，分区对应业务域和动态范文的检索范围。它们不替代未知业务规则。EntSQL 的结论仍然有效：文档里的口径若没有收进指标定义，模型还是会猜。

### 2.3 知识从哪里来

知识不会从一次建模会议里长全。材料给出的来源和提取方式是：

| 来源 | 提供什么 | 怎么收 |
| --- | --- | --- |
| DDL / 数据字典 | 表、列、类型、注释 | 解析 DDL |
| ETL 脚本 | 真实关联和字段转换 | 解析 SQL / 脚本，人工确认键 |
| 指标文档、报送规则、部门词典 | 口径、时间边界、排除项 | 抽取后由指标负责人确认 |
| BI 报表、Tableau / Power BI | 已经在用的度量和维度 | 导入为语义视图的种子。Snowflake Semantic View Autopilot 走的就是这条 |
| 历史问句–SQL | 高频表组合、WHERE 模式、可改写的示例 | 日志聚类；改写后做执行等价校验 |
| 术语表 | 别名 | 人工整理，模型辅助候选 |

超过 95% 的字段往往没有描述。DBAutoDoc 一类「统计 + LLM 迭代精化」大约两次迭代收敛，成本约 0.7 美元 / 100 张表。对 1000 张表，这是摸底阶段的小投入，用来补描述和做访问频次聚类，不是用来自动发布指标口径。口径发布必须有人签字：LLM 可以提议 `MAPS_TO`，不能独自宣布「销售额」的权威定义。

表示上，问数场景更适合属性图（节点和边带属性，便于遍历依赖和影响面）。需要与外部本体做形式化推理时再用 RDF/OWL。语义层产品本身不一定上图数据库：dbt 把指标放进版本管理的代码，Snowflake 放进仓库内的语义视图，Cube 放进独立语义服务，OSI 用 YAML/JSON 描述 metrics 和 `ai_context`。图是依赖和消歧的索引，YAML/代码是可发布的口径版本。

### 2.4 实施：离线把口径编译成资产

离线阶段的产出是一套能被查询编译器读取的资产，而不是一叠提示词。

1. **域与责任人。** 按主题域列出候选表。用历史查询做表聚类，确认每个域的负责人。一个域先只收能讲清粒度的核心事实表和标准维表。
2. **指标卡。** 每个 Tier-0 指标写成：业务名、权威公式、默认过滤、时间字段（下单还是结算）、排除项（测试单、内部单）、可用维度、不可加总的情况、口径变体、责任人。近义指标分开建，别名只指向其中一个。
3. **Join 图与视图。** 只登记有业务含义的关联和基数。对历史 SQL 中反复出现的路径生成逻辑视图，用改写前后的结果集是否等价做验收。不生成「什么都能 JOIN」的 omni-view。
4. **维度与时间。** 写清层级、财年还是自然年、周的起算日。时间语义放在维度上，编译器展开，不放在每次 prompt 里临场解释。
5. **权限策略。** 行级、列级规则挂在语义对象上，标记编译期注入点。
6. **示例库。** 每个已发布指标保留「问句 → DSL → 等价 SQL」。schema 或视图一变，示例一起改，未通过等价校验的示例不进检索。
7. **证据挂接。** 指标卡链接到制度原文或报表说明，供追问时展示「这次按哪条口径算」。没有挂接的口径，不宣称已经完成 grounding。

验收标准先于覆盖率：同一个指标从问数、报表和 API 进来，数字一致；未定义的问法返回「语义层未覆盖」而不是一条猜测 SQL。

### 2.5 实施：在线只让模型填 DSL

在线路径分成命中和未命中。

```text
用户问题
  → 意图分类（是否像已定义指标）
  → 命中：在该业务域的语义层里做指标/维度链接
       → 生成 DSL
       → 编译器展开公式、JOIN、时间、权限
       → 目标方言 SQL
       → 执行
       → 返回结果 + 本次使用的指标口径
  → 未命中：长尾链路
       → 域粗筛 → 域内检索表/列 → 生成 SQL → 本地语法校验 → 执行验证
       → 低置信度则澄清或拒答
       → 重复出现且口径已确认的问题，回灌为新指标
```

DSL 的形状就是 SMQ 那种结构：`metrics`、`filters`、`group_by`。模型的输出空间限制在已发布名称里。物理列要到编译阶段才出现。

编译器要做的确定性工作：

- 按指标定义展开聚合和默认过滤；
- 按 join 图补关联，并检查本次维度是否会把行粒度乘大；
- 把「上季度」「上个月」按该指标绑定的时间维度展开；
- 注入行级、列级权限；
- 用 SQLGlot、Calcite 一类引擎落到 Hive、Spark、ClickHouse 或 MySQL，而不是让模型直接写方言。

路由可以用小模型，不必每次都叫大模型。材料里的 vLLM Semantic Router 用轻量分类器区分简单/复杂，整体准确率约 +10%、延迟约 −50%；COGNI 用 LoRA 微调的 1.5B 模型做同类判断，准确率 93.8%，成本约大模型的 1/7。语义缓存是 embedding 粗筛之后，再做实体、意图和时效校验，目标是零误命中。大部分调用应在这一层被拦住。

长尾链路的 schema linking 在千表（约 2–3 万列）上不能做一次全库向量召回。材料引用的拐点是：大约 3000 列之后，一次性检索召回率会跌破 40%，迭代式方法可以维持在 90% 左右。做法是业务域粗筛，再在域内检索、校验、补列。候选表可以只抽样一行用来消除命名歧义。生成后用 `sqlglot` 做不调用 LLM 的语法检查，再执行。低置信度澄清，禁止静默补默认时间。

### 2.6 和 SuperSonic 已有能力怎么接

[千表备忘](./技术选型/千张表、两种查询：智能问数系统的架构选择.md) 对 SuperSonic 的判断是：确定性编译和编译期权限已经有了，缺的是域内检索、快车道和拒答。

| 已有能力 | 对应语义层的哪一步 |
| --- | --- |
| `DefaultSemanticTranslator` 用 Calcite 生成物理 JOIN 和聚合 | 编译器：DSL / S2SQL 到物理 SQL |
| `S2DataPermissionAspect` 在 AST 上注入行级、列级权限 | compile-time governance |
| `dataSetId` | 业务域分片 |

千表下会先出问题的三点：`EmbeddingMapper` 对整个知识库做单次向量召回，超过约 3000 列后召回会掉；`ChatWorkflowEngine` 对每条查询都跑完整流水线，没有缓存快车道；`TimeCorrector` 在缺少时间条件时自动补默认日期，应改成低置信度澄清。

因此实施顺序是：先把 20 个 Tier-0 指标放进现有语义模型和翻译器，保证同一指标数字一致；再加意图路由和 fail-closed 缓存；最后把未命中的查询改成「域粗筛 → 域内检索 → 生成 → 校验」，并把确认过的长尾晋升回语义层。

### 2.7 阶段顺序

| 阶段 | 做什么 | 做到什么算完成 |
| --- | --- | --- |
| 0 摸底 | 统计字段描述覆盖率，用日志做表访问聚类，列出 20 个易混问题 | 知道哪些词有多套口径、哪些表其实很少被问 |
| 1 语义层 | 发布 Tier-0 指标、维度、join 图、别名、权限；编译走现有翻译器 | 同一指标不同入口结果一致；未覆盖问题报错 |
| 2 路由与缓存 | 轻量分类器分流；缓存做实体和时效校验 | 高频问题不进入长尾 Agent；缓存零误命中 |
| 3 长尾与回灌 | 域内迭代检索、语法校验、澄清或拒答；稳定问题晋升为指标 | 长尾可用，且语义层覆盖面随使用变厚 |
| 4 契约补全 | 逻辑视图与重命名、证据挂接、影响分析、必要时再加信息流控制 | 面向更宽的 schema 和跨会话权限，而不是先追求榜单分数 |

短期别名和列描述、中期语义层与追问拒绝、长期 +A/+P/+R，是同一条线的三个深度，不是三套互相替换的架构。

### 2.8 用一句问话走完设计到实施

下面用材料里反复出现的那类问句，把上一节的对象串成一次建设。公式是教学示例，用来展示编译器展开什么；上线前的权威公式以指标负责人签字的指标卡为准。

问句是：「上季度华东区重点客户的净销售额趋势如何？」

**第一步，设计时先把词拆开，不让模型以后再猜。** 业务负责人要确认四件事，每一件都写成语义对象上的字段，而不是写进 prompt：

| 词 | 未确认时模型会猜的东西 | 收成语义对象之后 |
| --- | --- | --- |
| 净销售额 | 含税、扣退货、扣返利、扣内部单，四套都像对的 | 两个指标：`net_sales_ops`（经营净额，扣退货和内部单）、`net_sales_fin`（财务净额，再扣返利）。别名只指向其中一个 |
| 上季度 | 自然季或财季，按下单日或结算日 | 挂在该指标的时间维度上：经营净额用下单日、自然季 |
| 华东 | 注册地、销售归属或履约地 | 维度 `region` 的层级和取值来源写死，例如销售归属 |
| 重点客户 | 合同分级、近十二月贡献，或手工名单 | 维度属性或默认过滤，不放进指标公式里偷偷写 |

若两个部门坚持各用各的净额，就建成两个指标。合成一个叫 `profit` 的名字，等于把私人语言又包了一层。

**第二步，离线写成可编译的指标卡。** 经营净额可以长这样：

```text
指标 net_sales_ops
  名称：经营净销售额
  别名：净销售额（经营）
  公式：SUM(order_amount) - SUM(refund_amount)
  默认过滤：status = completed AND is_internal = false
  时间维度：order_date，自然季
  可用维度：region、customer_tier、month
  不可用：不能再按订单明细行加总后当客户级净额
  关联：order.customer_id → customer.id（N:1）
  权限：销售只能看自己的 region
  证据：经营分析口径说明 v3，责任人：经营分析
```

Join 图只登记这一条已经在数仓里用过的路径。若历史 SQL 里「订单–客户–区域」反复一起出现，可以收成逻辑视图，但改写后的示例必须和原 SQL 执行结果一致。区域维上的空键行不能因为多 JOIN 一张无关表而消失。

**第三步，在线命中时，模型只填 DSL。** 路由判断这句话落在销售域、且「经营净销售额」已发布。模型输出的是名称，不是表：

```text
metrics:   [net_sales_ops]
filters:   [region = 华东, customer_tier = 重点]
time:      LAST_QUARTER
group_by:  [month]
```

编译器然后做模型不该做的事：把公式展开成物理表达式，按 join 图补上客户表，把「上季度」按 `order_date` 的自然季展开，把「只能看华东」从权限策略注入 WHERE，再用 Calcite 或 SQLGlot 落到目标方言。返回给用户的除了序列，还有一句口径：「经营净销售额，扣退货与内部单，按下单日、自然季，区域按销售归属。」用户能复核的是这句，不是一条没人读的 SQL。

**第四步，没把握时停住。** 三种情况不编译成一个「看起来合理」的数：

- 用户只说「净销售额」，两个已发布指标都匹配：追问经营口径还是财务口径。
- 用户要「净销售额 / 广告花费」，广告花费尚未建模：语义层报未覆盖。若走长尾，低置信度仍澄清或拒答，不用一张临时 JOIN 冒充指标。
- 缓存里有「上季度华东净销售额」：先核对年份、季度和指标名。实体或时间对不上就视为未命中。

**第五步，长尾回灌。** 同一个未覆盖问法被确认口径、重复出现之后，才晋升为新指标卡，补上别名、示例和证据链接。语义层变厚靠的是这条闭环，不是一次把 1000 张表建模完。

这条路径里，设计解决「这个词指什么」，实施解决「这句话如何变成一次可复核的编译」。物理 SQL 始终是编译结果。

### 3.4 交互、数据质量和安全：语义层覆盖不到的部分

| R³ | 多个 Agent 独立生成 SQL，再投票取共识 | ACL 2025 Workshop |
| Agentar-Scale-SQL | 推理时投入更多计算。材料记 BIRD Test 81.67% | 蚂蚁集团，2025 |
| AskData + GPT-4o | 材料记 BIRD 最高分方案之一，Test EX 81.95%，核心是对数据库知识做工程化，细节未完全公开 | 2025 |
| OmniSQL | 大规模合成 Text2SQL 训练数据，说明微调侧的杠杆在数据，不在再堆一套提示 | VLDB 2025 |
| CodeS、ROUTE | 与 OmniSQL 一起，被列为微调路线的代表；和 DAIL-SQL、DIN-SQL、CHESS 的 ICL 路线并列 | 《前世今生》3.5 节 |
| GraphRAG | 文档抽成实体和关系，再做社区摘要。问数上的用法是：从 DDL、数据字典、指标文档建成表–列–概念–指标图，检索时同时给 DDL、口径和社区摘要 | Microsoft Research，2024 |
| 两篇综述 | 把 LLM 时代的 Text-to-SQL 方法收成图谱。材料用来定位各代路线，不提供新的架构结论 | IEEE TKDE，2025 |

GraphRAG 和指标图谱是一层知识索引：帮助找到「退货率」对应哪段 SQL 模式、要经过哪几张表。找到之后，若这个指标已经发布，仍应编译成 DSL，而不是把图里的 SQL 片段交给模型改写。

### 3.7 这些论文怎么接成一条论证

把上面几组按决策顺序接起来，就是材料里的选型论证：

1. Spider、DIN-SQL、CHASE-SQL、XiYan、Arctic 说明：在干净或给定 hint 的基准上，把 linking、分解、候选和执行奖励做强，单轮 EX 可以很高。
2. Spider 2.0、EntSQL、LinkedIn 的消融说明：表一多、口径一进私有文档，失败就从「SQL 写错」变成「知识没给到或没找对」。元数据、历史样例和表聚类带来的提升，大于再叠一个修复器。
3. SMQ 与 Text-to-SQL Friendly Logical Design 说明：把指标选择和物理 SQL 分开，并把名称、常用关联、可见范围做成逻辑接口，能从结构上去掉一整类幻觉，同时不必改物理库。提升幅度可以不大（+4.2 个百分点那一组），方向是改模型的输入契约。
4. BIRD-Interact、CLARITY、RTS 说明：语义层没有覆盖的问句，正确行为是追问或弃权。多轮交互本身很难，不能假设单轮能力会线性延伸。
5. ReViSQL 说明基准标注会脏；SEMA-SQL 和泄露研究说明，一旦越过表格或放开 Agent 工具，成本和权限会先于「更聪明的模型」成为约束。

所以 Text2DSL 不是因为其他论文失败了才被选中。那些论文把「模型侧还能挤出多少分」标了出来；语义层论文和工程案例把「这些分测不到的口径、权限和失败模式」标了出来。高频且必须可审计的查询走 DSL 编译，长尾走受限制的 Agent，两者用路由和指标回灌接上。

## 四、现阶段 SuperSonic 有什么问题

SuperSonic 已经是 Text2DSL 的一种实现：模型写的是 S2SQL，用的是指标名、维度名和数据集名，物理表、指标表达式和 JOIN 由 `SemanticTranslator` 展开。权限在 AST 上注入。这一层不该推倒。

现阶段的问题是：语义层停在「可编译的指标和维度」，还没有变成「带口径变体、对象关系和证据的公共词典」。模型仍在写一种 SQL，系统在编译之后用校正器补猜。

### 4.1 已经有的，和名字容易误会的

| 现有对象 | 实际做什么 | 还不是什么 |
| --- | --- | --- |
| Metric / Dimension / Term / Value | 指标公式、切分方式、业务说法、维值 | 指标依赖图、部门语境下的口径变体、制度证据 |
| `dataSetId` | 一组 Model 组成的查询视图，映射结果按数据集归堆 | 按问句先选域、再在域内检索的两阶段路由 |
| `Ontology` | 代码注释写明：一组可以按星型或雪花型 JOIN 的数据模型，外加指标、维度和 `JoinRelation` | 业务本体。它回答「这些模型怎么连」，不回答「净销售额在经营和财务里是不是同一个概念」 |
| S2SQL | `SELECT 期间费用 FROM 财务数据集 WHERE 公司名称 = '比亚迪'` | SMQ 那种只含 `metrics` / `filters` / `group_by` 的结构。模型仍然要自己写出 SELECT、WHERE、分组 |
| 多候选 parse | 一次提问可以产出多个候选，交给用户选 | 低置信度时的主动澄清或拒答。选候选发生在系统已经生成 SQL 之后 |

`SchemaElementType` 里没有 `ENTITY`。用户说的「比亚迪」是维度值；「期间费用」是 Term，用来把说法连到指标。主键一类的 Identify 描述实体类型，但不会作为独立概念节点进入词典。所以对象消歧、口径变体和「依据在哪份文档」现在都没有一等公民。

### 4.2 会在规模和口径上先坏的行为

这些是对照代码和《千张表》备忘能指到的点。

**召回是一次向量检索。** `EmbeddingMapper` 用整句问话做一次 embedding 匹配，再按返回元数据里的 `dataSetId` 把命中分到数据集。它不是「先判定业务域，再在该域的表和列里迭代检索」。备忘录按 AutoLink 的拐点估计：大约 3000 列之后，这种一次性检索的召回会掉到 40% 以下。类里还有一处未做的状态传递：LOOSE 已经跑过，LLM_OR_RULE 阶段可能再跑一遍。

**缺时间就补默认区间。** `TimeCorrector` 发现分区维度不在 WHERE 里，就按数据集上的 `TimeDefaultConfig` 算出起止日期，直接 `AND` 进 S2SQL。查询能执行，用户没有确认「上季度」或「默认近一段」指哪一段。这和第二节的原则相反：未声明的时间约定不该由校正器代填。

**每条问句都走完整流水线。** `ChatWorkflowEngine` 固定经过映射、解析、S2SQL 校正、翻译、物理 SQL 校正。没有「命中已发布指标就编译返回」的快车道，也没有 fail-closed 的语义缓存。重复的 KPI 问法和长尾探索付同样的延迟。

**物理 SQL 上还有一轮模型改写。** `LLMPhysicalSqlCorrector` 对已经翻译好的 SQL 做 JOIN 顺序和条件下推。编译器把口径锁住之后，模型又拿到了物理语句。这一轮的目的是性能，它也让「模型不接触底表」出现一个例外。

**近义指标靠向量和 Term 撞上，没有反向校验。** 材料里的双向 schema linking 要求：召回一个指标之后，再问它满足原问题的哪一项、有没有口径冲突。当前映射没有这步。落地笔记里的失败就是这个形状：中港异名规则匹配不上，近义簇选错字段；静态范文来自演示域「超音数」，时间口径和 SQL 骨架会被教到金融问题上。记忆库后来把端到端从约 72% 提到约 87%，但记忆侧没有 TTL，也没有「召回后答错就降权」。

**未覆盖时仍倾向于给出 SQL。** 语义层没有该指标时，解析器仍会在可见 schema 上生成 S2SQL。失败模式更接近 Text2SQL 的「看起来对」，而不是 dbt 基准里语义层的「明确报未覆盖」。多候选让用户事后挑选，不等于系统在生成前发现两个「净销售额」并追问。

**指标卡没有证据边，改口径也没有影响面。** 指标表达式写在 Metric 上，翻译时展开。改一个底层字段，系统不会沿着依赖找出客单价、退款率等受影响指标，也不会把经营分析口径说明挂到这次查询的返回里。EntSQL 指出的那层 grounding，现在还在文档和人的脑子里。

### 4.3 这些问题怎么排

先改会制造错数的行为，再补图谱。顺序是：

1. `TimeCorrector` 在缺少时间、且问句里也看不出时间时，改为澄清，不再写默认区间。
2. 近义指标同时命中时，先消歧再解析；解析失败或指标未发布时返回未覆盖，不降级成自由 S2SQL。
3. 召回改成数据集粗筛，再在域内做表、列和维值检索。LOOSE 与 LLM 阶段不要重复打全库。
4. 高频且已发布的指标走编译快车道；缓存核对指标名、时间实体和数据集，对不上就视为未命中。
5. 物理 SQL 的性能改写改成规则或优化器，不再交给 LLM。
6. 下面第五节的图谱，用来支撑 2 和影响分析，不替代现有的 Metric 和 `Ontology` JOIN。

## 五、如何建设知识图谱和本体论驱动的语义层

这里的本体不是把 SuperSonic 的 `Ontology` 换个存储。现有 `Ontology` 继续负责星型或雪花模型上的物理 JOIN。新建的是它上面的一层业务本体：概念、口径变体、对象、关系和证据。图是这层本体的索引。查询仍然编译成 SQL，图不直接充当执行引擎。

指标语义层回答怎么算，对象本体回答是谁、和谁有关，证据层回答依据在哪。三者都挂在同一套标识上，避免文档、Term 和指标各写各的名字。

### 5.1 本体里有哪些类型

沿用《前世今生》里的类型，但落到已有元数据上，避免再造一套平行词典。

| 本体类型 | 落到 SuperSonic 的哪里 | 图上多出来的内容 |
| --- | --- | --- |
| Domain | DataSet，或一组 DataSet | 域的负责人、问句路由时的入口 |
| Model / Table / Column | Model 与物理字段 | 只给编译器和影响分析看，不进模型的生成词表 |
| Metric | 现有 Metric 及其表达式 | 权威口径、变体、依赖指标、可用维度、时间字段 |
| Dimension / Value | Dimension、维值 | 层级、取值来自哪张维表 |
| BusinessConcept | Term 升格 | 一个说法可以连到多个指标，并带上下文约束 |
| SQLPattern | 不新暴露给模型 | 由 `DEFINES_AS` 指向 Metric 表达式，供编译器读取 |
| Evidence | 现有模型没有 | 制度、报表说明、指标文档的位置和版本 |

关系用有限的几种，够支撑问数，不必上完整 OWL：

```text
CONTAINS       Domain → DataSet → Model → Column
REFERENCES     Model → Model          已有 JoinRelation，同步进图
MAPS_TO        BusinessConcept → Metric 或 Dimension
DEFINES_AS     Metric → 表达式
ALIAS_OF       BusinessConcept → BusinessConcept
REQUIRES       Metric → Metric        客单价 REQUIRES 净销售额与订单数
CONSTRAINS     BusinessConcept → 上下文   财务部 + 「净销售额」→ net_sales_fin
SUPPORTED_BY   Metric → Evidence
```

「经营净销售额」和「财务净销售额」是两个 Metric。`ALIAS_OF` 只连接无歧义的说法。有歧义的说法留在 BusinessConcept 上，用 `CONSTRAINS` 消歧，消不掉就追问。

表示用属性图即可。节点和边带责任人、版本和生效时间。RDF/OWL 只在需要和外部本体做 `subClassOf` 一类推理时再考虑。问数的遍历是「从这个说法走到哪个指标、改这个字段会影响谁」，属性图足够。

### 5.2 图怎么建，才不会和语义层各写一套

构建顺序跟第二节的指标卡相同，多的是把已经签字的对象写成边，而不是让模型从文档里直接抽完就发布。

1. **从现有语义模型灌底图。** DataSet、Model、Metric 表达式、Dimension、`JoinRelation`、Term 与指标的现有关联，先原样进图。这一步不产生新口径。
2. **补变体和依赖。** 人工标出同一说法下的指标变体，以及公式之间的 `REQUIRES`。客单价若是净销售额除以订单数，两条依赖都要显式存在。
3. **从日志补路径，不从日志发明口径。** 历史问句和 S2SQL 用来发现频繁一起出现的指标和维度，以及该给哪个概念加别名。频繁不等于正确。新边停留在候选，指标负责人确认后才变成 `MAPS_TO`。
4. **挂证据。** 每条已发布 Metric 至少链接一份口径说明。没有 `SUPPORTED_BY` 的指标可以编译，但返回里不能声称「已按制度口径」。
5. **和示例一起版本化。** 指标或视图一改，沿 `REQUIRES` 列出受影响指标，并标出哪些记忆和 few-shot 仍指向旧表达式。未复核的示例退出检索。这同时补上记忆库没有 TTL、旧 SQL 教错时间口径的问题。

LLM 可以提议候选边。发布权在指标负责人。这是《前世今生》里「抽取之后人工校验」的同一条约束。

### 5.3 在线时图用在编译之前

图不生成 SQL。它缩小模型能选的名字，并决定要不要追问。

```text
问句
  → 链接到 BusinessConcept / Value（域内，而不是全库一次向量）
  → 沿 MAPS_TO、CONSTRAINS 找 Metric 和 Dimension
  → 零个命中：未覆盖，不降级成自由 S2SQL
  → 多个口径且上下文约束消不掉：追问
  → 唯一口径：取出该 Metric 的可用维度和 JoinRelation
  → 组装本轮可见的语义 schema 与同域示例
  → 现有解析器在这个子图上写 S2SQL
  → 现有 Translator 用 Ontology 的 JOIN 和表达式展开成物理 SQL
  → 返回结果时带上 SUPPORTED_BY 的口径说明
```

和今天的差别有三点。召回的单位从「相似的词」变成「沿定义边走到的指标」。近义冲突在解析前处理，而不是生成几条 SQL 再让用户猜。编译器读到的 JOIN 仍来自现有 `JoinRelation`，图只决定这次要带上哪些。

反向检查放在链接之后、解析之前：这个指标满足问句里的哪一个词；它的默认过滤和时间字段是否覆盖了用户说的「上季度」「扣退货」。对不上就追问，而不是进 `TimeCorrector` 补一段默认日期。

未建模的对象，例如跨系统的「负责人是谁、该触发什么工单」，先不要塞进这条编译路径。那是行动契约，等指标和对象稳定后再加。第一期的图只服务已有问数：消歧、影响分析和口径展示。

### 5.4 做到哪一步算这层语义层成立

| 验收 | 说明 |
| --- | --- |
| 同一说法的多口径会被追问 | 「净销售额」连着两个 Metric 时，不默认选相似度更高的一个 |
| 改字段能列出影响面 | 沿 `REQUIRES` 和表达式引用，找出要复核的指标与示例 |
| 返回能指出依据 | 已发布指标的答案带着证据链接；没有证据的不宣称已接地 |
| 编译路径不变 | 物理 SQL 仍只由 Translator 从 Metric 表达式和 `Ontology` JOIN 生成 |
| 未覆盖不硬答 | 图上没有这条概念时，返回未覆盖，长尾链路单独走 |

这层的成本在确认边，不在选图数据库。边没有人签字时，图谱只是把私人语言换了一个存储。
