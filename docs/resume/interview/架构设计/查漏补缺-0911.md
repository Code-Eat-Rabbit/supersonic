## 1. Agent 交互

> 主项目：深度研究。精读见 `[03](../深度研究/03-Main-Sub-Agent编排.md)`。

### 1.1 主 Agent 和子 Agent 的上下文怎么处理？

- **第一句：** 子 Agent 开独立 `message_history`，只拿到任务描述；干完只回传 summary，主会话看不到子轨迹全文。
- **项目证据：**
  - 配置里的子 Agent 经 `expose_sub_agents_as_tools` 暴露成主 Agent 可调用的工具。主 Agent 选中后，`run_sub_agent(task_description)` 调 `start_sub_agent_session`，用任务描述初始化全新 history，不复制主会话。
  - `TaskTracer` 分存 `main_agent_message_history` 和按 `session_id` 索引的 `sub_agent_message_history_sessions`：推理隔离，排障仍能回放。
  - 隔离的代价是子 Agent 看不到主会话里的隐含条件。做法不是回灌全量历史，而是要求委派时写全目标、范围、输入事实、输出要求和约束；仍缺信息就收紧描述后重派。
- **业界补全：** 本项基本不需要。理想回传是「结论 / 证据 / 缺口 / 不确定性」；标本目前是自然语言 summary，没有代码级 JSON schema 强校验。
- **易踩坑：** 说成子 Agent 共享主会话全量上下文；把简历「并发」说成标本已 `gather`。
- **回看：** `src/core/orchestrator.py` 的 `run_sub_agent`；`[03` E13](../深度研究/03-Main-Sub-Agent编排.md#e13-子会话隔离具体怎么做信息缺失怎么办)。

#### 追问：子 Agent 怎么包装成工具？做了哪些处理？

- **第一句：** 不是再起一个真 MCP Server，而是造一条看起来像 MCP 工具的定义，塞进 Main 的工具目录；执行时编排器按名字拦截。
- **项目证据：**
  1. **命名闸门：** 配置名必须以 `agent-` 开头，否则 `expose_sub_agents_as_tools` 直接抛错。
  2. **假工具定义：** `SubAgentWorkerPrompt.expose_agent_as_tool` 产出 `{name: "agent-worker", tools: [execute_subtask]}`。入参只有必填字符串 `subtask`；description 告诉 Main：这是能上网/读文件/编程的执行 agent，不擅长复杂推理，回传的是加工后的摘要而不是原料。
  3. **并列进目录：** `run_main_agent` 里把它 `+=` 进 `tool_definitions`，和 searching / reading 等真 MCP 长一样。Main 的调用格式不变，仍是 `<use_mcp_tool>`。
  4. **运行时分流：** 编排器看见 `server_name.startswith("agent-")` 就走 `run_sub_agent`，**不走** `ToolManager.execute_tool_call`。假工具没有独立进程。
- **易踩坑：** 说成「子 Agent 本身是一个 MCP Server」；把 description 说成另读了 Sub 的 system prompt。
- **回看：** `[03` §4 伪工具](../深度研究/03-Main-Sub-Agent编排.md#main-怎么委派-sub)；`src/utils/tool_utils.py`；`config/agent_prompts/sub_worker.py` 的 `expose_agent_as_tool`。

#### 追问：Main 怎么写任务描述？涉及哪些提示词？质量怎么保证？

- **第一句：** 任务描述就是 `execute_subtask` 的 `subtask` 字段，由 Main 的 LLM 当场写；质量靠工具说明书 + 系统提示里的「自包含」约束，没有代码级打分器。
- **涉及的提示词（三处，别混）：**


| 位置                                   | 谁读   | 管什么                                                                                                                         |
| ------------------------------------ | ---- | --------------------------------------------------------------------------------------------------------------------------- |
| 假工具 `description`                    | Main | 怎么委派：清晰、含背景、单一范围；不接含糊/投机性子任务                                                                                                |
| Main system · Tool-Use Guidelines §3 | Main | 「All tool queries must include full, self-contained context. Tools do not retain memory between calls.」上一轮事实要写进本轮 `subtask` |
| Main system · Task Strategy + 中文块    | Main | 行动前先写编号计划；中文任务则 `subtask` 用中文                                                                                               |
| 运行时追加一句                              | Sub  | `run_sub_agent` 在描述末尾再拼「Please provide the answer and detailed supporting information…」                                     |


- **质量怎么保证：**
  1. **写之前：** 计划把大任务拆成单范围步骤，每步对应一次委派，避免一条 `subtask` 塞整题。
  2. **写的时候：** description 要求背景 + 单一目标；Guidelines 要求自包含，因为 Sub 看不见主 history。
  3. **写完之后：** 没有 schema 校验 `subtask` 文案。质量差会表现为 Sub 摘要答非所问；Main 复盘后收紧描述再派。这是闭环，不是预检。
- **易踩坑：** 说有模板引擎/JSON 强制字段；说 Sub 能「自己去主会话里补上下文」。

### 1.2 为什么一次只能调用一个工具，而不是并发调多个？怎么权衡？

- **第一句：** 深度研究的下一步几乎总依赖上一步结果，所以做成「一步一工具 → 停 → 看结果再决定」；并发省时，但要先解决依赖、超时隔离和结果合并，标本没上。
- **项目证据：**
  - Prompt 硬约束：`exactly ONE tool call`，发出后必须 STOP，禁止在同一次回复里连发或假装已经有结果。
  - 代码一致：主循环对 `tool_calls[0][:max_tool_calls]` **顺序 `for` + `await`**。`max_tool_calls_per_turn` 是模型违规连发时的截断，不是并发度。
  - 子 Agent 也是同文：Worker 同样一步一工具。Main 若一轮委派多个无依赖 Sub，标本仍然排队执行。
- **权衡：**


|     | 一步一工具（现状）                               | 并发多工具                        |
| --- | --------------------------------------- | ---------------------------- |
| 适合  | 搜完再读、读完再算、委派后再汇总                        | 两个无关检索、互不依赖的 Sub             |
| 好处  | 计划可 revise；失败只影响当前步；主会话前缀更稳（利 KV cache） | 墙钟时间短                        |
| 代价  | 延迟叠加                                    | 要分析依赖、单路超时、部分失败怎么汇总；乱序结果更难复盘 |


  选顺序，是因为开放域研究的默认形状是依赖链，不是 fan-out。简历里的「并发」指架构上可以对无依赖子任务并行化，以及评测多题 `Semaphore + gather`；**不是**单题内已经 `gather`。

- **超时仍在，只是换了问题：** 工具 900 s、整单 14 min、问数侧静默回退。因为顺序执行，一个调用挂住，后面的根本还没开始。
- **业界补全（非本项目落地）：** 先让模型标依赖图，无边的才 `gather`；每个调用单独 `wait_for`；失败隔离，已完成的仍交回。
- **易踩坑：** 把 `10` 说成同时 10 个；把「一步一工具」说成模型能力不够、只好串行。
- **回看：** `[03` §4 Task Strategy](../深度研究/03-Main-Sub-Agent编排.md#4-prompt-精读计划任务分发与收束)；`[03` §9](../深度研究/03-Main-Sub-Agent编排.md#9-专节顺序执行-vs-简历并发)。

### 1.3 有没有提高 KV cache 命中的手段？拼提示词有没有特别处理？

- **第一句：** 有意识做前缀稳定，但不是完整的 cache 工程；命中主要靠「system 固定 + 历史只追加」。
- **项目证据：**
  - Claude 路径给 system 和最后一条 user 打 `cache_control: ephemeral`。
  - 拼词：Main / Sub 的 system（角色 + 工具目录）相对固定，**增强后的 user query 放在 user 消息，不塞进 system**。
  - 子轨迹不进主会话，主 Agent 多轮前缀更稳，这是隔离的副作用，不是单独做的 cache 产品。
  - 反向：`msg_{uuid}` 的注释是避免跨会话误命中，不是为了提高命中。
- **业界补全（非本项目落地）：** 工具定义放 system 且排序稳定；可变内容只追加；不要每轮改 system 或重排历史。`keep_tool_result` 截断旧工具结果会破坏前缀，和 cache 是权衡。业务配置里该值常见 `-1`（先不砍）。没有量化命中率。
- **易踩坑：** 把随机 message id 说成 cache 优化；声称有命中率数字；把 `ResearchDirective` 说成改了 Main 的 `prompt_class`。

#### 追问：那不就是 system 一套固定稿，增强后的 query 不进 system？Main 的系统提示词由哪些部分组成？

- **第一句：** 对。`prompt_class`（如 `MainAgentPrompt_GAIA`）在配置期钉死；Intent / `ResearchDirective` 只改交给 pipeline 的 **user 任务文本**（`full_task`）。
- **System 里有什么（`generate_system_prompt_with_mcp_tools`，按拼接顺序）：**


| 段                                    | 内容                                                                                                 |
| ------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 1. 环境约束                              | 只能用下面这些工具；每条消息只用一个工具；等下一条 user 才给结果；今天的日期                                                          |
| 2. 工具调用格式                            | XML：`<use_mcp_tool>` / `<server_name>` / `<tool_name>` / `<arguments>`；强调放在回复末尾、顶层、用正则解析           |
| 3. 工具目录                              | 真 MCP（reasoning / searching / …）+ 假工具 `agent-worker.execute_subtask`，每条带 description 和 JSON schema |
| 4. General Objective · Task Strategy | 拆子目标 → 行动前写编号计划 → 顺序执行 → 步后复盘 → 必要时改计划                                                             |
| 5. Tool-Use Guidelines               | 一步一工具；调用前交代已知/缺口；查询必须自包含；时间类题要想到归档检索                                                               |
| 6. Communication Rules               | 发出 tool 立刻 STOP；未完成不给终答；不提工具名；与用户语言一致                                                              |
| 7. 可选中文块                             | `chinese_context=true` 时：子任务中文、搜索词中文、思考和终答中文                                                       |


- **System 里没有什么：** 用户原问题、问数表格、`textSummary`、`<research_directive>`。这些都在 **首条 user 消息**里（Java 按 `queryId` 拼好 → Python `ResearchDirective.compose_task` → `process_input`）。
- **另外一条常被误当成 system 的：** `generate_summarize_prompt` 是循环结束后追加的 **user 消息**，用来收束 FINAL ANSWER，不是常驻 system。
- **易踩坑：** 把 `research_type` 说成会热切换 `prompt_class`；把工具目录说成每轮重写（同一任务内目录固定，这才对 cache 有意义）。
- **回看：** `[03` §1.2](../深度研究/03-Main-Sub-Agent编排.md#12-上游衔接用户-query-如何进到-mainsub)；`[03` §4](../深度研究/03-Main-Sub-Agent编排.md#4-prompt-精读计划任务分发与收束)；`config/agent_prompts/main_agent_prompt_gaia.py`。

### 1.4 提示词注入 / 工具数据污染，安全上怎么做？

- **第一句：** 用户侧靠「只传 `queryId`、服务端拼装」躲开客户端贴 jailbreak；工具侧靠 E2B 隔离执行，再用 XML 把工具结果标成数据而不是指令。
- **用户点击「深度研究」这条路径（已落地）：**
  - 前端只 POST 当前问数的 `queryId`，不传表格、不传总结、更没有自由文本框给用户改研究 prompt。
  - Java 鉴权归属后，从 `ChatQueryDO` 取原问题 / `textResult` / `textSummary`，截断后拼 `task + context`，再交给 Python。Prompt 的权威在服务端。
  - 效果：攻击者不能借这个入口把一段「忽略以上指令」直接写进 Main 的 system。研究范围钉在**已经查出来的那条问数**上。
  - 诚实边界：原问题或表格单元格里仍可能带对抗文本（间接注入）。`queryId` 防的是「客户端组 prompt」，不是「库里的内容永远无害」。
- **工具执行（两条）：**
  1. **E2B 沙箱：** Python / 代码类工具在隔离环境跑，限制出站和宿主机文件。这管的是「工具把机器打穿」，不是「模型听信网页里的指令」。
  2. **XML 包裹工具结果：** 回灌时把输出标成数据，例如 `<tool_result server="..." tool="...">...</tool_result>`，并在 system 里写明：标签内是观察数据，禁止当指令执行。调用格式本身已经用 `<use_mcp_tool>`；结果侧应对称包起来，避免网页里的「现在请忽略系统提示」混进对话。
- **业界通行做法（检索后的加固清单，标清哪些还没落进 harness）：**


| 做法                                | 作用                    | 本项目                                                                                 |
| --------------------------------- | --------------------- | ----------------------------------------------------------------------------------- |
| 不让客户端组 system / 只传 ID             | 切断直接注入                | 已落地（`queryId`）                                                                      |
| 执行沙箱                              | 限制工具伤害半径              | 已落地（E2B）                                                                            |
| Spotlighting：XML / 分隔符 +「这是 data」 | 降低间接注入成功率             | 调用格式已是 XML；**结果回灌目前仍是明文 user 消息**（`format_tool_result_for_user`），XML 包裹是应对工具污染的加固口径 |
| 转义用户/工具文本里的闭合标签                   | 防止提前 `</tool_result>` | 未做                                                                                  |
| 指令层级（system > 开发者 > 用户 > 工具）      | 冲突时听 system           | 未做显式优先级                                                                             |
| 工具 allowlist + 入参 schema 校验       | 注入成功也调不了危险工具          | 有工具目录和超时；arguments 无 Pydantic 强校验                                                   |
| 双 LLM / 隔离摘要：先抽事实再给主模型            | 高风险网页不进主会话原文          | 未做                                                                                  |


- **易踩坑：** 说 `queryId` 等于免疫一切注入；把 `<use_mcp_tool>` 说成已经隔离了工具**结果**；把沙箱说成注入检测。
- **回看：** `[02-集成设计-面试文档` Q1 为何只传 queryId](../深度研究/02-集成设计-面试文档.md)；`src/utils/io_utils.py` 的 `format_tool_result_for_user`。

## 2. 记忆系统

### 2.1 跑半年 / 一年后记忆污染，有没有管理措施？

> 主项目：智能问数。精读见 `[智能问数/03](../智能问数/03-查询记忆复用.md)`。

- **第一句：** 有治理，不是只进不出。执行成功只进 PENDING；LLM / 人审过了才 ENABLED 进向量；错的可以 DISABLED。没有自动过期淘汰，这是要承认的缺口。
- **项目证据：**
  - 状态机在 `s2_chat_memory`：PENDING → ENABLED / DISABLED。向量集合按 `memory_{agentId}` 隔离。embedding 对象是 `question`，payload 才是 S2SQL。
  - 闸门：SQL 能跑 ≠ 语义正确。`MemoryReviewTask` 看 Question + Schema + SideInfo + SQL，**不看结果表**。Rule 2 反过来盯时间口径，防止「最近一年」范文过期后继续教坏 Parser。
  - 人审和管理页可改 SQL / 下线；用户赞踩是介入通道。库累计 800+ 条 ENABLED。
  - 没有 TTL、没有「召回后答错自动降权」、没有长期未召回衰减。
- **业界补全（非本项目落地）：** 使用反馈闭环、TTL / 衰减、矛盾检测（和 LLM Wiki 的 lint 同一类问题）。项目里还没有系统化做。
- **易踩坑：** 把 800+ 说成越大越好；把 LLM 评审说成看过执行结果；说有自动遗忘。
- **回看：** `[智能问数/03](../智能问数/03-查询记忆复用.md)` 状态机与评审；题纲里「淘汰机制」追问。

### 2.2 压缩丢精度 vs 不压缩膨胀，权衡怎么做？

> 主项目：深度研究。

- **第一句：** 先靠架构少进主上下文；同一条会话里再按触发顺序压：先遮旧工具正文，再停手写总结，总结仍超窗才从尾巴剥历史，最后才切给用户看的报告字数。
- **权衡口径：** 精度优先保「结论 + 证据线索」在摘要里。宁肯摘要略粗，也不把子 Agent 的检索轨迹拼进主上下文。这是用结构换 token，不是无损压缩。

行文分两块：**先讲架构上如何少膨胀，再讲同一条会话里一旦要压、先做什么后做什么。**

#### A. 架构：子会话隔离（默认一直在起作用）

子 Agent 在自己的 `message_history` 里搜、读、跑代码。回主会话的只有一段 summary，不是那几十轮工具原文。过程细节进 `TaskTracer` 落盘，给人排障看，不进下一轮推理。

这不是「窗口爆了才启动」的开关，而是编排边界：膨胀被挡在 Sub 会话里。Main 的 history 只追加摘要，前缀更稳，也少碰后面的压缩。**业务上真正日常起作用的就是这一层。**

同一条会话内部（Main 自己、某个 Sub 自己）工具原文仍会叠。那才进入下面的触发链。

#### B. 同一条会话里：触发压缩时的先后顺序

```
每一轮准备调用 LLM
    ① 先 keep_tool_result：给副本遮旧工具正文（业务常关，这一步空操作）
    ② 送给模型
         ├─ 正常 → 继续下一轮
         └─ 模型停手 / 跑满 max_turns / 循环中已超窗
                ③ 停探索，追加总结提示，再调一次 LLM（写 summary）
                     写的时候会再走一遍 ①
                     └─ 仍报 context_limit
                            ④ 从尾巴剥掉最近一轮，再试总结
pipeline 返回 final_answer
    ⑤ enforce_length_budget：只切展示长度，不管推理窗口
```

① 和 ④ 最容易混：① 是预防（少送正文），④ 是急救（已经超了才剥）。业务把 ① 关掉时，窗口压力会直接落到 ③④。④ 的尽头现在是终止；完整改进架构见 [2.3](#23-压缩方法改进结构化-compaction未落地)。

##### ① 先：发给模型前，遮住旧工具正文（`keep_tool_result`）

每调一次工具，结果会作为一条 **user 消息**写进 history（网页全文、搜索 JSON 往往很长）。下一轮再调 LLM 时，默认会把**整段 history**再送一遍。

`keep_tool_result` 管的是：**这次调用前，要不要把较早的那些 user/tool 正文遮掉**。它改的是送进 API 的副本，history 本身和落盘日志还在。


| 配置值          | 发给模型时看见什么                                                                         |
| ------------ | --------------------------------------------------------------------------------- |
| `-1`（业务配置常见） | 全部工具结果原文都带上，**等于没压**                                                              |
| `2`          | 保留首条用户任务 + **最近 2 条** user/tool 正文；更早的改成 `Tool result is omitted to save tokens.` |
| `0`          | 只留首条用户任务，中间工具正文全遮掉                                                                |


**例子。** 主会话已经走了 4 轮：

```
[0] user: 原始研究任务          ← 永远保留
[1] assistant: 调用搜索
[2] user: 搜索结果 8000 字
[3] assistant: 调用读网页
[4] user: 网页正文 2 万字
[5] assistant: 再搜索
[6] user: 新搜索结果            ← 最近一条
```

若 `keep_tool_result=1`，发给模型时 `[2]`、`[4]` 的正文会被换成省略句，`[0]` 和 `[6]` 还在；`[1][3][5]` 那些 assistant 消息不动。模型还知道「我搜过、读过」，但看不见旧网页原文。

**为什么业务常配 `-1`：** 怕过早遮掉关键数字和 URL，宁可窗口涨，把压缩交给架构隔离（A）和后面的 ③④。不要把这个配置说成「我们已经在压工具结果」。

精度代价：被遮的那段里若有唯一证据，后面只能靠模型记忆或再调一次工具。这一步**不会**把任务标成 failed。

##### ②③ 然后：停探索，把轨迹压成总结（`max_turns` / 提前停 / 循环中超窗）

一轮 = 模型说一次话（通常跟一次工具）。标本示例：Main `max_turns=20`，Sub worker `50`。循环在这些情况下结束，**结束不是杀进程，而是改去写总结**：

- 模型这轮**没有**再调工具 → 正常提前停，`task_failed=False`
- 跑满 20 / 50 轮还在调工具 → 触顶，`task_failed=True`
- 中途 LLM 失败，或 ① 挡完仍然超窗 → 结束循环，并带失败标记

无论哪种结束，都进入同一段收束：`_handle_summary_with_context_limit_retry`。它往 history 末尾追加一条 **user 消息**（`generate_summarize_prompt`），再调一次 LLM，禁止再调工具，要求输出 FINAL ANSWER。写这次 summary 时，① 会再挡一遍旧工具正文。

`task_failed` 只改提示词口气，不改「还做不做总结」：


| 怎么结束的               | `task_failed` | 总结提示额外要求             |
| ------------------- | ------------- | -------------------- |
| 模型自己停手              | `False`       | 汇总已有证据，给出终答          |
| 触顶 / 循环中超窗 / LLM 失败 | `True`        | 必须明确说任务没做完，再尽量交出已有发现 |


没有单独的「提前终止 prompt」。提前停和触顶走同一套 `generate_summarize_prompt(..., task_failed=)`。Sub 的 summary 交回 Main 当工具结果；Main 的才是给用户看的终稿雏形。

精度代价：后面本可以再验证的步骤没了；触顶时要求承认失败，避免把半成品包装成定论。

##### ④ 仍超窗：从尾巴剥一轮，再试总结

「爆窗」= ③ 那次要把 **system + 整段 history + 总结提示** 送出去，① 挡完仍然超过模型上下文上限（报 `context_limit`）。这时才开始剥，不是一上来就删：

```
先把「请写最终总结」追加成最后一条 user
调 LLM（发送前仍先走 ①）
  ├─ 成功 → 返回总结，结束
  ├─ 网络抖动 → 最多隔 60 s 重试 5 次（history 不动）
  └─ 仍然 context_limit
        ① 把刚追加的总结提示 pop 掉
        ② 再 pop 掉最近一条 assistant（通常是最后一次 tool 请求）
        ③ 把 task_failed 打成 True（已经丢信息了）
        ④ 若还剩超过 2 条消息 → 再追加总结提示，重试
        ⑤ 只剩最初那一两轮还爆 → 放弃，返回错误句
```

可以把它想成剥洋葱：每次丢掉**最近**一轮，腾出 token 再请模型总结。最早的用户任务尽量留到最后。

和 ① 的差别（同一条链的前后手，不是平行方案）：


|      | ① `keep_tool_result`   | ④ 爆窗剥历史                          |
| ---- | ---------------------- | -------------------------------- |
| 角色   | 预防：少送正文，尽量别超窗          | 急救：已经超了，剥一轮再试                    |
| 何时   | 每一轮调 LLM 前（含写 summary） | 写 summary 且这次真报了 `context_limit` |
| 丢什么  | 旧工具正文换成省略句，消息还在        | 从尾巴 `pop` 掉整条最近的 assistant       |
| 业务默认 | `-1`，常常空操作             | 真超限才丢                            |
| 失败标记 | 不打 failed              | 一开始剥就 `task_failed=True`         |


业务把 ① 关掉时，等于把「窗口不够」全部交给 ③④。① 丢的是旧原文、骨架还在；④ 丢的是最近整轮，缺口更大。剥到只剩最初一两轮还爆，现状就是返回错误句、**任务终止**。这是 ④ 的尽头，也是最该改的地方。

##### ⑤ 最后：报告已经写出来，再卡展示字数

①–④ 管的是 **推理窗口**。pipeline 返回 `final_answer` 之后，才管 **给用户看的报告有多长**。

分两刀，不靠模型自觉：

**软引导（进模型之前）。** `ResearchDirective.compose_task` 在 user 任务末尾写：

```text
## 输出长度
请在 {length_budget} 字以内完成报告。
```

默认 `length_budget=4000`（请求体可改，进 job 行）。模型写总结时看得到，但经常写超。

**硬兜底（出模型之后）。** `enforce_length_budget(final_answer, budget)`：

1. 若 `len(报告) ≤ budget × 1.2`（4000 字放到 4800）→ 原样返回。20% 松紧带，避免 4001 字就从句中切开。
2. 若超过松紧带 → 按 `。！？` 和换行拆句，从前往后累加，加上下一句会超过 `budget` 就停。
3. 切过则文末追加：`…（已省略部分细节，完整报告见 report_full）`。

落盘两份：`report_markdown` 仍是模型原文；`report_summary` 才是截断后给前端 / SSE 的。出口丢的是展示长度，完整稿还在。

精度代价：硬切从前往后，后半的限制条件 / 反证可能被丢掉。所以还要软引导，让模型把结论写在前部。

- **业界补全（非本项目落地）：** 会话内 compaction 的机制设计见 [2.3](#23-压缩方法改进结构化-compaction未落地)。标本没有 citation 级回源，也没有滚动摘要。
- **易踩坑：** 把隔离说成窗口爆了才启动；把 Sub summary 说成无损；把 `keep_tool_result=-1` 说成已经在压工具结果；把 `max_turns` 说成超时杀进程；把 ① 和 ④ 说成同一件事；把 `enforce_length_budget` 说成推理窗口压缩；把阶段摘要替换说成已经落地。
- **回看：** `src/llm/provider_client_base.py` 的 `_remove_tool_result_from_messages`；`orchestrator.py` 的 `_handle_summary_with_context_limit_retry`；`server/rest/length_control.py`；`server/rest/research_directive.py`。

### 2.3 压缩方法改进（未落地）

> 演进思路，不是现状。

原来这么设计，主要是默认轮数不多（Main 大约 20、Sub 大约 50），膨胀先靠隔离挡住；中途再压一层摘要会有副作用——事实和推断混在一起、数字 / URL 被改写、刚搜到的证据被抹掉，还多一次调用。所以业务常把 `keep_tool_result` 关掉，宁可原文进窗口，爆了再用 ④ 确定性 `pop`，行为好测。

现在深度研究里单轮工具结果（网页、检索 JSON）就能把窗口顶满，还没跑满轮数就超窗；这时 ④ 丢掉的往往是最近状态，任务直接停。所以改进思路是：接近窗口上限时，用结构化阶段摘要换掉中间段、近端原文留下，同一任务继续跑；④ 的 `pop` 到终止只当最后保险丝。隔离继续留着挡膨胀，旧工具正文能清先清，全文进外存可回放。不要隔一段时间把全部历史粗暴总结一次。

### 3.1 如何保障工具调用可靠性，拿到结构化结果？四段分别做了什么？

#### 深度研究

- **第一句：** 可靠性靠编排层卡住四个时机，不靠模型自觉。调用外壳是 XML、入参是 JSON；编排器只抠标签去执行，不校验上面的计划正文。

下面按调用链走，每段先机制、再例子。场景统一用「查茅台毛利率」。

##### 1. 模型调用前

- **机制：** 系统提示前部钉死调用契约：外壳用 `use_mcp_tool` 标签当锚点，里面服务名 / 工具名 / 参数各包一层，参数仍是 JSON。强制调用顶层、放末尾、一步一次。计划用编号写在标签上面——代码不校验写没写「第一步、第二步」，只认末尾那一次调用。
- **为什么外壳是 XML、不是整段 JSON：** 同一条回复既要写计划，又要贴调用。整段 JSON 会和散文打架；常用模型路径也没走原生 function calling。标签当锚点，周围写乱了也能抠；复杂入参留在 JSON 里，不用硬塞进标签属性。不要求合法 XML，参数里的引号、花括号不该让整段解析报废。
- **例子：** 模型自己写出的一条回复长这样（上面是计划，末尾才是调用）。编排器发出去之前不检查计划写全没有，只认最后这一段四件套：

```text
第一步：搜年报口径，先拿到毛利率的权威来源再读原文。

<use_mcp_tool>
<server_name>tool-searching</server_name>
<tool_name>google_search</tool_name>
<arguments>
{"q": "茅台 毛利率 年报", "gl": "cn", "hl": "zh"}
</arguments>
</use_mcp_tool>
```

##### 2. 模型调用后

- **机制：** 模型吐出的是一段纯文本。编排器用正则抠标签，拆成两个篮子：完整四件套（外壳 + 服务名 + 工具名 + 参数，都闭合）进「能执行」；缺闭合进「写坏」。缺参数结束标签会试着补一次，其余残缺不修。参数区按 JSON 宽松读，修不好仍放进能执行（带着原文）——回灌改格式针对标签残缺，不是入参 schema。两边都空 → 当没调工具，去写总结。写坏不抛错，也不打断已经抠对的那些。同轮多个只按顺序跑前 N 个（配置常见 10），N 是截断不是并发。

下面每个例子都是：模型原文 → 拆出来的篮子 → 接下来做什么。

**能执行。** 就是上一节那条完整回复。不管上面的计划正文，只抽出：

```text
能执行 = [{
  server_name: "tool-searching",
  tool_name: "google_search",
  arguments: {"q": "茅台 毛利率 年报", "gl": "cn", "hl": "zh"}
}]
写坏 = []
```

下一步：真的去调搜索。上面那句「第一步：搜年报口径」没有字段、不会被执行。

**写坏。** 模型漏了外壳闭合标签：

```text
第一步：搜年报口径。

<use_mcp_tool>
<server_name>tool-searching</server_name>
<tool_name>google_search</tool_name>
<arguments>
{"q": "茅台 毛利率 年报"}
</arguments>
```

```text
能执行 = []
写坏 = [{ error: "Unclosed use_mcp_tool tag" }]
```

不调搜索、不抛异常。合成一条用户消息喂回去（大意）：

```text
Your tool call format was incorrect, error_message: Unclosed use_mcp_tool tag;
please review it carefully and try calling again.
```

下一轮模型补上闭合标签即可。

**标签齐、JSON 烂。** 四个标签都在，但参数不是合法 JSON：

```text
<use_mcp_tool>
<server_name>tool-searching</server_name>
<tool_name>google_search</tool_name>
<arguments>
{q: 茅台毛利率
</arguments>
</use_mcp_tool>
```

```text
能执行 = [{
  server_name: "tool-searching",
  tool_name: "google_search",
  arguments: {error: "Failed to parse arguments", raw: "{q: 茅台毛利率"}
}]
写坏 = []
```

这不走「再想一次」。它仍会被拿去调工具，工具侧看到的是解不开的参数，失败发生在执行期。别说成 schema 拦截。

**两边都空。**

```text
根据已有材料，茅台毛利率约 90%。
```

```text
能执行 = []
写坏 = []
```

循环正常结束，去写最终总结，不当异常。

**一对一坏。** 同一条回复里先写完整搜索，再写一个没闭合的读文件：

```text
<use_mcp_tool>
...google_search，标签齐全...
</use_mcp_tool>

<use_mcp_tool>
<server_name>tool-reading</server_name>
<tool_name>read_file</tool_name>
<arguments>
{"uri": "https://example.com/moutai.pdf"}
```

```text
能执行 = [搜索那一次]
写坏   = [{ error: "Unclosed use_mcp_tool tag" }]
```

搜索会跑；读文件不跑。跑完搜索后，再追加一句格式错误。整轮不作废。

**超上限。** 一口气写了 11 个都闭合的调用。拆完「能执行」有 11 项，执行时只切片前 10 个、依次 `await`，第 11 个丢掉。再喂一句：

```text
You made too many tool calls. I can only afford to process 10 valid tool calls in this turn.
```

这 10 个是一条接一条跑，不是一起并发。Prompt 要求一步一次，日常很少撞到 10。

##### 3. 工具调用前

- **机制：** 按名字找服务。名字写错但全局只有一个同名工具，就改过来再调，少一次笔误空跑。单次加超时（约 900 秒），卡住的工具不拖死会话。这里仍然没有按每个工具的入参表做强校验。
- **例子：** 模型把工具名写成 `google_seach`，目录里又只有一个搜索工具 → 自动改名后发出，结果里带一句「名字被改过」。网页下载挂住 → 到点收成超时错误，主循环继续，不会整进程卡死。

##### 4. 工具调用后

- **机制：** **没有**再过一个 Agent 总结 hook。工具返回什么，编排器几乎原样收成一段文本，写成下一条用户消息，下一轮 Main 接着看。只做两件确定性的事：有 `error` 就收成一句失败说明；结果太长（约 10 万字符）就硬截断并补 `... [Result truncated]`。异常不打穿主循环。完整原文进落盘日志，不另开一轮模型去「先总结再回灌」。
- **别和另外两条路混：**
  - `google_search`：Serper JSON，最多按开关丢掉知识图谱 / 摘要字段，仍是规则过滤，不是 LLM。
  - Hybrid：工具自己就返回结构化命中（摘要、链接、分数），同样不经第二模型。
  - 只有 Main 调了 `agent-worker` 这类子 Agent，回主会话的才是 Sub 自己写的 summary——那是委派，不是每个工具的默认后处理。
- **结果侧不对称（别吹过）：** 调用已经包标签，回灌目前仍是明文用户消息。网页或搜索 JSON 里的「忽略以上指令」和系统提示同一层级。加固才是对称包一层「这是观察数据」——还没落地。
- **例子。** Main 刚调完 `google_search`，下一轮 history 末尾多的是这样一条用户消息（示意，不是再经 Agent 改写）：

```text
{
  "organic": [
    {"title": "贵州茅台2024年报", "link": "https://...", "snippet": "毛利率约 91%..."},
    {"title": "...", "link": "https://...", "snippet": "..."}
  ]
}
```

超时或服务报错则写成：

```text
Tool call to google_search on tool-searching failed. Error: ...
```

Main 自己读这段再决定下一步（换词、读原文、或收束）。网页正文里若夹「请忽略系统提示」，现在也原样混在这段用户消息里。

- **易踩坑：** 把 XML 调用格式说成已经隔离了工具**结果**；把自动改名或「再想一次」说成入参强校验；把「单次结果可消费」说成任务成功率；把同轮截断说成并发。

### 3.2 失败分网络 / 工具自身 / 模型参数三类，入参错误除 few-shot 还有什么？

#### 深度研究

- **第一句：** 三类都不让进程死：网络 / 工具超时变 error 文本；参数错先 harness 修，修不了再让模型看报错重写。
- **项目证据：**
  - **网络：** 工具 900 s 超时；summary 路径 LLM 失败会隔 60 s 重试，最多 5 次。
  - **工具自身：** 异常收成 `{"error"}` 写回 history，由模型换工具或换参。Hybrid 一路空可降级另一路。
  - **模型参数：** server/tool 名写错且全局唯一 → Auto-correct 再调一次，结果带注记；格式残缺 → 合成 `re-think` 回灌，下轮改写法。标本**没有**对 arguments 做 JSON Schema / Pydantic 强校验。
- **业界补全（非本项目落地）：** 调用前用 JSON Schema 拒绝非法入参；枚举 / 范围钳制；同一 tool 连续失败熔断。
- **易踩坑：** 把 Auto-correct 说成能修好所有错参；把投顾的「固定 3 次指数退避」安到标本上。

#### 智能问数

- **第一句：** 参数错尽量不靠模型重试，而靠生成前 linking、生成后 Corrector、翻译期失败即失败。
- **项目证据：**
  - **网络 / 引擎：** JDBC / 查询失败 → 非 `QueryState.SUCCESS`，用户看到失败，记忆不入库。
  - **模型参数（错字段、错时间、错过滤）：** Mapper 先把实体对上；`SchemaCorrector` / `WhereCorrector` / `TimeCorrector` 改回合法 S2SQL；JOIN 和物理列不让模型写。SchemaMapper 的 LLM 精选有 `json_format`，解析失败会带错重试 1 次。
  - 除 few-shot 外，真正兜底的是**确定性校正器 + 语义层约束**，不是再喊模型「请按规范输出」。
- **易踩坑：** 把 SQL 报错原文当下一轮系统指令；说 Corrector 能修所有口径错误（「最近一年」一口三义，Corrector 修不了，要靠记忆范文）。

### 3.3 工具返回后怎样让模型更好解析、理解？

#### 深度研究

- **第一句：** 先变成短结构化文本再写进 history；过程细节留日志，不把 HTML / 沙箱 dump 原样塞给模型。
- **项目证据：** Hybrid 回 `SearchHit`（snippet / url / score / chunk_id）；过长追加 `... [Result truncated]`；Sub 只回 summary；Prompt 要求先抽 partial 再走下一步。
- **业界补全（非本项目落地）：** 给稳定 citation id，模型只引 id，需要时再 hydrate。标本没有引用 schema 强校验。
- **易踩坑：** 说模型直接读原始网页 DOM。

#### 智能问数

- **第一句：** 执行结果先格式化成表，再按预算截断后给解读 / 深度研究，不把万行 ResultSet 灌进 LLM。
- **项目证据：** `ResultFormatter.transform2TextNew` 用 `bizName` 做列名；灌深度研究时表 / 解读 / 整段有截断上限（约 2000 / 1000 / 4000 字）；默认解读只基于这张表，不擅自联网。
- **易踩坑：** 说模型直接看 JDBC ResultSet；把截断说成无损。

## 4. RAG

> 主项目：深度研究 Hybrid Search。问数主链路靠语义层生成 SQL，不是向量问答。精读见 `[04` §3](../深度研究/04-Hybrid-Search-MCP.md#3-hybrid-search路由--召回--融合--mcp-返回--证据链与引用)。

### 4.1 结合落地场景，当前 RAG 有哪些解不了的局限？

- **第一句：** 能解「把相关片段找来」，解不了「跨来源综合、口径冲突、时效和表格结构」。金融归因和行为科学相似研究都会踩这几条。
- **项目证据：**
  1. **切片切断结构：** 本地索引滑窗 800 / 120，研报表格、实验设计会被切开，召回的是残段不是完整口径。
  2. **查询时重发现：** 每次 `hybrid_search` 从 chunk / 网页重拼，不积累「净利润该用 TTM 还是财年」这种已综合知识。
  3. **路由不是语义：** `route_query` 是关键词 hints + 强制 mode；本地分是 token 交集。`VectorBackend` 接口在，当前常回退本地索引。
  4. **冲突不预检：** 研报 vs 年报、旧政策 vs 新政策，融合只做加权排序（默认 0.6 / 0.4），不会在入库时标矛盾。
  5. **多跳归因：** 「碳价 → 高碳行业估值」要跨库、跨时点，chunk 近邻给不出因果链；所以才上 Main–Sub 多步工具，而不是单次 RAG。
- **场景对照：** 金融看时效和口径；行为科学的实验约束写在方法段，容易被切掉。问数不靠 RAG 写 SQL。
- **易踩坑：** 把 Hybrid 说成已上线生产向量库；把 0.6 / 0.4 说成业务最优。

### 4.2 Karpathy 的 LLM Wiki？和传统 RAG 最大区别？知识图谱解决什么？

- **第一句：** 它不是一个软件，而是工作流：资料进来时先编译成互相链接、可版本管理的 Markdown 百科，人和 Agent 都围着这套页提问。RAG 是提问时才去切原始文档。图谱在 Wiki 语境里解决交叉引用和矛盾，不是换一个向量库。
- **项目证据：** 项目没做 LLM Wiki。Hybrid 仍是提问时检索。最接近「编译知识」的是问数语义层（指标口径预先写死），但那是 Headless BI，不是 Wiki。
- **业界补全（非本项目落地；Karpathy 公开的是思路 / gist，不是官方产品仓库）：**

  页面通常包括：概念页、实体页、来源页、比较页、综述页、索引页、矛盾 / 待验证页。工作流五步：摄入 → 编译更新已有页 → 人浏览（Obsidian / 文件系统）→ 基于 Wiki 查询 → 定期 lint（死链、重复、缺出处、过时结论、冲突）。

| | 传统 RAG | LLM Wiki |
|--|----------|----------|
| 何时综合 | 每次提问临时拼 | 新资料进入时先编译 |
| 知识形态 | 无状态 chunk / 向量 | 持久 Markdown 页 + 双向链接 + Git |
| 是否积累 | 答完通常不沉淀 | 持续改已有页 |
| 给谁读 | 主要给模型检索 | 人和模型都能直接读 |
| 矛盾 | 通常不预检 | ingest / lint 时标出来 |
| 规模 | 可到百万文档即时问答 | 适合稳定、中小、长期研究集 |

  **不是取代 RAG。** Wiki 夹在「原始资料」和「问答」中间：RAG 负责回原文核证据，Wiki 提供已经整理好的长期知识。落地可以是：PDF / 网页 → Markdown 原文 → Agent 编译 → Obsidian Wiki → Git → 研究 Agent 先读 Wiki 再回源。

  限制：结构化不等于正确。LLM 可能把推测写成事实、合并错概念、更新时丢掉语境。重要结论要留出处和页码、原文片段、置信度，并区分事实 / 作者解释 / Agent 推断，还要人工审核。

- **「知识图谱」怎么拆（面试官常把 Wiki 和 GraphRAG 混在一起）：**
  1. Karpathy 原文：wiki 链接 + Obsidian graph view，解决孤儿页、枢纽实体、跨页引用，**不是**图数据库。
  2. GraphRAG / KG：把「A 收购 B、B 属于行业 C」变成显式边，补 RAG 不擅长的多跳关系。
  3. 两者不是同一个东西。Wiki 的图是页面链接；KG 的图是事实三元组。
- **易踩坑：** 说项目已实现 Wiki；把 gist 说成官方产品；把 Wiki 说成已经取代 RAG；把 KG 吹成能替代全部检索。

## 5. Vibe Coding

> 主证据：正在用的 Cursor + Superpowers + 仓库内规范，不是业务 Agent 代码。

### 5.1 Web Coding 里如何约束模型不偏离规范？

- **第一句：** 规范写进仓库，用门禁执行，不靠聊天里口头提醒。
- **项目证据：**
  1. **设计门：** 功能未完成头脑风暴、未批准设计之前不写代码。
  2. **仓库宪法：** `CLAUDE.md` 钉死 Java 21、Maven、Spotless、前端 pnpm；Agent 先读再改。
  3. **技能即 SOP：** TDD、verification-before-completion、code-review——流程技能优先于「直接开写」。
  4. **机器门禁：** `mvn` / `pnpm test` / Spotless；Web 改动要走真实交互验证，不是只看截图。
- **业界补全（非本项目落地）：** lint + 架构测试（禁止乱建目录）；PR 模板检查清单。团队级 CLI 封装是同一方向，本仓库还没有上。
- **易踩坑：** 把「prompt 里写了编码规范」说成已经约束住；Web 规范只讲 CSS，不讲路由 / 状态 / 测试。

### 5.2 这套是否只适合单人？多人混用不同 AI 编码工具怎么统一？

- **第一句：** 单人靠习惯，多人靠与 IDE 无关的仓库资产：规则文件、技能、CI。工具可以不同，门禁必须同一套。
- **项目证据：** Superpowers / `CLAUDE.md` / skills 放在 git 里，Cursor、Claude Code、Codex 都会读到。本机 IDE 只是执行器。
- **业界补全（非本项目落地）：** 一份 `AGENTS.md`、一份 skills、一份 CI；禁止把规范只写在某个产品的 GUI 设置里。Agent Skills 生态是同一思路：规范版本化，不绑定单一 IDE。
- **易踩坑：** 要求全组换同一款 AI 工具；说「口口相传 code review」就算标准化。

### 5.3 产品要 Agent「零漂移、100% 稳定」，怎么沟通？

- **第一句：** 先翻译需求：100% 不是工程目标，要换成可测的 SLO 和失败时用户看到什么。
- **项目证据：**
  - GAIA 整体 53%（L3 仅 19%）说明多步 Agent 有结构性失败，不是调参能调成 100%。
  - 产品上已经用静默回退：深度研究失败不挡查数。
  - 超时是临时建议不是 SLA；记忆有评审闸门，承认会漂。
- **沟通框架：**
  1. 把「零漂移」拆成：答案对、工具成功、不阻断主链路——三件不是一件事。
  2. 给对照：问数有语义层 + 评测集，所以能把准确率当指标；开放域研究没有同一把尺。
  3. 给替代承诺：评测集回归、预算熔断、失败可见性、人审通道。
  4. 问清楚：100% 指的是「页面不挂」还是「结论永远对」？前者能逼近，后者做不到。
- **易踩坑：** 当场答应 100%；用「模型会越来越强」糊弄；嘲笑产品不懂。
