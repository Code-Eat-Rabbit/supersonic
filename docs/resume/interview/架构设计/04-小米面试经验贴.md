## 一、三大核心痛点：字段级歧义、状态过滤缺失、跨表关联逻辑

**问题**：以本项目架构师视角，说明项目在元数据管理、语义层设计、规则注入、上下文构建、SQL 生成约束、后处理校验等环节，哪些机制能规避这三类错误，且如何在模型"无感知/少感知"的情况下将业务知识显式融入查询链路。

### 总体答案

本项目的根本解法与小米结论一致：**不让 LLM 接触物理 schema**。LLM 全程只看到语义层（指标名/维度名/别名/术语），生成的是 S2SQL（语义 SQL）；物理字段的聚合展开、状态过滤、跨表 JOIN 全部由确定性引擎在翻译阶段完成。链路：

```
用户查询 → SchemaMapper（别名/向量识别语义元素）
        → SemanticParser（LLM 生成 S2SQL，只含指标名/维度名）
        → SemanticCorrector（规则修正）
        → SemanticTranslator（指标展开 + filter 注入 + Calcite 生成 JOIN）
        → JdbcExecutor 执行
```

### 痛点一：字段级歧义 → 指标对象封装

**字段级歧义**：数据库里跟「钱」相关的字段有十几个（`order_amt` / `pay_amt` / `refund_amt` ……），用户问「销售额」时，模型不知道哪一个或哪几个组合才是业务认可的口径。Text-to-SQL 等于让模型每次现场猜列。

**消歧做法：不让模型选列，只让它选指标。** 口径在定义时写死，查询时模型看不见物理字段。分两层：

1. **定义时消歧——把口径封进指标对象。** `MetricResp`（`headless/api/.../pojo/response/MetricResp.java`）就是这个对象。基类 `MetricDefineParams` 用 `expr`（怎么算，如 `SUM(pay_amt)`）和 `filterSql`（如 `status = 'paid'`）把「销售额 = 已支付实付金额合计」一次写死。三种 defineType（MEASURE / FIELD / METRIC）只是「用度量、用字段、还是用已有指标再组合」的差别，对 LLM 都不可见。翻译阶段 `MetricExpressionParser` 按 `expr` 把 S2SQL 里的「销售额」替换成物理表达式——纯 Java，不经过模型。

2. **上下文消歧——prompt 里根本没有物理列。** `PromptHelper.buildSchemaStr()`（`headless/chat/.../parser/llm/PromptHelper.java:105-199`）只拼出 `<销售额 ALIAS '营收,GMV' COMMENT '已支付订单实付金额合计' AGGREGATE 'SUM'>`。模型只能写 `SELECT 销售额 FROM ...`，没法在十几个金额列里挑。歧义在源头被消掉，而不是靠模型判断。

用户说法和指标名对不上（说「营收」、库里叫「销售额」）是另一层消歧，交给 SchemaMapper 的别名/向量映射（见第三、四节），同样不是让模型猜物理列。

### 痛点二：状态过滤缺失 → 设计时绑定的过滤注入

**状态过滤缺失**：已取消、已退款、已退货的订单需要排除，但模型不知道什么时候该加这些条件。用户没说「排除取消单」，模型就不会写 `status != 'cancelled'`；用户说了「已取消的订单」，模型也可能把「已取消」当普通文本，对不上 `status` 这一列。

两种处理。第一种是口径内置：默认排除取消/退款/退货，写进 `ModelDetail.filterSql` 或指标的 `filterSql`，由 `DataModelNode.build()` 强制拼进物理 SQL，用户没提也不会漏。下面说第二种——用户话里带了过滤条件时，怎么识别出来并真正用上。

**从自然语言识别过滤条件并落地**，走三步：识别 → 交给生成 → 校正写入 WHERE。

1. **识别。** 发生在 SchemaMapper，先于 LLM。订单状态这类维度值（「已取消」「已退款」）事先注册进 HanLP 词典。`KeywordMapper` + `HanlpDictMatchStrategy` 把 query 里的「已取消」命中为 `SchemaElementType.VALUE`，挂到维度「订单状态」上。`KeywordMapper.doDimValueAliasLogic()` 把别名换成技术值（「已取消」→ `cancelled`）。前端如果已经带了 `QueryFilters`，`QueryFilterMapper` 直接注入成 VALUE 命中，不必再从文本里抠。

2. **交给生成。** LLM 路径：`LLMRequestService.getMappedValues()` 把命中的维度值塞进 prompt，`PromptHelper.buildSchemaStr()` 拼成 `Values=[<订单状态='cancelled'>]`。模型写 S2SQL 时只是把这份 linking 填进 WHERE，不用猜物理列名。规则路径：`RuleSemanticQuery.fillSchemaElement()` 把 VALUE 命中转成 `QueryFilter`（等值一条、多值变 IN），写入 `dimensionFilters`。

3. **校正落地。** `SchemaCorrector` 用 linking value 校正 WHERE 里的字段名和字段值，模型写错维度名也能改回来。`WhereCorrector` 再做两件事：把请求里的 `QueryFilters` 用 `SqlAddHelper.addWhere()` 补进 S2SQL；按维度值映射把别名换成技术名。之后翻译阶段把 S2SQL 的 WHERE 变成物理 SQL 的 WHERE。

所以：默认口径不靠模型记；用户话里的过滤条件由 Mapper 识别成维度值，再经 prompt / `QueryFilter` 进入生成，最后由 Corrector 保证写进 WHERE。模型负责理解「这是一个过滤」，系统负责对上哪一列、写成什么值。

### 痛点三：跨表关联 → 预声明的 JOIN 图 + 最短路径

**跨表关联**：用户问「各门店销售额」，销售额在订单表、门店名在门店表。模型不知道该 JOIN 哪几张表、ON 哪个字段、用 LEFT 还是 INNER；两张表不直接相连时，还可能要经过第三张中间表。JOIN 猜错就会错数，或者打出笛卡尔积。

**做法：JOIN 不让模型写。** LLM 只看到 dataset（prompt 里的 Table 是数据集名），S2SQL 只写 `SELECT 销售额, 门店名 FROM 销售数据集`。翻译阶段根据这次查询用到的指标/维度，反查出它们属于哪几个 model（`SqlQueryParser.buildOntologyQuery()`），再决定要不要拼 JOIN。下面分两种情况。

**情况一：事前配置了 model 之间的关联——理想路径。**

LLM 看到的是 dataset 里的指标名，这些指标在 model 层已经用 `ModelRela` 连好：`fromModelId` / `toModelId`、`joinType`、`joinConditions`。构建 schema 时 `SchemaServiceImpl.buildSemanticSchema()` 按 dataset 的 modelId 拉这些边，`SemanticSchemaManager.getJoinRelation()` 转成 `JoinRelation`。

查询真正用到 2 个以上 model 时，`SqlBuilder` 才走 JOIN 图（条件：`joinRelations 非空 && dataModels.size() > 1`）：

- `buildGraph()` 把 `JoinRelation` 建成无向图；
- `probeRelatedModels()` 用 Dijkstra 找一条覆盖本次用到的模型的最短路径，中间 model 也会被带上；
- `render()` 为每个 model 生成子 SELECT，`buildJoin()` 按声明的 joinType / joinCondition 生成 `JOIN ... ON ...`。

这就是「指标在 dataset 里平铺给 LLM，关联在 model 层一次写死」。

**情况二：选中的指标没有预先定义关联——系统怎么兜底、会在哪失败。**

先分清「要不要 JOIN」。`buildOntologyQuery()` 会尽量把字段收进同一个 model：优先在已有指标的 model 里找维度，再找「一张表就能覆盖剩余字段」的 model。能收进 1 个 model，就不 JOIN，没配 `ModelRela` 也没事。

一旦指标和维度分属两个没有 `ModelRela` 的 model，`joinRelations` 为空，**Dijkstra 直接跳过**，`render()` 仍按本次用到的 model 逐个 `buildJoin()`。这时没有声明的 ON，只能走启发式：

1. **同名字段相交。** `getCondition(left, right)` 取两边子查询 SELECT 的交集，且字段得是维度或主键/外键（`Identify`）。对上了就生成 `t1.user_id = t2.user_id`，JOIN 类型默认 INNER。
2. **对不上就没有合法 ON。** 两边字段名不同（`store_id` vs `shop_id`）、或者 JOIN 键根本没出现在子查询 SELECT 里（用户只问了「销售额」和「门店名」，子查询里没有 `store_id`），交集为空，`condition` 为 null，生成的是无 ON 条件的 JOIN，结果不可用。
3. **带不来中间表。** 没有图就没有最短路径，第三张桥接表不会被自动加入。
4. **同名维度可能误连。** 两边都有 `status` 且都进了 SELECT，启发式会拿它当 JOIN 键，这和业务关联不是一回事。

所以没预定义关联时，系统不是「让 LLM 去写 JOIN」，而是「用同名主键赌一把」。赌得中的前提很窄：两边字段同名、键在 SELECT 里、一对就是主键/外键。实际跨表问数通常不满足，这正是痛点本身。

治理上只有三条路，都不经过模型：

- 补 `ModelRela`，回到情况一；
- 把本来要 JOIN 的 SQL 写进某一个 model 的 `sqlQuery`（`ModelDetail.java:23`），上层看成单表；
- 不要把互不关联的指标放进同一个 dataset，从源头避免跨 model 查询。

### 后处理兜底

`RuleSqlCorrector` 编排 `SchemaCorrector`（字段名校正、linking value 修正）、`TimeCorrector`（时间条件补齐）、`GrammarCorrector`（内含 Select/Where/GroupBy/Agg/Having 五个子校正器，目录 `headless/chat/.../corrector/`），对 S2SQL 做确定性修正——即使 LLM 输出有小偏差（缺 GROUP BY、大小写聚合函数），也会被规则引擎纠正，进一步降低错误外溢。

**业务效果验证思路**：本项目 `evaluation/` 目录提供 Text2SQL 准确率评测脚本，基于期望 SQL/期望结果构造测试集，与小米"DSL 准确率 + 答案准确率"双维度评测同构；badcase 修复后追加专项用例回归。

## 二、Text-to-Metrics + RAG（召回指标）为何比 Text-to-SQL + RAG（召回字段）更具确定性

一句话：召回字段时，口径、过滤、JOIN 都要模型现场组装；召回指标时，这些已经封在指标对象里，模型只负责选哪个指标，展开由引擎完成。

**1. 召回的是完整对象，不是字段注释碎片**

- Text-to-SQL + RAG 召回的是「某列叫 pay_amt、注释是实付金额」这类散片。怎么聚、滤不滤取消单、跟哪张表 JOIN，只存在于模型推理那一刻，每次都可能不一样。
- Text-to-Metrics 召回的是指标对象：名字、别名、计算公式、自带过滤、默认聚合绑在一起。向量库里存的是指标名 + 描述，命中后拿回的是整个语义元素，不是一段文档。口径一次定义、全局复用。

**2. 过滤和 JOIN 在定义时绑定，不在生成时拼**

- 指标/模型上的 `filterSql`、model 之间的 JOIN 关系都是事前配置。
- 翻译阶段用确定性代码注入过滤、展开表达式、按关系图拼 JOIN，不经过 LLM。模型现场漏写 WHERE、猜错 JOIN，在这条链路上发生不了。

**3. 多指标歧义用规则收敛，不靠模型临场判断**

- 指标带着归属（哪个 dataset / model）和热度，本身就有「适用边界」。
- 映射阶段完全匹配优先、长词优先；多个 dataset 时按相似度、指标热度排序，收到一个再给 LLM。
- 仍拿不准时，返回多个候选 parse 让用户选，是事后选择，不是让模型在十几个金额字段里猜。主动追问式消歧目前没有独立模块。

**4. 口径白盒，对账能直接看定义**

- 指标市场能看到「销售额」怎么算、滤了什么、属于哪个模型，不必翻物理 SQL、不必问数据团队。
- Text-to-SQL 对上账只能 diff 模型写出来的 SQL，口径藏在 prompt 和文档里，审计成本高。

**5. 改口径改一处，不必动 RAG 文档和 few-shot**

- 改指标记录或模型过滤即可；词典和向量由事件增量刷新，prompt、few-shot 不用改。
- Text-to-SQL 口径散落在文档和示例 SQL 里，一改就要更新 RAG、改写 few-shot、调 prompt，旧示例还可能带着旧口径。

**结论**：确定性来自「绑定时机前移」——业务口径封在指标对象里，LLM 降级为选指标、填维度；过滤、JOIN、聚合展开是 Java 逻辑。召回字段则是把组装工作留给模型，每次都是概率行为。

## 三、别名映射解析发生在哪个环节？

发生在问数主链路最前面的 **MAPPING**（`SchemaMapper`），在规则解析和 LLM 写 S2SQL 之前。用户说法对不上指标正式名，必须在这一步先对上，后面才能选指标、写 SQL。

用一个具体问句走一遍。语义层里指标正式名是「销售额」，别名写成 `["营收", "GMV"]`。用户问「上个月营收」。

1. **别名事先写在语义对象上，并灌进词典。** 「营收」存在指标的 `alias` 里（库表是 `s2_metric.alias`，维度、术语同理）。加载时每个别名当成独立词条进 HanLP 词典，但指向**同一个** `SchemaElement`（还是那条「销售额」指标）。所以词典里「销售额」「营收」「GMV」三条路，走到同一扇门。

2. **原句进来，先做映射，不经过模型。** `KeywordMapper` 拿问句去词典里搜。扫到「营收」，命中结果不是一个字符串，而是一条 `SchemaElementMatch`：元素 = 销售额指标，用户原词 = 营收。多条命中按 dataset 收进 `SchemaMapInfo`。这一步结束时系统已经知道：用户说的「营收」= 指标「销售额」。规则解析和 LLM 都还没跑。

3. **后面写 SQL 时，用正式名，不再认「营收」。** 规则路径直接拿 `SchemaMapInfo` 里的指标去拼 `SELECT 销售额`。LLM 路径把命中的指标塞进 prompt，长这样：`<销售额 ALIAS '营收,GMV' COMMENT '...' AGGREGATE 'SUM'>`。模型看到的是正式名加别名提示，写出 `SELECT 销售额 FROM ...`，不会在物理列里找 `revenue`。翻译阶段再按第一节把「销售额」展开成 `SUM(pay_amt)`。

维度值同理，只是多一步换成技术值。用户说「已取消的订单」，词典命中维度「订单状态」的值别名「已取消」，`KeywordMapper` 把它换成库里的 `cancelled`，后面 WHERE 写的是技术值，不是中文。

对不上词典时，**不会立刻放弃**，但 Embedding 也不是每句话都跑。用「比亚迪的期内溢利是多少」看（词典里指标叫「净利润」，别名没有「期内溢利」）：

1. **先 STRICT / MODERATE，只走词典，不开向量。** 「比亚迪」可能命中维度值，「期内溢利」对不上任何指标名 / 别名。规则拼 SQL 至少要 1 个指标，这一轮出不来候选。
2. **两档都空，才降到 LOOSE，打开 `EmbeddingMapper`。** 把问句切成片段（如「期内」「溢利」），去向量库找近邻指标 / 维度，默认相似度低于 0.9 丢掉。这时**会命中一些**：常常是「净利润」「利润总额」「营业利润」这一簇，再交给一次 LLM 精选，留下它认为相关的 ID。后面 prompt 里只有这些召回结果，模型从里面挑一个写 `SELECT 净利润`。
3. **向量也一个都没召回**（说法差太远，或全低于阈值）：规则仍然失败，再兜底把当前 dataset 的**全部**指标和维度塞进 prompt（`MapMode=ALL`），让模型自己选。候选越多越容易选错。

所以：关键词没命中指标，LOOSE 下 Embedding **会尝试命中一些近义指标**，不是直接失败。危险之处和「营收」写进别名正好相反——别名命中是唯一正确的那一个；向量命中的是一簇像的，排错了 SQL 照样能跑、数字却是别的口径。能写进 alias 的（「期内溢利」→ 净利润）尽量写进 alias。用户说成「期内溢价」这种更远的说法，召回更飘，更该靠别名或术语，而不是指望 Embedding 猜准。

整条链就是：**用户说法 → 词典 / 向量对上 SchemaElement → SchemaMapInfo → prompt 或规则拼 SQL 用正式名。** 小米那边的「决策表」在本项目里，就是别名 + 术语 + 映射打分这一套。

## 四、缩小指标选择范围的关键设计；多 dataset 候选如何收敛为一个

### 缩小范围的三层设计

1. **空间隔离——dataset/model 划分**：指标按模型/数据集组织，Agent 配置的 `dataSetIds`（`Agent.getDataSetIds()`，chat/server/.../agent/Agent.java:99-115）在入口即限定候选空间（类似小米的 8 个业务领域语义分区）。
2. **关键词路由——词典精确命中**：HanlpDictMatchStrategy + `MapFilter` 的确定性过滤（完全匹配优先于模糊匹配，长词优先于短词，`MapFilter.java:111-159`）。
3. **语义路由——向量召回 + LLM 筛选**：EmbeddingMatchStrategy（阈值 0.9，`EMBEDDING_MAPPER_THRESHOLD`）+ LLM 二次过滤；`BaseMatchStrategy.getThreshold():113-121` 还支持 STRICT/MODERATE/LOOSE 三档模式动态调阈值。

### 多 dataset 如何收敛

映射之后，`SchemaMapInfo` 可能同时挂着好几个 dataset 的命中。收敛分两步：先圈定范围，再按分数挑一个（或排出一个列表给前端）。Agent 配置的 `dataSetIds` 会先和命中结果取交集，不在 Agent 里的直接丢掉。只剩一个就不用比了。

**分数从哪来。** 每条命中带着 `similarity`：词典精确命中一般是 1；别名 / 模糊略低；向量召回是余弦相似度（默认低于 0.9 已丢掉）。每个 dataset 把自家命中收成四个数（第四档热度见下）：

| 档位 | 怎么算 | 看的是什么 |
|---|---|---|
| 1. dataset 最大相似度 | 类型为 DATASET 的命中里，similarity 取 max | 用户有没有点名这个数据集（如问句里出现「超音数」） |
| 2. 指标最大相似度 | 类型为 METRIC 的命中里，similarity 取 max | 指标对得有多准；维度、维度值不进这一档 |
| 3. 总相似度 | **所有**命中的 similarity **求和**（不是平均） | 命中条数多也能抬分：指标 + 维度 + 维度值都会加进来 |
| 4. 指标热度 | 命中指标里 `useCnt` 的最大值 | 代码里算了，但塞进排序对象时没带上，**两边都是 0，这一档目前不起作用** |

比较是短路的：第 1 档能分出胜负就停，否则比第 2 档，再否则第 3 档。没有加权求和。

用测试里那组数走一遍，更容易看懂为什么「点名数据集」压过「指标更像」。

用户问「超音数的访问次数」，两个 dataset 都有命中：

| | 超音数数据集 | 另一个流量数据集 |
|---|---|---|
| 命中 | DATASET「超音数」= 1.0，METRIC「访问次数」= 0.5 | METRIC「访问用户数」= 1.0，DIMENSION「用户」= 1.0 |
| 第 1 档 dataset 最大相似度 | **1.0** | 0（问句没点它的名字） |
| 第 2 档指标最大相似度 | 0.5（用不上） | 1.0（用不上） |
| 第 3 档总相似度 | 1.5（用不上） | 2.0（用不上） |

选超音数。即便对面指标完全匹配、还多命中了一个维度，只要问句里出现了数据集名，第 1 档就定了。

问句没点数据集名时，第 1 档两边都是 0，才看指标。例如一边「访问次数」= 1.0，另一边「访问用户数」= 0.6（即便那边还命中了「用户」= 1.0）——维度不进第 2 档，选指标更准的那边。

指标最大相似度也打平（都是 0.8）时，才看总和：一边 0.8 + 0.7 = 1.5，另一边 0.8 + 1.0 = 1.8，选总和更高的。所以「多命中几个维度 / 维值」只在前两档分不出时才帮忙；也可能让命中很杂的数据集把总分抬上去，这就是总和放在第 3 档、不放第 1 档的原因。

**解析前（给 LLM 挑一个 dataset）。** 上面这套排序选出**唯一**一个 dataset，prompt 里只放它的指标 / 维度。LLM 不在多个数据集之间做选择题。

**解析后（规则已经为每个 dataset 产出了候选）。** Chat 入口对每个候选 dataset 各跑一轮 STRICT / MODERATE（空了再 LOOSE），每轮只留该 dataset 的第 1 名，再拿到全局比。排序同一套四档，多一刀：第 1 档几乎打平（相差小于 0.0005）且不是同一个 dataset 时，先数 `similarity == 1` 的完全匹配条数，多的排前面。实践里用户说法比较规范、精确命中多时，这一刀比微调过的小数相似度更稳。排完取前 `PARSER_SHOW_COUNT` 个给前端；用户不选，就执行第一名。

测评时同一问句、同一份 schema，映射分数和排序结果是确定的，不靠 LLM 掷骰子。LLM 只在被选中的那一个 dataset 里写 S2SQL。

## 五、校验与权限：白名单、执行拦截、空结果

三件事不要混成一层「校验」：

- **白名单**：模型能不能写出语义层里不存在的字段。
- **权限**：这个人能不能看这些数。不靠模型自觉，翻译和执行两道门统一拦。
- **空结果**：查出来是空的，要不要偷偷改条件再查一遍。本项目不会。

主链路仍是：映射 → 解析 → 校正 → 翻译 → 执行。三件事卡在不同阶段，不要以为「一进问数就按人过滤」。

1. **映射 / 解析 / 校正：白名单开始生效，权限还不管。** 没登记的字段，映射命不中，prompt 里没有，S2SQL 写不进去。这一段不看「是谁在问」——朝阳店店长问「各门店销售额」，LLM 仍按全市口径写 `SELECT 销售额 GROUP BY 门店`。映射不过滤 schema，避免模型靠「看不看得见」去猜权限。
2. **翻译（解析末尾就会走到）：权限第一次按人拦，白名单最后一关。** Chat 解析状态机在校正之后会把 S2SQL 译成物理 SQL，给解析卡片用。切面挂在这个入口：模型看不见就拒绝；敏感列带上了就拦截；行条件在翻译前写进请求，物理 SQL 自然带上 `WHERE 门店 = '朝阳店'`。同时把语义名换成技术名（`销售额` → `pay_amt`），对不上就失败。
3. **执行（真正查库）：同一套切面再拦一遍，空结果在这里判定。** 防止绕过解析直查。JDBC 返回 0 行就记 EMPTY，不改条件重试。

店长问「各门店销售额」时，前面几步和普通用户一样能解析出 S2SQL；到生成物理 SQL、再到查库，才按「朝阳店店长」拦截或注入。

### 白名单：没注册进语义层的字段，进不了 SQL

用户问「上个月成本」，库里没有叫「成本」的指标，别名也没有。映射命不中，prompt 里就没有这个字段。规则要求「SQL 里的列必须在 Schema 里提到」；翻译时还要把语义名换成技术名，对不上号的名字过不了这一步。写错的字段名会按映射结果改回来。

所以白名单不是另做一张表，而是：**物理列必须先登记成指标 / 维度，才能出现在 S2SQL 里。** 贯穿映射到翻译，和第一节「不让模型选列」是同一套。

### 权限：店长只能看本店，不靠模型自觉

权限绑在用户（及部门）上，规则存在授权组里：能看哪些模型、哪些敏感列、行上要加什么条件。问数时 LLM **看不到**这些规则。规则写在授权组，拦在语义层门面：解析末尾的翻译拦一次，真正查库再拦一次，Chat 问数和 Headless API 走同一道门。

用「朝阳店店长问各门店销售额」走一遍（这三层都发生在翻译 / 执行，不发生在映射）：

1. **模型看不见。** 这个人不在销售模型的可见名单里（模型自己的 viewers，或从主题域继承）→ 直接拒绝，报「无权限」，不报「表不存在」，避免试探。
2. **列太敏感。** 「手机号」标成 HIGH，授权组没把这一列给他 → 查询一旦带上这列就拦截，并提示去申请。普通指标（销售额）不在敏感名单里，不拦。
3. **行只能看本店。** 授权组里有一条行条件，例如 `门店 = '朝阳店'`。切面在翻译前把它拼进 WHERE，不管模型有没有写门店过滤。最终物理 SQL 一定带上这个条件；查库返回时还会附带一句说明，前端能展示「已按你的权限过滤」。

小米「店长只能查自身门店」就是第 3 层。注入点在 SQL 构造层，模型写偏了也兜得住。

### 空结果：空就是空，不改条件重试

空结果只在**执行之后**判定。查完没有行，状态记成 EMPTY，原样返回。**不会**自动把「近两周」改成「近一个月」再查一次，以免用户以为系统还在按原问题答。和「空结果也是有效业务结论」一致。

解析阶段另有降级：规则拼不出 SQL 才改走 LLM，那是「没理解问句」，发生在解析阶段；不是「理解了但数据是空的」。

## 六、如何区分"业务定义缺失"与"模型判断偏差"

项目的评测与排查体系（`evaluation/` + 查询状态回溯）支撑这一区分，方法论与小米一致——**按 badcase 断裂点定位环节**：

1. **映射阶段断裂 → 业务定义缺失**：`SchemaMapInfo` 中命不中目标指标/维度，可直接归因：query 里的业务说法没有对应的 alias/术语/指标定义（语义资产缺口），修复动作是补别名、补术语（`s2_term`）、补维度值知识，即"补充语义资产"。
2. **S2SQL 与期望不一致但 schema 命中正确 → 模型判断偏差**：映射对了但 LLM 选错指标、时间条件写错，修复动作是优化 prompt 约束（`OnePassSCSqlGenStrategy` 的 INSTRUCTION 规则）、增加 few-shot 示例、启用 `LLMSqlCorrector` 二次修正，以及把高质量问答存入记忆（`MemoryServiceImpl.enableMemory()` 将 question+s2sql 注入向量库，`NL2SQLParser.addDynamicExemplars()` 召回为动态示例）形成正向循环。
3. **S2SQL 正确但物理 SQL 错 → 语义层配置问题**：指标表达式、model filterSql、JOIN 关系配置错误，属于治理侧 bug，修复语义模型。
4. **结果数据错误但 SQL 正确 → 数据源问题**：脱离问数链路，转数据团队。

判别工具：`ChatWorkflowEngine` 各阶段产物（mapInfo / candidateQuery / S2SQL / 物理 SQL）均随 `QueryResult` 持久化到查询明细，可逐环节 diff；`evaluation/` 的准确率脚本支持按 badcase 聚类找共性根因（同小米"17 条 badcase 中 8 条同一根因"的做法）。

## 七、时间口径相关的 badcase 与解决

### 时间信息如何从自然语言走到执行 SQL

时间不走一条单独的管道，而是嵌在问数主链路里：映射 → 解析 → 校正 → 翻译 → 执行。每一层只做一件事：认字段、算区间、写进 WHERE、落到物理列。

1. **映射：先钉死「时间写在哪个字段上」。** 用户原句先进 SchemaMapper。`PartitionTimeMapper` 并不从句子里抠「近两周」，而是把该 dataset 的分区时间维度（如「数据日期」）塞进命中列表。后面 prompt 和 S2SQL 才知道时间条件该写在哪个语义字段上。

2. **解析：把「哪一段日期」写成 S2SQL 的 WHERE。** 问数入口是先规则、后 LLM。

   - **规则路径**（先跑）：`TimeRangeParser` 从原句抠时间，三种写法依次试——「近 N 天/周/月/年」、`20240801` 这种 8 位日期、「昨天 / 上个月」（TimeNLP）。抠到的范围写入 `dateInfo`（就是一个 `DateConf` 对象），并绑到分区时间字段。例如今天是 2026-08-28，用户说「近两周销售额」，规则按滚动 14 天抠完大致是：

     ```text
     dateInfo.detectWord = "近两周"
     dateInfo.period     = WEEK
     dateInfo.unit       = 2
     dateInfo.startDate  = "2026-08-14"   // today - 14 天
     dateInfo.endDate    = "2026-08-28"
     dateInfo.dateField  = "数据日期"      // 该 dataset 的分区时间维度
     ```

     句子里没时间，则 `fillDateInfo` 用 dataset 的 `TimeDefaultConfig` 填默认区间。随后 `buildS2Sql` 把上面这份 `dateInfo` 转成 `数据日期 >= '2026-08-14' AND 数据日期 <= '2026-08-28'`。

   - **LLM 路径**（规则出了候选之后才跑）：prompt 里带原句、当天日期（`CurrentDate`）和分区时间字段名/格式。模型自己在 S2SQL 里写 WHERE。这一轮不再跑 `TimeRangeParser`，日期对不对交给下一步校正。生成约束写在 `OnePassSCSqlGenStrategy` 的规则里：有时间就用 `>=` / `<=` 写字面量，**不要用日期函数去算**；原句没提时间，WHERE 里就不要写时间（留给 `TimeCorrector` 补默认）。

     仍以今天 `CurrentDate=[2026-08-28]`、分区字段「数据日期」为例，模型看到的大致是：

     ```text
     Question: 近两周销售额
     Schema: Table=[销售数据集], PartitionTimeField=[数据日期 FORMAT 'yyyy-MM-dd'], Metrics=[<销售额 ...>]
     SideInfo: CurrentDate=[2026-08-28]
     #Exemplars: （记忆库召回的同构成功 SQL，见下）
     ```

     **写对时长这样**（字面量区间，不用 `date_add`）：

     ```sql
     SELECT 销售额 FROM 销售数据集
     WHERE 数据日期 >= '2026-08-14' AND 数据日期 <= '2026-08-28'
     ```

     「近两周」本身一口三义，模型可能随机写成其中一种（今天按 2026-08-28 周五）：

     | 理解 | 区间大概是 |
     |---|---|
     | 滚动 14 天 | `2026-08-14`～`2026-08-28` |
     | 本周 + 上周 | `2026-08-17`～`2026-08-28`（上周一到今天） |
     | 不含本周的过去两个整周 | `2026-08-10`～`2026-08-23` |

     `TimeCorrector` 看见 WHERE 里已经有时间字段就不会改，**改不了这种口径歧义**。处理靠两层：

     1. **记忆范文。** 过审的成功 SQL 按当前问句召回进 `#Exemplars`。业务里「近两周」约定成滚动 14 天，就把这种写法沉淀下来，模型更听范文不听长规则。这和「最近一年」时点 / TTM / 财年是同一类问题。
     2. **parse 和 execute 分开，用户先看再跑。** prompt 要求时间用 `>=` / `<=` 写字面量、不要用日期函数，就是为了让区间可读。`ParseInfoFormatProcessor` 从 S2SQL 抽出「数据时间: 2026-08-14~2026-08-28」展示在解析卡片上。前端先 parse 再 execute：多个候选时用户选一个再跑；即使用户没改，看到的也是具体起止日，对不上可以换候选或不执行。若写成 `datediff(...) <= 14`，卡片抽不出这段可读区间，用户也难核对。

     **其他常见写错**——字段往往都对，SQL 也能跑，数字却不对。结合查询记忆复用里的 case：

     | 原句 | 模型可能写出 | 错在哪 | 后面谁能兜 |
     |---|---|---|---|
     | 「近两周销售额」 | `datediff('day', 数据日期, '2026-08-28') <= 14` | 违规用了日期函数，卡片也抽不出起止日 | 校正不改写法；靠 `LLMSqlCorrector`、记忆范文，或用户看到看不懂的 SQL 后不执行 |
     | 「销售额」（没提时间） | 不写时间 WHERE | 符合 prompt「没提时间就别写」；若不补就会全表扫 | `TimeCorrector` 按默认配置注入，这是设计如此 |
     | 「销售额」（没提时间） | 自己猜 `数据日期 >= '2026-01-01'` | 违反「没提就别写」；WHERE 已有分区字段 | `TimeCorrector` **不会覆盖**；用户能在卡片上看到这段日期再决定是否执行 |
     | 「销售额」 | `数据日期 <= '2026-08-28'`（只有上界） | 从历史第一天扫到今天 | `TimeCorrector` 把下界补成等于上界，收成单日 |
     | 「比亚迪最近一年的净利润」 | `数据日期 >= '2026-01-01' AND 数据日期 <= '2026-12-31'` | 「最近一年」一口三义：时点、滚动 12 个月、财年 | 校正管不了口径；靠记忆召回各自过审过的 SQL，卡片上的「数据时间」给用户二次确认 |
     | 同上，但 few-shot 是演示域旧题 | 把范文里的 `CurrentDate=[2024-06-04]` 和那段日期原样抄进本轮 | 记忆 / 静态范文的 SideInfo 过期 | 审核盯时间和 `CurrentDate` 是否对齐；人审把错范文 DISABLED |

     记忆复用的关键点：LLM 更听 `#Exemplars` 不听长规则。`TimeCorrector` 只能补「缺了时间 / 缺了下界」，**补不了「时间写了但口径选错」**；那种靠范文钉死一种约定，再靠 parse 卡片上的字面量日期让用户确认。

3. **校正：只看 S2SQL，不看原句。** `TimeCorrector` 检查 WHERE 里有没有分区时间字段：没有就按默认配置强制注入一段区间；只有上界没有下界就补下界；dataset 根本没有分区时间，则把模型误写的日期条件删掉。

4. **翻译：WHERE 跟着语义字段落到物理列。** 校正后的 S2SQL 作为查询请求进入翻译，时间条件已经在 WHERE 里，随字段名从语义名换成物理列（如 `imp_date`），进入最终 SQL。

5. **执行。** 物理 SQL 交给 JdbcExecutor。卡片上若还要展示环比/同比，是主查询返回后再补的，见下一节。

举例：「近两周销售额」——规则路径按滚动 14 天写入 `dateInfo`；LLM 路径可能写成三种口径之一。两边都会经过 `TimeCorrector`（已有完整时间字段则不再盖默认）。字面量日期会被抽到解析卡片的「数据时间」上，用户确认后再 execute。翻译后 `imp_date` 出现在物理 SQL 的 WHERE 里。

### 这条链路上的典型 badcase

时间口径的共性坏处：用户说法含糊（不提时间、说「近两周」），模型每次自己算日期，容易算错或干脆不加时间条件。上面第 2、3 步就是把「该用哪段日期」从模型手里拿走。按 badcase 看怎么处理。

**1. 用户问「销售额」但不带时间 → 全表扫描**

是的：三种模式就是「没时间时往 WHERE 里填什么」的默认方案，配在 dataset 的 `TimeDefaultConfig.timeMode` 上。`TimeCorrector` 在校正阶段检查：dataset 有分区时间（如 `imp_date`），且 S2SQL 的 WHERE 里没有这个字段，就按这份配置算出一段区间，用 `addWhere` 强制写进去。

- CURRENT：本周期第一天到今天（本月、本年）
- RECENT：近 N 个周期到今天（例如近 7 天）
- LAST：恰好 N 个周期前那一天（代码默认就是这个：`unit=1`、`DAY`，即昨天）

聚合查询和明细查询可以各配一套。日期格式跟分区字段的 `timeFormat` 对齐，避免 `yyyy-MM-dd` 对不上 `yyyyMMdd`。dataset 没有分区时间时反过来：把模型误写进去的日期条件删掉，避免无中生有。

规则路径更早就会用同一套配置：`fillDateInfo()` 发现还没有 `dateInfo` 时先填上，不坐等到校正。LLM 路径 prompt 要求「原句没提时间就别写 WHERE」，所以缺时间主要靠这一步 Corrector 补。

**2. 只有上界、没有下界 → 从历史第一天扫到那天**

例如模型写出 `imp_date <= '2024-08-01'`。`TimeCorrector.addLowerBoundDate()` 检测到有上界无下界，把下界补成等于上界，收成单日，避免「那天之前的全部数据」。

**3. 中文时间说不清 → 「近两周」「上个月」对不上字段**

`TimeRangeParser` 在规则解析阶段从原句抠时间，三种写法依次试：

- 「近 N 天/周/月/年」「过去 N 天」：正则，算出 start/end
- `20240801` 这种 8 位数字日期
- 「昨天」「上个月」：TimeNLP

抠出来的范围写入 `dateInfo`，并绑到该 dataset 的分区时间字段上。规则路径直接用；LLM 路径 prompt 里也会带上分区时间字段名和格式。有 `dateInfo` 之后，上面第 1 条的「没时间就套默认」就不会再盖一层。

## 八、横向比较：直接对比、环比、同比

先分清两类「比较」，别混成同一种 SQL：

- **横向比较**：同一时间切面，按维度拆开。用户说「各门店销售额」，要的是 `GROUP BY 门店`，不是减日期。
- **环比 / 同比**：同一个对象，换一段时间再比。环比是相邻周期（昨天、上周、上月）；同比是跨一个更大周期对齐（日粒度对齐上周同一天，月粒度对齐去年同月）。

环比、同比的日期偏移**不经过模型**。优先在语义层把同比建成指标：问数时走上一节那条普通链路，只是选中的指标换成「销售额同比」。没有建这个指标时，系统才对普通指标查询默认再补两次比率查询。

### 环比、同比：从自然语言走到 SQL

两种做法。**先建指标；没建才走默认补两次。**

**做法一（优先）：语义层建好同比 / 环比指标。**

和第一节一样：不让模型减日期，让它选一个已经定义好的指标。口径（比哪段、怎么算、用哪个时间字段）一次写死。

怎么建，常见两种：

- 底表已经有增长率列：建成度量。demo 里「营收同比增长」对的就是列 `revenue_growth_year_on_year`，聚合用 AVG。
- 没有现成列：用指标的 `expr` 把公式写进 `MetricDefineParams`（MEASURE / FIELD / METRIC 均可），别名带上「同比」「同比增长」，让 Mapper 能从原句命中。

自然语言到 SQL：用户说「营收同比增长多少」。Mapper 命中这个指标（名字或别名），时间仍按上一节抠进 WHERE。主 SQL 就是：

```sql
SELECT 营收同比增长 FROM 企业数据集
WHERE 数据日期 >= '2026-01-01' AND 数据日期 <= '2026-08-28'
```

翻译阶段 `MetricExpressionParser` 按 `expr` 换成物理表达式。一次查询，没有自连接，也没有「先当期再补两次」。模型只负责选中这个指标。

别名要把「同比」钉到这个指标上。否则 Mapper 只命中「销售额」，后面就会掉进做法二，算的是系统默认偏移，不一定等于业务口径。

**做法二（没有这个指标时）：先查当期，再补环比、同比两次。**

用户问「8 月 28 日销售额同比」，库里只有「销售额」，「同比」进不了 schema，规则解析也不认这两个词，LLM 的 prompt 里没有比率算子。主 SQL 和没说「同比」时一样：

```sql
SELECT 销售额 FROM 销售数据集
WHERE 数据日期 >= '2026-08-28' AND 数据日期 <= '2026-08-28'
```

模型如果自己写 `date_add` 去减一年，属于上一节说的违规写法，系统也不会把它当成同比算子。Chat 主链路走的是 S2SQL，翻译阶段的比率解析器接不住它，这条主 SQL 里没有自连接、也没有减日期。

比率发生在主查询跑完之后。结果里有指标、查询是聚合、开关 `s2.metric.aggregator.ratio.enable` 默认打开，系统就会再查两次：一次环比、一次同比。用户没说「同比」也会算——问数对话对聚合指标查询默认就补这两条。下面用日粒度把「结果表 → 对比日 → 最终 SQL」走一遍。

假设主查询已经返回：

```text
数据日期      销售额
2026-08-28    100
```

卡片上还要一个环比、一个同比。缺的是「对比那天」的销售额，以及 `(当天 - 对比天) / 对比天`。系统按下面三步做，全程 Java。

1. **定锚点。** 从结果里取出时间字段最晚的那天，这里是 `2026-08-28`。后面所有加减都围着这一天，不回去看原句。

2. **按粒度算出对比日。** 用的是主查询的周期（日 / 周 / 月），不是用户有没有说「同比」。日粒度写死：环比减 1 天 → 要比 `2026-08-27`；同比减 7 天 → 要比 `2026-08-21`（上周同一天）。周、月见下表。

3. **把同一张聚合表当两份来 JOIN，让「当天」和「对比天」出现在同一行。** 系统发两条结构化请求（分别标明环比算子、同比算子），不再转成 S2SQL，也不再问 LLM。翻译器生成的 SQL 形态如下——先看环比：

   ```sql
   SELECT
     IF(t1.销售额 != 0, (t0.销售额 - t1.销售额) / t1.销售额, 0) AS 销售额_RATIO_ROLL,
     t0.销售额,
     t0.数据日期
   FROM 当期聚合 t0
   LEFT JOIN 当期聚合 t1
     ON t0.数据日期 = DATE_ADD(t1.数据日期, INTERVAL 1 DAY)
   ```

   读 JOIN 条件：左边的日期 = 右边的日期再加 1 天。`t1` 上 8 月 27 日加 1 天等于 8 月 28 日，于是：

   | 角色 | 日期 | 销售额 |
   |---|---|---|
   | `t0` 当期 | 2026-08-28 | 100 |
   | `t1` 对比期 | 2026-08-27 | （再查出来的前天销售额） |

   两行对上之后，才能在同一行里做 `(100 - 前天) / 前天`。同比同一张模板，只把 `INTERVAL 1 DAY` 换成 `INTERVAL 7 DAY`，8 月 28 日就会对上 8 月 21 日。算出来的比率挂到卡片上，日粒度展示名是「日环比」「周环比」。

周、月只是偏移不同，JOIN 写法一样：

| 粒度 | 环比减多少 | 同比减多少 | 卡片上叫 |
|---|---|---|---|
| 日 | 1 天 | 7 天 | 日环比 / 周环比 |
| 周 | 7 天 | 1 个月（对齐到周一） | 周环比 / 月环比 |
| 月 | 1 个月 | 1 年 | 月环比 / 年同比 |

所以「近两周销售额」规则抠完周期是周，锚点若是 `2026-08-28`，环比对比日是 `2026-08-21`，JOIN 用 `INTERVAL 7 DAY`。这套偏移是系统默认，和业务口径不一定一致——这也是做法一更优先的原因。

Headless 调用方也可以在结构化请求里直接带环比 / 同比算子，一次翻译就出上面的自连接，不必先跑 Chat 主查询；走的是同一套翻译，不是第三条口径。

**尚未覆盖**：多个指标各自绑不同业务时间字段（下单日 vs 支付日 vs 退款日），且偏移互不相同。当前一个 dataset 默认一个分区时间，环比同比都绕这一个字段做自连接。变通是拆成不同 model，或把口径写进 `filterSql`。

### 跨门店这类横向比较

「各门店销售额」不是减日期，是同一时间切面按维度拆开。没有单独的「标杆店对比」算子；要的就是 `GROUP BY 门店` 加上指标上的聚合。时间怎么进 WHERE、指标怎么展开，上一节和第一节已经讲过，这里只说分组和聚合怎么来的。

1. **映射：认出「比的是哪一刀」。** 「各门店销售额」命中指标「销售额」和维度「门店」。「各」一般不是 schema 元素，不会单独进 `mapInfo`。如果说了店名（「朝阳店和海淀店」），还会命中维度值 VALUE，后面进 WHERE，不是进 GROUP BY。

2. **解析：决定 SELECT 里有谁、GROUP BY 写谁、聚合用哪个函数。** 先规则、后 LLM。分组不是靠「各」「对比」当关键词触发的，规则只是数 `mapInfo`：至少 1 个维度 + 1 个指标，就标成 `queryMode = METRIC_GROUPBY`。没有单独的 `needGroupBy` 标志。LLM 路径是 `queryMode = LLM_S2SQL`，有没有 GROUP BY 全看写出的 SQL。

   **规则路径（略）。** `dimensions` 进 SELECT 和 GROUP BY，`metrics` 套聚合（没说聚合词用 `defaultAgg`，说了「平均 / 最大」覆盖成 AVG / MAX），店名 VALUE 进 WHERE，一次写成 `SELECT 门店, SUM(销售额) ... GROUP BY 门店`。

   **LLM 路径：分组要模型自己写进 S2SQL。** prompt 里能看到映射命中的指标和维度，例如 `Metrics=[<销售额 AGGREGATE 'SUM'>]`、`Dimensions=[<门店 ...>]`，以及命中的店名 `Values=[<门店='朝阳店'>]`。没有「见到维度就必须 GROUP BY」的硬规则，「各门店」靠模型理解成分组。写对时长这样：

   ```sql
   SELECT 门店, SUM(销售额)
   FROM 销售数据集
   WHERE 数据日期 >= '2026-08-01' AND 数据日期 <= '2026-08-28'
   GROUP BY 门店
   ```

   常见写错——字段往往都在 schema 里，SQL 也能过解析，数字却不对，或根本没按店拆开：

   | 原句 | 模型可能写出 | 错在哪 | 后面谁能兜 |
   |---|---|---|---|
   | 「各门店销售额」 | `SELECT SUM(销售额) FROM ...`（没门店） | 理解成全市合计，没分组 | 校正不补维度；靠范文，或 Mapper 没命中「门店」时 prompt 里根本没有这个字段 |
   | 「各网点销售额」 | 同上，或乱猜一个维度 | 词典里叫「门店」，「网点」没命中 | 映射缺口，补别名；校正帮不上 |
   | 「各门店销售额」 | `SELECT 门店, 销售额 FROM ...`（无 SUM、无 GROUP BY） | 被当成明细 | `queryType` 不是聚合，GROUP BY 和 SUM 两边都不补 |
   | 「各门店销售额」 | `SELECT 门店, SUM(销售额) FROM ...`（漏 GROUP BY） | 非法聚合 SQL | 已判定为聚合且 SELECT 里有「门店」时，校正补 `GROUP BY 门店` |
   | 「各门店销售额」 | `SELECT 门店, 销售额 ... GROUP BY 门店`（漏 SUM） | 非聚合列和聚合混在一起 | 已有 GROUP BY 时，校正按 `defaultAgg` 套上 `SUM` |
   | 「各门店销售额」 | `GROUP BY 门店, 数据日期` | 多按天拆开，一行变成很多行 | 校正不删多余分组；靠范文或用户看卡片 |
   | 「朝阳店和海淀店销售额对比」 | 只 `GROUP BY 门店`，没有 `WHERE 门店 IN (...)` | 所有店都出来了 | 店名若已在 `Values=` 里，校正 / Schema 校正可能补 WHERE；没命中 VALUE 就补不上 |
   | 「朝阳店和海淀店销售额对比」 | `HAVING 门店 IN ('朝阳店','海淀店')` | 店名不是聚合结果，不该进 HAVING | 校正不改这种；HAVING 留给「销售额 > 100 万」这类指标阈值 |
   | 「销售额超过 100 万的门店」 | `WHERE 销售额 > 1000000` | WHERE 阶段还没有加总后的销售额 | 校正发现 WHERE 里是指标，会挪到 `HAVING SUM(销售额) > 1000000` |

3. **校正：只补「写出了一半」的情况。** 上表里能兜的，就是这一步：已有 SUM、SELECT 里有门店 → 补 GROUP BY；已有 GROUP BY、指标还是裸字段 → 套上 SUM；指标条件误写进 WHERE → 挪到 HAVING。`SELECT 门店, 销售额` 两个都没有，当成明细，两边都不补。SELECT 和 GROUP BY 还要对齐：GROUP BY 里有的字段，SELECT 里没有就补上。

4. **翻译：语义名换成物理表达式，GROUP BY 跟着走。** `SUM(销售额)` 按指标 `expr` 换成 `SUM(pay_amt)`；`GROUP BY 门店` 换成 `GROUP BY store_name`。门店和订单不在一张表时，JOIN 按第一节的关系图拼。最终形态大致是：

   ```sql
   SELECT t1.store_name AS 门店, SUM(t0.pay_amt) AS 销售额
   FROM order_table t0
   JOIN store_table t1 ON t0.store_id = t1.id
   WHERE t0.imp_date >= '2026-08-01' AND t0.imp_date <= '2026-08-28'
   GROUP BY t1.store_name
   ```

拿本店对标全市均值再归因，要再拼查询，不是翻译阶段多一种 JOIN。

## 九、项目实践经验总结

与小米三点经验对照，本项目沉淀的实践经验：

1. **用确定性换可靠性（分层降智）**：LLM 只做"理解与选择"（S2SQL 只含语义名），聚合展开（MetricExpressionParser）、过滤注入（DataModelNode）、JOIN 生成（SqlBuilder + 最短路径）、权限（AOP 切面）全部是确定性代码。可错的环节越少，系统越稳。
2. **不确定性不向下游传递**：映射不确定→四级相似度排序收敛 dataset（HeuristicDataSetResolver）；阈值按 STRICT/MODERATE/LOOSE 动态收紧；规则解析失败才降级 LLM；权限不确定→执行入口统一拦截。每层要么收敛，要么显式暴露候选给用户，不让模糊状态流入 SQL 执行。
3. **模型负责理解，系统负责执行**：schema 只以语义元素形式进入 prompt（PromptHelper），物理细节对 LLM 不可见；口径变更一处修改、事件驱动自动同步词典与向量（SchemaDictUpdateListener / MetaEmbeddingListener），无 prompt/few-shot 连锁修改。
4. **语义资产是第一生产力**：别名、术语（TermDescMapper 的"术语描述二次映射"）、维度值知识、记忆复用共同决定映射上限——badcase 的相当比例最终归结为语义资产缺口而非模型能力。
5. **评测闭环必不可少**：DSL 准确率与答案准确率分开评（evaluation/ 脚本），badcase 按环节归因，修复后追加专项用例回归；启用记忆机制让线上好 case 持续转化为 few-shot 资产。
