> 技术调研备忘录 · 智能问数 / Text2SQL 架构

数据部门给了 1000 张表，业务要同时要 BI 报表的稳和长尾探索的宽——这两个诉求天生互斥，架构必须先把它们拆开，再决定怎么接回来。

## 核心结论

1000 张表已经超出所有主流厂商公开建议的单一语义空间上限 10～30 倍（Snowflake 建议 ≤10 表，Databricks Genie 硬性上限 30 表、推荐 ≤5 表），所以"选一个框架吃下全部 1000 表"从一开始就不是选型问题，而是一个必然要做业务域拆分的工程问题。

BI 查询和长尾查询不应该走同一条链路：应该用 **确定性的语义层** 吃掉高频可预期的 BI 报表（失败要"报错"，不能"编造"），用 **更重的检索+Agent 链路** 兜底长尾探索式问题，中间加一层 **路由/缓存** 做分流。dbt 2026 年的内部基准显示，语义层覆盖到的问题准确率能到 98～100%，而裸 Text2SQL 直接对原始 schema 生成只有 64.5%——且两者失败模式本质不同：语义层失败是"答不出"，Text2SQL 失败常是"给出一个看起来对但错的数字"，后者对企业决策的破坏性要大得多。

## 01 千表意味着什么

先把规模感建立起来——这不是"多做一点工程"的量变，是好几个方案会直接失效的质变。

| 厂商/产品                | 单空间建议表数            | 应对超规模的做法                           |
| ------------------------ | ------------------------- | ------------------------------------------ |
| Snowflake Cortex Analyst | ≤ 10 表 / 50–100 列       | Cortex Agents 编排多个语义视图             |
| Databricks AI/BI Genie   | 硬上限 30 表，推荐 ≤ 5 表 | 多个 Genie Space（按业务域）+ Orchestrator |
| Amazon Q / QuickSight    | 按 Topic 划分             | NLU 先识别意图，路由到最相关 Topic         |
| Uber QueryGPT            | 按 12 个业务域切分        | Intent Agent → Workspace → Table Agent     |

没有一家公开披露过"单一语义层直接稳定支撑千表规模"的生产案例。某 2025 年行业报告称约 65% 的企业问数项目部署后因"准确性不足、业务适配性差"未达预期。 **这意味着预算和排期要按"需要自研大量 schema 拆分与治理工作"来做。**

> **规模拐点** ：当 schema 规模突破约 3000 列量级时，传统一次性检索方法召回率会跌破 40%，而迭代式方法（如 AutoLink）能维持在 90% 左右。1000 张表 × 20～30 列/表 ≈ 2～3 万列，刚好踩在这个拐点上。

## 02 推荐架构：三层，不是一条流水线

国际厂商、国内厂商和学术界在 2025–2026 年收敛到几乎同一个骨架：

**语义层（确定性）** ——承接高频、可预期的 BI 查询。指标/维度口径预先治理好，命中就直接出结果，失败就明确报错——不猜、不编。准确率目标接近 100%。

**路由 / 缓存（分流）** ——判断一个问题该走快车道还是慢车道。轻量意图分类器 + 语义缓存，命中语义层已定义的指标就走确定性路径；未命中才升级到重链路。大部分调用应该在这里被"拦下来"。

**长尾 Agent（概率性）** ——承接开放式、探索性的即席问题。做 schema 检索、多表推理、SQL 生成与自纠错，接受比语义层更低但可用的准确率，作为补充而不是主力。

关键心态转变： **不要把"能不能直接对 1000 张表做端到端 Text2SQL"当作核心难题** ——业界已有大量证据说明这条路径准确率有天花板（Spider 2.0 上顶尖模型也只有 20～30%），真正该攻克的是"怎么让尽可能多的高频问题绕开这条路径"。

## 03 语义层：先做 20 个指标

- • **起步范围要小。** dbt/Cube/衡石一致建议先圈定 Tier-0 核心指标（量级 10～30 个）进语义层，而不是试图一次性覆盖全部 1000 张表。
- • **权限要在编译期做。** 2026 年 Cube/ThoughtSpot 提出的"compile-time governance"思路——行级/列级权限在 SQL 生成阶段就注入，让 Agent"物理上拼不出"越权查询。
- • **MCP 正在成为标准接口。** 让 Agent 通过 MCP 协议"按指标名请求"，而不是现场编写 SQL。

> dbt 2026 年基准：原始 schema 上直接 Text2SQL 的整体准确率 64.5%，接入语义层后 72.7%，而语义层覆盖到的子集准确率高达 98～100%。更关键的是失败模式差异——语义层失败时明确报错，Text2SQL 失败时经常返回"看起来合理但错误"的答案。

## 04 路由与降级

企业数仓的真实查询分布高度倾斜——约 94.5% 的查询是重复性的，约 50% 能在历史记录里找到匹配模板。

**意图分类** ：vLLM Semantic Router 用轻量分类器（ModernBERT）判断问题复杂度，simple 走快速路径，complex 进入 CoT 链路，实测整体准确率提升约 10%、延迟下降约 50%。COGNI 用 LoRA 微调的 1.5B 小模型做同类判定，准确率 93.8%，推理成本只有大模型的约 1/7。 **这类小模型路由器是目前公开资料里性价比最高的组件。**

**语义缓存** ：纯 embedding 相似度缓存会把"2024 年 Q1 的 MAU"和"2025 年 Q1 的 MAU"误判为命中——这是最危险的失败模式。COGNI 的解法是 embedding 粗筛 + 实体校验 + 意图分类 + 时效性校验的多重联合验证，做到零误命中、87% 召回。 **"fail-closed"（宁可不命中也不能命中错）应该是缓存层的第一原则。**

**域内分片** ：Uber QueryGPT、LinkedIn SQL Bot 的共同做法是先按业务域把千表问题切成若干个几十表的子问题，再在子问题内部做检索。

## 05 长尾 Schema Linking：要做成迭代循环

Spider 2.0（ICLR 2025 Oral）引入"企业级真实规模"评测——schema 常超 1000 列，即便 o1-preview 准确率也只有约 21%，论文明确把"大规模 schema 下的表/列错误链接"列为主要失败原因。

主流应对方案已从"单次 embedding 召回"演化为多轮迭代式架构：

- • **AutoLink** ：把 schema linking 定义为 Agent 交互式序列发现—— `explore_schema` → `retrieve_schema` → `verify_schema` → `add_schema` ，最多 10 轮。3000+ 列大库上基线方法召回率跌破 40%，AutoLink 维持约 90%，token 消耗降低约 87.7%。
- • **LinkAlign** ：两阶段——Database Retrieval（多轮语义检索筛库）+ Schema Item Grounding（库内定位表/列），在 Spider2.0-lite 上做到 33.09%，当时排行榜第一。
- • **CHESS（Stanford）** ：用局部敏感哈希检索实体值 + 向量检索元数据 → Schema Selector 把"数百列"收窄到"通常少于 10 列"，BIRD dev 上开源方案做到 61.5%。

**Agentic 自纠错** 方面，Google Cloud 归纳的六大失败模式值得参考：Agent 自行决定执行顺序导致跳步、schema 幻觉、复杂 JOIN 出错、每步都调 LLM 浪费成本、未验证直接执行危险查询、输出混入多余文本。对应解法是用 `sqlglot` 做 **本地、免 LLM 调用的语法校验** 先挡一轮——这个分层思路性价比很高。

**"Peek"技术** ——为每个候选表抓一行样本数据"偷看"真实结构，能澄清命名歧义，相比全量 schema 转储节省约 85% token，首次生成成功率 78%，自我修正后升到 94%。

## 07 对照 SuperSonic

**值得保留/强化** ： `DefaultSemanticTranslator` 用 Calcite 生成物理 join/聚合逻辑的思路，本质就是"确定性语义层生成 SQL"，值得作为语义层基础。 `S2DataPermissionAspect` 在 AST 层面注入行级/列级权限，已经是"compile-time governance"。 `dataSetId` 概念本身就是一种"业务域分片"。

**在千表规模下会先出问题** ： `EmbeddingMapper` 目前是对整个知识库做单次向量召回——按 AutoLink 结论，超过 3000 列规模后召回率会跌破 40%，需要改成两阶段先域粗筛再表/列精排。 `ChatWorkflowEngine` 对每条查询都跑完整五阶段流水线，没有缓存快车道。 `TimeCorrector` 缺时间条件时自动补默认日期——这是"静默猜测"，应改为低置信度时触发澄清。

## 08 元数据治理

LinkedIn 千表级生产案例的消融实验显示：知识图谱相关组件（历史样例查询、表聚类、元数据属性）把答案质量分从 9% 提升到 48%，而排序器/修复器主要降低幻觉率，对语义正确性提升有限。 **元数据治理对准确率的贡献可能比换一个更强的模型或更复杂的 Agent 框架更大。**

现实很残酷：超过 95% 的字段缺乏描述。DBAutoDoc 这类"统计分析 + LLM 迭代精化"方案，2 次迭代即收敛，成本约 0.7 美元/100 张表——对 1000 张表而言，这是一笔很小但杠杆很大的投入。

## 10 落地路线图

- • **阶段 0 — 元数据摸底** ：跑字段/表描述覆盖率统计，用自动化工具补全；从历史查询日志做表访问频次聚类。
- • **阶段 1 — 先立住 20 个 Tier-0 指标** ：挑高频核心表和指标，建小而确定的语义层，把"同一指标不同入口数字一致"做对。
- • **阶段 2 — 路由 + 缓存上线** ：加轻量意图分类器判断命中语义层还是升级；语义缓存按 fail-closed 原则设计。
- • **阶段 3 — 长尾 Agent 兜底** ：走"业务域粗筛 → 域内向量检索 → LLM 精排 → 生成 → 执行验证"的迭代式 pipeline，低置信度触发澄清或拒答。持续把新长尾问题"晋升"进语义层，形成闭环。
