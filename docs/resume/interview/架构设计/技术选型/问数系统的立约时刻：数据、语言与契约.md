维特根斯坦说过，语言的意义在于使用。任何一家成规模的企业里，大概都没有哪个部门能单独垄断「销售额」这个词的定义权——财务部、运营部、市场部各自在用，各自指向不同的表、不同的过滤条件、不同的历史惯例。问数系统要做的，表面上是把自然语言翻译成 SQL；往深处说，是在两种语言游戏之间架桥：一边是业务人员的日常提问，一边是数仓里那套只为 ETL 工程师可读而设计的命名体系。

桥搭不好，就会出现一种特别现代的错误：SQL 执行成功，结果看起来合理，口径却是错的。

这类错误比系统崩溃更麻烦。崩溃至少诚实；口径错误则像一句语法正确、语义漂移的谎话——它有自己的执行计划，有自己的返回行数，甚至还有图表。

## 一、两个分数，两种认识论

2026 年 6 月，EntSQL benchmark 公布了一组的数字。

EntSQL 测的是 Text2SQL——自然语言到 SQL 的转换——在企业真实知识条件下的表现。1066 道 BI 场景题，96% 需要表结构之外的企业 domain knowledge；即便把长文档全部喂给模型，当时最佳系统的执行准确率（Execution Accuracy, EX）只有15.9%。

几乎同一时期，BIRD leaderboard 上，顶尖方案的 EX 已进入75%–80%区间。

若只读新闻标题，你会以为行业在飞速进步；若把两份榜单并排放，你会意识到它们测量的不是同一种「知道」。BIRD 更接近封闭考试：题目、hint、schema 均已给定，考察模型能否在规则内完成推导。EntSQL 更接近上班：用户只丢来一句业务话，系统得自己去找哪份文档、哪条口径、哪段历史约定才算数。

认识论上，这是「在已知框架内正确推理」与「在开放语境中正确理解」的分野。前者可以刷分，后者决定你能不能上线。

对企业问数而言，这不是学术细节。同一句「销售额」，在对外披露、经营分析、绩效考核里可能对应三套完全不同的 SQL。EntSQL 用的正是中文企业 BI 域——它测的，是 leaderboard 之外、PPT 之外那个更吵闹的生产世界。

## 二、在 SQL 之前，问题已经发生了

取一个常见问句：

「上季度华东区重点客户的净销售额趋势如何？」

这句话在语法上完整，在语义上却像一个未打开的俄罗斯套娃。「上季度」是自然季度还是财务季度？「华东」按注册地、销售归属还是履约地？「重点客户」看合同分级、近十二个月贡献，还是销售手工维护的名单？「净销售额」扣不扣退货、返利、冲销？

金融、零售、制造、SaaS 的字段名和口径各不相同，但歧义结构是同一类：每个词都在等待一个尚未说出的组织约定。

解释学有一个老概念叫「解释学循环」：理解部分总是预设了对整体的理解，而整体又只能通过部分来把握。问数系统每回答一题，都在这个循环里打转。用户以为自己在问一个指标；系统必须先猜用户处在哪一个部门、哪一种口径、哪一种时间约定里。

猜错了，后面的 JOIN 再漂亮也没有意义。

2026 年 2 月至 6 月涌现的一批论文——EntSQL、CLARITY、BIRD-Interact、LLM-friendly Schema、TACO、OSI、Snowflake Semantic View Autopilot——名字各异，却在同一条哲学线索上汇合：LLM 不是进入数据库的裸眼，它需要中介；而中介不能只有模型权重，必须有组织愿意公开化的意义结构。

## 三、Benchmark 分层，或：我们究竟在测量什么

上一篇公众号讲过 Spider、BIRD、Spider 2.0 的阶梯。2026 年上半年，阶梯又多了几级，每一级都在逼问同一个元问题：你想证明的是智能，还是表演？

BIRD-Interact把多轮交互推上舞台：澄清、改口、读知识库、从执行错误里爬出来。GPT-5 在 FULL 任务集 c-Interact 模式下成功率8.67%，a-Interact17.00%。数字会随模型迭代波动，量级不会骗人——对话式问数仍然极难。

CLARITY则更接近诊断哲学：它不仅问「答错了没有」，还问「错在哪一层 meaning 上」。系统常能感到「这话有问题」，却指不出是 GMV 的口径、时间的边界，还是根本不存在对应字段。

Spider 2.0把场景拉到企业工作流：上千列、上百行 SQL、多方言、项目级代码。o1-preview 类 agent 成功率约21%。

三层能力由此浮现：（1）单轮 SQL 正确性；（2）企业知识 grounding；（3）模糊、多轮、受限条件下的交互可靠性。只拿第一层分数论证第三层能力，在逻辑上站不住，在激励结构上却极其常见——因为 EX 好测，诚实难测。

古德哈特定律在这里换了个马甲：当 Execution Accuracy 成为唯一 KPI，系统就会学会硬答。硬答在 benchmark 里是分数，在生产里是事故。

## 四、Schema 契约：命名即世界观

Schema——表、字段、类型、关联——不是中性的物理描述，而是一套组织如何切分世界的语法。t_ods_cst_bas_inf对人类数据工程师可读，因为它嵌入在 ODS 分层、字段规范、治理流程之中；对 LLM，它往往只是一串缺少公共生活形式的符号。

2026 年 6 月的LLM-friendly Logical Database Design提出了一个工程上朴素、哲学上却不简单的命题：逻辑 schema 的设计目标函数，应增加「LLM 可读」这一维。论文给出三个语义保持变换：抽象（+A）、分区（+P）、重命名（+R）。在 BIRD-Union / Spider-Union 上，完整 +A+P+R 最高带来4.2 pp的 EX 提升——幅度不大，方向明确：改进发生在 middleware，而非推倒物理数仓。

命名因此不是审美问题，是认识论问题。你让模型读内部黑话，它就只能在黑话里猜；新员工猜错了会问你，模型猜错了会给你 SQL。

列名可读之后，仍有解释空间。monthly_average_balance是日均还是月末？是否含未入账项或附属科目？TACO用任务感知的列描述去填这个缝，下游实体链接最高提升52%。另一项合成 metadata 研究则发现：对人冗余的描述，对模型可能是必要的——人类追求简洁，机器需要语境；这几乎是对「解释学循环」的一次工程化脚注。

2026 年 6 月底的 on-prem 横评（BIRD dev，n=1534）补了另一刀：self-correction稳定显著（+1.2 至 +3.6 pp）；schema linking 即便 96.5% 金表召回，在 BIRD 窄 schema 下无显著增益；self-consistency 花 5 倍 token 换+0.13 pp。在宽 schema 生产环境里 linking 依然关键——但它的天花板，首先由 Schema 是否可读决定。

## 五、语义契约：从私人语言到公共口径

维特根斯坦晚年警惕「私人语言」：若意义只存在于说话者内心，则无法被检验。企业数据领域有一种结构性的私人语言——每个部门都有自己的「销售额」，文档里各写各的，报表里各算各的，会议里各认各的。

语义层要做的事，是把私人语言收编为可执行的公共词典：指标如何定义、维度如何切分、筛选如何生效；LLM 先把自然语言映射到语义查询（如 MQL），再由引擎确定性编译为 SQL。不确定性留在意图理解，确定性留给编译——这是「意图不确定、执行确定」的分工，也是组织愿意为自己的口径负责的分工。

2026 年的行业动作，是在把这套词典标准化、资产化。OSI（0.1.1）用 YAML/JSON 描述 metrics 与 ai_context；Snowflake Semantic View Autopilot（2026-02-03 GA）从 Tableau / Power BI 导入已有度量；国内Aloudata的 NL2MQL2SQL 与之同构。厂商「100% 准确」的表述需独立验证，但方向清楚：语义不是 prompt 里的临时补丁，而是组织记忆的正式版本。

EntSQL 15.9% 则提醒：仅有 semantic view、没有长文档 grounding，仍不够。语义层必须接入指标说明、报送规则、部门词典——否则它只是一层薄薄的翻译，底下仍是各自为政的私人语言。

## 六、交互契约：知道 limits 的智慧

可靠问数还有第三份契约，最容易被 leaderboard 忽略：交互契约——系统何时追问、何时拒绝、如何把口径暴露给用户复核。

CLARITY把失败拆成语义模糊、不可回答、上下文不足，且常叠加。RTS（Adaptive Abstention）用 conformal prediction 在 schema linking 阶段给出统计保证：不确定则 abstain，转入人机澄清。论文没有规定「应拒绝百分之几」——那会把 humility 再次变成 KPI。可靠的是流程可审计，不是拒绝率好看。

BIRD-Interact的低成功率说明：多轮交互是独立难度，不是单轮能力的线性延伸。一线业务人员问「这个客户的回款风险怎么样」，系统若基于单一历史字段给出笃定答案，而未识别数据覆盖不足或权限边界——这在伦理上比 abstain 更成问题。

这里涉及一种古老的认识论美德：在证据不足时 withhold judgment。问数产品若从不拒绝，不是全知，是无边界。

生产评估因此应超出 EX：Hallucination Rate、Abstention / Clarification 质量、Trust calibration、权限合规、口径可复核性。指标多不是累赘，是在对抗「唯分数论」对系统的扭曲。

## 七、Agent：工具理性需要规范基础

Agent 化是 2026 年的显学。AgentNLQ（含 JPMorgan 研究人员）以 schema enrichment 与 multi-agent 编排，在 BIRD 11 域 dev 达78.1% semantic accuracy；复杂查询确实需要规划、探索、验证的闭环。

ReViSQL则提供对照：清洗 BIRD Train，61.1%样例有标注错误；verified 数据 + RLVR 单轮提升8.2–13.9 pp；235B 在 expert-verified mini-dev 达93.2% EX，超代理人类92.96%。两条路线测量切片不同，不宜比高低；共同结论是：Agent 编排与数据质量并非互斥，但 Agent 不能替代 schema 与语义治理。

哲学上，Agent 是工具理性的放大器：能走更多步、查更多表、试更多路径。但若规范基础——可读 Schema、公共口径、交互边界——尚未建立，放大器的唯一效果，是把幻觉和越权也放大。

Agent 应是执行引擎，不是意义来源。

## 八、边界：语义算子、成本与他者

问数正在越过结构化表格，进入合同文本、工单、录音。SEMA-SQL 把 LLM UDF 纳入 Hybrid Relational Algebra，semantic join 调用减少约93%；Sema 在 DuckDB 上将语义算子作为一等公民优化。哲学问题随即变成经济学问题：对百万条合同逐条调用 LLM，成本与延迟都会失控——先结构化过滤，再语义处理，是常识，也是边界意识。

Agents That Know Too Much（2026-06）从数据面梳理 Agent 泄露：Schema 暴露业务逻辑，中间查询暴露分布，跨会话记忆暴露他者。AgentSCOPE报告80%+场景存在 pipeline 中间违规。信息流控制（IFC）是目前少数能同时应对组合泄露与跨会话推理的机制。

Schema 最小暴露因此有两重含义：安全上的，也是认识论上的——未授权的东西，不应进入解释循环。

## 九、Steelman：包一层语义层，够了吗？

为数仓和 BI 体系已投入多年的团队，最常见的反驳是这样的：分层治理、指标平台、报表资产都已就位；SVA、Aloudata 可从存量 BI 导入语义；ReViSQL 表明强模型 + 自校正可在 academic benchmark 触顶——为何还要动 Schema 与交互？

这个反驳成立一半。一半成立，是因为不应推倒物理数仓；另一半不成立，是因为「包一层」若只包 DDL，不包文档、不包追问、不包拒绝，就仍是私人语言的临时遮羞布。

回应可以压缩为四句。+A/+P/+R是逻辑 middleware，与语义层兼容。EntSQL证明仅有 schema、无长文档 grounding 不够。BIRD 高分 ≠ 生产高分——ReViSQL 93.2% 在 expert-verified mini-dev；Spider 2.0 / EntSQL 才更接近真实生产。交互契约无法靠语义层自动长出。

结论不是 Schema 与语义层二选一，而是Schema × 语义 × 交互的乘积。缺一项，另两项的边际效益被稀释——乘积关系比加法关系更冷酷。

## 十、落地：立约的三阶段

| 阶段 | 动作                                 | 为何先做                    |
| ---- | ------------------------------------ | --------------------------- |
| 短期 | 元数据别名、列描述、verified queries | 不改物理表，ROI 最高        |
| 中期 | 语义层、轻量 Agent、abstain/clarify  | 口径可证、交互可控          |
| 长期 | +A+P+R、语义算子治理、IFC            | 面向 EntSQL/Spider 2 级场景 |

立约的顺序也有讲究。先盘点 20 个高频且易混口径的问题——指标定义、字段映射、权限边界、责任人。再建 LLM 可读逻辑 schema：别名、视图、分区。最后把追问、拒绝、口径展示、SQL 复核写进产品规格，而不是写进 prompt 里的「请谨慎回答」。

业务负责人可以参与第一步：列出团队最常问的 20 个数据问题，逐项确认「这个词在我们部门到底指什么」。这不写 SQL，但决定问数系统的语义上限——公共语言不是技术团队的私产，是组织的合约。

两次转向

问数系统正在经历两次转向。

第一次，是承认 LLM 会写错 SQL——于是有了 schema linking、few-shot、自校正。

第二次，是承认数据栈尚未为新的语言消费者提供足够的公共意义与交互边界——Schema 像内部方言，口径像部门传说，benchmark 却假设 hint 永远完备、问题永远可答。

2026 年 2 至 6 月的论文与行业动作，拼起来是一句话：让 LLM 适应数据库的旧路趋近饱和；让数据库（广义：Schema、语义、交互协议）适应 LLM，才是下一程。务实路径不是抢购「BIRD 第一」的 API，而是分阶段履行三份契约——可读、可证、可控。

模型不会替机构定义「销售额」。

它只会把尚未定义清楚的概念，以 SQL 的形式，坚定而忠实地执行出来——这正是问数系统最哲学、也最危险的地方。

## 附录：EntSQL

[EntSQL](https://arxiv.org/abs/2606.03363)（*EntSQL: A Benchmark for Grounding Text-to-SQL in Long-Context Enterprise Knowledge*，2026 年 6 月）测的是：模型能否从长篇企业文档中找到指标口径、报表惯例和组织规则，并落实到 SQL。数据集见 [Hugging Face](https://huggingface.co/datasets/XuWave/Rethinking_Enterprise_Text_to_SQL)。

规模是 1,066 个中英文对齐样例、五个业务领域；多数样例需要问题和 schema 之外的领域知识。英文且提供长文档时，被测系统最好为 15.9%。这是该设置下的最好结果，不能直接和 Spider、BIRD 的分数比较。1,066 是对齐样例数，中英两份输入不是 2,132 道独立题。

Spider、BIRD、Spider 2.0 分别覆盖 schema 泛化、大规模库与外部知识、工业工作流。EntSQL 补的是私有长文档上的 grounding。不要和 [BIRD-Ent、Spider-Ent](https://openreview.net/forum?id=gXkIkSN2Ha) 混淆：那是另一项工作里的企业化基准，重点是大规模表范围、复杂命名和分散文档检索。

可借鉴三组对照，这是本项目的实验设计，不是论文结论：只给 schema；给 schema 加原始业务文档；给已治理的指标定义或语义层。用来区分知识没有给到、给了但没找对、找对了但 SQL 没落实。

## 附录：Text-to-SQL Friendly Logical Database Design

[The Case for Text-to-SQL Friendly Logical Database Design](https://arxiv.org/abs/2606.03145)（Zhang、Miao、Wang，2026 年 6 月）把优化对象从模型、提示词和推理流程，扩到模型看到的数据库。底层数据与关系语义保持不变，逻辑 schema 被当成可设计的接口。正文第四节的三个变换，对应模型读 schema 时要处理的三件事：

- **+A 抽象**：从历史 SQL 里挖反复出现的多表组合，收成逻辑视图；历史示例同步改写成使用该视图的 SQL，且只保留执行结果等价的改写。视图增强原 schema，供模型选用。多余的 INNER JOIN 会因关联键为空而滤行、改变结果，所以不把所有表合成一张宽表。
- **+P 分区**：这里的分区是面向查询的局部 schema，不是物理分区。先定位相关区域，再从该区域的历史查询里检索示例，使范文和本轮看到的表范围一致。裁剪必须留下回答问题所需的表、列和关系。
- **+R 重命名**：只改模型看到的名称，例如 `molecule.label` 换成 `Chem_Molecules.carcinogenic_flag`，再经可逆映射还原到物理库。物理表不必改。没有历史查询时，+R 可直接用；+A 可按当前问题按需生成视图并缓存。

在 BIRD-Union / Spider-Union 上，七种非空组合里表现最好的一组会随模型和流水线变化；完整 +A+P+R 持续有提升，执行准确率最高约提高 4.2 个百分点。对本项目，它对应三件已有工作是否对齐：近义指标的名称能否区分，常用关联是否已是验证过的逻辑结构，动态范文是否与本轮 schema 和逻辑视图一致。清晰的逻辑 schema 不会自动补上未知的业务规则。
