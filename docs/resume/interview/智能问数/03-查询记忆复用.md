| **实现归属** | 开源 SuperSonic 链路；业务侧打开 Memory Review、冷启动、人审运营、评测 | 「我从零自研了记忆向量库框架」 |

| **推荐异步** | `CompletableFuture.runAsync` 按 `queryId` 回写 `similarQueries` | 开源里**没有**独立 version 字段防竞态——勿编「版本号协议」除非你们 fork 加了 |

## 0.4 存什么：DB 一行 + 向量一条

### 表 `s2_chat_memory`（`ChatMemoryDO`）

| 字段 | 含义 | 面试怎么说 |
|------|------|-----------|
| `id` | PK | — |
| `agent_id` | Agent 隔离 | 跨 Agent 不召回 |
| `query_id` | 来源问答 | 可回溯 ELK / 人审 |
| `question` | 用户问题 | **做 embedding 的文本** |
| `side_info` | SideInfo（如 CurrentDate） | 范文四元组之一 |
| `db_schema` | 当时 Schema 串 | 范文四元组之一 |
| `s2_sql` | S2SQL | 范文四元组之一 |
| `status` | `PENDING` / `ENABLED` / `DISABLED` | 只有 ENABLED 进向量可召回 |
| `llm_review` / `llm_comment` | POSITIVE\|NEGATIVE + 评语 | 自动审 |
| `human_review` / `human_comment` | 人审 | **冲突以人审为准**（运营约定） |
| `created_*` / `updated_*` | 审计 | 有用户名；**无「被召回次数」** |

代码：`chat/server/.../persistence/dataobject/ChatMemoryDO.java`。

### 向量侧 `Text2SQLExemplar`（不进上表）

| 项 | 值 |
|----|-----|
| 集合名 | `memory_{agentId}`（前缀 `s2.embedding.memory.collection.prefix`，默认 `memory_`） |
| 向量化对象 | **`question` 文本** |
| metadata / payload | JSON：`question` + `sideInfo` + `dbSchema` + `sql` |
| 系统静态兜底集 | `text2dsl_agent_collection`（`s2-exemplar.json`，演示域「超音数」） |

```
Text2SQLExemplar { question, sideInfo, dbSchema, sql, similarity }
```

**金句**：DB 是状态机与人审台账；向量库是「可被 Parser / 推荐召回的 ENABLED 投影」。Embedding **只打 question**，SQL 在 metadata 里当 payload。

### 生命周期状态机（背这张）

```
LLM_S2SQL 执行 SUCCESS
        │
        ▼
  createMemory → status=PENDING   （只写 DB，不写向量）
        │
        ├─ MemoryReviewTask（60s）opinion=POSITIVE
        │         → status=ENABLED → enableMemory → storeExemplar(memory_{agentId})
        │
        ├─ opinion=NEGATIVE
        │         → 记下 llm_review；status 通常仍 PENDING → 人审周批次
        │              ├─ 人审通过 → ENABLED + 入向量
        │              └─ 否决 → DISABLED（并从向量 remove，若曾启用）
        │
        └─ 用户反馈 score≥5 / ≤1（ChatManage）也可直接 ENABLED / DISABLED
```

## 0.5 调用点：写路径 / 读路径 / 与推荐同库

### 写路径（沉淀）

| 步骤 | 类 · 方法 | 要点 |
|------|-----------|------|
| 1. Parse 成功挂四元组 | `LLMResponseService.addParseInfo` | `properties[sql_exemplar]=Text2SQLExemplar` |
| 2. 执行成功落 PENDING | `SqlExecutor.execute` | 仅 `QueryState.SUCCESS` **且** `LLMSqlQuery.QUERY_MODE`；规则 SQL 不入库 |
| 3. 去重 | `MemoryServiceImpl.createMemory` | 同 agent + 同 question 已有 ENABLED → **跳过** |
| 4. 定时审 | `MemoryReviewTask.review` `@Scheduled(60s)` | 需 `Agent.enableMemoryReview()`；已有 llm/human review 则跳过 |
| 5. 入向量 | `MemoryServiceImpl.enableMemory` | `exemplarService.storeExemplar(memory_{id}, …)` |
| 6. 启动回灌 | `MemoryServiceImpl.run`（ApplicationRunner） | 把已有 ENABLED 重新灌进向量，防重启丢索引 |

**面试时怎么说**：

> 「执行成功只证明能跑，不证明能当范文。先 PENDING 进表；MemoryReview 判 POSITIVE 才 ENABLED 并写入 `memory_{agentId}`。人审每周清 NEGATIVE。」

### 读路径（复用 → `#Exemplars`）

| 步骤 | 类 · 方法 | 配置 |
|------|-----------|------|
| 1. 召回 | `NL2SQLParser.addDynamicExemplars` → `ExemplarService.recallExemplars` | `exemplar-recall.number=10` |
| 2. 挂到请求 | `QueryNLReq.dynamicExemplars` | 同步，堵在 Parser 前 |
| 3. 筛成 few-shot | `PromptHelper.getFewShotExemplars` | `few-shot.number=5`；similarity>0.989 必留 |
| 4. 拼 prompt | `OnePassSCSqlGenStrategy` | `#Exemplars: {{exemplar}}`；每行 `Question,Schema,SideInfo,SQL` |
| 5. 不足时 | 同上 PromptHelper | 用系统集 `text2dsl_agent_collection` 补齐候选池 |

配置见 `assembly/conf/s2-config.yaml`：`parser.exemplar-recall.number: 10`、`few-shot.number: 5`、`self-consistency.number: 1`。

### 与相似推荐：同一库，两条读路径

| | 记忆复用（本文） | 相似推荐（[04](./04-推荐问题.md)） |
|--|----------------|----------------------------------|
| 类 | `NL2SQLParser.addDynamicExemplars` | `QueryRecommendProcessor` |
| 时机 | Parse **前**，同步 | Parse **后**，`runAsync` |
| topK | 召回 10 → 用 5 | 硬编码召回 **5** |
| 用字段 | 四元组进 LLM | **只取 `question`** → `similarQueries` JSON |
| 集合 | `memory_{agentId}` | **同一个** |

**金句**：简历拆两个模块，不是两个向量库——是 **同步教模型** vs **异步给人点**。

## 2.1 30 秒概括

> "SchemaMapper 优化完后端到端卡在 72%——字段常选对，Parser 仍因 **Few-shot 结构不对齐** 翻车。业界（DIN-SQL / DAIL-SQL）已证明 Text2SQL 高度依赖示范质量与示例选择；我们原来是 JSON **写死静态范文**（演示域『超音数』），对金融题甚至变成有害示范（如把『去年』教成滚动 365 天）。记忆复用：成功 SQL 过审入库，Parser 按相似度动态召回同构范文。端到端 72%→87%；Schema 已对子集上 Parser 条件准确率约 75%→90%。核心不是『存 SQL』，是 **按题选对示范，而不是堆死示例**。"

## 2.2 功能实现类问题

**Q：为什么会想到做记忆复用？最核心的痛点是什么？原来什么样？不做的替代方案呢？**

> "**核心痛点：Text2SQL 的准确率高度依赖 Few-shot 范文的『结构相似度』，而原来用的是对所有题一视同仁的静态范文——结构不对齐时，范文不但帮不上忙，还会教坏。**
>
> **产品价值（顺带说清『为什么值得做』）**：
> 1. 研究员查询**结构大量重复**（只换实体/时间），同构范文收益高
> 2. T1 后瓶颈在 **Parser**——字段对了仍可能时间/聚合写错
> 3. 成功经验要在 **同一 Agent 内跨用户沉淀**——甲做对的题，乙直接受益
>
> **业界背景（为什么必须较真 Few-shot）**：
> - DIN-SQL（NeurIPS 2023）：合适的 in-context 示例相对简单 few-shot 大约 **+10pp** 量级
> - DAIL-SQL：few-shot 相对 zero-shot 可到 **+11pp**；**精选示例显著优于随机示例**
> - 静态写死 demonstration 在范文与当前题差距大时会出现 **retrieval bias**——LLM 被不相关示例带偏
> - 该选的是 **SQL 意图/结构相近** 的题，而不是表名、公司名碰巧相似的题
>
> 结论：**Parser 不是缺『几条 SQL』，缺的是『跟当前题同构的成功写法』。**
>
> **原来的状态（T1：Schema 已优化，记忆库未上）**：
> - `#Exemplars` 主要靠配置里的**静态 Few-shot**（如 `s2-exemplar.json`）
> - 内容是开源演示域：『超音数近 12 个月访问人数按部门』等
> - **所有金融 query 共用这一小撮范文**——和真实题型的 SQL 骨架对不上
>
> **能说明痛点的例子（结构错位 / 有害示范）**：
>
> | 当前用户问题（需要的 SQL 骨架） | 静态范文在教什么 | 实际翻车 |
> |-------------------------------|-----------------|---------|
> | 「A 股去年 ROE 排名前 10」→ `ORDER BY` + `LIMIT` + 衍生指标 | 『查某用户访问次数』→ 简单 `WHERE` | 学不会排序/截断 |
> | 「比亚迪去年营收」→ 自然年区间 | 『超音数近 12 个月』→ **滚动 365 天** | **照着写成滚动窗口（有害示范）** |
> | 「比亚迪与宁德时代营收对比」→ `IN` / 多实体 | 单实体等值过滤 | 结构迁不过去 |
>
> **如果不做动态记忆，替代方案及为何否掉**：
>
> | 替代方案 | 做法 | 为什么不够 |
> |---------|------|-----------|
> | **一直堆静态 Few-shot** | 每种骨架手写进 JSON | 滞后线上；堆数量 ≠ 选得准；token/维护双爆 |
> | **每次 prompt 塞尽量多范文** | 几十上百条全进 `#Exemplars` | 超上下文；噪声大 |
> | **微调专用模型** | 用成功 SQL 微调 | 成本高、迭代慢 |
> | **动态检索同构范文（我们选的）** | 成功过审 → 向量库 → 按 query 召回注入 | 对齐 example selection；范文跟业务长 |
>
> **一句话**：业界证明 Text2SQL 拼的是 **选对示范**；我们原来是 **写死示范**；记忆复用是把『做过对的同构题』动态选进 Parser prompt。"

**Q：记忆复用作用在链路的哪一步？怎么起作用的？和 SchemaMapper / 相似推荐什么关系？**

> "准确落点是 **Parser 阶段**（Semantic Parser / `NL2SQLParser` → `OnePassSCSqlGenStrategy`）：
>
> ```
> 多轮改写 → SchemaMapper（字段映射 → 产出本轮 Schema）
>         → 【Parser：生成 S2SQL ← 记忆复用注入 #Exemplars】
>         → Corrector → Translator → SQL 执行
>                                      ↓
>                              成功且过审 → 写入记忆库
>                                      ↓（异步另一用途）
>                              相似问题推荐只取 question 文案展示
> ```
>
> **读路径（复用，同步）**：
> 1. SchemaMapper 选好字段后进入 Parser
> 2. 向量召回候选（最多 10）→ 筛成 few-shot（本仓库 5）→ 注入 `#Exemplars`
> 3. LLM 照着同构成功题写当前 S2SQL
>
> **写路径（沉淀）**：执行成功 → PENDING → LLM/人审 → ENABLED 才可被召回
>
> **和另外两个模块的分工**（常被追问，一次讲清）：
>
> | 模块 | 链路位置 | 给谁用 | 取什么 |
> |------|---------|--------|--------|
> | **SchemaMapper** | 映射阶段 | 系统选字段 | metric/dimension → 拼进 Parser 的 `{{schema}}` |
> | **记忆复用** | **Parser 阶段** | 给 LLM 当范文 | `(Question, Schema, SideInfo, SQL)` → `{{exemplar}}` |
> | **相似推荐** | **Parse 之后异步**（不堵主解析） | 给人点（行为实验期尤甚） | 只展示历史 `question`；**与记忆复用共用向量库**；写进该 `queryId` 的 `similarQueries`，前端展开再读 |
>
> **一句话**：SchemaMapper 选对字段；记忆复用教 Parser 写法；相似推荐把成功问法露给人——实验运维反复查时最省打字。"

**Q：怎么注入到 prompt 的？完整 prompt 长什么样？10 条候选怎么筛成 5 条？**

> "Parser 模板四个占位符：`{{exemplar}}` / `{{question}}` / `{{schema}}` / `{{information}}`（模板中英对照见下）。
>
> **模板原文（中英对照）**：
>
> ```
> #Role: You are a data analyst experienced in SQL languages.
> #角色：你是一位精通 SQL 的数据分析师。
>
> #Task: You will be provided with a natural language question asked by users,
> please convert it to a SQL query so that relevant data could be returned
> by executing the SQL query against underlying database.
> #任务：把用户自然语言问题转成可执行 SQL。
>
> #Rules: / #规则：
> 1. 列名和取值必须出现在 Schema 里，禁止幻觉。
> 2. 时间范围用 > < >= <= 写出。
> 3. Question 没提时间就不要擅自加时间条件。
> 4. 不要用函数推算日期区间。
> 5. 嵌套聚合用 WITH。
> 6. AS 别名用下划线包起来。
> 7. 别名语言与 Question 一致。
>
> #Exemplars: {{exemplar}}
> #Query: Question:{{question}},Schema:{{schema}},SideInfo:{{information}}
> ```
>
> **条数配置**：
>
> | 配置项 | 本仓库 | 含义 |
> |--------|--------|------|
> | `exemplar-recall.number` | **10** | 向量召回**候选池**上限 |
> | `few-shot.number` | **5**（参数默认 3） | **真正写入 `#Exemplars` 的条数** |
>
> **10 → 5 具体怎么筛（`PromptHelper.getFewShotExemplars`）**：
>
> 1. **组候选池（≤10）**
>    - 先放入本轮从记忆库召回的 **dynamicExemplars**（Agent 记忆）
>    - 若不足 10，再用系统预设 exemplar 集合按当前 query 向量补齐
> 2. **按相似度拆两桶**
>    - `same`：similarity **> 0.989**（几乎同题，必须进 prompt）
>    - `noSame`：其余候选
> 3. **砍掉过弱的尾部**（候选明显多于 few-shot 时）
>    - 对 `noSame` 按 similarity **升序**排序，丢掉最低的一截，只保留相对更像的一段（避免最差范文进 prompt）
> 4. **凑满 few-shot.number（5）条**
>    - 有 `same`：全部保留 `same`，再用 `noSame` 补到 5
>    - 无 `same`：从 `noSame` 取 5 条，但**强制保留相似度最高的那 1 条**（shuffle 后若被挤掉会换回来）
> 5. 若开启 self-consistency 多次推理，每一轮各自按上面规则组一份（本仓库 self-consistency=1，通常只组一次）
>
> **面试口径**：先召回最多约 10 条 → 近重复必留、最像必留、弱相似丢掉 → **最终注入约 5 条**。
>
> **记忆怎么塞进 `{{exemplar}}`**：每条一行 `Question:...,Schema:...,SideInfo:...,SQL:...`，多条拼接。范文是历史轮四元组；当前轮 Schema 在 `#Query`。
>
> **填好后的完整 prompt 示例**（问「宁德时代去年的营收」）：
>
> ```
> #Role: ...
> #Task: ...
> #Rules: 1....7....
> #Exemplars:
> Question:比亚迪去年的营收,Schema:...,SideInfo:CurrentDate=[2026-07-30],SQL:SELECT SUM(营业收入) ... WHERE 公司名称='比亚迪' AND 报告期 >= '2025-01-01' AND 报告期 <= '2025-12-31'
> Question:茅台去年营业收入,Schema:...,SideInfo:...,SQL:SELECT SUM(营业收入) ... WHERE 公司名称='贵州茅台' AND ...
> （最多再拼到约 5 条）
> #Query: Question:宁德时代去年的营收,Schema:...(本轮 SchemaMapper 产出),SideInfo:CurrentDate=[2026-07-30]
> ```
>
> **要点**：不是贴一句历史 SQL，而是 **四元组范文**；教写法，不替映射。"

**Q：LLM 自动审核怎么做的？prompt 和判定标准是什么？**

> "写路径的闸门在 `MemoryReviewTask`（定时约 60s 扫一遍）。**开源实现是 POSITIVE / NEGATIVE 二分类，不是打 1–5 分。**
>
> **触发与范围**：
> - 仅处理：尚未被 LLM/人审过的记忆（`llmReviewRet`、`humanReviewRet` 皆空）
> - Agent 需开启 memory review；对应 ChatApp `MEMORY_REVIEW` 需 enable
>
> **审核 prompt（代码 `MemoryReviewTask.INSTRUCTION`，中英对照）**：
>
> ```
> #Role: You are a senior data engineer experienced in writing SQL.
> #角色：你是一位擅长写 SQL 的资深数据工程师。
>
> #Task: You will be provided with a user question and the SQL written by a junior engineer,
> please take a review and give your opinion.
> #任务：下面是用户问题和初级工程师写的 SQL，请你评审并给出意见。
>
> #Rules:
> 1.ALWAYS follow the output format: opinion=(POSITIVE|NEGATIVE),comment=(your comment).
>   输出必须是：opinion=(POSITIVE|NEGATIVE),comment=(你的评语)
> 2.NO NEED to check date filters as the junior engineer seldom makes mistakes in this regard.
>   不必重点抠日期过滤（默认初级工程师在日期上较少出错）——注意：这是开源默认；我们业务上仍会靠人审兜时间口径问题。
>
> #Question: {用户问题}
> #Schema: {当时的 dbSchema}
> #SideInfo: {sideInfo}
> #SQL: {s2sql}
> #Response:
> ```
>
> **判定标准与后续状态**：
>
> | LLM 输出 | 含义 | 系统动作 |
> |---------|------|---------|
> | `opinion=POSITIVE` | 认为该 SQL 可作范文 | **直接 ENABLED**，写入向量库，可被 Parser 召回 |
> | `opinion=NEGATIVE` | 认为有问题 | **保持 PENDING**，进人工审核队列；人审通过才 ENABLED，否决则 DISABLED |
> | 解析失败（格式不对） | 正则抽不出 opinion | 本轮不改状态，下个调度周期可能重试 |
>
> **人审怎么接**：数据工程师/我看 PENDING；人审与 LLM 冲突时 **以人审为准**，冲突 case 进评测集回归。
>
> **和『语法成功就入库』的区别**：执行成功只进入 PENDING；**只有 POSITIVE（或人审通过）才能当 Few-shot**——否则错 SQL 会污染 `#Exemplars`。
>
> **诚实边界**：开源 prompt 默认『不重点查日期』，和金融场景『去年=自然年』的痛点不完全匹配——所以人审兜底仍然必要；若重做会把时间口径、字段是否覆盖用户意图写进 Rules。"

**Q：人工审核是谁在做？怎么保证效率？800+ 条是怎么攒出来的？有没有冷启动？**

> "**30 秒答法**：人审是我 + 数据工程师，**每周集中一次**；平时靠 LLM 自动 POSITIVE 放行。简历 **800+** = **冷启动 200**（4 个 Agent 分摊）+ **4–7 月线上约 600**（约 200/月，流量稳，不讲爬坡）。冷启动是为了上线就能召满约 5 条同构范文；飞轮看新题过审率，不是每次查询都变一条记忆。
>
> ---
>
> **① 谁在审、怎么保证效率**
>
> | 角色 | 节奏 | 做什么 |
> |------|------|--------|
> | **LLM** | 持续（约每 60s 扫 PENDING） | `POSITIVE` → 当场 ENABLED；`NEGATIVE` → 等人 |
> | **人工** | **每周一次**（约 0.5～1 小时） | 清 NEGATIVE/格式失败；**抽检**部分 POSITIVE；冲突进评测集 |
>
> - 人审单条 **30 秒～1 分钟**；周队列大约十几～三十条 NEGATIVE + 少量抽检
> - 效率靠三件事：**LLM 先筛**、**同 question 去重**、**只收 LLM_S2SQL 成功题**（规则 SQL 不入库）
> - 人不盯盘——日常放行交给 LLM，人做周批次兜底
>
> ---
>
> **② 800+ 怎么来的（构成 + 节奏）**
>
> - **4 月初上线** → 到 7 月约 **3 个月**
> - **800+ ENABLED** = 冷启动种子 **200** + 线上沉淀约 **600**
> - 月净增约 **200**（周约 **50**）；日均查询 ~150 稳定，**不讲爬坡**
>
> | 时点 | 净增 | 累计 |
> |------|------|------|
> | 4 月初 | 种子 +200 | 200 |
> | 4 / 5 / 6 月 | 各 +200 | 400 → 600 → 800 |
> | 7 月 | 少量补录 | **800+** |
>
> ---
>
> **③ 有没有冷启动？200 怎么分到 Agent？和 prompt 里 5 条什么关系？**
>
> **有，必须有。** 库空着时只能吃静态『超音数』范文，金融/实验题会被带偏。
>
> **两层数字不要混**：
>
> | 层级 | 条数 | 含义 |
> |------|------|------|
> | **每次注入 prompt** | **~5**（`few-shot.number`） | 业界甜点：DAIL-SQL（Gao et al., VLDB 2024 / arXiv:2308.15363）在 Spider-dev 上 1/3/5-shot 执行准确率约 80.2%→81.7%→82.4%，再往后边际变小 |
> | **每个 Agent 的库** | **远大于 5**（我们冷启动约 **40～60**） | 库要覆盖多种 SQL 骨架，才能**随时召到** 5 条同构范文——**40～60 是我们的工程定标，不是某篇论文的「飞轮阈值」** |
>
> **文献怎么说「记忆条数 vs 收益」（勿与 40～60 混为一谈）**：
>
> - 出处：Cook, Patel, Vellaichamy, et al.（JPMorganChase），***Continual Learning of Domain Knowledge from Human Feedback in Text-to-SQL***，[arXiv:2511.10674](https://arxiv.org/abs/2511.10674)（2025-11），§4.3 / **Figure 4**
> - 原文要点：在 BIRD Dev 上画了「memory store 里 online instances 数量 → 执行准确率」曲线；**非 procedural 的 memory baseline 在前约 10～20 条实例时早期学习更快**（faster initial learning within the first 10–20 instances）；实例继续增多后，更复杂的 Procedural Agent 才反超
> - 因此面试应说：**文献支持『同域记忆从大约十几～二十条起就开始有可见收益』**；我们定 **单 Agent 冷启动 40～60**，是在「已有早期收益」之上再留余量，保证多种骨架（自然年/排名/多实体/JOIN…）都能召满约 5 条，**不是论文写了 40～60**
>
> **4 个 Agent × 种子 ≈ 200**（按主题域隔离，飞轮在 Agent 内转）：
>
> | Agent | 种子 | 为何这个量 |
> |-------|------|-----------|
> | 公司研究 | **~60** | 问得最多：单/多指标、自然年、多实体、排名 |
> | 绿色经济 | **~50** | 跨表与口径相对多 |
> | 经济研究（宏观） | **~50** | 时间序列、同比环比 |
> | 行为实验 | **~40** | 表少、骨架少 |
>
> 种子来自 ELK 高复用成功题 + 端到端评测已验证写法，**上线前集中人审**后批量 ENABLED；系统静态 exemplar 仍作召回不足时的兜底。
>
> ---
>
> **④ 转化率（成功查询 → ENABLED）**
>
> 周漏斗（流量稳定时）：
>
> ```
> 周查询 ≈ 1050（150×7）
>   → 成功且 LLM_S2SQL ≈ 700～800
>   → 去重后新 PENDING ≈ 80～100（同问已有 ENABLED 则跳过）
>   → 新 ENABLED ≈ 50/周
> ```
>
> | 口径 | 约值 | 一句话 |
> |------|------|--------|
> | 全量查询 → 新 ENABLED | **~5%** | 低是正常的——大量重复不问不入库 |
> | 新 PENDING → ENABLED | **~50%～60%** | 才是闸门过审率 |
>
> **金句**：飞轮看『新结构过审』，不看『每次查询都变记忆』。
>
> ---
>
> **⑤ Agent 隔离（顺带答清）**：集合 `memory_{agentId}`；同 Agent 多用户共享范文；跨 Agent 不召回。
>
> **收束**：人周审 + LLM 日审；800 = 200 种子（4×~50，为召满 5 条）+ 3×200 月增量；转化报漏斗不要报单点。"

## 2.3 端到端测评集与指标

**⚠️ 时间线前提：端到端测评集先于 SchemaMapper 优化存在**

| 阶段 | 端到端准确率 | SchemaMapper EM | 说明 |
|------|------------|-----------------|------|
| **T0**（加入时） | **45%** | 58% | 端到端测评集已就绪；Schema 专属集从它倒推 |
| **T1**（Schema + LLM 消歧后） | **72%**（+27pp） | **81%** | 同一批 200 条 query 复测 |
| **T2**（记忆库上线后） | **87%**（+15pp） | 81% | Schema 已优化完，+15pp 全是记忆库 |

**Q：端到端 200 条测评集怎么构建的？**

> "这是**整条问数链路的基准集**，在我做 SchemaMapper 优化之前就建好了——T0 的 45% 就是它测出来的。为什么是 200 条？因为**人工一天深度标注的上限大约就是 200 条**——每条要定 query、字段映射、期望结果口径，快的 1 分钟、慢的几分钟。
>
> **覆盖范围**：金融经济三个子域——绿色经济、公司研究、经济研究
>
> **难度分布**（200 条按此比例，Schema 专属集继承同一分布）：
>
> | 难度 | 占比 | 条数 | 具体测什么 | 示例 query |
> |------|------|------|----------|-----------|
> | **简单单表** | 40% | ~80 | 单张表内查某个指标 + 单个实体 | "比亚迪去年的营业收入是多少？" |
> | **多表关联** | 35% | ~70 | query 涉及 2-3 张表的字段 | "比亚迪去年的营收和资产负债率" |
> | **复杂聚合** | 25% | ~50 | 排名/分组/筛选 + 衍生指标（ROE/毛利率） | "A 股去年 ROE 排名前 10 的公司" |
>
> **为什么要分难度**：不同难度的失败环节不同——简单单表错多在映射排序；多表关联错多在召回遗漏；复杂聚合错多在衍生指标或 SQL 生成。**按难度分层才能定位该改哪一层**。
>
> 标注在人工初标基础上，补了两步验证：
>
> **第一步：多大模型交叉验证**
> - 用 qwen-plus 和 deepseek 两个 LLM 独立对 200 条做字段映射 + 结果口径预测
> - 两个 LLM 一致 + 人工认可 → high-confidence（约 70%）
> - 两个 LLM 不一致 → 人工逐条复审（约 30%）——这些往往是真正的语义消歧难点
> - 标注规则文档化——如'PE 默认选 TTM 而不是 Forward'、'营收默认指营业总收入而不是营业收入净额'
>
> **第二步：固化评测集**
> - 输出标准 JSON：每条同时带**端到端 gold**（期望结果口径 / 关键约束）和**字段映射 gold**（`gold_elements`）
> - SchemaMapper 专属测评集 = **抽出同一批的 `gold_elements` 层**——一一对应，不是另抽一套题"

**端到端标注 JSON 示例：**

```json
{
  "id": 42,
  "query_text": "比亚迪去年的营收和净利润",
  "gold_elements": [
    {"type": "METRIC", "id": 101, "name": "营业收入", "bizName": "revenue"},
    {"type": "METRIC", "id": 105, "name": "净利润", "bizName": "net_profit"},
    {"type": "ENTITY", "id": 201, "name": "比亚迪", "value": "002594"},
    {"type": "DIMENSION", "id": 301, "name": "报告期", "value": "2025"}
  ],
  "gold_answer": {
    "entity": "比亚迪",
    "period": "2025",
    "metrics": ["营业收入", "净利润"],
    "result_check": "两列数值量级分别为百亿级营收、十亿~百亿级净利润；报告期为 2025 年报/年累计"
  },
  "difficulty": "medium",
  "domain": "corporate_finance",
  "ambiguous": false,
  "confidence": "high",
  "notes": "多指标查询，营收和净利润都在利润表"
}
```

```json
{
  "id": 78,
  "query_text": "比亚迪的扣非利润",
  "gold_elements": [
    {"type": "METRIC", "id": 106, "name": "扣非净利润", "bizName": "net_profit_excluding"},
    {"type": "ENTITY", "id": 201, "name": "比亚迪", "value": "002594"}
  ],
  "gold_answer": {
    "entity": "比亚迪",
    "metrics": ["扣非净利润"],
    "result_check": "返回扣非净利润而非合并净利润；数值应与净利润接近但通常更低"
  },
  "difficulty": "hard",
  "domain": "corporate_finance",
  "ambiguous": true,
  "confidence": "low",
  "notes": "用户说'扣非利润'——是'扣除非经常性损益后的净利润'的简称，靠别名匹配"
}
```

> "每条标注包含：query 原文、`gold_elements`（给 SchemaMapper 用）、`gold_answer`（给端到端执行核对用）、难度、主题域、是否歧义、置信度、备注。`confidence=low` 是两个 LLM 不一致后人工裁定的——往往是真正难点。
>
> **和 § 1 的关系**：§ 1 线上抽 50 条失败只负责**发现瓶颈**；真正回归用的 200 条是这套端到端集；Schema 专属集是它的字段映射切片。"

**Q：45% → 72% → 87% 怎么测的？**

> "全程用**同一套 200 条端到端测评集**，保证纵向可比：
> - **评测方式**：一条 query 进去，一个答案出来，**中间不允许任何人工干预**（无 human in the loop）
> - **判定**：执行结果是否满足 `gold_answer` 的口径约束 + 五维度语义评分（字段是否对、实体是否对、时间是否对、聚合是否对、数值量级是否合理）
> - 这跟线上不同——线上用户可以改 query、选候选字段、纠错反馈，所以线上体验准确率会高于 87%。我们的 45%/72%/87% 测的是**系统独立能力**
>
> **和 SchemaMapper 200 条的关系**：同一批 query。Schema 层只比对 `gold_elements`（不跑 SQL）；端到端跑完整链路比对答案。所以可以说 Schema 测评是端到端测评的**一部分 / 单步显微镜**。"

**Q：为什么简历/对外讲的是端到端指标，而不是 Parser 环节指标？Parser 本身提升了多少？**

> "**对外讲端到端，是因为记忆复用的产品价值是『整题答对了没有』；对内下钻才看 Parser。**
>
> **为什么主指标用端到端（72%→87%），而不是只报 Parser**：
> 1. **验收口径**：研究员只关心答案对不对，不关心中间 S2SQL 字符串是否和 gold 逐字相同
> 2. **简历一致性**：记忆库写在『端到端准确率』上；SchemaMapper 才单独报映射 EM
> 3. **T1 之后瓶颈已转移到 Parser**：Schema 已到 81%，再优化映射边际变小；记忆库上线后端到端 +15pp，**几乎都可以归因到 Parser 写法变好**（Schema 数字没变）
> 4. **Parser 单独 gold 更贵**：要标「标准 S2SQL」比标字段集合难（写法不唯一：等价 SQL 很多），所以日常回归以端到端为主，Parser 做**条件切片**分析
>
> **Parser 环节怎么报（面试深挖时用）**：
>
> 在同一套 200 条上，取 **SchemaMapper EM 已正确** 的子集，看最终答案是否对——这近似「映射对了的前提下，Parser（+Corrector/执行）有没有写对」：
>
> | 阶段 | 条件（Schema EM=对）下的成功率 | 说明 |
> |------|-------------------------------|------|
> | **T1**（静态 Few-shot） | 约 **75%** | 字段对了仍常栽在时间/同比/换实体 |
> | **T2**（动态记忆） | 约 **90%**（**+15pp**） | 同结构成功题被召回当范文 |
>
> 和端到端 +15pp（72%→87%）**量级对齐**——因为 T1→T2 Schema 没变，端到端提升主要由 Parser 条件准确率抬升贡献。
>
> **诚实边界**：75%→90% 是端到端集上的**条件切片**，不是另建一套 Parser 逐字 EM 评测集；若面试官追问『有没有 S2SQL Exact Match』，答：没做严格字符串 EM（等价 SQL 太多），用的是执行结果/语义口径，和端到端判定一致。"

**Q：记忆库的 +15pp 贡献怎么拆解？**

> "时间线很清晰（T0→T1→T2），且端到端数字都来自同一套 200 条：
> - **T0→T1**：SchemaMapper 优化（58%→81%），端到端 45%→72%（+27pp 是 SchemaMapper 的贡献）
> - **T1→T2**：记忆库上线，端到端 72%→87%（**+15pp 全是记忆库的贡献**，因为 SchemaMapper 在 T1 已经优化完）；Parser 条件准确率同步约 75%→90%
>
> 所以记忆库单独贡献端到端 15pp，SchemaMapper 单独贡献 27pp——**SchemaMapper 对端到端的贡献反而比记忆库大**；但记忆库是 Schema 优化之后的**下一瓶颈解锁**。"

**Q：测评集构建过程中遇到了什么困难？**

> "三个困难：
> 1. **gold answer 口径不唯一**——有些 query 正确映射/结果不唯一（如'PE'可以是 TTM 也可以是 Forward）。定义了'默认选 TTM，评测里标注为 ambiguous'
> 2. **端到端判定比字段映射更难**——字段对了 SQL 还可能时间条件错；要同时标 `gold_elements` 和结果口径约束
> 3. **评测集偏小**——200 条不能完全覆盖线上长尾。业界如 Spider 2.0 有几千条。后续在扩——但宁可 200 条标得牢，也不要几千条标得飘"

**Q：记忆库有没有帮倒忙的时候？**

> "有——这是真实的风险。如果记忆库里有一条**看似成功但实际错误**的 SQL，被召回后做 few-shot 会引导 LLM 犯同样的错。我们遇到过：
> - 某条 SQL 的时间范围识别错了（把'去年'理解成最近 365 天而不是自然年）
> - 被召回后，后续类似的 query 也跟着错
>
> 兜底机制：(1) LLM 评审 + 人工审核尽量挡住错误 SQL 入库；(2) 如果用户在线上反馈'答错了'，我们会回溯召回的记忆库 SQL，发现错的就标记为 DISABLED。"

## 2.4 诚实边界与技术债

> "记忆库目前没有**淘汰机制**——只进不出。长期来看这有两个问题：
> 1. **语义层改了之后旧 SQL 过时**（比如字段改名了）
> 2. **低质量记忆稀释高质量记忆**——如果库里 800 条里有 50 条是边缘 case，召回时可能命中低质量的
>
> 端到端测评集本身的短板：200 条偏小；目前主要覆盖金融经济三域，行为实验数据覆盖不足。
>
> 如果重做我会加：(1) TTL（30 天未召回的 SQL 降权）；(2) 召回后反馈闭环（被用户否决的 SQL 自动降权）；(3) 端到端集扩到 500–1000 条并补行为实验域；(4) 表上补 `recall_count` / 最后召回时间，方便运营；(5) Review prompt 强制校验『去年=自然年』，与开源默认『不必重点抠日期』对齐金融场景。"

**污染怎么下线（对应题纲 F19）**：

1. 用户反馈答错 → 按 `queryId` / 当日召回的 `usedExemplars`（parse 响应里有）回溯  
2. `MemoryService` 将对应记忆 **DISABLED** → `disableMemory` → `removeExemplar`  
3. 冲突 case 进评测集回归，避免人审/LLM 再放行同类错误
