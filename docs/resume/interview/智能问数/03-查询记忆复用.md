# 查询记忆复用（72% → 87%，800+ 条）

## 诚实边界总表

| 说法 | 可讲 | 不可讲 |
|------|------|--------|
| **实现归属** | 开源 SuperSonic 链路；业务侧开 Review、冷启动、人审、评测 | 「我从零自研记忆向量框架」 |
| **审核形态** | `POSITIVE` / `NEGATIVE`；人审；反馈 score>=5/<=1 | 「1-5 分、>=4 自动入库」 |
| **召回条数** | 向量召回 **10** -> 注入约 **5** | 「Top-3 few-shot」作主口径 |
| **评测集** | 离线 **200**、无 HITL；T1->T2 +15pp | 「线上 300」作 87% 主口径 |
| **表字段** | 无表内 embedding、无复用次数 | 「表里有 hit count」 |
| **执行成功** | 只 PENDING；ENABLED 要过审 | 「不报错就进 few-shot」 |
| **NEGATIVE** | 记 llm_review；status 常仍 PENDING | 「NEGATIVE 自动 DISABLED」 |
| **推荐 / version** | 一行链 04；async 按 queryId | 编造 OSS「版本号协议」 |

## Part A · 需求与效果

### A1 背景与动机

SchemaMapper 把字段映射做到 81% 后，端到端卡在 72%——字段常选对，**Parser 仍因 Few-shot 结构不对齐翻车**。

核心痛点：Text2SQL 准确率高度依赖范文的**结构相似度**，而系统只有一套 JSON 写死的静态范文（演示域「超音数」），对金融题不但帮不上忙还会教坏——比如把「去年」教成滚动 365 天，和金融场景「自然年」的语义完全错位。

业界已反复验证这一点：DIN-SQL（NeurIPS 2023）表明合适的 in-context 示例可带来约 +10pp 提升量级；DAIL-SQL（Gao et al., arXiv:2308.15363）显示精选示例显著优于随机选取。静态写死 demonstration 在范文与当前题差距大时会出现 retrieval bias，LLM 被不相关示例带偏。

替代方案对比：

| 方案 | 做法 | 不足 |
|------|------|------|
| 堆静态 Few-shot | 每种骨架手写进 JSON | 滞后线上；堆数量不等于选得准；token/维护双爆 |
| 全量塞 prompt | 几十条全进 `#Exemplars` | 超上下文；噪声大 |
| 微调专用模型 | 用成功 SQL 微调 | 成本高、迭代慢 |
| **动态检索同构范文**（我们选的） | 成功过审 -> 向量库 -> 按 query 召回注入 | 对齐 example selection；范文随业务增长 |

一句话：Parser 不是缺「几条 SQL」，缺的是「跟当前题同构的成功写法」。

### A2 目标与非目标

**目标**：成功 SQL 过审后入库，Parser 按相似度动态召回同构范文注入 `#Exemplars`，提升端到端准确率。

**非目标**：

- 自研向量框架——基于开源 SuperSonic 链路，业务侧负责开 Review、冷启动、人审运营与评测
- 替代 SchemaMapper——记忆复用作用于 Parser 阶段，与字段映射是上下游关系
- 为相似推荐单独建模——两者共用同一向量库，推荐只取 question 展示（详见 [04](./04-推荐问题.md)）

### A3 已实现效果

端到端准确率从 **72% 提升到 87%**（同一批 200 条离线评测集，无 HITL）；其中 T1->T2 的 **+15pp** 几乎全部归因于记忆库（SchemaMapper 在 T1 已优化完毕，映射 EM 保持在 81%）。

记忆库累计 **800+ 条 ENABLED**，其中冷启动种子 **200 条**（4 个 Agent 按主题域分摊），4-7 月线上沉淀约 600 条。

在 Schema 已正确的子集上，Parser 条件准确率约 **75% -> 90%**。

### A4 评测口径

评测基于自维护离线集，**同一批 200 条**贯穿全部阶段，中间无人工干预（无 HITL）。

| 阶段 | 端到端准确率 | Schema EM | Parser 条件准确率（Schema 正确子集） | 说明 |
|------|------------|-----------|----------------------------------|------|
| T0（加入时） | 45% | 58% | — | 端到端测评集已就绪 |
| T1（Schema + LLM 消歧） | 72% (+27pp) | 81% (+23pp) | ~75% | 记忆库未上线 |
| T2（记忆库上线） | 87% (+15pp) | 81% | ~90% (+15pp) | +15pp 全归因记忆库 |

Parser 条件准确率是端到端集上的条件切片（Schema EM 正确的前提下看最终答案是否对），不是另建一套 S2SQL Exact Match 评测集。

判定方式：执行结果是否满足 gold_answer 的口径约束 + 五维度语义评分（字段、实体、时间、聚合、量级）。

### A5 与 02/04 边界

| 模块 | 链路位置 | 消费什么 | 面试一句 |
|------|---------|---------|---------|
| [02 SchemaMapper](./02-SchemaMapper.md) | 映射阶段 | 字段 -> 本轮 `{{schema}}` | 选对字段 |
| **本文 记忆复用** | **Parser（同步）** | 历史四元组 -> `#Exemplars` | 教 Parser 写法 |
| [04 推荐问题](./04-推荐问题.md) | Parse 后**异步** | 同一向量库，只取 `question` | 同库异步只读，一行链 |

一句话：SchemaMapper 选对字段；记忆复用教 Parser 写法；相似推荐把成功问法露给人。

### A6 实现难点与过程困难

记忆库不是「存 SQL 就涨点」，过程里踩过的坑收在下面，每条对应后文 B 节展开。

#### 1. 语义成功 ≠ 执行成功

**难在哪**：LLM 生成的 S2SQL 能跑通、不报错，不代表时间口径/字段选择正确。「去年」被理解成滚动 365 天而非自然年，执行照样返回结果，但金融侧判定为错。

**当时怎么扛**：状态机把执行成功只落到 PENDING，不写向量库；必须经过 LLM Review（POSITIVE）或人审通过才 ENABLED + 入库。宁可漏放也不能放错。→ B2

**留下什么**：闸门设计写进 B2 状态机；面试要点——「SUCCESS 不等于可做范文」。

#### 2. 有害示范 / 静态域错位

**难在哪**：系统原配一套写死的演示域（超音数）范文，「去年」= 滚动 365 天。这套范文对金融场景是**有害示范**——金融侧「去年」= 自然年（1 月 1 日–12 月 31 日），语义完全错位。静态范文不区分场景，召回即带偏。→ 动机回扣 A1

**当时怎么扛**：记忆库上线后用动态同构范文替换静态范文，召回按业务域注入；但存量静态范文仍存在，直到全面切到记忆库后才降级为 fallback。→ B4.2

**留下什么**：「演示域教坏金融」的案例成为 A1 动机的核心佐证，也是后续改进 prompt 强制校验时间口径的驱动力。

#### 3. 冷启动鸡生蛋

**难在哪**：记忆库空 → 召回不足 5 条 → Parser 退回吃静态范文 → 静态范文有害 → 准确率起不来。要召满约 5 条同构范文，库里得有足够密度的种子，否则向量检索变成近邻随机。数字见 A3（200 种子、4 Agent 分摊）。

**当时怎么扛**：4 个 Agent 按主题域分摊，每 Agent 灌 40–60 条种子 SQL（人工编写 + 审校），先有「面粉」才能「烤面包」。运营节奏见 B5。→ B5

**留下什么**：冷启动成本是记忆库方案的固有代价，种子质量直接决定初始召回效果；面试时用「先灌种子再开闸」一句话概括。

#### 4. 评测贵且口径不唯一

**难在哪**：gold SQL 不唯一——同一 query 可有多种等价写法（如 PE 取 TTM 还是 Forward）；端到端判定比字段映射更难，要同时标 gold_elements 和结果口径约束。200 条已到人工标注上限，行为实验域覆盖不足。口径见 A4。→ 承接 A4

**当时怎么扛**：宁可 200 条标得牢也不要几千条标得飘；ambiguous case 标注为「默认口径 + 备选口径」，评测时以默认口径为准。五维度语义评分兜底纯 SQL Exact Match 的不足。

**留下什么**：200 条评测集是当前可信基线，但覆盖不足是诚实边界；面试时主动说「行为域待补」比被追问更稳。

#### 5. Review 信号偏弱

**难在哪**：开源审核 prompt（`MemoryReviewTask.INSTRUCTION`）显式写了「NO NEED to check date filters」，即**不重点抠日期**，且不看执行结果表——只凭 schema + SQL 静态审核。金融场景的时间口径痛点（去年 = 自然年）恰好被这条规则漏掉。→ B2 如实写

**当时怎么扛**：LLM Review 做初筛，人审做终兜；人审与 LLM 冲突时以人审为准。冲突 case 进评测集回归，避免同类错误再放行。

**留下什么**：「开源 prompt 不重点抠日期」是诚实边界关键点，也是改进方向（把时间口径校验写进 Rules）。→ B4.2

#### 6. 负迁移 / 污染

**难在哪**：一条看似正确但实际错误的 SQL 过审入库后，会被后续相似 query 召回，把错误写法「教」给 Parser——典型负迁移。发现与下线成本高：线上反馈 → 回溯召回记录 → 定位污染源 → DISABLED。→ 展开见 B4.1

**当时怎么扛**：用户反馈「答错」后，按 queryId 回溯当日召回的 usedExemplars，定位污染源后调用 `disableMemory` + `removeExemplar` 下线。冲突 case 进评测集回归。

**留下什么**：下线流程（disableMemory + removeExemplar）写进 B4.1；面试时用「错 SQL 过审带歪后续」一句话点出风险，再讲兜底机制。

#### 7. 只进不出

**难在哪**：记忆库无 TTL、无召回反馈降权机制，只进不出。长期存在两个问题：语义层变更后旧 SQL 过时（字段改名/指标口径调整），低质量记忆稀释高质量记忆（800 条里 50 条边缘 case 就能拉低召回命中率）。

**当时怎么扛**：靠人工定期巡检 + 用户反馈驱动下线，但没有系统化的淘汰机制。当前是已知技术债。

**留下什么**：改进方向明确——(1) TTL（30 天未召回降权）；(2) 召回后反馈闭环（被否决的 SQL 自动降权）；(3) 表上补 recall_count / 最后召回时间。→ B4.2

### B1 这条记忆长什么样

> 执行刚返回 SUCCESS，要把这条经验沉淀下来——它在 DB 里长什么样、在向量库里长什么样？

#### B1.1 场景

用户问「去年营收是多少」，Parser 生成 S2SQL、执行 SUCCESS。这条经验要存下来，供后续相似 query 召回。它分成两份：DB 表（状态机 + 人审台账）和向量库（可被召回的 ENABLED 投影）。

#### B1.2 代码落点

**DB 侧 — `ChatMemoryDO` / 表 `s2_chat_memory`**

| 字段 | 含义 | 面试怎么说 |
|------|------|-----------|
| `id` | PK | — |
| `agent_id` | Agent 隔离 | 跨 Agent 不召回 |
| `query_id` | 来源问答 | 可回溯 ELK / 人审 |
| `question` | 用户问题 | **做 embedding 的文本** |
| `side_info` | SideInfo（如 CurrentDate） | 范文四元组之一 |
| `db_schema` | 当时 Schema 串 | 范文四元组之一 |
| `s2_sql` | S2SQL | 范文四元组之一 |
| `status` | `PENDING` / `ENABLED` / `DISABLED` | 只有 ENABLED 进向量可召回 |
| `llm_review` / `llm_comment` | POSITIVE\|NEGATIVE + 评语 | 自动审 |
| `human_review` / `human_comment` | 人审 | **冲突以人审为准**（运营约定） |
| `created_*` / `updated_*` | 审计 | 有用户名；**无「被召回次数」** |

代码：`chat/server/.../persistence/dataobject/ChatMemoryDO.java`

**向量侧 — `Text2SQLExemplar`**

| 项 | 值 |
|----|-----|
| 集合名 | `memory_{agentId}`（前缀 `s2.embedding.memory.collection.prefix`，默认 `memory_`） |
| 向量化对象 | **`question` 文本** |
| metadata / payload | JSON：`question` + `sideInfo` + `dbSchema` + `sql` |
| 系统静态兜底集 | `text2dsl_agent_collection`（`s2-exemplar.json`，演示域「超音数」） |


#### B1.4 易踩坑

- 表里**无** embedding 列、**无** `recall_count`（向量侧 metadata 也不存 hit count）
- embedding 只打 `question`，SQL 在向量侧是 metadata payload——面试别说「SQL 也做 embedding」
- 状态机 `PENDING / ENABLED / DISABLED` 在 DB 的 `status` 字段，向量库**不存**状态——向量库里只有 ENABLED 的投影

### B2 写出来：SUCCESS → PENDING → Review 定时扫 → ENABLED

> 面试场景：「一条 SQL 从执行成功到能被召回，中间经历什么？」

#### B2.1 挂四元组 + 执行 SUCCESS → 落 PENDING

**场景**：LLM 生成 S2SQL 后执行返回 SUCCESS，这时候要把四元组挂到 ParseResult 上、把 DB 行写到 PENDING 状态。

**代码落点**：

1. `LLMResponseService.addParseInfo` —— 把 `Text2SQLExemplar` 挂进 `properties[sql_exemplar]`
2. `SqlExecutor.execute` —— 仅当 `QueryState.SUCCESS` **且** `LLMSqlQuery.QUERY_MODE` 时才调用 `createMemory`；规则 SQL 不入库
3. `MemoryServiceImpl.createMemory` —— 同 agent + 同 question 已有 ENABLED → **直接跳过**（不重复写入）

**数据样例**（PENDING 状态 DB 行）：

```json
{
  "id": 1024,
  "agent_id": 7,
  "question": "去年营收是多少",
  "status": "PENDING",
  "llm_review": null,
  "llm_comment": null,
  "human_review": null,
  "human_comment": null
}
```

**易踩坑**：执行 SUCCESS 只落到 PENDING，**不等于** ENABLED；规则 SQL（非 LLM 生成）不进记忆；同 question 已有 ENABLED 的直接跳过，不会重写。

#### B2.2 MemoryReviewTask 定时审（60s）

**场景**：PENDING 积起来了，谁来把它们过审？答案是 `MemoryReviewTask`，每 60 秒扫一轮。

**代码落点**：

`MemoryReviewTask.review` 通过 `@Scheduled(fixedDelay = 60 * 1000)` 触发。遍历所有 Agent，只有 `Agent.enableMemoryReview()` 返回 true 的才处理（对应 DB 动态配置 `MEMORY_REVIEW.enable=true`）。已有 `llm_review` 或 `human_review` 的条目跳过，避免重复审核。

审核输入只有 Question + Schema + SideInfo + SQL，**不看执行结果表**——这是静态审核。

**数据样例**（审核 prompt Rules 段，中英对照）：

```
#Rules:
1.ALWAYS follow the output format: opinion=(POSITIVE|NEGATIVE),comment=(your comment).
  输出必须是：opinion=(POSITIVE|NEGATIVE),comment=(你的评语)
2.NO NEED to check date filters as the junior engineer seldom makes mistakes in this regard.
  不必重点抠日期过滤（默认初级工程师在日期上较少出错）——注意：这是开源默认；我们业务上仍会靠人审兜时间口径问题。

#Question: {用户问题}
#Schema: {当时的 dbSchema}
#SideInfo: {sideInfo}
#SQL: {s2sql}
#Response:
```

**判定与状态变化**：

| LLM 输出 | 系统动作 |
|---------|---------|
| `opinion=POSITIVE` | **直接 ENABLED** + `enableMemory` → `storeExemplar(memory_{agentId})` 入向量 |
| `opinion=NEGATIVE` | **保持 PENDING**（不改 status），记 `llm_review=NEGATIVE` + `llm_comment`，进人审队列 |
| 格式解析失败 | 本轮不改状态，下个周期重试 |

**易踩坑**：开源 prompt 默认「不重点抠日期」（Rule 2），金融场景「去年=自然年」漏审靠人审兜底；Review 只看 schema + SQL 静态审核，不看执行结果；NEGATIVE **不自动 DISABLED**，通常仍保持 PENDING。

#### B2.3 CommandLineRunner 启动回灌 + 旁路（人审 / 用户反馈）

**场景**：进程重启后向量索引会丢，怎么把 ENABLED 的记忆灌回向量库？另外，除了自动审核，人审和用户反馈怎么接？

**代码落点**：

`MemoryServiceImpl` 同时实现 `MemoryService` 和 `CommandLineRunner`（注意：是 `CommandLineRunner`，不是 `ApplicationRunner`）。`run(String... args)` 只有一行，委托给 `loadSysExemplars()`：

```java
// MemoryServiceImpl.run (CommandLineRunner)
public void run(String... args) {
    loadSysExemplars();
}

public void loadSysExemplars() {
    List<ChatMemory> memories = this
        .getMemories(ChatMemoryFilter.builder().status(MemoryStatus.ENABLED).build());
    for (ChatMemory memory : memories) {
        exemplarService.storeExemplar(
            embeddingConfig.getMemoryCollectionName(memory.getAgentId()),
            Text2SQLExemplar.builder().question(memory.getQuestion())
                .sideInfo(memory.getSideInfo()).dbSchema(memory.getDbSchema())
                .sql(memory.getS2sql()).build());
    }
}
```

**旁路 1：人审** —— `human_review` / `human_comment` 字段；冲突以人审为准（运营约定）；运营每周批次清理 NEGATIVE。

**旁路 2：用户反馈** —— `ChatManage` 触发，score>=5 直接 `enableMemory`，score<=1 直接 `disableMemory`；**不经过 Review 流程**，是直接启停。

**易踩坑**：回灌只灌 `status=ENABLED`，PENDING / DISABLED 不回灌；`run` 只是壳，真正逻辑在 `loadSysExemplars`；score>=5 / <=1 是直接启停，绕过 Review（人审与 Review 的差异——人审写 `human_review` 字段，反馈直接调 `enableMemory` / `disableMemory`）。

### B3 读回去：recall → #Exemplars

> 面试场景：「下一次用户来问，Parser 前怎么把同构范文捞回来。」

#### B3.1 场景

用户问「宁德时代去年的营收」，Parser 还没跑——先从向量库捞一批同构历史问答，筛到约 5 条塞进 prompt 的 `#Exemplars` 段，教 LLM 按相似骨架写 S2SQL。

#### B3.2 代码落点

一条链：召回 → 挂请求 → 筛 few-shot → 拼 prompt。

**1. `NL2SQLParser.addDynamicExemplars`**（同步，堵在 Parser 前）

```java
private void addDynamicExemplars(ParseContext parseContext, QueryNLReq queryNLReq) {
    ExemplarServiceImpl exemplarManager = ContextUtils.getBean(ExemplarServiceImpl.class);
    EmbeddingConfig embeddingConfig = ContextUtils.getBean(EmbeddingConfig.class);
    String memoryCollectionName =
            embeddingConfig.getMemoryCollectionName(parseContext.getAgent().getId());
    ParserConfig parserConfig = ContextUtils.getBean(ParserConfig.class);
    int exemplarRecallNumber =
            Integer.parseInt(parserConfig.getParameterValue(PARSER_EXEMPLAR_RECALL_NUMBER));
    List<Text2SQLExemplar> exemplars = exemplarManager.recallExemplars(memoryCollectionName,
            queryNLReq.getQueryText(), exemplarRecallNumber);
    queryNLReq.getDynamicExemplars().addAll(exemplars);
    parseContext.getResponse().setUsedExemplars(exemplars);
}
```

- 集合名 `memory_{agentId}`，读 `parserConfig.getParameterValue(PARSER_EXEMPLAR_RECALL_NUMBER)` = **10**
- `recallExemplars(memoryCollectionName, queryText, 10)` → `List<Text2SQLExemplar>`
- 挂到 `queryNLReq.getDynamicExemplars()`；**同步**挂到 `parseContext.getResponse().setUsedExemplars(exemplars)`（B4.1 回溯用）
- 与相似推荐不同：召回**同步**堵 Parser（推荐那把是 `runAsync`，不堵主解析）

**2. `PromptHelper.getFewShotExemplars`**（recall 10 → 注入约 5）

- 候选池组（≤10）：先放 dynamicExemplars（Agent 记忆），不足用系统集 `text2dsl_agent_collection`（`s2-exemplar.json`）按当前 query 向量补齐
- 按 similarity 拆两桶：`same`（> 0.989，几乎同题，**必留**）；`noSame`（其余）
- 凑满 `few-shot.number` = **5**：有 same 则全保留 same + noSame 补到 5；无 same 则从 noSame 取 5，但强制保留相似度最高那 1 条（shuffle 后若被挤掉会换回来）
- self-consistency 多次推理时每轮各自组一份（本仓库 self-consistency=1，通常只组一次）

**3. `OnePassSCSqlGenStrategy` 拼 prompt**

模板含 `#Exemplars: {{exemplar}}`、`#Query: Question:{{question}},Schema:{{schema}},SideInfo:{{information}}`。每条范文一行：`Question:...,Schema:...,SideInfo:...,SQL:...`。范文是历史四元组，当前轮 Schema 在 `#Query`。

#### B3.3 数据样例

**1. recall 10 → 注入约 5 的筛选算法**（`PromptHelper.getFewShotExemplars`）

1. 组候选池（≤10）：先放 dynamicExemplars（Agent 记忆），不足用系统预设 exemplar 集合按当前 query 向量补齐
2. 按相似度拆两桶：`same`（similarity > 0.989，几乎同题，必须进 prompt）；`noSame`（其余）
3. 砍尾：候选明显多于 few-shot 时，`noSame` 升序排，丢最低一截，只留相对更像的一段
4. 凑满 few-shot.number=5：有 same 则全保留 same + noSame 补到 5；无 same 则从 noSame 取 5，但强制保留相似度最高的那 1 条（shuffle 后若被挤掉会换回来）
5. 若开启 self-consistency 多次推理，每一轮各自组一份（本仓库 self-consistency=1，通常只组一次）

**2. 填好后的 prompt 示例**（问「宁德时代去年的营收」）

```
#Role: You are a data analyst experienced in SQL languages.
#Task: ...
#Rules: 1....7....
#Exemplars:
Question:比亚迪去年的营收,Schema:...,SideInfo:CurrentDate=[2026-07-30],SQL:SELECT SUM(营业收入) ... WHERE 公司名称='比亚迪' AND 报告期 >= '2025-01-01' AND 报告期 <= '2025-12-31'
Question:茅台去年营业收入,Schema:...,SideInfo:...,SQL:SELECT SUM(营业收入) ... WHERE 公司名称='贵州茅台' AND ...
（最多再拼到约 5 条）
#Query: Question:宁德时代去年的营收,Schema:...(本轮 SchemaMapper 产出),SideInfo:CurrentDate=[2026-07-30]
```

**3. 配置表**

| 配置项 | 本仓库值 | 含义 |
|--------|---------|------|
| `parser.exemplar-recall.number` | **10** | 向量召回候选池上限 |
| `parser.few-shot.number` | **5**（Parameter 默认 3） | 真正写入 `#Exemplars` 的条数 |
| `parser.self-consistency.number` | **1** | self-consistency 推理轮次 |

#### B3.4 易踩坑

- 召回**同步**堵 Parser（相似推荐那把是 `runAsync`，不堵主解析）
- 召回 10 ≠ 注入 10；真正进 prompt 是筛后的约 5
- 范文是**四元组**（Question, Schema, SideInfo, SQL）不是单条 SQL；`{{exemplar}}` 每条一行
