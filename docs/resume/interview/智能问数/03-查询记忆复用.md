# 查询记忆复用（72% → 87%，800+ 条）

## 1. 背景：为什么做，怎么发现的问题

**原先卡在哪**：SchemaMapper 把字段映射做到 81% 后，端到端仍卡在 72%。起点不是论文，而是「字段对、SQL 能跑、数字却对不上年报」的事故。Schema linking 解决 **which fields**；Parser 还要决定时间口径和 SQL 骨架，字段 Exact Match 管不到。

**代表性 bad case**（字段都对、SQL 都能跑，业务判错）：

1. **「最近一年」一口三义**——同一句「比亚迪最近一年的净利润是多少」，口径随指标和语境变：指标不带 TTM，问的是时点值（12 月 31 日）；指标带 TTM（「净利润（TTM）」），问的是滚动 12 个月；会计语境里「最近一年」又常指财年（出财报的日子）。静态 few-shot 只能示范其中一种，另外两种就被教坏。这是 Chat-BI 最危险的失败模式：语法对、能执行、数字量级也像净利润。
2. **多实体被揉成总平均**——「比较 A、B、C 三家公司的 ROE」生成 `SELECT AVG(roe) WHERE company IN ('A','B','C')`，漏了 `GROUP BY company`。`AVG` 合法，结果像一个比较值，其实丢掉了三家各自的数。schema 里三家实体和 `roe` 都在，缺的是输出粒度。演示域范文多为单实体 / 总体指标，没有「多实体必须保留实体维度」。
3. **聚合条件放进 WHERE**——「找出 2024 年收入超过 10 亿元的公司」生成 `WHERE revenue > 1e9 GROUP BY company`，应为 `GROUP BY company HAVING SUM(revenue) > 1e9`。过滤的是单笔交易而不是年度汇总，结果仍可能看起来像高收入公司。演示域「超过阈值」都直接用 `WHERE`，没有聚合后 `HAVING`。

**怎么定位的**（事故 → 范文 → 论文，数字只出现一次）：

1. **用户反馈数字不对**——对不上年报 / 手算，不是 syntax error。
2. **排除 SchemaMapper**——T1 映射 EM 81%、端到端 72%；Schema 正确子集上 Parser 约 75%。字段对，错在口径和骨架——**Parser 是下一个瓶颈**。
3. **打开 prompt 对上根因**——所有请求都在吃演示域「超音数」写死的 `#Exemplars`。范文在演示域里可能是对的，迁到金融域就是有害示范。同一 schema、同一模型，换成同构写法后对应题能过：错误跟着范文走，所以不是先换更大的模型。
4. **因此校正 few-shot**——不同口径、不同骨架要不同范文。不堆静态 JSON、不回头改 SchemaMapper，给 Parser 动态注入跟当前题同构的成功写法。Parser 不是缺「几条 SQL」，缺的是「跟当前题同构的成功写法」。

事后才去查文献，用来校正 example selection，不是用来发明需求。公开论文没有「最近一年：时点 vs TTM vs 财年」的对照实验，那条因果来自 prompt replay。

- **ODIS**（arXiv:2310.06302）：跨域能传格式，也会把源域口径一起迁过来。
- **DAIL-SQL**（arXiv:2308.15363）：精选范文优于随机，要同时看问题和 query 结构。
- **DIN-SQL**（NeurIPS 2023）约 +10pp 证明的是**分解推理**，不是动态范文选择。

## 2. 方案选型：考虑了哪些方案，如何权衡

**选型前提**：SchemaMapper 不动、Parser 已在，不改主链路。比的是**怎么让 Parser 用对的口径和骨架写 S2SQL**，不是换模型、不是重做字段映射。切入点挂在已有 `NL2SQLParser.addDynamicExemplars`（Parser 前同步召回）——记忆复用只教写法，和字段映射是上下游。DIN-SQL 的分解推理是另一条轴，它的约 +10pp **不能**写成 example selection 收益。

**逐步淘汰**：


| 顺序    | 方案                       | 做法                                                                   | 淘汰 / 入选理由                                                                                                                                                               |
| ----- | ------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 淘汰  | **A. Prompt 里加规则**       | 系统提示写死时点 / TTM / 财年、多实体 `GROUP BY`、阈值用 `HAVING`                      | 1. 三种「最近一年」都写成规则，和超音数范文一冲突就失效——LLM 更听 few-shot 不听长规则 2. 「最近一年」的 if-else 写进 prompt，等于把 Parser 该做的事再写一遍 3. 新口径要改提示、发版；多实体漏分组、阈值放错 `WHERE` 这类未预见骨架，规则盖不住                   |
| ② 淘汰  | **B. 堆 / 静态替换 Few-shot** | 往 JSON 里堆骨架；或删掉超音数、换成几条金融范文                                          | 1. 一套静态范文只能示范一种「最近一年」，时点 / TTM / 财年另外两种被教坏 2. 能止血三张已知事故，盖不住口径 × 骨架的组合爆炸 3. 新口径要改 JSON、回归，滞后线上                                                                           |
| ③ 淘汰  | **C. 按问题路由到不同 Prompt**   | 先分类（时点 / TTM / 财年 / 多实体 / 阈值），再进各自 prompt + few-shot                 | 1. 「最近一年」一口三义，必须先判对是时点还是 TTM——**路由本身就是原问题** 2. 分错类则整段 prompt 都错，比混在一个 prompt 里更伤 3. N 套模板要维护，未见过的意图只能 fallback；多一次分类调用，延迟也涨                                             |
| ④ 暂不选 | **D. 微调**（SFT / LoRA）    | 用成功 SQL 把金融口径写入参数                                                    | 1. **现在不当主方案**：新口径不能当天生效，错 SQL 进训练集后难以按条回滚 2. **后续要做**：先用已收集的 800+ 条 ENABLED 记忆试水微调 **7B** 小模型 3. 若有效，数据扩到约 **5000** 条，再逐步加大模型参数量；检索和微调是先后，不是互斥                         |
| ✅ 入选  | **E. 动态检索同构范文**          | 过审成功 query → `memory_{agentId}` → Parser 前召回 10、筛约 5 注入 `#Exemplars` | 1. 「净利润」和「净利润（TTM）」分别召回各自过审过的成功 SQL，一口三义不用先分类 2. 多实体补上 `GROUP BY`、阈值改成 `HAVING`，靠同构范文带骨架，不改 Parser、不训新模型 3. 每条按 `queryId` 可回溯、可下线；DAIL-SQL / ODIS 只支持方向，**不保证** 72%→87% |


**目标**：成功 SQL 过审后入库，按当前 query 召回同构范文注入 `#Exemplars`。

## 3. 行动计划：怎么一步步写出来的

按真实开发时序，分四步落地。状态机骨架先画完，主链路接通晚一些，人审通道更晚（标注时提出，后面才做成管理页）——典型的"先画框架、后填逻辑"打法。异常隔离和向量一致性是后来修的，放在第 4 节迭代优化。

### 第一步：地基日——状态机骨架 + 评审任务 + 入库/读出链路一次性设计

**为什么先做这步**：状态机是整个记忆库的骨架，先一次性设计好（PENDING/ENABLED/DISABLED + POSITIVE/NEGATIVE），避免后续重构。骨架包含五个部分，同一天内全部落地：

1. **状态机数据结构** —— `ChatMemoryDO` / `s2_chat_memory`。一行记忆长这样（表里**没有** embedding 列；向量化对象是 `question`）：

```java
@TableName("s2_chat_memory")
public class ChatMemoryDO {
    private Integer agentId;       // Agent 隔离 → 向量集合 memory_{agentId}
    private Long queryId;          // 来源问答，回溯 ELK / 人审 / usedExemplars
    private String question;       // ★ 做 embedding 的文本，不是 SQL
    private String sideInfo;       // 如 CurrentDate
    private String dbSchema;       // 当时 Schema 串
    private String s2sql;          // S2SQL（列名 s2_sql）
    private String status;         // PENDING / ENABLED / DISABLED
    private String llmReviewRet;   // POSITIVE / NEGATIVE（列 llm_review）
    private String llmReviewCmt;   // 列 llm_comment
    private String humanReviewRet; // 列 human_review
    private String humanReviewCmt; // 列 human_comment
}
```

1. **入库点** —— `SqlExecutor.execute` 仅当 `QueryState.SUCCESS` 且 `LLMSqlQuery.QUERY_MODE` 时调用 `createMemory`；规则 SQL 不入库；同 agent + 同 question 已有 ENABLED → 跳过（不重复写入）
2. **评审任务** —— `MemoryReviewTask.review` 每小时扫一轮（开源默认 60s，线上改为 1 小时）
3. **读出点** —— `NL2SQLParser.addDynamicExemplars` 在 Parser 前同步召回
4. **入向量两条线** —— **热路径**：审过 ENABLED 当次 `enableMemory` → `storeExemplar`，下一轮 query 就能召回，不用重启；**冷路径**：进程起来时 `CommandLineRunner.loadSysExemplars` 把 DB 里已有 ENABLED 再灌回去（向量随进程走、重启会空）

**关键类名**：`ChatMemoryDO`、`MemoryService`/`MemoryServiceImpl`、`MemoryReviewTask`、`SqlExemplar`、`ExemplarService`/`ExemplarServiceImpl`、`s2_chat_memory` 表

**状态机核心**：

```
LLM 产出四元组(question, sideInfo, dbSchema, s2SQL)
        │
        ▼  LLMResponseService.addParseInfo 挂到 ParseResult
SqlExecutor.execute → SUCCESS → createMemory → status=PENDING（只写 DB）
        │
        ▼  MemoryReviewTask 每小时扫一轮
   opinion=POSITIVE → updateMemory(ENABLED) → enableMemory → storeExemplar（热路径，当次生效）
        │
        ├─ 旁路：人审 / 用户反馈 score≥5(ENABLED) / ≤1(DISABLED) —— 同样走 updateMemory
        │
        ▼  下一轮 query（不用重启）
NL2SQLParser.addDynamicExemplars → recall 10
        → PromptHelper.getFewShotExemplars 筛成 ≤5 → #Exemplars → 新 S2SQL

冷路径（仅进程启动）：CommandLineRunner.loadSysExemplars 把 DB 里已有 ENABLED 再 storeExemplar
（不是每次审阅都要走；重启丢向量才靠它）
```

**向量侧——**`Text2SQLExemplar`：

- 集合名 `memory_{agentId}`（前缀 `s2.embedding.memory.collection.prefix`，默认 `memory_`）
- 向量化对象：`question` **文本**（不是 SQL）
- metadata / payload：JSON 含 `question` + `sideInfo` + `dbSchema` + `sql`
- 系统静态兜底集：`text2dsl_agent_collection`（`s2-exemplar.json`，演示域"超音数"）



### 第二步：成本控制 + 接通主链路（自动 ENABLED）

这一步核心就两件事：feature toggle，以及写审核提示词。POSITIVE → ENABLED 的状态机见附录阶段二。

**1. Feature toggle** —— LLM Review 按 Agent 开关，默认关，避免全站烧 token。`MEMORY_REVIEW.enable` 存在 Agent 的 ChatApp 配置里（DB，不在 yaml）；注册默认 `false`，业务 Agent 在管理界面打开。`MemoryReviewTask` 只扫 `agent.enableMemoryReview()==true` 的 Agent。

```java
public boolean enableMemoryReview() {
    ChatApp app = chatAppConfig.get("MEMORY_REVIEW");
    return app != null && app.isEnable();
}
```

**2. 审核提示词** —— `MemoryReviewTask.INSTRUCTION`，只看 Question / Schema / SideInfo / SQL，**不看执行结果表**（静态审核）。`%s` 按这四项填入：

```
#Role: You are a senior data engineer experienced in writing SQL.
#Task: Your will be provided with a user question and the SQL written by a junior engineer,
please take a review and give your opinion.
#Rules:
1. ALWAYS follow the output format: `opinion=(POSITIVE|NEGATIVE),comment=(your comment)`.
2. ALWAYS check date/time filters. Pay special attention to whether
   「去年 / 近一年 / YTD / 最近一年」maps to calendar year vs rolling 12 months,
   and whether the SQL date range is consistent with SideInfo (CurrentDate).
   If the time grain is wrong, mark NEGATIVE.
#Question: %s
#Schema: %s
#SideInfo: %s
#SQL: %s
#Response:
```

Rule 1 锁输出，后面 `processResponse` 用正则抽 `opinion` / `comment`。Rule 2 **开源默认是「不必查日期」**（`NO NEED to check date filters`）；金融场景会漏审「去年 = 自然年」，我们反过来改成必须盯时间口径。详见坑 3。

### 第三步：冷启动种子——编写金融场景静态种子

**为什么单独成步**：记忆库空 → 召回凑不满约 5 条 → Parser 退回吃演示域静态范文 → 跨域口径会教坏。要召满约 5 条同构范文，库里得先有密度。

**怎么灌进去**：不是手插整行记忆。给 Agent 写好 `examples`，**保存 Agent** 时旁路自动跑问数，成功的落 PENDING。和 04 内置推荐共用同一份 `agent.examples`。当时**还没有第四步人审通道**（没有 `updateMemory` 页面），数仓直接在 `s2_chat_memory` 里审语义 SQL。

```text
管理页写好 agent.examples（覆盖骨架的问句）
        │
        ▼  createAgent / updateAgent
executeAgentExamplesAsync → doExecuteAgentExamples
  前置：DatasetTool + MEMORY_REVIEW.enable + examples 非空
  同 question 已有记忆 → skip
  其余逐条 parseAndExecute(chatId=-1)
        │
        ▼  成功且 LLM_S2SQL（阶段一）
createMemory → PENDING
        │
        ▼  第四步人审通道当时还没有
数仓直接 UPDATE s2_chat_memory（改 s2_sql / 口径，再把 status 打成 ENABLED）
约一周（5 个工作日）标完 ~200 条
        │
        ▼  热路径 enableMemory 没走通，靠启动回灌
loadSysExemplars 把 ENABLED 灌进向量
```

**标注谁来做**：只有约 200 条，**数仓（DBA）全量标**——对照口径在库里改 `s2_sql`，两可的标「默认 + 备选」，耗时约一周（5 个工作日）。选题和口径标准是数仓和算法博士后一起定的；我接工程入口（配 `examples` 让 LLM 先跑出第一稿），不把标注说成自己标的。测评集既覆盖线上常见 SQL，也补一些线上没覆盖到的。类型四类：① 单表过滤 + 简单聚合；② 多表 JOIN；③ `GROUP BY` + `HAVING`；④ `ORDER BY` + `LIMIT`。这四类自由组合，收成简单 / 中等 / 复杂三档。

**灌多少**：4 个 Agent 按主题域分摊，每 Agent 约 40–60 条问句，合计约 200。来源：ELK 高复用题 + 评测已验证写法。


| Agent    | 种子数      | 为什么这个量                |
| -------- | -------- | --------------------- |
| 公司研究     | ~60      | 问得最多：单/多指标、自然年、多实体、排名 |
| 绿色经济     | ~50      | 跨表与口径相对多              |
| 经济研究（宏观） | ~50      | 时间序列、同比环比             |
| 行为实验     | ~40      | 表少、骨架少                |
| **合计**   | **~200** | 4 Agent 分摊            |


**40–60 是工程定标，不是论文阈值**：

- Prompt 里约 5 条 ≠ 种子库只要 5 条。DAIL-SQL 在 Spider-dev、GPT-4、**同一 5-shot** 下 Random 79.5、DAIL 82.4——比的是**怎么选**，候选池仍是 Spider train（8000+）。
- ODIS 的 30 条是实验点，不是「每域最低稳定数量」。
- 我们定 40–60：覆盖自然年 / 排名 / 多实体 `GROUP BY` / JOIN / `HAVING`，检索时才召得满约 5 条同构范文。
- 工业文档（Vanna）写过 3–5 起步、20+ 更好，那是产品建议，不能外推成每域阈值。



### 第四步：人审通道——管理员审核 + 用户投票

**为什么这时做**：第三步冷启动标注时提出来的。当时没有管理页，数仓只能直接改 `s2_chat_memory`，约一周才标完 ~200 条。要给 DBA / 管理员一个能改语义 SQL、启停记忆的入口，也要让用户对答对 / 答错投票，不能总进库改表。LLM Review 仍在跑，人审是介入通道，不是取代定时审。接口和状态机见附录阶段三、四。

两条入口：管理页审、改、启用 / 停用；用户赞 / 踩（高分直接启用，低分直接停用，不走 LLM Review）。冲突以人审为准，冲突 case 进评测集。

**周节奏**：


| 角色 | 节奏 | 做什么 |
|------|------|--------|
| **LLM** | **每小时一次** | POSITIVE → 当场 ENABLED；NEGATIVE → 等人 |
| **人工** | **每周一次**（约 0.5–1 小时） | 清 NEGATIVE + 抽检 POSITIVE；冲突进评测集 |


人不盯盘。日常放行交给 LLM，人做周批次兜底。单条约 30 秒–1 分钟；周队列约十几到三十条 NEGATIVE + 少量抽检。效率靠 LLM 先筛、同 question 去重、只收 LLM_S2SQL 成功题。

### 召回与注入（贯穿所有步骤）

Parser 前同步召回（`NL2SQLParser.addDynamicExemplars`）：从 `memory_{agentId}` 按当前问句向量召回最多 10 条，挂到 `dynamicExemplars`，并写入 `usedExemplars`。代码见附录阶段五。

`PromptHelper.getFewShotExemplars` 把候选筛成约 5 条进 `#Exemplars`：先 Agent 记忆、不够用系统集补；相似度 > 0.989 的 same 全留（可超过 5）；没有 same 则取 5 条，强制保住最高分那条。

| 配置项 | 本仓库值 | 含义 |
|--------|---------|------|
| `parser.exemplar-recall.number` | **10** | 向量召回候选池上限 |
| `parser.few-shot.number` | **5**（Parameter 默认 3） | 真正进 `#Exemplars` 的条数 |

## 4. 迭代优化：遇到什么问题，怎么克服

记忆库不是「存 SQL 就涨点」。下面几条是仓库里真实修过的（开源 commit，面试讲「踩到 / 跟过」，不要说成自己提的 PR）。

### 坑 1：单条评审失败拖垮整批

- **难在哪**：`MemoryReviewTask` 整批套一个 try-catch，一条 LLM 调用抛错，后面的记忆本轮全停
- **怎么扛**：`72d01bb41`（2024-10-11，PR `#1788`）。改成 `forEach` 里每条单独 catch
- **关键类**：`MemoryReviewTask.review`



### 坑 2：已 ENABLED 再改 SQL，向量仍是旧稿

- **难在哪**：人审改过 `s2_sql` 后 DB 已是新稿，向量里还是旧四元组，后续召回会把错写法再教给 Parser。ENABLED 退回 PENDING / DISABLED 时向量也不清，下线了仍能被召到
- **怎么扛**：`c24ba59bb`（2025-05-29）。只要请求是 ENABLED 就重新 `storeExemplar`（覆盖旧稿）；从 ENABLED 退到 PENDING / DISABLED 都 `removeExemplar`
- **关键类**：`MemoryServiceImpl.updateMemory`

### 坑 3：开源审核不抠日期，金融时间口径漏审

- **难在哪**：开源 Rule 2 写着 `NO NEED to check date filters`。金融场景「去年 / 近一年 / YTD」一口三义，漏审会把错口径范文放进记忆库
- **怎么扛**：把 Rule 2 **反过来**——审核时必须检查时间过滤是否和问句、`SideInfo.CurrentDate` 对齐；口径不对直接 NEGATIVE。改后的提示词见第二步
- **留下什么**：仍是静态审核（不看执行结果表）；人审做抽检，不再当时间口径的唯一兜底

### 后续改进方向

记忆库目前只进不出：无 TTL、无召回反馈降权，语义层变更后旧 SQL 过时，低质量会稀释高质量。靠人工巡检和用户反馈下线，没有系统化淘汰。Parser 侧 `self-consistency=1`，还是单模型一次出 SQL。

| 优先级 | 方向 | 问题 | 拟改法 |
|--------|------|------|--------|
| **P0** | 召回后反馈闭环 | 错范文被召回无降权，污染半衰期长 | 用户否决 / 答错 → 自动降权或 DISABLED |
| **P1** | TTL / 长期未召回降权 | 只进不出；语义层变更后旧 SQL 过时 | N 天未召回降权；schema 变更时批量失效或重审 |
| **P1** | 表字段补 `recall_count` / `last_recalled_at` | 现表无 hit count，运营盲 | 加字段（或等价观测） |
| **P1** | 多 LLM 投票做自一致性 | 当前 `self-consistency=1`，单模型一次出 SQL；时间口径、`GROUP BY` 仍可能一次写错 | 多模型各自生成，投票取一致 S2SQL；审核侧也可多模型投 POSITIVE / NEGATIVE |

## 5. 成果展示：怎么衡量，效果如何



### 评测口径

评测基于自维护离线集，**同一批 200 条**贯穿 T0/T1/T2，中间无人工干预（无 HITL）。既有线上常见 SQL，也补线上没覆盖到的。类型四类：单表过滤 + 简单聚合、多表 JOIN、`GROUP BY` + `HAVING`、`ORDER BY` + `LIMIT`；自由组合后收成简单 / 中等 / 复杂三档。


| 阶段                  | 端到端准确率      | Schema EM   | Parser 条件准确率（Schema 正确子集） | 说明           |
| ------------------- | ----------- | ----------- | ------------------------- | ------------ |
| T0（加入时）             | 45%         | 58%         | —                         | 端到端测评集已就绪    |
| T1（Schema + LLM 消歧） | 72% (+27pp) | 81% (+23pp) | ~75%                      | 记忆库未上线       |
| T2（记忆库上线）           | 87% (+15pp) | 81%         | ~90% (+15pp)              | +15pp 全归因记忆库 |


Parser 条件准确率是端到端集上的条件切片（Schema EM 正确的前提下看最终答案是否对），不是另建一套 S2SQL Exact Match 评测集。

判定方式：执行结果是否满足 gold_answer 的口径约束 + 五维度语义评分（字段、实体、时间、聚合、量级）。

### 已实现效果

端到端准确率从 **72% 提升到 87%**（同一批 200 条离线评测集，无 HITL）；其中 T1→T2 的 **+15pp** 几乎全部归因于记忆库（SchemaMapper 在 T1 已优化完毕，映射 EM 保持在 81%）。

记忆库累计 **800+ 条 ENABLED**，其中冷启动种子 **约 200 条**（4 个 Agent 按主题域分摊），4-7 月线上沉淀约 600 条。

在 Schema 已正确的子集上，Parser 条件准确率约 **75% → 90%**。

### 漏斗表（周）

```
周查询 ≈ 1050（150×7）
  → 成功且 LLM_S2SQL ≈ 700–800
  → 去重后新 PENDING ≈ 80–100（同问已有 ENABLED 则跳过）
  → 新 ENABLED ≈ 50/周
```


| 口径                  | 约值           | 一句话              |
| ------------------- | ------------ | ---------------- |
| 全量查询 → 新 ENABLED    | **~5%**      | 低是正常的——大量重复不问不入库 |
| 新 PENDING → ENABLED | **~50%–60%** | 才是闸门过审率          |


飞轮看"新结构过审"，不看"每次查询都变记忆"。

### 阶段二：定时审 —— PENDING → 调 updateMemory

#### 二-1：调度入口 → 审完交出去

> 来源：`MemoryReviewTask.review` / `processMemory` / `processResponse`
> 对应正文：行动计划第二步；坑 1 单条 try-catch；坑 3 Rule 2 反过来盯时间

```java
@Scheduled(fixedDelay = 60 * 60 * 1000)  // 线上 1 小时；开源默认 60s

    for (Agent agent : agentService.getAgents()) {
        if (!agent.enableMemoryReview()) continue;          // Agent 级开关
        memoryService.getMemories(/* 该 agentId */).forEach(memory -> {
            try {
                processMemory(memory, agent);               // 单条隔离，避免拖垮整批
            } catch (Exception e) { /* log */ }
        });
    }
}

private void processMemory(ChatMemory m, Agent agent) {
    if (m.getLlmReviewRet() != null || m.getHumanReviewRet() != null) return; // 已审过
    ChatApp chatApp = agent.getChatAppConfig().get("MEMORY_REVIEW");
    if (chatApp == null || !chatApp.isEnable()) return;

    String promptStr = String.format(chatApp.getPrompt(),
            m.getQuestion(), m.getDbSchema(), m.getSideInfo(), m.getS2sql());
    // 调 LLM；关键 Rule 2：必须检查时间口径（开源是 NO NEED to check date filters，我们反过来）
    String response = chatLanguageModel.generate(...);
    processResponse(response, m);
}

private void processResponse(String response, ChatMemory m) {
    // 解析 opinion=(POSITIVE|NEGATIVE),comment=...
    if (POSITIVE.equals(m.getLlmReviewRet())) {
        m.setStatus(MemoryStatus.ENABLED);
    }
    // NEGATIVE：不改 status，仍是 PENDING；不会自动 DISABLED
```

### 阶段四：写向量 —— updateMemory 汇合点 + 启动回灌

定时审、人审、反馈都交到 `updateMemory`，`storeExemplar` 是同步的（embed + add），审完下一轮 query 就能召回，不用重启。`loadSysExemplars` 只在进程起来时跑，用来把 DB 里已有 ENABLED 灌回可能被重启清空的向量库。

```text
定时审 processResponse / 人审 / 反馈
        │
        ▼
updateMemory
  ├─ 目标 ENABLED                    → enableMemory  → storeExemplar
  ├─ 从 ENABLED 退到 DISABLED/PENDING → disableMemory → removeExemplar
  └─ 再 UPDATE s2_chat_memory

进程启动（Spring Boot CommandLineRunner.run）
  → loadSysExemplars：只灌 ENABLED（PENDING / DISABLED 不回灌）
```



#### 四-1：汇合点 —— updateMemory → enable / disable 动向量

> 来源：`MemoryServiceImpl.updateMemory` / `enableMemory` / `disableMemory` + `ExemplarServiceImpl.storeExemplar`
> 面试要点：定时审、人审、用户反馈**三条入口都只调到这里**。先按请求 status 决定动不动向量，再 UPDATE DB。`enableMemory` 里的 `storeExemplar` 同步写入 `memory_{agentId}`，**不经过启动回灌**，下一轮 query 的 `addDynamicExemplars` 就能召到。embedding 只打 **question**；DISABLE 清向量但 **DB 行留着作账**；只有「曾经 ENABLED」再退下来才 `removeExemplar`

```java
public void updateMemory(ChatMemoryUpdateReq req, User user) {
    ChatMemoryDO row = chatMemoryRepository.getMemory(req.getId());
    boolean hadEnabled = ENABLED.equals(row.getStatus());

    if (ENABLED.equals(req.getStatus())) {
        row.setS2sql(req.getS2sql());   // 人审可能改过 SQL / Schema
        row.setDbSchema(req.getDbSchema());
        enableMemory(row);              // → storeExemplar
    } else if ((DISABLED 或 PENDING) && hadEnabled) {
        disableMemory(row);             // → removeExemplar；从未 ENABLED 过则向量里没有，不必清
    }
    // 再 UPDATE s2_chat_memory：status / llm_review / human_review / s2sql ...
}

public void enableMemory(ChatMemoryDO memory) {
    memory.setStatus(ENABLED);
    exemplarService.storeExemplar(
            embeddingConfig.getMemoryCollectionName(memory.getAgentId()),
            /* 四元组：question + sideInfo + dbSchema + sql */);
}

public void disableMemory(ChatMemoryDO memory) {
    memory.setStatus(DISABLED);
    exemplarService.removeExemplar(/* 同一集合、同一四元组 */); // 不 delete DB 行
}

// ExemplarServiceImpl.storeExemplar
```

| 请求 status          | 库里原来           | 向量动作                    |
| ------------------ | -------------- | ----------------------- |
| ENABLED            | 任意             | `enableMemory`（写入 / 覆盖） |
| DISABLED 或 PENDING | **曾经 ENABLED** | `disableMemory`（删除向量）   |
| DISABLED 或 PENDING | 本来就是 PENDING   | 不动向量（从未进去过）             |




#### 四-2：启动回灌 —— Spring Boot 起来时跑 CommandLineRunner

> **从哪里触发**：**是 Spring Boot 启动时回灌**。`MemoryServiceImpl` 实现了 `CommandLineRunner`，容器刷新完成后 Spring 自动调 `run()`，不是定时任务，也不是第一次 query 才灌。
> 来源：`MemoryServiceImpl implements MemoryService, CommandLineRunner`
> 面试要点：这是**冷路径**，补偿重启丢向量，不是审阅生效的前提。只灌 ENABLED（PENDING / DISABLED 不回灌）。同一进程里还有另一份 `CommandLineRunner`（`ExemplarServiceImpl`，`@Order(0)` 先跑），加载的是 classpath `s2-exemplar.json`（超音数预设集），别和这份记忆回灌混成一次。

#### 五-3：补齐 → 筛桶 → 注入 prompt —— PromptHelper + OnePassSCSqlGenStrategy

> 来源：`LLMRequestService` 拷贝 dynamicExemplars → `OnePassSCSqlGenStrategy.generate` → `PromptHelper.getFewShotExemplars`
> 面试要点：降级在这里——记忆侧不足 10，用系统预设集 `text2dsl_agent_collection`（超音数，启动时灌 `s2-exemplar.json`）按问句补差。筛桶阈值 `similarity > 0.989`；**same 全留、可以超过** `few-shot.number=5`。

```java
// 模板 #Exemplars: {{exemplar}}；每条拼成 Question/Schema/SideInfo/SQL

public List<List<Text2SQLExemplar>> getFewShotExemplars(LLMReq llmReq) {
    int recallN = 10, fewShot = 5; // self-consistency 本仓库 = 1，下面循环只跑一轮

    List<Text2SQLExemplar> pool = new ArrayList<>(llmReq.getDynamicExemplars());
    int gap = recallN - pool.size();
    if (gap > 0) {
        // ★ 降级：记忆侧 0 条则补 10；7 条则再补 3。打的是系统集，不是 memory_{agentId}
        pool.addAll(exemplarService.recallExemplars(llmReq.getQueryText(), gap));
    }

    List<Text2SQLExemplar> same = /* similarity > 0.989，几乎同题 */;
    List<Text2SQLExemplar> noSame = /* 其余 */;

    // 砍尾：仅当 noSame 比 same 多出超过 5 条时，noSame 升序丢掉最低一截
    // 例：7 same + 3 noSame → (3-7)=-4 > 5？否，不砍

    // 砍尾若发生，noSame 已按相似度升序，last = 最高分；记下后再 shuffle
    Text2SQLExemplar mostSimilar = noSame.get(noSame.size() - 1);
    Collections.shuffle(noSame);

    if (!same.isEmpty()) {
        // same 必须全部进 prompt，不截断（所以最终条数可以 > 5）
        int need = Math.min(noSame.size() + same.size(), 5);
        if (need > same.size()) {
            ts.addAll(noSame.subList(0, need - same.size())); // same 不够 5，才从打乱后的 noSame 补差
        }
        ts.addAll(same);
        // 7 same + 3 noSame：need=min(10,5)=5；5>7？否 → 不取 noSame → 进 prompt 共 7 条 same
        // 2 same + 8 noSame：先砍尾（8-2=6>5）→ need=5>2 → 3 条 noSame + 2 条 same = 5
    } else {
        // 10 条全是 noSame（都 ≤0.989）时走这里：
        //   1. 上面已砍尾（10-0=10>5），升序丢掉最低 2 条，剩 8 条
        //   2. shuffle 这 8 条，取前 5 —— 最高分那条可能被洗出前 5
        //   3. 若洗出去了：丢掉这 5 条里的最后一条，把最高分补回来
        // 目的：prompt 里随机抽 5 条，但至少保住「相对最像」的 1 条
        ts = noSame.subList(0, Math.min(noSame.size(), 5));
        if (!ts.contains(mostSimilar)) {
            ts.remove(ts.size() - 1);
            ts.add(mostSimilar);
        }
    }
    return List.of(ts);
}
```
