# 推荐问题（内置 15% + 相似 11%）

## 1. 背景：为什么做，怎么发现的问题

推荐要拆场景——不是全站统一痛点，更不是"用户不会提问"。

**主场景：行为实验开展期，实验助理反复查 + 连续追问**

谁在问：兼职大学生、实习生，在实验实施的约 4 周内高频查运维题——没发报酬有哪些人、校准失败要不要补招、场次男女比例、实验预算花了/剩下/人均多少。骨架固定，变的是实验名和场次。查完报酬名单后，下一步常问预算、校准失败人数或样本结构——这是一张固定运维清单上的连续追问，不是随机发散。

**次场景：绿色金融等金融经济研究，引导开口**

实证研究一次一问、换假设就换结构，不像实验运维那样近重复扎堆。痛点是"这套库自然语言怎么起头才问得出面板"——内置引导题是开口模板，点下去走完整问数链路。

**一句话**：相似吃"查完 A 还要问 B"；内置吃"不知道怎么开口"。两条通道互补，权重不同。

讲场景时先把范围锁死再谈数字，否则贡献率口径经不起追问。

## 2. 方案选型：考虑了哪些方案，如何权衡

选型时最先被追问的替代方案是：运维题问来问去很重复，能不能上 Redis 把「问题 → 答案」缓存起来（精确命中 + 语义近邻复用），少跑 Text2SQL？

### ① 淘汰：Redis 缓存回答

**不这么做，核心是权限。** 问数里每个人能看的数据范围不一样——同一句「未发报酬有哪些人」，A 助理和 B 助理看到的名单可以完全不同。答案一旦按问题文案进缓存，很容易把别人的结果返回给当前用户；按人、按权限集拆 key 又复杂，语义相似命中更危险（近邻对上了、权限却对不上）。

推荐只给人看下一问的**文案**，真正查询仍走完整 `parseAndExecute` 和权限校验，不会把结果缓存成「谁问都一样」。

事后用埋点看重复查询与可缓存空间，也印证了**当前体量下没有上 Redis 的必要**——权限风险先否掉，数据上再确认不值得做。

### ② 入选：双通道分工设计

放弃缓存之后，按场景拆成两条推荐通道：


| 通道                                      | 解决什么                 | 数据源                               | 时机        |
| --------------------------------------- | -------------------- | --------------------------------- | --------- |
| **通道一：进门内置**（`Agent.examples`）          | 不知道怎么开口——绿色金融引导题     | 管理员预配置的 `List<String>`            | 进门前展示     |
| **通道二：查完相似**（`QueryRecommendProcessor`） | 查完 A 还要问 B——行为实验连续追问 | 同一 `memory_{agentId}`，只取 question | Parse 后异步 |


**两通道关系**：**B1 ∥ B2 并行**，不是先后工序。会话中常先遇 B1、查完再遇 B2；但用户纯手打（不点 B1）也会触发 B2——B2 不依赖 B1 被点过。

**汇合点（B3）**：两通道的**共同出口**——点击后果走完整 `parseAndExecute`，差异只在归因 `source` 字段。

**刻意不做**：输入联想（边打边出是另一套能力）；不另建推荐向量库——与记忆复用共用 `memory_{agentId}`，这里只取 `question` 给人点。

**目标**：

- 降低开口成本：内置引导题让绿色金融用户点一下就走完整链路
- 结果旁下一跳：相似推荐把历史成功问法摊在结果区，助理连着点下去

## 3. 行动计划：怎么一步步写出来的

按真实开发时序，分五步落地。相似通道先做（端到端打通），内置通道晚了约 6 个月引入，两者最终通过共用 ExemplarService 融合。

### 第一步：相似通道先行——一天内端到端三连击

**为什么先做相似**：行为实验助理的"连续追问"痛点最具体，相似推荐直接吃已有记忆库，工程路径最短。

**一天内三连击**：

1. **后端 Processor + Manager + DB schema** —— 新增 `QueryRecommendProcessor`（相似问题召回 + 异步回写 queryId）、`SimilarQueryRecallResp`（响应结构）、`ChatQueryDO.similar_queries` 字段（DB 持久化）。异步用 `CompletableFuture.runAsync` 不指定线程池 → 用 `ForkJoinPool.commonPool()`
2. **改名"Recommend"语义** —— 把 `SimilarQueryProcessor` 改名 `QueryRecommendProcessor`，把"相似"语义改成"推荐"语义（产品视角统一）
3. **前端 UI 接入** —— `SimilarQuestionItem.tsx`（导出名 `SimilarQuestions`）接到新接口，结果区渲染可点列表

**关键类名**：`QueryRecommendProcessor.process`、`getSimilarQueries`、`SimilarQueryRecallResp`、`ChatQueryDO.similarQueries`、`SimilarQuestionItem.tsx`

**召回逻辑**：从 `memory_{agentId}` 召回 topK=5，**只取 question** 展示（不取 SQL 四元组）；候选池为执行成功且 ENABLED 的记忆。

**异步回写**：`CompletableFuture.runAsync(() -> doProcess(parseContext))` 不堵 parse 返回；列表以 String JSON 写入 `ChatQueryDO.similarQueries`。

### 第二步：链路兜底——失败路径也要有 queryId

相似推荐上线约 6 天后踩到：失败查询不返回 `queryId`，异步回写与前端拉取都挂掉。详情与修复见 [§4 坑 1](#坑-1失败查询不返回-queryid推荐链路断掉)。

### 第三步：内置通道——与 ChatMemory 模块同日引入

**为什么这天做**：内置通道的诞生与 ChatMemory 模块（03）是**同一天、同一个 feature 的两个 commit**（绑定关系，不是巧合）——Agent examples 既能进门展示给人点，又能异步灌入 ChatMemory 表当冷启动种子。

**怎么做的**：新增 `AgentExample2MemoryTransformer`（49 行 `@Async`）——把 `agent.examples` 走一遍 `chatService.parseAndExecute`，结果以 PENDING 状态灌入 ChatMemory 表。

**关键类名**：`AgentExample2MemoryTransformer`、`MemoryController`、`ChatMemoryFilter`、`MemoryStatus` 枚举、`MemoryReviewResult` 枚举

**内置通道存储**：

- Domain 层：`Agent.examples` 是 `List<String>`
- DB 层：`AgentDO.examples` 是 **String JSON**
- DO ↔ Domain 转换在 `AgentServiceImpl`：`JsonUtil.toList` / `JsonUtil.toString`

**前端展示 + 点击**：chat-sdk 进门拉 `Agent.examples`，结果区渲染可点列表。用户点某条 example → 前端把文字当 `queryText` 提交，走完整 `parseAndExecute`。

**勿混 `preset_query_collection`**：`EmbeddingConfig.presetCollection`（字段名，默认 `preset_query_collection`）给 **Plugin** embedding 识别用（`PluginManager.recognize` 消费），不是结果旁"点一下再查"的内置 FAQ 列表——**两套不互通**。

### 第四步：重构内置灌记忆旁路（@Async → 内部线程池）

初版裸用 `@Async` 会落到不重用线程的 `SimpleAsyncTaskExecutor`；后来收进 `AgentServiceImpl` 自管线程池。详情见 [§4 坑 2](#坑-2内置灌记忆旁路独立-async-组件的优化)。

### 第五步：两通道融合——相似通道切换到 ExemplarService

**为什么做这步**：相似通道原本直查 embedding store + 低分过滤 + QueryResp 查询，代码冗余且与 03 的数据源割裂。ChatMemory 模块上线后，两通道应该共用同一数据底座。

**怎么改的**：`QueryRecommendProcessor` 从"直查 embedding store"改成走 `ExemplarService.recallExemplars(agentId, queryText, 5)`，**删除整个 `SimilarQueryManager`（-80 行）**，代码量净减少。

**这是"架构收敛"的典型例子**——两通道共用同一 `memory_{agentId}` 集合，03 同步写入/召回，04 异步只读。

## 4. 迭代优化：遇到什么问题，怎么克服

### 坑 1：失败查询不返回 queryId，推荐链路断掉

- **现象**：相似推荐上线约 **6 天**后（git：`#511`/`#513` 2023-12-15 → `#562` 2023-12-21），发现查询一失败，推荐就挂——异步回写找不到行，前端 `getChatQuery/{queryId}` 也没 id 可拉。
- **根因**：一次提问其实分两层落库——① **查询行**（`s2_chat_query`：用户问了这句话，主键就是 `queryId`）；② **解析明细**（这次解析出了哪些候选 SQL）。当时 `RespBuildProcessor` 只在有候选 parse 时才 `batchAddParse`；`FAILED` 时只标失败、**连查询行都不建**，自然没有 `queryId`。而相似推荐的契约是：后台按 `queryId` 写 `similar_queries`，前端再按同一 id 拉——**id 是挂载点**。
- **怎么修**（真实 commit `#562`）：无论成功失败都走 `batchAddParse`（内部会 `createChatQuery`）；没有候选 parse 时跳过写解析明细，但查询行仍在。

```java
// 修前（RespBuildProcessor）：只有成功才落库 → 失败没有 queryId
if (candidateQueries.size() > 0) {
    parseResp.setState(COMPLETED);
    chatService.batchAddParse(...);   // 这里才会 createChatQuery
} else {
    parseResp.setState(FAILED);       // 只标失败，不建查询行
}

// 修后：失败也走 batchAddParse，保证有 queryId
if (candidateQueries.size() > 0) {
    parseResp.setState(COMPLETED);
} else {
    parseResp.setState(FAILED);
}
chatService.batchAddParse(...);       // 成功/失败都执行

// ChatQueryRepositoryImpl.batchSaveParseInfo 内部（同 PR）
Long queryId = createChatQuery(...);  // 查询行一定插入
if (!CollectionUtils.isEmpty(candidateParses)) {
    chatParseMapper.batchSaveParseInfo(...);  // 有解析明细才写第二层
}
// 失败时：有 queryId，没有 parse 明细 —— 推荐仍可挂在这条查询行上
```

- **留下什么**：异步推荐的完整性前提是「**任何查询路径都要有 queryId**」——成功要有，失败也要有。失败记录上仍可挂相似推荐（候选池仍是成功过审记忆）；没有 id，写库和拉取两头都断。

### 坑 2：内置灌记忆旁路——独立 @Async 组件的优化

> 先分清：用户进门点的内置题，走的是 `AgentTip`（主链路）。这里讲的是**另一件事**——管理员保存 Agent 时，后台偷偷把 examples 跑一遍问数，成功的写进 03 记忆库当冷启动种子（旁路）。

- **当初怎么做的**：单独写了个 `AgentExample2MemoryTransformer`，方法上挂 `@Async`。一保存 Agent 就丢给 Spring 异步去跑。
- **为啥不用默认 `@Async`（核心）**：没自定义线程池时，`AsyncExecutionInterceptor.getDefaultExecutor` 会落到 `SimpleAsyncTaskExecutor`。它**不是真正的线程池**——不重用线程，每次调用新建一条；也没有最大线程数上限。并发一上来就会狂建线程，性能很差。灌记忆这种「保存时触发、可能连跑多条 example」的活，更不该踩这个默认实现。
- **连带还有的问题**：独立组件散落在 memory 包，和 Agent 保存入口割裂，不好加「LLM/开关预检」、也不好做同步互斥；LLM 挂了还硬跑会空转失败。
- **怎么改的**（同日 `#1249` 引入 → `#1258` 重构）：删掉 `@Async` 组件，逻辑收进 `AgentServiceImpl`，用显式单线程池（重构当时是 `newFixedThreadPool(1)`，现行是注入的多线程 `chatExecutor`）。方法上加 `synchronized`：任务进池后可能并行，锁住「查记忆有没有 → 再灌」这段，避免连续保存把同一批 examples 灌两遍。

```java
// 改前：独立组件 + 裸 @Async（未配 Executor 时走 SimpleAsyncTaskExecutor）
@Component
public class AgentExample2MemoryTransformer {
    @Async
    public void transform(Agent agent) {
        for (String example : agent.getExamples()) {
            chatService.parseAndExecute(...);  // 每次调用可能新建线程，且不复用
        }
    }
}
// createAgent / updateAgent 里：
agentExample2MemoryTransformer.transform(agent);

// 改后：自管线程池（#1258 当时写法；现行注入 chatExecutor，语义相同）
private final ExecutorService executorService = Executors.newFixedThreadPool(1);

private void executeAgentExamplesAsync(Agent agent) {
    executorService.execute(() -> doExecuteAgentExamples(agent));  // 线程可复用、并发可控
}

private synchronized void doExecuteAgentExamples(Agent agent) {
    // synchronized：锁的是 AgentServiceImpl 单例。
    // 任务进的是多线程 chatExecutor（8~16），连续保存可能并发进来；
    // 不加锁时两个线程都「查记忆还没有」→ 同一批 example 灌两遍。
    if (!可跑灌记忆的前置条件) return;  // 预检：工具 / 开关 / examples 等
    for (String example : agent.getExamples()) {
        if (记忆里已有该 question) continue;
        chatQueryService.parseAndExecute(...);
    }
}
```

- **留下什么**：要异步就**自己管 Executor**，别裸用无配置的 `@Async` 吃 `SimpleAsyncTaskExecutor`；进池之后还要用 `synchronized`（或等价互斥）护住「查重 + 灌入」临界区。更完整代码见附录「阶段一-3」。

## 5. 成果展示：怎么衡量，效果如何

### 指标口径

每次真正提交问数打一条 `query_submit`，带归因字段 `source`。贡献率：`count(source=X) / count(全部 query_submit)`——分母都是总查询次数，分子分别是各来源查询数。

**为什么不用 impression CTR**：内部 B 端工具，关心的是"有多少查询真的从推荐进来"，不是资讯流式曝光点击。只看了推荐没提交，不进分子，也不单独当主 KPI。

| source | 含义 | 指标 | 公式 | 简历值 | 日均 150 次时约 |
|--------|------|------|------|--------|----------------|
| `manual` | 手打提交 | — | — | — | — |
| `preset` | 点内置推荐触发 | 内置贡献率 | `count(source=preset) / count(全部)` | **15%** | ~23 次 |
| `similar` | 点相似推荐触发 | 相似贡献率 | `count(source=similar) / count(全部)` | **11%** | ~17 次 |
| — | 推荐合计 | 双通道合计 | 内置 + 相似 | **26%** | ~40 次 |

### 行为实验侧——相似推荐代表性样例


| 问法                           | 推荐来源   | 连续追问链       |
| ---------------------------- | ------ | ----------- |
| "xxx 实验未发报酬人员有哪些"            | 内置 FAQ | → 预算花了/剩/人均 |
| "注意力校准失败的被试有多少"              | 相似近邻   | → 要不要补招     |
| "xxx 实验预算花了多少 / 还剩多少 / 人均多少" | 相似近邻   | 查完报酬常被推     |


### 绿色金融侧——内置引导题代表性样例


| 引导题                                        | 示范什么             |
| ------------------------------------------ | ---------------- |
| 绿色金融改革试验区地级市 2010–2020 碳排放、GDP、第二产业占比面板    | 政策试点 × 面板口径      |
| A 股公司按 ESG 评级分组平均 ROA / Tobin's Q，区分国企与非国企 | ESG × 财务 × 所有制异质 |


### 点击后链路——"连续追问"闭环

不论点的是内置题还是相似题，后果一样——前端把文案当新 `queryText` 提交，走完整 `parseAndExecute`。差异不在链路，在归因。

`ParseResultProcessor` 链中 `QueryRecommendProcessor` 会被**再次触发**——给新一轮查询继续推相似。这意味着：用户点相似推荐 → 走完整 `parseAndExecute` → 又异步召回新的相似题 → 再点再推——形成**连续追问**的产品语义闭环。

### 通道一：内置 —— 完整调用链

> **生命周期（跟代码顺序读）**：
> 管理员在 Agent 表单配置「示例问题」并保存 → `examples` 落 `AgentDO` → 前端 `getAgentList` 拿到当前 Agent（含 `examples`）→ 空会话渲染 `AgentTip` 列出可点文案 → 用户点击 → `onSendMsg(example)` → 完整 `parse` / `execute`（与手打同一条路）
>
> **旁路（别和主链路混）**：保存 Agent 时若开启记忆评审，会异步把 examples 跑一遍 `parseAndExecute`，成功则按 03 落 PENDING→Review，给记忆库冷启动。这是**灌记忆**，不是「再推一遍推荐给用户」。
>
> 对应正文：行动计划第三步（引入）+ [§4 坑 2](#坑-2内置灌记忆旁路独立-async-组件的优化)（@Async 重构）；与通道二汇合点相同——点击后都走完整问数链路。

```text
【主链路：给人点】
管理员配置 examples 并 create/update Agent
        │
        ▼
AgentDO.examples（DB String JSON）
        │
        ▼
GET /chat/agent/getAgentList → Agent.examples（List<String>）
        │
        ▼
空会话 MessageType=AGENT_LIST → AgentTip 渲染可点列表
        │
        ▼ 用户点击某条
onSendMsg(example 文案)
        │
        ▼
与手打相同：ChatQueryServiceImpl.parse → execute
（随后通道二 QueryRecommendProcessor 仍会异步推相似）

【旁路：灌记忆，服务 03】
createAgent / updateAgent
        │
        └─ executeAgentExamplesAsync（chatExecutor 线程池）
              └─ doExecuteAgentExamples
                    ├─ 前置：含 DatasetTool + enableMemoryReview + examples 非空
                    ├─ 已在记忆库的 question 跳过
                    └─ 对其余 example：parseAndExecute → 成功则 03 入库 PENDING
```

#### 阶段一-1：配置与落库 —— Agent.examples

> 来源：`Agent` / `AgentDO` + `AgentServiceImpl.convert`；管理端 `AgentForm`「示例问题」
> 面试要点：给人看的内置题就是 Agent 上的字符串列表；Domain ↔ DB 用 `JsonUtil.toList` / `toString`；**不是** `preset_query_collection`（那是 Plugin embedding 用的另一套）

```java
// 保存时：List<String> → JSON 字符串进 AgentDO
```

> 来源：`ChatQueryServiceImpl.parse` + `META-INF/spring.factories` 的 `ParseResultProcessor` 列表

#### 阶段二-2：异步入口 —— QueryRecommendProcessor.process / doProcess

> 来源：`QueryRecommendProcessor`（约 67 行）
> 面试要点：`runAsync` **不指定线程池** → `ForkJoinPool.commonPool()`；**无超时**；回写按 `questionId`（即 queryId）；列表尚未写完时前端展开会看到空

```java
public class QueryRecommendProcessor implements ParseResultProcessor {

    public boolean accept(ParseContext parseContext) {
        return true;  // 每条 parse 都跑（含失败 query——只要有 queryId 就能挂推荐）
    }

    public void process(ParseContext parseContext) {
        // 异步：parse 响应先返回；相似列表稍后写进 DB
        CompletableFuture.runAsync(() -> doProcess(parseContext));
    }

    private void doProcess(ParseContext parseContext) {
        Long queryId = parseContext.getResponse().getQueryId();
        // 按当前问句 + agentId 召回相似题（见二-3）
        List<SimilarQueryRecallResp> solvedQueries = getSimilarQueries(
                parseContext.getRequest().getQueryText(),
                parseContext.getAgent().getId());

        // 按 queryId 把 JSON 列表写回 s2_chat_query.similar_queries
        ChatQueryDO chatQueryDO = getChatQuery(queryId);
        chatQueryDO.setSimilarQueries(JSONObject.toJSONString(solvedQueries));
        updateChatQuery(chatQueryDO);  // UPDATE WHERE question_id = queryId
    }
}
```

#### 阶段二-4：读出 —— 不是异步推前端，是前端再拉一次

> 来源：`ChatController.getChatQuery` → `ChatQueryRepositoryImpl.convertTo` → `SimilarQuestionItem.tsx`
>
> **容易晕的一点**：`runAsync` **不会**把相似列表塞进这次 parse 的 HTTP 响应里推给前端。异步线程只干一件事——写进 DB 的 `similar_queries` 字段。前端要看到列表，必须**另外**拿着 `queryId` 再请求一次。
>
> **时间线**：
>
> ```text
> T0  parse 返回前端（带 queryId；similar 通常还是空的）
> T1  后台 async：向量召回 → UPDATE s2_chat_query.similar_queries
> T2  用户展开「推荐相似问题」→ GET /chat/manage/getChatQuery/{queryId}
>     → 从 DB 读出刚写好的 JSON → 渲染列表
> ```
>
> 若用户在 T1 完成前就展开 → 拉到空列表 → 显示「暂无推荐」。没有 WebSocket、没有服务端推送。
>
> 面试要点：异步 = **写库**；展示 = **按 queryId 拉取**；点击只把文案当新 query 发出

```text
async 线程                         前端
   │                                │
   │  UPDATE similar_queries        │  parse 响应已返回（先有 queryId）
   │         │                      │
   │         ▼                      │  用户点开「推荐相似问题」
   │      DB 落盘  ────────────────►│  GET getChatQuery/{queryId}
   │                                │  ← 这时才读到列表
```

不是轮询。展开「推荐相似问题」且本地还没有列表时，**只打一次** `GET getChatQuery/{queryId}`。没有 `setInterval`，也不会自动重试——异步还没写完就展开，就停在「暂无推荐」。点击某条则 `onSendMsg(queryText)`，再走完整 parse/execute（连续追问闭环）。
