### 0.2 诚实边界总表

| 说法 | 可讲 | 不可讲 / 需纠正 |
|------|------|----------------|
| **相似推荐** | Parse 后异步；`QueryRecommendProcessor`；`memory_{agentId}` 召回 5；只写 `question` 到 `similarQueries` | 「输入框联想就是相似推荐」 |
| **同库** | 与记忆复用**同一**向量集（详见 [03 §0.5](./03-查询记忆复用.md)） | 「推荐另建一个向量库」 |
| **内置推荐（产品）** | Agent 配置的 **examples** 列表，前端进门展示；点下去当新 query | 与插件用的 `preset_query_collection`（PluginManager）混为一谈——那是**另一套**插件召回 |
| **`source=preset|similar|manual`** | 作为**产品/埋点口径**讲贡献率 15%/11% | 声称本仓库 Java 主链路已有同名字段——**当前 OSS 未检索到 `source` 枚举**；要对齐前端/ELK 自定义埋点 |
| **版本号防竞态** | 可讲工程风险：async 写完用户已进下一问 | 开源实现是按 **queryId** 回写；**无独立 version 字段**——勿背「版本号协议」除非 fork 有 |
| **去重** | 前端展示层可去重（同文案）；后端召回本身不去重内置 | 「库内已做复杂交叉降权」却说不出规则 |

### 0.3 相似通道调用点（对齐代码）

```
ChatQueryServiceImpl.parse
  └─ ParseResultProcessor 链
        └─ QueryRecommendProcessor.process
              └─ CompletableFuture.runAsync {
                    recallExemplars(memory_{agentId}, queryText, 5)
                    → SimilarQueryRecallResp{ queryText }
                    → ChatQueryDO.similarQueries = JSON
                    → update by questionId / queryId
                 }
```

| 项 | 值 |
|----|-----|
| 类 | `chat/server/.../processor/parse/QueryRecommendProcessor.java` |
| 异步 | `CompletableFuture.runAsync`（不堵 parse 返回） |
| topK | **硬编码 5**（不是 yaml） |
| 前端 | `chat-sdk` `SimilarQuestionItem`：结果区展开；若空则 `getChatQuery/{queryId}` 再拉 |

**超时 / 空态（诚实）**：开源无专门 timeout UI 协议——异步慢则列表短暂为空，展开重试读库；用户已发下一问则旧 `queryId` 上的推荐「挂在上一题结果旁」，一般可接受。

### 0.4 内置通道（Agent.examples）

| 项 | 说明 |
|----|------|
| 存储 | `Agent` / `AgentDO.examples`（字符串列表） |
| 用途 1 | **前端示例题 / 引导题**（产品「内置推荐」主叙事） |
| 用途 2 | `AgentServiceImpl.doExecuteAgentExamples`：可自动跑 parseAndExecute，正确则助记忆冷启动（需 Memory Review 开） |

**和 `preset_query_collection` 的区别**：后者给 **Plugin** embedding 识别用（`PluginManager`），不是结果旁「点一下再查」的内置 FAQ 列表。面试别混。

> **本节主叙事（先背这四句）**
> 1. **反复查**主战场 = **行为实验开展期**的实验助理（兼职大学生 / 实习生），不是「所有研究员都不知道问什么」。
> 2. **相似推荐的产品意义** = 结果旁的**连续追问**：查完「未发报酬名单」→ 接着「预算花了多少 / 还剩多少 / 人均」或校准失败、样本结构——**不是输入联想**。
> 3. **金融经济（以绿色金融为例）** = **内置引导题**示范怎么开口，不是天天近重复。
> 4. 双通道共用记忆向量库；指标统一用**查询贡献率**（同分母）：内置 **15%**、相似 **11%**。

## 3.1 30 秒概括

> "推荐要拆场景。行为实验开展时，实验助理会反复问运维题——没发报酬有哪些人、校准失败要不要补招、场次结构、**实验预算花了/剩下/人均多少**。内置给 FAQ 清单；**相似推荐挂在查完结果旁，专门吃连续追问**（刚问完报酬名单，推预算/补招近邻），不是边输入边联想。绿色金融更偏探索，靠内置引导开口。贡献率同分母：内置 **15%**、相似 **11%**；和记忆复用共用 `memory_{agentId}`。"

## 3.2 真实问法样例（面试必背）

### A. 行为实验 · 反复查（实验助理高频）

| # | 真实问法 | 业务含义 | 推荐怎么吃 |
|---|---------|---------|-----------|
| 1 | 「xxx 行为实验还没有发放实验报酬的人员有哪些」 | 发被试费清单 | 内置 FAQ + 相似近邻（换实验名） |
| 2 | 「注意力校准失败的被试有多少」 | **要补招被试**的信号 | 问完报酬常被相似推出 |
| 3 | 「xxx 行为实验现在所有场次中的男女比例是多少？男性中风险态度是厌恶风险的比例是多少」 | 样本结构 / 量表交叉 | 复合问法，适合固化进内置或被相似召回 |
| 4 | 「xxx 行为实验已经花费多少预算 / 还剩多少 / 人均多少」 | 实验经费进度 | **连续追问**：刚查完未发报酬名单 → 相似常推预算类 |

**连续追问（产品金句，相似通道核心价值）**：

> "相似推荐吃的是『查完 A 还要问 B』，不是『开始输入时联想』。例：刚问『信任博弈还没发报酬的人有哪些』→ 助理下一步常问『这笔实验花了多少 / 还剩多少 / 人均多少』，或校准失败人数、场次男女比×厌恶风险——都在**同一实验运维清单**上。记忆库里有过成功问法，向量近邻摊在结果旁，点一下继续查，**不用重新组织自然语言**。"

**面试金句**：

> "这些不是博导闲聊，是**实验助理排班时的刚需与连续追问**。骨架固定，变的是实验名、场次、人——所以相似推荐在行为 Agent、实验实施周特别值钱。"

### B. 绿色金融 · 引导题（内置示范开口）

| # | 内置引导例题 | 示范什么 |
|---|-------------|---------|
| 1 | 「绿色金融改革试验区地级市 2010–2020 年碳排放、GDP、第二产业占比面板」 | 政策试点 × 面板口径 |
| 2 | 「A 股公司按 ESG 评级分组的平均 ROA / Tobin's Q，区分国企与非国企」 | ESG × 财务 × 所有制异质 |
| 3 | 「试点碳交易省市的碳配额成交均价与当地 AQI / PM2.5 的年度关系」 | 碳市场 × 环境指标 |
| 4 | 「绿色信贷余额占比最高的前 10 个省份，及其绿色债券发行只数」 | 绿贷 / 绿债区域对比 |

**面试金句**：

> "绿色金融侧不是助理每天换个省名重问一遍，而是**第一次不知道自然语言怎么起头**——内置题是研究开口模板，点下去走完整问数链路。"

## 3.3 功能实现类问题

**Q：为什么要做推荐问题？是用户反馈，还是看 ELK 发现的？**

> "**两边都有，但必须拆场景——别说成全站统一痛点。**
>
> **主场景：行为科学 · 实验开展期（反复查 + 连续追问）**
> - 谁在问：**实验助理**（兼职大学生、实习生）
> - 反馈：天天查报酬 / 校准 / 场次 / **预算**，问法骨架差不多，且**查完 A 还要连着问 B**（真实问法与追问链见 §3.2-A）
> - 实验实施约 4 周、数据 T+1，助理**高频、短间隔、换实体**
> - ELK：行为实验域约占全量 **~45%**，被试管理类近重复扎堆
>
> **次场景：绿色金融等金融经济研究（引导）**
> - 实证题一次一问、换假设就换结构，**不像实验运维那样近重复扎堆**
> - 痛点：『这套库自然语言怎么起头才问得出面板』→ **内置引导题**（§3.2-B）
>
> **结论**：相似 ← 行为**连续追问**；内置 ← 绿色金融**引导** + 行为运维 FAQ。"

**Q：相似推荐的产品意义是什么？是不是有助于连续追问？**

> "**对——相似的主价值就是结果旁的连续追问，不是输入联想，也不是替代内置开口。**
>
> **分工**：
> | 通道 | 解决哪一段 | 典型行为实验例子 |
> |------|-----------|-----------------|
> | 内置 | 还没开口 / FAQ 清单 | 进门就能点『未发报酬有哪些人』 |
> | **相似** | **刚查完一题，下一跳问什么** | 刚查完未发报酬 → 推『预算花了/剩下/人均』『校准失败多少人』『男女比×厌恶风险』 |
>
> **为什么挂在 parse 之后**：产品语义是『基于你刚问的那句，摊开历史上成功的近邻题』；技术上 `QueryRecommendProcessor` 用本轮 `queryText` 异步召回，结果区展开再读——时机和『查完还要追问』对齐。
>
> **条件（诚实）**：记忆库里要有过这些成功问法且向量够近才会出现；不是工作流引擎硬编码下一步，是**用历史成功题当下一跳**。
>
> **一句话**：内置教怎么开口；相似让助理在同一实验运维清单上**连着点下去**。"

**Q：数据埋点怎么设计的？15% / 11% 怎么算？**

> "**B 端不主报曝光点击率——两条通道统一成『查询贡献率』，分母都是总查询次数。**
>
> 每次真正提交问数打一条 `query_submit`，带归因字段 `source`：
>
> | `source` | 含义 |
> |----------|------|
> | `manual` | 手打提交 |
> | `preset` | 点**内置推荐**触发的查询 |
> | `similar` | 点**相似推荐**触发的查询 |
>
> | 指标 | 公式 | 简历值 | 日均 150 次时约 |
> |------|------|--------|----------------|
> | **内置贡献率** | `count(source=preset)` / `count(全部 query_submit)` | **15%** | ~23 次 |
> | **相似贡献率** | `count(source=similar)` / `count(全部 query_submit)` | **11%** | ~17 次 |
> | （对照）手打占比 | `count(source=manual)` / 全部 | ~74% | ~110 次 |
>
> **为什么不用 impression CTR**：这是实验室内部 B 端工具，关心的是『有多少查询真的从推荐进来』，不是资讯流式的『看了多少次点了多少次』。只看了推荐没提交，**不进这两个贡献率的分子，也不单独当主 KPI**（异步按 queryId 回写；错挂风险见 §0.2，不进简历数字）。
>
> **加分**：11% 叙事抬**行为实验周·助理**；15% 叙事抬**绿色金融点引导题**。两数可同框横比（同分母），加起来约 **26%** 查询来自推荐。
>
> **注意**：`source` 必填，否则手打和点推荐分不清。"

**Q：整个作用链条是怎样的？**

> "两条链，汇合都是『点推荐 → 当新 query 再走 parse/execute』。
>
> **A. 内置（引导 + FAQ）**——进门就能看，**不依赖当前输入**
>
> ```
> 管理员按 Agent 配 Top-N（绿色引导题 / 行为运维 FAQ）
>   → 打开问数页拉内置列表 → 点击 → 当作新 query 提交（source=preset）
> ```
>
> **B. 相似——不是『开始输入时』召回，而是『本轮 query 已经提交、进入 Parse 之后』异步召回**
>
> ```
> 用户提交本轮问数（手打或点推荐）
>         │
>         ▼
> ChatQueryServiceImpl.parse()
>   ├─【同步】ChatQueryParser 做 SchemaMapper / S2SQL…
>   └─【Parse 结束后】ParseResultProcessor 链
>         └─ QueryRecommendProcessor.process()
>               └─ CompletableFuture.runAsync {   // 不堵 parse 返回
>                     ExemplarService.recallExemplars(
>                       memory_{agentId}, 本轮 queryText, topK=5)
>                     → 只取 question 文案
>                     → 写入该 queryId 的 ChatQueryDO.similarQueries
>                  }
>         │
>         ▼
> 前端结果区出现「推荐相似问题」；展开时若列表还空，
> GET /chat/manage/getChatQuery/{queryId} 再读库（等异步写完）
>         │
>         ▼ 用户点击某条
> 当作新 query 再走 parse（source=similar）
> ```
>
> **和记忆复用**：同一 `memory_{agentId}`；记忆在 Parser **同步**注入 SQL 四元组，相似在 Parse 后**异步**只给人看 question。
>
> **别和输入联想混淆**：输入框边打边出的联想是另一套 search/recommend，不是这条相似推荐。
>
> **一句话**：绿色内置 = 进门引导；行为相似 = **查完报酬名单后推预算/补招等连续追问**，**不是按键输入触发**。"

**Q：为什么两个通道？一个不行吗？**

> - **内置**：绿色金融要引导开口；行为要运维 FAQ——不依赖『当前刚问了什么』
> - **相似**：吃『查完 A 还要问 B』——助理问完未发报酬，立刻推预算花了多少、校准失败、样本结构最自然
>
> 只有内置盖不住换实验名 + 连续追问长尾；只有相似则第一次开口缺示范。**互补，权重不同**。"

**Q：这两个通道是同一个向量库吗？**

> "是，`memory_{agentId}`。相似只要 question、异步、容错；记忆复用整四元组进 Parser、同步、精度优先。简历拆两个模块：准确率 vs 提问体验（引导 + 少打字）。"

## 3.4 指标类问题

**Q：15% 和 11% 再强调一次？分域怎么讲？**

> - **同一套口径**：分母都是总 `query_submit`；分子分别是 `preset` / `similar`
> - **15%**：内置贡献——绿色引导题 + 行为 FAQ
> - **11%**：相似贡献——实验期近邻被点进去查的占比
> - 同分母，**可以横比、可以相加**（约 26% 来自推荐）；分域叙事仍是：**行为抬相似 11%**，**绿色金融抬内置 15%**
> - 诚实：简历是全站汇总；实验周切片若追问，可答分析时看过、日常看板未必按周拆

**Q：怎么证明推荐真帮到实验助理，而不只是占比好看？**

> "贡献率只说明『从推荐入口进来的查询占比』。更深一层：对这些 `source=similar|preset` 的 query 看执行成功率，以及同骨架手打是否下降（规范化 queryText 后的近重复率）。现状主报两个贡献率（§3.5）；『证明少打字』还可以做更深。"

## 3.5 诚实边界

> "1. 主 KPI 已统一为查询贡献率（B 端合理）；更深的『少打字 / 引导后首问成功率』还没系统做
> 2. 全站 15%/11%，**按 Agent / 实验周切片**不够系统
> 3. 还没严肃 A/B
> 4. 绿色内置多样性；引导例题若与线上清单有出入以当时配置为准
>
> 若重做：`source` + `agentId` 分开验收『助理少打字 / 绿色被引导』。"
