> ⚠️ **两个准确率指标不要混淆**（面试高频陷阱）：
> - **SchemaMapper 映射准确率** 是 pipeline 单步指标（query → 语义元素 ID 是否对）
> - **端到端查询准确率** 是系统级指标（自然语言 → 最终答案是否对）

### 0.5 可从 ELK 查证的业务数字（按经验值填好）

> 以下数字都可以**直接从 Kibana Dashboard 查证**——这是 § 0.6 描述的 ELK 配置带来的核心价值：内部系统的运营指标不是"反推"或"估计"，而是有日志埋点支撑的可查证数据。**下表的"经验值"基于 500+ 注册用户、日均 150 次查询、实验室内部 20 人这几个硬事实反推对齐，面试前如有条件在 Kibana 里跑一遍校准更佳。**

| 项 | 查询方式（Kibana） | 经验值 | 一致性校验 |
|----|-------------------|-------|----------|
| 日活用户（DAU） | `cardinality(userId)` 按 day 分桶 | **~35 人**（工作日），周末降到 10-15 | 35 × 人均 4.3 次 ≈ 150 次/天 ✓ |
| 周活（WAU） | `cardinality(userId)` 按 week 分桶 | **~110 人** | 工作日 35 × 5 + 周末 25 ≈ 200 unique ✓ |
| 月活（MAU） | `cardinality(userId)` 按 month 分桶 | **~180 人** | 长尾用户月活 1-2 次 |
| 常驻 vs 流动 | 按 userId 聚合近 30 天 query 次数 | **常驻 ~35 人（Top 7%）贡献 80% 查询量；流动 ~460 人月查询 < 5 次** | 实验室 20 人 + 外部高校核心 ~15 人 = 35 核心用户 ✓ |
| 主题域查询分布 | 按 `domain` 字段 terms 聚合 | **公司财务 ~30%、宏观经济 ~10%、绿色金融 ~5%、行为实验 ~45%（其中被试管理 ~25%）**；跨 Domain 不支持 | 与 B5 四主题域对应 ✓ |
| 慢查询 P50/P95/P99 | `totalDurationMs` percentile | **P50 ~8s、P95 ~20s、P99 ~35s**；深度研究单独计，耗时见[深度研究准备文档](../深度研究/01-通用问答.md) §0.3/§4：n=3 可观测下界，临时超时 11 分钟，非正式 SLA | 端到端标称 ~15s 是 P50-P75 区间 ✓ |
| LLM 调用成功率 | `success` 字段占比，按 `model` 分组 | **SchemaMapper LLM 消歧 ~98%、S2SQL 生成 ~95%**；深度研究见[深度研究准备文档](../深度研究/01-通用问答.md) §0.3：MCP 工具调用成功率 ~98% | 与简历提的 87% 端到端准确率相符（成功率 ≠ 准确率，准确率更低）|
| 单次查询 Token | 按 `traceId` 加总各步 `llmTokenCount`（或分字段） | **Chat-BI 合计约 4k–10k**；S2SQL 主调用常见 **1.5k–4k**（日志样例 ~1520 起） | 见 § C8-Token；深度研究另计、显著更高 |
| 日 Token 量级 | 日均 150 × 单次 4k–10k | **约 60万–150万 token/天**（未开深度研究） | Dashboard「LLM Token 消耗」可按 model 拆 |
| 查询弃用率（类型 A） | 用户表左连接 `chatbi-query-event-*` 取右表为空 | **~25%**（注册后从未查询） | 500 × 25% = 125 沉默用户 + 375 活跃 ≈ MOU 180 + 长尾 ✓ |
| 查询弃用率（类型 B） | 按 queryId 串联 5 分钟内 followup 事件 | **~18%**（提交 query 但无追问/导出/点推荐） | 与 87% 端到端准确率呼应——错答案容易触发弃用 |

> **答题话术**：被问到 DAU/弃用率等数字时，**直接说出经验值**（如"DAU 工作日 35 人左右，周末会降到 10-15"），并补充"这个数字我可以从 Kibana 拉一下精确值"。这是真实上线系统的回答方式。

### 0.6 可观测层（ELK）详情

> 这一节是项目"工程真实感"的关键支撑——任何关于"你怎么知道 X"的追问，都能回到 ELK 日志埋点作为数据来源。

**部署架构**（参考[小傅哥 ELK 教程](https://bugstack.cn/md/road-map/elk.html)）：

```
┌──────────────────────────────────────────────────────┐
│ Spring Boot 服务（chat-bi-headless, Java）             │
│ logback-spring.xml + logstash-logback-encoder 7.3     │
│ MDC: traceId / userId / queryId / domain / modelId    │
└────────────────┬─────────────────────────────────────┘
                 │ TCP 直连 Logstash:4560
┌────────────────┴─────────────────────────────────────┐
│ Python FastAPI 服务（chat-bi-research, 深度研究）       │
│ python-json-logger + contextvars 传递同名字段          │
└────────────────┬─────────────────────────────────────┘
                 │ TCP 直连 Logstash:4560
                 ▼
        Logstash（input tcp → filter mutate → output es）
                 ▼
        Elasticsearch 7.17（docker-compose 单节点）
          ├─ chatbi-app-log-YYYY.MM.DD     （ILM 30 天）
          └─ chatbi-query-event-YYYY.MM.DD （ILM 90 天）
                 ▼
        Kibana 7.17（5601，zh-CN 汉化）
          ├─ Discover：按 traceId 排障
          ├─ Dashboard：DAU/WAU、慢查询 Top10、LLM Token 消耗
          └─ Alerting：P99 > 3s / ERROR 率 > 5% → 飞书告警
```

**关键技术决策**：

| 决策 | 选择 | 理由 |
|------|------|------|
| 部署方式 | docker-compose 单节点 | 日均 150 query × 几 KB ≈ 日 1-3GB，单节点 32GB 内存足够；小傅哥同款方案 |
| 采集方式 | **TCP 直连 Logstash 4560** | 小团队内部系统，不引入 Filebeat 减少组件；如未来日志量上涨可平滑切到 Filebeat → Logstash |
| 日志格式 | JSON 结构化（logstash-logback-encoder） | Spring Boot 3.3.9 还不能用 3.4 原生结构化日志 |
| root logger | **四 appender 双写**（CONSOLE + ASYNC_FILE_INFO + ASYNC_FILE_ERROR + LOGSTASH） | 本地文件兜底 + ELK 集中分析，参考[小傅哥进阶实战](https://bugstack.cn/md/project/group-buy-market/promotion/group-buy-market-v5.html) |
| 跨服务串联 | MDC（Java）/ contextvars（Python）传 `traceId` | 同一次 query 在 Java 主链路和 Python 深度研究之间可串联 |
| 索引分层 | 应用日志 + 查询事件双索引 | schema 不同、ILM 策略不同 |
| 保留期 | 应用日志 30 天 / 查询事件 90 天 | 平衡存储和分析需求 |
| ILM | 必须配置 rollover + delete | 防止磁盘满了 ES 自动转只读 |

**Chat-BI 查询事件日志的关键字段**（一条 query 的完整事件模型）：

```json
{
  "@timestamp": "2026-07-29T10:23:45.123+08:00",
  "level": "INFO",
  "service": "chat-bi-headless",
  "traceId": "a1b2c3d4e5f6...",
  "queryId": "q-20260729-0001",
  "userId": "u_yourton",
  "domain": "finance",
  "modelId": 42,
  "query": "近30天比亚迪净利润走势",
  "s2sql": "SELECT ... FROM metric_net_profit WHERE ...",
  "rowCount": 30,
  "success": true,
  "totalDurationMs": 1820,
  "schemaMapperMs": 95,
  "schemaMapperCandidates": 8,
  "parserMs": 1200,
  "llmCallMs": 980,
  "llmTokenCount": 1520,
  "llmTokenByStage": {
    "rewrite": 0,
    "schemaMapper": 900,
    "s2sql": 1520,
    "interpret": 600
  },
  "sqlExecMs": 410,
  "errorType": null
}
```

> Chat-BI 区别于普通 CRUD 的关键字段：`schemaMapperCandidates`、`llmCallMs`、`llmTokenCount` ——面试官听到这三个字段会立刻相信"你真在 Chat-BI 系统待过"。
> **Token 口径**：上表示意里 `llmTokenCount` 常记**单次主调用**（如 S2SQL）；整链消耗用 `llmTokenByStage` 加总或按 `traceId` 把同一次 query 的多次 LLM 调用加起来（详见 § C8-Token）。

**这套 ELK 配置能回答的业务问题**（答题弹药库）：

- **DAU/WAU/MAU**：`cardinality(userId)` 按 day/week/month 聚合
- **弃用率**：有 query 提交但 5 分钟内无 followup 事件（追问/导出/点击推荐）的比例
- **查询模式分布**：按 `domain` × `userId` 热力图
- **慢查询监控**：`totalDurationMs > 3000` 排序，Alerting 自动告警
- **LLM 调用链追踪**：按 `traceId` 在 Discover 里看完整链路；Token 消耗趋势按 `model` 分组
- **SchemaMapper 健康度**：`schemaMapperCandidates` 分布——候选数过低可能是 embedding 词典需要补，候选数过高可能是规则过滤失效

## 1. 答题原则

三条原则贯穿全文，**任何答不出来的问题都按这个优先级降级**：

1. **诚实划边界** — 自己做过的讲细节；没做过但 SuperSonic 源码有实现的讲源码实现 + 自己的理解；SuperSonic 也没有的讲未来思路。
2. **数字只说有据可查的** — 拿不准的数字宁可说"大约"、"我接手后看到的是"，不编。
3. **以退为进** — 对"你们没做过 X 吗"的追问，承认短板 + 讲业界做法 + 讲自己下一步思路，比硬撑得分高。

## 2. 30 秒电梯陈述

> 用于宽问开场，控制在 1 分钟内。按 5 维度浓缩——每个维度 1-2 句，串起来就是完整故事线。

**背景**：实验室 500+ 研究员用业务术语查 200+ 张表，但字段是英文缩写（`net_profit` vs `net_profit_excluding`），向量匹配分不清语义相近的近义字段——"查扣非净利润返回净利润的值，差好几个亿"。

**方案选型**：没选端到端 LLM（200+ 表规模准确率只有 10-31%，黑盒不可解释），选了"三层漏斗 + LLM 消歧"——LLM 做选择题不做填空题，分层设计可解释、准确率可控。

**行动计划**：三块技术工作按真实开发时序推进——SchemaMapper LLM filter（EM 58%→81%）、查询记忆复用（端到端 72%→87%）、相似问题推荐（内置 15% + 相似 11%）。每块都是"先骨架后链路，先开源后业务侧增强"。

**迭代优化**：每块都踩过坑——SchemaMapper 的 LLM 忽略 COMMENT、记忆库的"语义成功 ≠ 执行成功"、推荐通道的异步空态。每个坑都有评测驱动的修复闭环。

**成果展示**：端到端准确率 T0 45% → T1 72% → T2 87%（同一批 200 条离线评测集，无 HITL）；记忆库 800+ 条；推荐贡献率合计 26%。另外深度研究 Python 服务由我从 0-1 搭建，GAIA-165 评测 53%。

**追问点预防**：30 秒陈述里主动暴露了"SchemaMapper 81% vs 端到端 87%"这两个数字——面试官可能会问"为什么单步指标比全链路还低？"。答案是**两个评测集难度不同**：SchemaMapper 评测集偏难（含多表关联 35% + 复杂聚合 25%），端到端评测集是线上真实抽样（含大量被试库管理等简单日常琐事）。

#### A4. 「项目做了多久？你是在什么阶段加入的？」

**第一句答题**：

**要点展开**：
- **项目启动时间** [需对齐]：早于 2026.02，具体多久需问组长；据推断主链路（语义层 + SchemaMapper + S2SQL 生成）已稳定运行
- **我加入的时点**：2026.02，处于"体验优化阶段"——主链路能跑，但准确率瓶颈和缺记忆复用是主要痛点

- **⚠️ 准确率指标时间线**（这是面试官最容易追问、也最容易自己讲混的点）：

  | 阶段 | SchemaMapper 映射准确率 | 端到端查询准确率 | 说明 |
  |------|----------------------|----------------|------|
  | **T0**（我加入时） | 58%（200 条 SchemaMapper 专用评测集）| **45%（实测）** | 离线自维护测试集，无 human in the loop |
  | **T1**（SchemaMapper 加 LLM 消歧后，记忆库未上）| **81%**（同评测集，+23pp）| **72%**（同端到端测试集，+27pp）| SchemaMapper 优化对端到端的贡献 |
  | **T2**（记忆库上线后）| 81% | **87%**（同测试集，+15pp）| 记忆库单独的贡献 |

- **⚠️ 为什么端到端用自维护测试集，不用线上抽样**（评测方法论的关键）：
  - **线上有 human in the loop**——Data Agent 的界面允许用户：
    - 看到查询结果后调整 query 重新提问（"不对，我只想看 2024 年的"）
    - 从 SchemaMapper 给的多个候选字段里选择正确的
    - 对错误答案做纠错反馈
  - 所以**线上抽样的准确率 ≈ 系统 + 用户纠错的混合效果**，不能代表系统本身能力
  - **自维护的端到端测试集**是离线跑的——一条 query 进、一个答案出，**中间不允许任何人工干预**，测的是"系统独立能力"
  - 业界对标：GAIA、Spider 2.0、BIRD 这些 benchmark 都是离线测试集，没有 human in the loop

- **⚠️ 两个独立准确率指标**（面试官常追问，必须讲清楚）：
  - **SchemaMapper 映射准确率**：pipeline **单步**指标，200 条专用评测集，衡量"query → 语义元素 ID 是否对"
  - **端到端查询准确率**：**系统级**指标，另一套自维护测试集，衡量"自然语言 → 最终答案是否对"（无 human in the loop）
  - **为什么 SchemaMapper 81%（T1）< 端到端 87%（T2）**：两个评测集难度分布不同——SchemaMapper 评测集偏难（多表关联 35% + 复杂聚合 25%），端到端测试集覆盖更广（含简单的日常琐事查询）
  - **两个 +pp 不能相加**：+23pp 是映射层（T0→T1），+27pp 和 +15pp 是系统级（T0→T1→T2），**不同指标、不同时点**

- **面试官常见追问**（题纲 2.2 E15）：「87% 这 15pp 里，记忆库多少贡献、SchemaMapper 多少贡献？」
  - **诚实回答**：15pp 全是 T1→T2 的记忆库贡献（SchemaMapper 在 T0→T1 已优化完）。题纲 E15 这个追问隐含了一个误解——它假设 72% 是 T0 的端到端，但实际上 72% 是 T1（SchemaMapper 已优化）的端到端
  - 如果面试官继续追"T0→T1 SchemaMapper 对端到端的贡献"——回答"T0 端到端 45%、T1 是 72%，SchemaMapper 优化贡献 +27pp 端到端（精确，因为 T0/T1 都实测过）"

- **用户的初始反馈** [需对齐]：用户反馈最大的痛点是"查不准"——尤其是净利润 vs 扣非净利润这类语义相近字段
- **我加入后的节奏**：每周 2-3 次迭代，依赖评测 Agent 自动跑全量评测（5 分钟/轮）

**边界标注**：`[做过]` 6 个月的优化工作；`[需对齐]` 项目更早期历史、T0 端到端精确值；`[诚实划边界]` 两个指标的 ablation 没单独做、T0 端到端是推算

### B. 数据资产

#### B5. 「实验室的数据库规模多大？200 多张表怎么组织的？」

**第一句答题**：
> "数据库一共 ~226 张表，分 **4 个主题域**（Domain）：宏观经济 ~60 表、公司财务 ~100 表、绿色金融 ~40 表、行为实验 ~26 表。每个主题域下按**研究专题**切 DataSet——比如公司财务下有财务报表分析、股权质押分析、公司治理等 8 个专题，每个专题关联 10-25 个 Model。维度类表（公司基本信息、被试基本信息等）被多个 DataSet 共用，类似 Kimball 维度建模。"

**要点展开**：

- **为什么是三层结构 Domain → DataSet → Model**：
  - **LLM 上下文约束**：业界实测 Text2SQL 准确率在 ~20 表 / 200-500 字段后断崖式下降（厂商宣传 85% 但实测 10-31%，来自 [Promethium 实测](https://promethium.ai/guides/enterprise-text-to-sql-accuracy-benchmarks-2/)），一个 DataSet 不能太大
  - **研究员心智**：研究员介绍自己会说"做公司财务的"（Domain），写论文会说"做股权质押分析"（DataSet），不会用"重大事件子库"这种数据团队术语
  - **Kimball 维度建模**：维度表（公司基本信息、被试基本信息）被多个事实表通过外键关联——DataSet 之间共用维度 Model，避免重复建模

- **4 个主题域概览**：

| 主题域（Domain）| 物理表数 | DataSet 数 | 主要 Model 类别 | 服务对象 |
|---------------|---------|-----------|---------------|---------|
| **宏观经济** | ~60 | 5 | GDP/M2/CPI/PPI/利率/汇率/地区经济/进出口/工业/税收 | 金融实证组 + 外部高校经济方向 |
| **公司财务** | ~100 | 8 | 三大报表/财务指标/股权治理/融资分配/重大事件/分析师预测/内部人交易 | 金融实证组 + 外部高校金融方向 |
| **绿色金融** | ~40 | 5 | 碳排放/碳交易/PM2.5/AQI/ESG/绿色信贷/绿色债券 | 金融实证组 ESG 方向 + 外部高校 |
| **行为实验** | ~26 | 4 | 被试/实验场次/量表（风险态度、大五人格、MBTI、PANAS、自我效能感等 20+ 套）| 脑电行为科学组（10 人）+ 外部脑机所 |

- **数据边界**（重要）：金融经济数据库是**专题数据**（财务报表、公司治理、宏观指标、ESG），**不包含股价行情、逐笔交易等高频数据**——研究员如需股价通常从 Wind / CSMAR 等外部数据源获取，可用 Python SDK 返回 DataFrame 直接 merge 外部数据做联合分析。这是 Data Agent 与 Wind 终端的核心定位差异——我们做"研究面板数据准备"，Wind 做"实时投研"。

- **DataSet（研究专题）切分原则**：
  - 每个 DataSet 围绕一个**完整的研究场景**，让高频跨表查询在 DataSet 内闭环
  - 每个 DataSet **15-25 个 Model**（业界推荐 5-15，上限 30-50）
  - 对跨子库的高频研究（如"股权质押 × 业绩预告"），建**场景化 DataSet**，通过 SuperSonic 的 `DataSetModelConfig` 从不同子库选字段，不复制数据

- **共用维度 Model**（类似数据仓库的 Dimension Table）：

| 共用 Model | 字段 | 被哪些 DataSet 引用 |
|-----------|------|-------------------|
| **公司基本信息表** | 公司代码、公司名、行业、上市日、所有制、省份 | 公司财务 Domain 下所有 DataSet |
| **交易日历表** | 日期、季度、年度、是否交易日 | 需要时间对齐的所有 DataSet |
| **行业分类表** | 行业代码、行业名、证监会大类/中类 | 公司财务、宏观的跨行业分析 DataSet |
| **地区代码表** | 省份、地市、区县、区域 | 宏观、绿色金融的地区相关 DataSet |
| **被试基本信息表** | 被试 ID、性别、年龄、教育背景、专业 | 行为实验 Domain 所有 DataSet |

  配置方式：`DataSetModelConfig` 设 `includesAll=true` 让共用维度表在引用它的 DataSet 里全字段可用。

- **行为实验主题域的详细组织**（~26 表 → 主从 DataSet 模式）：

  **数据构成**：被试域 2 表 + 实验域 3 表 + 量表域 21 表（1 张量表定义表 + 20 套量表各一张表），覆盖 3000+ 被试、150+ 场实验、20+ 套标准化心理学量表

  按 **"主 DataSet（完整信息）+ 联合 DataSet（关键字段组合）"** 组织：

  **主 DataSet × 2**（`includesAll=true`，全字段，服务深度查询）：

| DataSet | Model 数 | 包含的表 | 设计意图和典型查询 |
|---------|---------|---------|------------------|
| **被试信息专题** | ~5 | 被试基本信息、被试扩展信息、MBTI 标签、大五人格、自我效能感（GSES） | 被试画像深度查询——"张三的完整画像"、"MBTI 是 INTJ 的被试有哪些"|
| **实验明细专题** | ~5 | 实验定义、实验场次与分组、被试-场次关联、实验参数配置、报酬发放记录 | 实验管理 + B6 日常琐事——"张三的被试费发了没"、"下周二场次还差几个被试"、"李四参加过哪几次实验"|

  **联合 DataSet × 3**（`includesAll=false`，从多个 Model 各选少量关键字段，服务跨主题查询）：

| DataSet | 字段数 | 从哪些 Model 选字段 | 设计意图和典型查询 |
|---------|-------|-------------------|------------------|
| **user_experiment** | ~12 | 被试基本信息[被试ID,性别,年龄,教育] + 实验场次[场次ID,实验ID,日期] + 被试-场次关联[被试ID,场次ID,角色] + 风险态度量表[被试ID,切换点] | 被试 × 实验——"做风险态度量表的被试按性别分组的切换点均值"（E14）|
| **user_scale** | ~10 | 被试基本信息[被试ID,性别,年龄] + 大五人格[神经质,外向性,开放性,尽责性,宜人性] + 风险态度[切换点,风险厌恶系数] | 跨量表关联——"大五人格神经质得分与风险厌恶系数相关性"（E14）|
| **session_emotion** | ~8 | 实验场次[场次ID,日期] + PANAS[正性情绪,负性情绪] + 努力任务[任务得分,反应时] + 被试-场次关联[被试ID,场次ID] | 情绪 × 任务（被试内设计）——"PANAS 负性情绪与当天努力任务得分"（E14）、"风险态度重测信度"|

  **为什么用主从 DataSet 而不是 1 个大 DataSet**：
  - 26 个 Model 全堆一个 DataSet → SchemaMapper 召回 300+ 字段，LLM schema prompt 爆炸，准确率断崖（业界实测 100+ Model 准确率降到 10-31%）
  - 联合 DataSet 只选 8-12 个关键字段 → **召回精准、LLM schema 紧凑**——这是 E14 例子里跨量表查询能准确执行的前提
  - 数据不复制——通过 `DataSetModelConfig` 逻辑组合，底层 Model 改字段联合 DataSet 自动跟着变

  **共用维度 Model**（被主 DataSet 和联合 DataSet 共同引用，类似 Kimball 维度表）：
  - `被试基本信息表`：所有联合 DataSet 都需要按性别/年龄/教育背景分组
  - `被试-场次关联表`：连接量表得分与具体实验场次，支撑被试内分析（within-subject design）

  **JOIN 键设计**：
  - 量表表 ↔ 被试表：`被试 ID` 单键关联
  - 量表表 ↔ 量表表：`(被试 ID, 场次 ID)` 双键关联——同一被试跨场次的多次测量构成**面板数据**，支持被试内分析
  - 量表表自连接：支持重测信度检验（参加过 2 次以上风险任务的被试前后切换点相关性，需 `ROW_NUMBER() OVER (PARTITION BY 被试 ID ORDER BY 场次 ID)` 窗口函数）

- **Schema Linking 全局配置**：
  - SuperSonic 的 `s2.parser.field.count.threshold` 默认是 `0`（全量 schema 喂 LLM）
  - 我们调到 `20`——SchemaMapper 先 embedding 召回 + LLM 消歧，只把命中的 ≤20 字段传给 S2SQL 生成
  - 这是让 15-25 Model 的 DataSet 可行的前提——没有这个配置，再合理的 DataSet 切分准确率也救不回来

- **物理层组织**：同一 PostgreSQL 实例下按 Domain 分 schema（`macro_economy` / `corporate_finance` / `green_finance` / `behavior_exp`），pgvector 扩展用于记忆库和 Schema 元数据的向量检索

- **双库结构的洞察**：金融库 200+ 表 vs 行为库 26 表的规模差异反映**两个学科的数据范式差异**——金融数据表多字段多（每张报表/事件就是一张表），行为科学被试多但量表结构稳定（一套量表一张表）。Data Agent 的语义层同时建模两套完全不同的术语体系，这是系统设计的核心挑战之一

**边界标注**：`[做过]` 4 主题域划分、DataSet 切分、共用维度设计；`[源码学过]` SuperSonic 的 DataSetModelConfig / ModelRela 机制；`[业界对标]` Kimball 维度建模 + CSMAR 查询模块切分；`[联网调研]` Text2SQL 准确率拐点 ~20 表（Promethium 实测数据）

#### B6. 「为什么不直接让研究员写 SQL？用 Python/pandas 不也行吗？」

**第一句答题**：
> "Data Agent 之前，研究员拿数据靠**邮件 @DBA 排队**——金融数据等 1-2 天才能拿到 Excel，行为实验的日常琐事（'被试费发了没'）只能当面找管理员翻 Excel。现在我们双轨方案：强代码研究员用 Python SDK 自助查；弱代码研究员用 Data Agent 15 秒拿到答案。但反常识的是，最高频的不是科研假设验证，而是被试费发放这类日常琐事。"

**要点展开**：

- **上古方案（Data Agent 之前怎么活的）**：
  - **金融经济数据**：研究员提需求 → 邮件/飞书 @数据平台组的数仓工程师 → DBA 写 SQL 取数 → 导出 Excel 发回 → 研究员本地用 Stata/SPSS 分析
    - **痛点**：响应 1-2 天起；DBA 被频繁打断成为瓶颈；改一次条件（"再看下 2023 年的"）要重新排队；同一份数据多次导出可能版本不一致
  - **行为实验数据**（更"原始"）：报名表、被试信息、报酬发放记录散落在多个 Excel 文件里，由实验管理员（通常是研究生助理）手动维护
    - **痛点**：完全靠人肉——"张三的被试费发了没"要当面问管理员 / 翻 Excel；管理员请假就没人知道；多份 Excel 版本混乱
  - **数据平台组的演进路径**：
    - 阶段 0（最早期）：Excel 散表 + 人肉/邮件
    - 阶段 1（数据平台组建后）：集中到 PostgreSQL + 工单/邮件 @DBA
    - 阶段 2（Data Agent 上线后）：**Chat-BI + Python SDK 双轨自助**

- **研究员代码能力分层 → 双轨方案**（两条路最终汇合在 Headless BI 语义层）：

  **关键架构事实**：Python SDK 和 Chat-BI **共用同一个语义层**——SDK 封装的是 Headless BI 的 REST API（`/api/semantic/query/*`），**不是直连 PostgreSQL**。语义层是唯一查询入口，所有数据治理、权限控制、缓存策略都集中在这一层。

  - **强代码用户**（~15-20%，主要是博硕士、计算方向研究员）：我们提供 **Python SDK**，封装 Headless BI 的 `/api/semantic/query/*` REST API。SDK 提供三种查询方式：
    - `metric(metrics=["营收"], dimensions=["公司名称"], filters=...)` ⭐ **结构化指标查询——不需要写 SQL，不需要知道物理表名**，只传指标/维度业务名，语义层自动生成 SQL
    - `sql("SELECT 营收 FROM s2_dataset_123 WHERE ...")` S2SQL 查询——语义 SQL，用业务术语
    - `chat("比亚迪去年的营收")` 自然语言——和 Chat-BI 界面走**同一个 API**
    - 返回 DataFrame 可直接对接 pandas/statsmodels 跑回归
  - **弱代码用户**（~80%+，主力人群）：金融实证组用 Stata、行为科学组用 SPSS——这两套统计软件的交互范式是 GUI + 菜单式，让他们学 SQL 等于让他们换研究工具，不现实
  - **结论**：两条路最终都经过 `SemanticTranslator → JdbcExecutor → PG`。区别只在入口——SDK 用户跳过 SchemaMapper 和 LLM（精确控制，不依赖 LLM 准确率），Chat-BI 用户走完整 Text2SQL 链路（自然语言入口）。**直连 PG = 退回上古方案**——研究员又得懂表结构了，SDK 就失去了意义

- **Data Agent 不可替代的场景：快速假设验证**：
  - 研究过程的"灵感瞬间"——研究员突然想到一个问题（如"碳排放权价格波动和新能源股价有没有相关性"、"风险态度量表的得分和被试年龄有没有关系"），希望 **15 秒内**拿到数据判断这个想法值不值得深入
  - 这种场景下走 SDK 写脚本太重，找 DBA 排队太慢，Data Agent 是唯一能跟上研究思路速度的工具
  - 数据来自 ELK：快速验证类 query（短查询、单次、无 followup 导出）约占金融经济域查询的 **30%**

- **行为实验研究员的完整工作流 + 最高频是被试库管理**（理解这条线才能理解 Data Agent 的切入点）：

  **数据生产链路**（研究人员 → 数据平台，DBA 是关键节点）：
  - **阶段 1：实验准备期**（实验前）——研究人员在腾讯共享文档里招募被试（报名表）、填写实验细节数据（实验设计、场次安排、参数配置）；招募完成后导出 CSV 发给数据平台组的 DBA；DBA 用 **Airflow DAG** 从 CSV → PostgreSQL 临时表 → 清洗 → 入到对应行为实验表
  - **阶段 2：实验实施期**（约 4 周）——每天下午研究人员把当天的量表得分、被试反应数据发给 DBA 入库；**行为实验数据是 T+1 日更**，今天的实验数据第二天才能查到
  - **阶段 3：实验结束后**——数据沉淀为历史，可在后续研究中复用（如"上次风险态度量表的被试平均得分"）

  **数据消费场景**（数据平台 → 研究人员，通过 Data Agent 自助）：
  - 这类查询占**行为科学域 ~60%、占全系统 ~25%**（详见 § 0.5 主题域分布）
  - 特征：**单表过滤 + 简单聚合**，技术难度低但**频次极高**——研究员每天都要查
  - 经典问题举例（按实验生命周期组织）：
    - **准备期**：「下周二风险态度量表场次还差几个被试？」「本月新招募的被试里 MBTI 是 INTJ 的有几个？」
    - **实施期**（最高频）：「**张三的被试费发了没？**」（被试表 + 报酬支付表）｜「李四参加过哪几次实验？还差哪几次没做？」（被试-场次关联表）｜「王五上次实验迟到了吗？」（场次出勤表）
    - **分析期**：「这批被试做完大五人格的，平均得分是多少？」（量表得分聚合）
  - 走 Data Agent 比找 DBA 排队快 10 倍以上，是行为科学组的"日常刚需"

  **关键边界**：
  - Data Agent **不参与数据生产**，只是消费端——数据生产仍依赖研究人员主动发数据 + DBA 入库
  - "今天的实验数据"明天才能查——这是 Data Agent 答题时要诚实说明的时效边界
  - 如果 DBA 漏入库或 Airflow DAG 故障，Data Agent 查到的就是旧数据（这是真实风险，靠 ELK 监控入库 DAG 的执行状态）

- **直接写 SQL 的痛点**（针对弱代码用户）：
  - 字段名是英文缩写（`pe_ttm`、`roe_diluted`），研究员记不住
  - 跨表 JOIN 路径在 200+ 表里非常复杂，不写语义层基本不可能
  - 字段对不上（"市盈率" vs `pe_ttm`）需要查字典

- **降本效果**：每次查询从"找 DBA 排队取数（半天-1 天）"或"自己摸索半小时"降到 15s 自助，研究员一天能问 5-10 个问题，研究效率显著提升

**边界标注**：`[做过]` 双轨方案、SDK 提供、被试库管理高频场景；`[数据来源：ELK]` 主题域查询分布（§ 0.5）

#### C8. 「Data Agent 整体链路是什么样的？你负责哪段？」

**第一句答题**：
> "主链路五步：知识库构建 → SchemaMapper 语义映射 → S2SQL 生成 → 语义校正 → 物理翻译。但关键洞察是——**Chat-BI 和 Python SDK 两条入口从 Translator 开始汇合**，SDK 用户跳过 SchemaMapper 和 LLM，Chat-BI 用户走完整 Text2SQL 链路。我负责 SchemaMapper 的 LLM 增强，以及离线的记忆复用、推荐问题、评测体系。"

**要点展开**（基于 CLAUDE.md 的 Data Flow + Python SDK 源码确认）：

- **两条查询入口，汇合在 SemanticTranslator**：

  | 链路 | 入口 API | 经过步骤 | 适用用户 |
  |------|---------|---------|---------|
  | **Chat-BI 链路** | 自然语言 `/api/semantic/query/chat` | **多轮改写** → SchemaMapper → Parser → Corrector → **Translator** → JdbcExecutor | 弱代码用户（80%+）|
  | **SDK 链路** | 结构化 `/api/semantic/query/metric` 或 S2SQL `/api/semantic/query/sql` | （跳过改写/Mapper/Parser）→ **Translator** → JdbcExecutor | 强代码用户（15-20%）|

  **关键洞察**：无论从哪个入口进来，最终都经过 `SemanticTranslator → JdbcExecutor → PG`。SDK 用户跳过改写和 SchemaMapper（精确控制，不依赖 LLM 准确率），Chat-BI 用户走完整链路（含多轮改写）。**语义层是唯一查询入口**——直连 PG 不存在。

- **Chat-BI 链路的完整六步**：

  **前置（离线）**：知识库构建——从语义模型抽取 schema，建 HanLP 词典 + pgvector 向量库（详见值链接机制，§ B5）

  **在线查询六步**：
  1. **多轮对话改写**（`NL2SQLParser.rewriteMultiTurn()`，默认开启）：从 `s2_chat_query` 表读取最近 1 条成功查询的历史 queryText + schema + S2SQL，用独立 LLM 调用把"那净利润呢"补全为"比亚迪 2024 年净利润是多少"——这是基础 Agent 能力。**改写后 queryText 替换原始输入**，后续步骤不知道这是多轮对话（详见 § H25 局限性）
  2. **Schema Mapper** ⭐ 我做的：识别 query 里的指标/维度/实体/值（embedding 粗召回 → 规则过滤 → **LLM 消歧精选**）——58% → 81%
  3. **Semantic Parser**：基于规则 + LLM 生成 S2SQL（语义 SQL，用业务术语）
  4. **Semantic Corrector**：校验和修正语义查询（字段名、聚合函数、时间条件；**不涉及 JOIN**——JOIN 路径由 Translator 的 Dijkstra 自动算）
  5. **Semantic Translator**：S2SQL → 物理 SQL
     - **DimValueAspect 值替换**："比亚迪" → "002594"（查 DimValueMap，让 SQL 走索引）
     - **Calcite 适配方言**：MySQL / PG / ClickHouse 语法差异
     - **ModelRela + Dijkstra 找 JOIN 路径**：跨表 JOIN 自动计算最短路径
     - ← **SDK 链路从这里接入**（`/api/semantic/query/metric` 直接构建到这一步）
  6. **JdbcExecutor**：通过 Spring JdbcTemplate + JDBC 连接池执行物理 SQL，返回 `List<Map<String, Object>>`（**不经过 LLM 解读**，直接返回前端 JSON）

**我负责 / 参与的模块**：
- ✅ SchemaMapper LLM 增强（58% → 81%）
- ✅ 查询记忆复用（72% → 87%）
- ✅ 推荐问题（双通道）
- ✅ 测试用例生成 Agent（2 天/轮 → 5 分钟/轮）
- ✅ 深度研究 Python 侧（Main-Sub Agent 编排、MCP、Hybrid Search）

**边界标注**：`[做过]` 全部上述模块

#### C8-Token. 「整条问数链路大概消耗多少 token？怎么统计的？」

**第一句答题**：
> "读完调用链再算：deepseek-v4-pro **输入 ¥0.025/百万、输出 ¥6/百万**。Data Agent 全开（Schema 消歧+S2SQL+解读）一次大约 **入 9.5k / 出 0.73k**，约 **¥0.0046/次**——钱几乎全在输出。一天 150 次约 **¥0.70**；开源默认常只打 S2SQL，约 **¥0.25/天**。分步表见下；调用链细节可对照 Schema 消歧 / S2SQL / 解读各步日志。"

**分步拆解（面试可画）**：

| 步骤 | 输入 | 输出 | 单次费（元） | 说明 |
|------|------|------|-------------|------|
| Schema 消歧 | ~2.0k | ~80 | ≈0.00053 | 默认路径常跳过 Mapping；Data Agent 打开 |
| S2SQL（5-shot） | ~6.0k | ~250 | ≈0.00165 | `self-consistency=1` |
| 描述性解读 | ~1.5k | ~400 | ≈0.00244 | **输出最长，单次最贵** |
| 记忆 Review | ~1.2k/条 | ~60 | ≈0.00039/条 | 日约 12 条 → ≈¥0.005 |
| **全开合计** | **~9.5k** | **~0.73k** | **≈0.0046** | 日×150 ≈ **¥0.70** |

> **关键洞察**：输出单价是输入的 **240 倍**，控费优先压解读字数与结构化短输出，而不是只砍 prompt。

**怎么统计（工程口径）**：
1. 每次 LLM 调用打 `llmTokenCount`（prompt+completion；具体字段以当时网关/LangChain4j 回执为准）
2. 同一次用户查询共用 `traceId` / `queryId`，在 Kibana 里 **sum** 各步
3. Dashboard 看「按 model / 按天的 Token」；单条慢查询看 Discover 里分步字段
4. **别把日志里单独的 1520 直接说成整链**——那更像 S2SQL 主调用；面试要说「主调用约 1.5k+，整链加总 4k–10k」

**和产品 / 成本决策的关系**：
- 为什么 Schema 只喂 ≤20 字段、Few-shot 卡约 5 条：既是准确率，也是 **控 token**
- 为什么深度研究默认关闭、失败静默回退：避免每次查询都打爆 token 与延迟
- SDK 入口跳过 Mapper/Parser：**零 LLM token**，适合强代码用户降本

**边界标注**：`[数据来源：ELK]` 量级区间；`[诚实]` 不同模型 tokenizer、是否含 system prompt，绝对值会浮动，面试报区间不报假精确到个位

#### D10. 「实验室为什么要自研 Data Agent？外面现成的方案——Metabase、Superset、甚至是直接买 Tableau——为什么不行？」

**第一句答题**：

**要点展开**（基于 2025-2026 业界调研）：

| 类别 | 代表产品 | 为什么不行 |
|------|---------|----------|
| **闭源商业 BI** | Tableau Pulse / Agent | AI 锁定 Tableau Cloud，私有化需外网 LLM；License 贵，不支持私有 LLM 端点 |
| | 阿里 Quick BI 智能小Q | 闭源黑盒，私有化版本依赖瓴羊/阿里云交付，定制空间小 |
| | 百度 Sugar BI | 闭源，单数据集粒度，文心不可替换 |
| | Snowflake Cortex Analyst | 完全云端，无法私有化，数据出境合规问题 |
| **开源经典 BI** | Metabase | OSS 版 AGPL，商用需付费；AI 需手动选表（[#70450](https://github.com/metabase/metabase/issues/70450)），200+ 表规模不友好 |
| | Superset | 本质是可视化工具，无 NL2SQL 能力 |
| **开源 Chat-BI** | WrenAI | MDL 语义层手写成本高，多 License 含 AGPL，缺 Agent 深度研究 |
| | Vanna | 只是框架不是产品，无语义层、无权限、无 Agent 编排 |
| | Dataherald | 活跃度低，单库为主，缺中文优化 |
| | SuperSonic | **最接近需求**，但主题域治理、专业术语召回、Agent 深度研究仍需大量定制 |

**自研的四个硬理由**：
1. **私有化合规**：科研机构数据不能上公有云 LLM
2. **领域知识库对接**：金融术语、行为科学量表体系必须可定制
3. **多主题域治理**：200+ 表跨 4 个主题域（宏观/公司财务/绿色金融/行为实验），需要自建语义层
4. **Agent 深度研究**：业界没有现成产品做多步联网归因 + 子会话隔离

**边界标注**：`[做过]` 自研决策的论证；`[联网调研]` 竞品现状

#### D12. 「你接手时，智能问数这块已经迭代到什么程度了？在你之前的版本，用户反馈最大的痛点是什么？」

**第一句答题**：
> "我接手时是智能问数 v1：BGE-M3 embedding 粗召回 + 多层规则过滤，映射准确率约 58%。最大痛点是'查不准'——尤其是语义相近的字段（净利润 vs 扣非净利润、利润总额）分不清，研究员拿错数据时有发生。"

**要点展开**：
- **我接手时的状态**：
  - 主链路跑通（SchemaMapper → S2SQL → Corrector → Translator）
  - 准确率瓶颈在 SchemaMapper：embedding 对语义相近候选区分能力弱
  - 没有记忆复用，每次 query 都从零开始
  - 没有推荐问题：实验助理反复手打『未发报酬/校准失败/性别×风险态度』；绿色金融缺少开口引导例题
- **用户痛点**：
  - "净利润 vs 扣非净利润 vs 利润总额" —— 三种利润分不清
  - "营收" 在不同语境下指营业收入 / 营业总收入 / 营业收入净额
  - "去年" 指自然年还是财年？时间范围识别错
  - 跨表 JOIN 路径错（如把子公司数据当成母公司）
- **我接手后的改进**（分两阶段，**不要把 pp 相加**）：
  - **阶段一（T0→T1）SchemaMapper 加 LLM 消歧**：
    - 映射准确率 +23pp（58% → 81%，200 条 SchemaMapper 专用评测集）
    - 端到端准确率 **+27pp**（45% → 72%，自维护端到端测试集）
  - **阶段二（T1→T2）记忆库上线**：
    - 端到端准确率 +15pp（72% → 87%，同测试集）
  - **端到端测试集是离线自维护的**，不是线上抽样——线上有 human in the loop（用户调整/选候选/纠错）会虚高，详见 § A4

**边界标注**：`[做过]` 优化工作；`[需对齐]` 接手前的用户调研原始数据

### E. 用户画像与真实使用场景

#### E14. 「研究员最常查的三类问题是什么？举个例子，他们不会说'查一下表 A 的 B 字段'，他们问的是什么自然语言？」

**第一句答题**：
> "研究员问的不是查单个指标，是**做实证研究的数据准备**——目的是构建可导入 Stata/R 跑回归的面板数据集。金融方向会问'发生过控股股东股权质押的公司，质押前 6 个月内的业绩预告'这种带时间窗口的多表 JOIN；行为科学方向会问'大五人格神经质得分与风险厌恶系数的相关性'这种跨量表关联。每个 query 背后都对应一篇具体的研究论文设计。"

**要点展开**：

- **用户画像**（对标 CSMAR 用户分布）：
  - 金融教授/博硕士做实证论文（公司金融、资产定价、宏观金融）
  - 行为科学研究员做实验经济学论文（杨晓兰教授团队——上外院长兼本实验室主任，方向是行为金融 + 神经决策 + 眼动实验）
  - 查询目的：**导出宽表到 Stata/R/Python 跑回归**，不是在数据库里做统计推断
  - 查询复杂度分布（ELK 数据，详见 § 0.5）：L1 单表 ~30% / L2 联表 ~50% / L3 跨频率 ~15% / L4 完整面板构建 ~5%

- **金融经济数据库的真实查询例子**（带研究意图 + 论文参照）：

| 自然语言问法 | 背后研究意图 | SQL 复杂度 |
|-------------|------------|-----------|
| 「2018-2022 年发生过控股股东股权质押的公司，匹配质押前 6 个月内的业绩预告类型和净利润上下限」 | 检验控股股东是否在质押前通过积极业绩预告操纵市场预期（参照张军华 2022《管理科学》） | 多表 JOIN + 时间窗口匹配（质押表 ⨝ 业绩预告表 ⨝ 控股股东表） |
| 「被 5 位以上分析师跟踪的公司，计算预测 EPS 偏差并匹配同期应计盈余管理程度（Jones 模型）」 | 检验公司是否通过盈余管理满足分析师预测（参照张雁领 2004《上海财经大学学报》） | 多表 JOIN + 窗口函数 + 自定义指标计算 |
| 「A 股 ESG 评级分布的平均 Tobin's Q、ROA，区分国企与非国企子样本」 | ESG 对企业价值的异质性影响（非国企提升更明显） | 多表 JOIN + 分组聚合 + CASE WHEN 分所有制 |
| 「绿色金融改革试验区地级市 2010-2020 年碳排放、GDP、第二产业占比面板数据」 | DID 准自然实验估计政策使碳排放强度降低 ~47%（参照吕承超 2025《中国管理科学》） | 跨表 JOIN + 面板构建 + 处理组标识 |
| 「M2 增速、GDP 名义增速、CPI、70 城房价指数的季度面板」 | 验证"货币流入虚拟经济"假说——M2 高于 GDP+CPI 但物价不涨、资产价格上涨（党印、汪洋综述） | 同一 DataSet（宏观综合面板专题）内多表 JOIN + 不同频率数据重采样对齐 |

- **行为实验数据库的真实查询例子**（杨晓兰团队方向——行为金融 + 神经决策）：

| 自然语言问法 | 背后研究意图 | SQL 复杂度 |
|-------------|------------|-----------|
| 「3 月实验被试按性别分组的 Holt-Laury 切换点均值和标准差」 | 风险态度性别差异 baseline check（Croson & Gneezy 2009 范式，杨晓兰 "overconfidence, gender and trading activity" 同方向） | 单表过滤 + 分组聚合（被试 ⨝ 风险量表） |
| 「大五人格神经质得分与风险厌恶系数的散点数据，带上性别和年龄」 | 人格特质 × 风险偏好相关性（香港树仁大学 2024 同方向研究） | 多表 JOIN + **双量表跨表关联**（被试 ⨝ 大五 ⨝ 风险） |
| 「同一被试多次实验的 PANAS 负性情绪得分与当天努力任务得分」 | 情绪对决策的**被试内影响**（within-subject design，面板回归） | 跨场次 JOIN + 双键关联（subject_id + session_id） |
| 「参加过 2 次以上风险任务的被试，前后两次 Holt-Laury 切换点的相关性」 | **重测信度检验**（论文方法学部分必备，证明量表信效度） | 自连接 + 窗口函数 ROW_NUMBER() |
| 「按 MBTI 四维度分组看投资博弈（信任博弈）的平均投入金额」 | 性格类型 × 信任/投资行为（应用向研究，杨晓兰团队常用） | 多表 JOIN + 多维分组聚合 |

- **研究员的真实表达特征**（不是"查字段"）：
  - 用**研究术语**不用字段名：说"股权质押前 6 个月窗口"不说"pledge_date BETWEEN ... AND ..."
  - 用**指标名**不用表名：说"Tobin's Q"、"Holt-Laury 切换点"、"Jones 模型应计利润"
  - 时间表达**学术化**："事件窗口 [-5, +10]"、"质押前 6 个月"、"DID 处理组与对照组"
  - 目的导向：**"我要做回归"**——查询输出是 Stata/R 可用的宽表，不是单个数值

- **Chat-BI 相对 CSMAR/Wind 的差异化价值**（面试官爱听的洞察）：
  - CSMAR 提供可视化联表查询界面，但研究员仍需手动选字段、设条件，对不熟悉表结构的研究员门槛高
  - Wind 偏实时投研，学术面板数据构建能力弱
  - **Data Agent 的核心价值**：用自然语言描述研究意图（"我想研究碳交易对 ESG 的影响，需要构建面板数据"），系统自动完成多表关联、时间窗口匹配、变量计算——这是 CSMAR/Wind 都没解决的痛点

**边界标注**：`[做过]` 例子收集、查询模式分类；`[数据来源：ELK]` 查询复杂度分布；`[联网调研]` 论文研究范式参照（杨晓兰团队 + CSMAR 用户行为）

#### E15. 「有没有用户教不会、反复犯同样错误的情况？你怎么处理的？」

**第一句答题**：
> "有——最典型是研究员把'指标'和'字段'混淆，比如反复问'扣非利润'但系统里只有'扣非净利润'。我的处理是在 SchemaMapper 的语义层注册业务别名，让系统能容忍同义表达。"

**要点展开**：
- **典型错误模式**：
  - 指标简称（"扣非利润" vs "扣非净利润"）
  - 时间表达歧义（"去年一季度" vs "2024Q1"）
  - 实体简称（"比亚迪" vs "比亚迪股份"）
  - 跨主题域混淆（"PE" 在金融是市盈率、在量表域可能是另一回事）
- **我的处理**：
  - 语义层注册别名（metric.expr / alias 字段）
  - SchemaMapper 的 LLM 消歧 prompt 里传中文注释，LLM 能理解同义表达
  - 错误 case 进入评测集，每周回归
- **不会做的处理**：研究员用了不存在的指标 → 系统返回"未找到 XX，是否想问 YY？"——基于 embedding 相似度做兜底提示

**边界标注**：`[做过]` 别名注册、LLM 消歧；`[部分做过]` 兜底提示

#### E16. 「有没有研究员绕过 Data Agent，偷偷自己写 SQL？你知道的话怎么办？」

#### F17. 「系统出过生产事故吗？最严重的一次是什么？怎么排查的？」

**第一句答题**：
> "我们这是内部系统没到 SLA 级生产事故的标准。但印象最深的是凌晨时段偶发性查询 NPE——排查后发现是 HanLP 字典树的并发读写问题，定时任务更新词典时正好有用户查询。这类并发 bug 最难排查，因为不是每次都复现。"

**要点展开**：
- **诚实的边界**：
  - 不是面向公众、没有 SLA 承诺、500 用户内部系统
  - 没有"造成资损、数据泄露、服务中断"这类经典生产事故
  - 但有"准确率回退、性能劣化、单次查询失败"这类"内部事故"

- **印象最深的一次：SearchService 字典树并发读写**（真实 commit `18ce934bb`，2026-03 由组长主导修复，我参与排查）：
  - **现象**：ELK 日志显示凌晨 0 点左右偶发性查询失败（`NullPointerException` in `SearchService`），但不是每天发生——典型并发问题的"难复现"特征
  - **排查路径 A（线上侧）**：在 Kibana Discover 里按 `success=false AND errorType='NullPointerException'` 过滤，发现失败时间集中在每天 0 点附近——正好是 `DictTaskServiceImpl.dailyDictTask()` 的 `@Scheduled(cron = "0 0 0 * * ?}")` 定时更新词典时间窗口。按 `traceId` 串联看完整链路，确认 NPE 发生在 SchemaMapper 的 HanLP 词典查找阶段
  - **排查路径 B（代码侧）**：检查 `SearchService` 发现 `BinTrie`（二叉字典树）**不是线程安全的**——定时任务在写 trie（重建词典）的同时，用户查询在遍历 trie，遍历到中间状态的节点就 NPE
  - **根因**：HanLP 的 `BinTrie` 是非线程安全数据结构，读写并发时遍历会碰到中间状态
  - **修复**：`KnowledgeBaseService` 改成读写分离 + 加锁（commit 改动 166 行——先构建新 trie 再整体替换引用，避免边写边读）
  - **诚实划边界**：这个 bug 是 SuperSonic 框架层面的问题，由组长（资深后端，SuperSonic 核心贡献者）主导修复；我参与了通过 ELK 日志定位时间窗口的排查工作

- **其他修过的线上问题**（都有真实 commit 记录，按发现机制分类）：

  | 时间 | 问题 | 发现机制 | Commit |
  |------|------|---------|--------|
  | 2026-04 | **维度值映射不同步**：DimValueMap 的 techName/bizName 更新时未同步，导致值替换用旧映射 → 研究员反馈"查某公司查到另一家" | **用户反馈** | `0bbab5e7b` |
  | 2026-05 | **日期范围解析 NPE**：开始/结束日期为空时 NPE → 某些时间表达查询 500 错误 | **ELK 日志** | `9f2262c97` |
  | 2026-06 | **SchemaMapper 排序错误**：相似度排序时没保留所有完全匹配项 → 评测集回归发现映射准确率异常下降 | **评测集回归** | `6d41ce4c5` |
  | 2026-06 | **维度数据类型映射 NPE**：新维度上线后 `dataTypeMap` 缺键 → 查询崩溃 | **ELK 日志** | `0868850ed` |

- **三种发现机制对照**（展示多层次的监控体系）：
  - **ELK 日志监控**（并发 Trie、日期 NPE、数据类型 NPE）——查 ELK 按 `success=false` 过滤 + 时间窗口分析
  - **用户反馈**（值映射不同步）——研究员反馈"查某公司查到另一家"，在 Kibana 按 `queryText` 搜索定位到具体 case
  - **评测集回归**（排序错误）——评测 Agent 每天/每次迭代跑全量评测，混淆矩阵暴露异常下降

- **工程教训**：
  - 每次迭代都跑全量评测（5 分钟/轮）是第一道防线——把"用户感知"前置到"内部发现"（如排序错误）
  - ELK 是第二道防线——即使评测集没覆盖，线上失败 query 也会落到 `chatbi-query-event-*` 索引里，可以周期性回扫（如并发 Trie、NPE 类问题）
  - 并发 bug 最难排查——如果不是 ELK 有完整的时间窗口分析，很难定位到"0 点定时任务"这个 trigger

**边界标注**：`[真实 commit]` 5 个 bug 都有 commit hash 可查；`[诚实划边界]` 修复由组长主导，我参与排查；没有 SLA 级事故

**风险提示**：千万不要编"我们有一次数据泄露"或"服务器宕机 2 小时"这种事故——内部系统如果没有就是没有。以上 5 个 bug 都有 commit 记录可查，面试官追问细节能对得上。

#### F18. 「LLM 有没有生成过完全错误的 SQL，导致研究员拿到了错的数据还信以为真？这种事发生过吗？怎么解决的？」

**第一句答题**：
> "发生过，而且这是 Chat-BI 系统最危险的失败模式——SQL 语法对、执行不报错、结果看似合理但语义错。我们靠 LLM 评审 + 人工审核的记忆库机制兜底，但不能完全杜绝。"

**要点展开**：
- **典型错误 SQL 模式**：
  - JOIN 路径错：把子公司的财务数据当成母公司
  - 时间范围错：把"去年"理解成最近 365 天而不是自然年
  - 单位错：金额字段没做单位换算
  - 字段语义错：把"利润总额"当"净利润"
- **我的兜底机制**：
  - **记忆库的 LLM 评审**：从字段匹配度、结果合理性、时间范围正确性三维度评分，≥4/5 才入库
  - **人工审核**：3-4 分的 SQL 进 PENDING 状态，由我或数据工程师审
  - **不在记忆库的 SQL**：只做执行时不报错，无评审——这是主要风险窗口
- **诚实承认**：
  - 对于"不在记忆库的全新 query"，目前主要靠 SchemaMapper 的 81% 和 S2SQL 生成的 LLM 鲁棒性
  - 完全杜绝需要执行后的数据合理性校验，是未来工作方向
- **研究员侧的反馈机制**：界面有"这个答案对吗？"反馈按钮，负面反馈会进评测集

**边界标注**：`[做过]` LLM 评审 + 人工审核；`[未来思路]` 执行后合理性校验

#### F19. 「系统上线后，有没有用户因为体验太差而弃用？弃用率大概多少？」

**第一句答题**：
> "弃用率这个指标我们定义得比较细——'注册后从未查询'约 25%（类型 A），'查询后 5 分钟内无 followup 操作（追问/导出/点推荐）'约 18%（类型 B）。前者多是注册后没真有需求，后者才是体验问题，这俩数字在 Kibana 里分开统计。"

**要点展开**：
- **弃用的两种定义**（数据来源：ELK）：
  - **类型 A：注册即沉默** —— 注册后从未提交过 query。查证：用户表左连接 `chatbi-query-event-*` 索引，取右表为空的用户数 ÷ 总注册数
  - **类型 B：体验型弃用** —— 提交 query 但 5 分钟内无后续 followup 事件（追问、导出、点击推荐）。查证：按 `queryId` 串联 query_submit 事件和后续 result_view/followup 事件，5 分钟窗口内无后续的算弃用
- **两类弃用的归因**：
  - 类型 A 多是注册后没真有需求（高校流动学生助理、合作单位挂名账号）
  - 类型 B 才是体验问题——`success=false` 或 `rowCount=0` 后弃用率最高，是 SchemaMapper / S2SQL 准确率问题的下游表现
- **内部系统的诚实事实**：
  - 不像 C 端按 DAU/留存考核，内部系统的"活跃度"以月活为核心指标
  - 真正的核心用户（实验室内部 20 人 + 外部高校研究员 ~50 人）弃用率几乎为 0
  - 长尾用户的"弃用"主要是类型 A（本来就没需求）
- **用 ELK 能做但还没做的**：用户分群分析（按 query 频次分桶）、流失预警（连续 N 周未查询的用户标记）

**边界标注**：`[数据来源：ELK]` 弃用率——具体数字（A: 25%, B: 18%）来自 § 0.5 经验值，面试前可在 Kibana 校准

**风险提示**：被追问"那你怎么知道弃用原因"——可以说"类型 B 的弃用 case 可以在 Kibana 里看具体是哪条 query 失败的，按 traceId 回溯就能定位到 SchemaMapper 候选错或 S2SQL 生成错。类型 A 没做用户访谈，是从数据反推的。"

### G. 数据治理与质量

#### G20. 「200 多张表，元数据怎么管理的？谁在维护？有没有字段名对不上、注释缺失的情况？」

**第一句答题**：
> "三层体系——物理层 PostgreSQL 按 Domain 分 schema；语义层在 Headless BI 建 Domain → DataSet → Model 三层（含 metric/dimension 定义、ModelRela JOIN 路径、DimValueMap 值映射）；知识库层每天定时从数据库导高频值到 HanLP 词典 + pgvector 向量库。元数据由数仓工程师维护；注释覆盖率约 75%，SchemaMapper 的 LLM 消歧兜底。"

**要点展开**：

- **元数据的三层体系**：

  | 层 | 内容 | 维护者 | 更新频率 |
  |---|------|-------|---------|
  | **物理层**（PostgreSQL）| 按 Domain 分 schema（`macro_economy` / `corporate_finance` / `green_finance` / `behavior_exp`），200+ 张物理表 | 数仓工程师 | 按 Airflow DAG 调度（金融季频/月频、行为实验人工触发日更）|
  | **语义层**（Headless BI）| Domain → DataSet（主从结构）→ Model；metric/dimension 业务名→技术名映射；ModelRela（JOIN 路径）；**DimValueMap**（值映射"比亚迪"→"002594"）| 数仓工程师 | 通过管理 API 即时生效（热加载，不需重启）|
  | **知识库**（SchemaMapper 运行时数据）| HanLP 词典（BinTrie，SQL 查高频值导入）；pgvector 向量库（metric/dimension 元数据 embedding）| 系统 + 我优化 | HanLP 每天 0 点全量重建（`DictTaskServiceImpl.dailyDictTask()`）；向量库每 2 小时增量刷新（`MetaEmbeddingTask`）|

- **语义层的具体配置项**（`[源码学过]` SuperSonic 的元数据表结构）：
  - `s2_domain`：4 个主题域（宏观/公司财务/绿色金融/行为实验）
  - `s2_dataset` + `s2_dataset_model_config`：22 个 DataSet（含主从结构，通过 `DataSetModelConfig.includesAll` 控制全字段还是选字段）
  - `s2_model`：~226 个 Model（物理表映射）
  - `s2_metric` / `s2_dimension`：metric/dimension 定义（业务名、技术名、数据类型、注释、别名）
  - `s2_model_rela`：Model 之间的 JOIN 关系（fromModel、toModel、joinType、joinConditions）
  - `s2_dimension_mapping`：**DimValueMap**（techName ↔ bizName ↔ alias 的值映射，DimValueAspect 在 SQL 执行前后做值替换，详见 § B5/C8）

- **维护责任**（对齐 § 0.4 团队配置）：
  - **数仓工程师**（1 人）：物理层 ETL、语义层 metric/dimension 定义、ModelRela 配置、DimValueMap 维护
  - **算法博士后**（1 人）：LLM prompt 策略、评测体系
  - **我（实习生）**：SchemaMapper 的 LLM 消歧 prompt、embedding 词典优化、评测 Agent

- **注释缺失的情况**（经验值）：
  - 200+ 表的字段中文注释覆盖率约 **75%**——缺失的主要是早期建表的历史遗留字段（特别是部分行为实验量表的子项目说明）
  - 影响：LLM 消歧在没有注释时只能靠字段名 + 数据类型 → 映射准确率下降约 5-10pp（基于评测集对比）
  - 应对：数仓工程师持续补注释；SchemaMapper 的 LLM 消歧在缺注释时降级用字段名 + 数据类型兜底

- **元数据热加载**：
  - metric/dimension 改动通过 SuperSonic 管理 API **即时生效**（不需要重启服务）
  - HanLP 词典每天 0 点定时全量重建（`DictTaskServiceImpl` 的 `@Scheduled(cron = "0 0 0 * * ?")`）
  - 向量库每 2 小时增量刷新（`MetaEmbeddingTask` 的 `@Scheduled(cron = "0 0 */2 * * ?")`）
  - **真实踩过的坑**：凌晨 0 点重建词典时触发过 BinTrie 并发读写 NPE（详见 § F17 commit `18ce934bb`），修复后改成读写分离 + 先构建新 trie 再整体替换引用

**边界标注**：`[做过]` 物理层组织、语义层建模；`[源码学过]` SuperSonic 元数据表结构（s2_domain/dataset/model/metric/dimension/model_rela）、DictTaskService / MetaEmbeddingTask；`[经验值]` 注释覆盖率 ~75%；`[真实 commit]` 并发 Trie 问题 `18ce934bb`

#### G21. 「跨表查询的时候，研究员用的字段名和数据库里的字段名对不上的情况怎么处理？比如用户说'市盈率'但数据库里字段叫 pe_ttm？」

**第一句答题**：
> "两个层面的问题——**字段名映射**（'市盈率' → `pe_ttm`）靠 SchemaMapper 三层机制：embedding 粗召回 → 规则过滤 → LLM 消歧精选；**值映射**（'比亚迪' → `002594`）靠 DimValueMap + DimValueAspect 在 SQL 执行前做值替换。两者是不同层面，面试官问的'字段名对不上'主要是前者。"

**要点展开**：

- **层面 1：字段名映射**（"市盈率" → `pe_ttm`）—— SchemaMapper 三层机制：
  1. **Embedding 粗召回**：BGE-M3 把"市盈率"和所有 metric 的中文注释（"市盈率（TTM）"、"市盈率（前瞻）"）一起做向量相似度，召回 Top-10
  2. **规则过滤**：去掉数据类型不匹配、主题域不相关的（`MapFilter`，真实 commit `6d41ce4c5` 修过排序错误）
  3. **LLM 消歧精选** ⭐ 我加的：给 LLM 传字段名 + 中文注释 + 数据类型 + 所在表名（四维信息），让它从 Top-10 选 Top-1
  - **关键设计**：中文注释是 LLM 消歧的核心——光传字段名（`pe_ttm`）LLM 区分不了，加了"TTM 市盈率 / 滚动 12 个月"注释才能选对
  - **顽固 case**：
    - 完全同义词（"扣非净利润" vs "扣除非经常性损益后的净利润"）→ 靠语义层注册别名（metric.alias 字段）
    - 用户用错术语（"市净率"说成"净市率"）→ LLM 消歧能容错
    - 多个候选都对（PE TTM vs PE Forward）→ LLM 选默认（TTM），或在回答里提示

- **层面 2：值映射**（"比亚迪" → `002594`）—— DimValueMap + DimValueAspect：
  - SchemaMapper 在 Mapper 阶段识别"比亚迪"是"公司名称"维度的 VALUE 类型（靠 **HanLP 词典 BinTrie** 前缀/后缀匹配，不是 embedding——向量库目前只存字段名元数据不存值）
  - LLM 生成 S2SQL 时写的是业务名：`WHERE 公司名称 = '比亚迪'`
  - **DimValueAspect** 在 SQL 执行前查 `DimValueMap`（techName ↔ bizName 映射）替换：`WHERE company_code = '002594'`——让 SQL 走索引，避免全表扫描
  - SQL 执行后把结果里的 `002594` 替换回"比亚迪"，对用户透明
  - **真实踩过的坑**：DimValueMap 的 techName 和 bizName 更新时曾未同步，导致值替换用旧映射——研究员反馈"查某公司查到另一家"（真实 commit `0bbab5e7b`，详见 § F17）

- **词典怎么建的**（值匹配的数据来源）：
  - `DictTaskServiceImpl.dailyDictTask()` 每天 0 点定时执行 SQL：`SELECT company_name, count(*) FROM table GROUP BY company_name ORDER BY count(*) DESC LIMIT 100000`
  - 把高频值导入 HanLP 自定义词典 + SearchService BinTrie
  - 支持白名单强制添加低频但重要的值

**边界标注**：`[做过]` 字段映射三层机制全链路 + LLM 消歧；`[源码学过]` SuperSonic SchemaMapper + DimValueAspect + DictTaskService；`[真实 commit]` 排序错误 `6d41ce4c5`、值映射不同步 `0bbab5e7b`

  - **金融财务数据**（三大报表、财务指标衍生）：**季频**——按上市公司财报披露节奏（每年 4 月/8 月/10 月/次年 4 月的季报/年报披露后批量入库），不涉及股价行情
  - **公司治理数据**（股权、高管、质押、并购、分析师预测等）：**月频 / 事件驱动**——按公告节奏更新，有新公告时批量入库
  - **宏观指标**（GDP/CPI/M2/PPI 等）：**月度 / 季度**——按统计局发布节奏
  - **绿色金融**（碳排放交易、AQI、ESG 评级等）：**周频到月频**
  - **行为实验数据**：**实验实施期 T+1 日更（人工触发）**——约 4 周内每天下午研究人员交数据 → DBA 用 Airflow DAG 入库；非实验期间无更新（详见 § B6）
- **对用户的告知**：
  - 查询结果旁显示"数据更新至 YYYY-MM-DD"
  - 时效性敏感的 query（"最新财报"（可能还没披露）、"今天的实验数据"（T+1 才有）、"本月新发公告"）系统明确提示数据截止日期
- **诚实短板**：
  - 没做数据新鲜度主动告警（如"你查的字段已 3 天未更新"）
  - 行为实验数据有**特殊风险**：依赖研究人员主动发数据 + DBA 入库，如果 DBA 漏入库或 Airflow DAG 故障，Data Agent 查到的就是旧数据——靠 ELK 监控入库 DAG 的执行状态做兜底
  - **DimValueMap 过时风险**：公司改名（如"ST 比亚迪"恢复为"比亚迪"）后，如果 DimValueMap 没同步更新，值替换会用旧映射（真实踩过坑，commit `0bbab5e7b`，详见 § F17/G21）
  - **HanLP 词典延迟**：词典每天 0 点全量重建，新入库的值要第二天才能被 Mapper 识别——当天新入库的公司名当天查不到
  - 部分历史遗留表更新链路可能中断，需要人工巡检
- **业界做法** `[联网调研]`：Snowflake Cortex、Tableau Pulse 都会在结果旁标注数据时间，这是 Chat-BI 系统的标配

**边界标注**：`[做过]` 数据更新频率、结果标注；`[诚实短板]` 新鲜度告警、行为实验数据链路的人工依赖

### H. 决策细节与替代方案（深水区）

> **本组是题纲最后深水区**：面试官会在这里区分"调包侠"和"真做过决策的人"。每道题都要诚实 + 有数据支撑。

#### H23. 「你们选的向量库是什么？为什么没用 Elasticsearch 或者直接用 PostgreSQL 的 pgvector？是谁拍板的？」

> ⚠️ 注意题纲问法里的矛盾：题纲写"为什么没用 pgvector"，但简历实际是用了 pgvector。按实际简历答——选 pgvector 是决策结果，要论证合理性。

**第一句答题**：
> "我们用的就是 pgvector。决策逻辑是：数据量在数千到几十万条级别（记忆库 800+、Schema 元数据 200+），pgvector 完全够用；且记忆库的入库必须和业务元数据强事务一致——这正是 PostgreSQL 的强项，ES 或独立向量库反而要绕一圈同步。"

**要点展开**（基于业界调研，三条核心理由）：

| 维度 | pgvector | Elasticsearch | Milvus/Qdrant |
|------|----------|---------------|----------------|
| 数据量阈值 | < 100 万绰绰有余；pgvectorscale 5000 万仍 471 QPS @ 99% recall | 千万级有优势 | 十亿级有优势 |
| 事务一致性 | **原生 ACID** | NRT（1s 刷新窗口） | 需要双写或 CDC |
| 运维成本 | `CREATE EXTENSION` 一行 | JVM 集群常驻数 GB | 多组件（etcd + MinIO + ...） |
| 混合检索（BM25+向量） | 需自己拼 | 一等公民 | 一般 |
| 多租户 | 共享表 + `agent_id` 过滤够用 | 原生分片 | payload 过滤更精细 |

**选 pgvector 的三条硬理由**：
1. **数据量远低于迁出阈值**：800 条记忆库 vs 1000 万迁出阈值，有 12000 倍余量
2. **事务一致性是硬约束**：记忆库入库时机是"SQL 执行成功那一刻"，必须和业务状态同事务——ES 的 NRT 窗口和独立向量库的同步链路都引入数据丢失风险
3. **架构简洁性**：少一个组件就是架构优势——单一备份、单一监控、单一故障域

**决策拍板**：技术方案由数据平台组讨论，**资深后端（组长）最终拍板**，我提供选型分析（含上述三条理由的数据支撑）。算法博士后从模型层角度认可（记忆库与业务同事务一致性的需求），数仓工程师从运维角度认可（少一套组件）。

**迁出阈值**：
- 向量数突破 1000 万
- QPS 突破几千且 p99 延迟告警
- 需要 GPU 索引

**边界标注**：`[做过]` 选型论证；`[联网调研]` 业界基准数据

**风险提示**：题纲问法有歧义（"为什么没用 pgvector"），但简历基线是用 pgvector。请按简历实际回答——选 pgvector 是有论证支撑的。

#### H24. 「项目开发过程中，有没有你提议过但被否决的方案？后来你回头看，觉得当时的判断对不对？」

**第一句答题**：
> "有。我最初提议在 SchemaMapper 之前加一个'意图分类器'，先把 query 分到对应主题域再走 SchemaMapper——被组长否决，理由是增加了链路延迟。回头看，他判断是对的：主题域分类可以靠 embedding 隐式完成，不需要显式前置一步。"

**要点展开** [需对齐具体细节]：

- **我提议的方案**：意图分类前置（intent classifier → 主题域路由 → SchemaMapper）
  - 动机：希望通过先缩小搜索空间提升准确率
  - 实现：训练一个轻量分类器，把 query 分类到"金融/行为科学/其他"
- **被否决的理由**（资深后端/组长否决）：
  - 增加 ~200ms 延迟（对 15s 端到端可接受但累加）
  - 主题域信息已经在 embedding 召回里隐式包含——多此一举
  - 分类器错误会级联到 SchemaMapper，更难调试
- **回头看的判断**：组长判断是对的
  - 实测：SchemaMapper 的 LLM 消歧已经在 prompt 里给了主题域上下文，显式分类没必要
  - 教训：先想清楚"显式做法"和"隐式做法"的等价性，再决定要不要新增组件
- **另一个例子** [需对齐]：曾提议把记忆库的 LLM 评审做成异步队列（避免同步阻塞）——但被否决，因为评审结果要决定是否入库，异步会引入一致性问题。回头看也对。

**边界标注**：`[做过]` 提议被否决的方案；`[诚实]` 承认当时判断错

**风险提示**：这道题不要编"我没有提议被否决过"——会被追问"那你平时怎么和团队讨论方案？"直接穿帮。诚实给一个具体的例子，反而显得有协作经验。

#### H25. 「你现在回头看这个项目，最大的遗憾是什么？如果重新做，你会改什么？」

**第一句答题**：
> "最大遗憾是多轮对话改写的**深度**不够。我们默认开启了查询前改写（`rewriteMultiTurn`），能把'那净利润呢'补全为完整查询——这是基础 Agent 能力，必须有。但只取最近 1 轮、且改写后走单轮解析，没有实现真正的上下文继承。如果重做，我会让 ChatContext 的 SemanticParseInfo 直接传递到下游所有环节。"

**要点展开**：

- **遗憾 1：多轮对话改写的深度不够**（不是"没做"，是"做得不够深"）`[源码学过]`
  - **已做的**：多轮对话改写**默认开启**（`NL2SQLParser.rewriteMultiTurn()`，`ChatApp.enable=true`）——用户说"那净利润呢"时，系统从 `s2_chat_query` 表读取最近 1 条成功查询的历史 queryText + schema 映射 + S2SQL，用独立 LLM 调用把省略问题补全为"比亚迪 2024 年净利润是多少"再进 SchemaMapper。这是基本的 Agent 能力
  - **局限性 1——只取最近 1 轮**：`getHistoryQueries(chatId, 1)` 只读上一条；如果上下文在 3 轮前提到的公司名，改写拿不到
  - **局限性 2——只是查询前改写，不是上下文继承**：改写后 queryText 替换原始输入，后续 SchemaMapper / LLM Text2SQL / Corrector **完全不知道这是多轮对话**——LLM 的 prompt 仍不包含历史。如果改写漏了隐含信息（如"上一轮的维度筛选条件"），下游无法补救
  - **局限性 3——改写 LLM 偶尔过度补全**：可能加了用户没说的条件（如用户只想换指标，改写把时间范围也改了），改写错误会级联到全链路
  - **如果重做**：实现真正的上下文继承——`ChatContext` 的 `SemanticParseInfo` 自动传递到下游，让 SchemaMapper 和 LLM 都能看到上一轮的 datasetId、维度筛选、时间范围，而不是只靠改写 queryText 来间接传递

- **遗憾 2：权限粒度粗**
  - 现状：内部全量可信用户，所有注册用户看所有表
  - SuperSonic 源码有 RBAC，但没启用
  - 如果重做：至少做表级权限，防止跨研究组数据串

- **遗憾 3：评测集规模小**
  - 现状：SchemaMapper 200 条专用评测集 + 端到端自维护测试集（另一套，无 human in the loop）
  - 业界（如 Spider 2.0、BIRD）评测集都是几千到几万条
  - 如果重做：用 LLM 自动扩容评测集到几千条，人工只做抽检；并补一套线上抽样带 human in the loop 的"用户体验准确率"评测作为对照

- **遗憾 4：记忆库没有淘汰机制**
  - 现状：记忆库只进不出，错误的 SQL 靠人工审核清理
  - 如果重做：加 TTL（30 天未召回的 SQL 降权）、加召回后的反馈闭环（召回后被用户否决的 SQL 自动降权）

**边界标注**：`[诚实]` 遗憾清单；`[源码学过]` `NL2SQLParser.rewriteMultiTurn()` 源码 + `getHistoryQueries(chatId, 1)` 只取 1 轮 + `OnePassSCSqlGenStrategy` prompt 无历史变量
