【笔记】
- Deep Research Agent（深度研究 Agent）说白了就干三件事：动态决定下一步搜什么、把多轮检索来的信息整合到一起、判断什么时候够了可以停。
- 工具这块有四条设计原则，是我后来踩了坑才补上的：一个工具只做一件事（简单性）；每个工具自带重试和降级（可靠性）；相同输入尽量给相同输出，否则训练阶段模型学不到稳定模式（确定性）；每次调用都要有日志能回溯（可观测性）。这四条你现在记不住没关系，等系列讲到工具那几篇会一条条还回来。
- 我们用了一个叫 IterResearch 的框架，不把原始搜索结果堆进上下文，而是每轮更新一份固定大小的研究摘要，只记'目前已知'和'还缺什么'。这样上下文大小保持常量，跑多少轮都不溢出。"能说到这一层的候选人很少，直接拉开差距。
- 我们在内测阶段遇到过一个真实案例。一个用户问某上市公司的2023年财报数据，Agent 开始执行，前6步顺利找到了行业背景。第7步，搜索返回了一个内容付费网站，整页都是登录提示，"请订阅后查看完整财报"。没有任何异常被抛出，这个登录页被完整地送进了 Observation。接下来发生的事情很奇特：模型"看见"了一个说"请登录"的页面，开始推理自己应该怎么"绕过"这个限制，换了各种关键词继续搜。步骤7到14，8步里有6步都是"某公司财报 PDF 下载"、"某公司年度报告 免费"之类的变体。每次搜索结果都差不多，模型陷入了循环。整个任务跑了18步才超时停下，最后的报告是胡说八道。我们排查了很久，才在日志里发现步骤7那次搜索返回的东西。
- ①分级处理工具失败，②检测并打破重复搜索循环，③主动管理 token 预算。跑完这三件事，你手里会有一个可以接生产流量的 ReAct 执行器。
  - 分级处理工具失败：区分超时/空结果/垃圾内容三种失败
    - 第一类：超时/网络异常 → 指数退避重试，最多3次。为什么要指数退避（1s, 3s, 9s）而不是固定间隔？超时通常是服务器压力大导致的，固定间隔重试会在同一时间段内继续打压，指数退避给服务器时间恢复，重试成功率高很多
    - 第二类：空结果 → 不重试，换关键词。为什么空结果不重试？重试同一个关键词只会得到同样的空结果，纯粹浪费步数。正确做法是告知模型"没搜到"，让它自己决定换个角度，如“当前关键词未找到有效结果，请尝试换一种表述方式或拆分为更小的子问题”
    - 第三类：内容质量检查 → 过滤垃圾，不把垃圾传给模型。为什么要主动过滤，而不是把结果直接传给模型让它自己判断？因为"登录页面"、"404页面"在语义上和正常内容很相似，模型不一定能识别出来，会把垃圾当信息使，导致后续推理全部跑偏。检测常见的垃圾内容模式包括登录墙检测、空页面/404检测和广告页检测（内容里超过30%是URL）。
  - 重复搜索：比死循环更难发现的问题
    - 当 LLM 遇到的搜索关键词拿不到预期答案（比如搜索结果为空或全是登录墙/广告）时，它很容易陷入‘死循环’——不断微调关键词重复搜索同一个意思（例如刚搜完‘苹果2023财报 PDF’，搜不到又接着搜‘Apple annual report 2023’）。这不仅白白浪费 API Token 和搜索成本，还会导致任务直接卡死超时。
    - 为了彻底解决这个问题，我设计并实现了一套基于 语义相似度 + 失败原因反馈 的环路检测机制（LoopDetector）我的核心思路分为两步：实时精准检测 与 启发式反向引导。
      - 基于滑动窗口与向量相似度的‘重复判定’：传统精确匹配（String Match）无法识别同义词，所以我将每次搜索的 Query 转为向量（Embedding）。维护一个滑动窗口（比如只比对最近 5 次历史搜索），通过余弦相似度计算新 Query 与历史 Query 的语义贴近度。当最高相似度超过设定的经验阈值（如 0.88）时，系统立刻拦截，判定为陷入了‘死循环’。
      - 基于‘结果质量’的动态 Prompt 反馈：仅仅告诉 LLM ‘你重复了’ 是没用的，LLM 收到这种泛泛的警告后，大概率还是会在旧方向附近小修小补。因此，我们建立了一个结果质量回写机制（Mark Result Quality）。如果上一次搜索返回的是‘空结果’（empty_result）或者‘垃圾页面/登录墙’（garbage），我们会在判定重复时，将上次失败的具体原因注入到系统的 Hint 提示中。
    - 在具体的落地过程中，有两个工程细节非常关键：
      - 阈值 $0.88$ 的确定： 太低容易‘误报’（比如‘固态电池’和‘锂电池’虽然属于同一大类但含义不同，阈值低了会误拦截）；太高容易‘漏报’（如中英文同义词匹配）。我们通过历史 Query 样本拉取测试，最终选定了 $0.88$ 这个既能识别同义重述又能放行正常递进搜索的阈值。
      - 引导词的心理学设计：如果上次是无结果，Hint 会明确指示：“该方向此前无结果，请换上位概念、对立面或具体案例等完全不同的角度切入”；如果上次是垃圾页面，Hint 则指示：“该方向都是广告/登录墙，请放弃搜索，尝试寻找权威媒体的具体 URL
  - token 预算：要在"溢出前"处理，不是"溢出后"
    - 正常模式，完整传递搜索结果，保留3000字符；精简模式，截断每次搜索结果，只保留关键段落；压缩模式，触发历史摘要，极简摘要
    - 把历史的工具调用结果压缩为摘要，保留 think 部分。为什么要保留 think 而压缩 observation？ 模型的推理过程（think）反映了它怎么一步步缩小信息缺口，这个"思考轨迹"比具体的原始搜索结果更重要，它决定了模型接下来能做什么决策
  - 结构化日志：你的 Agent 出了问题，你怎么知道在哪步出的
    - entry = { "task_id": self.task_id, "step": step, "timestamp": datetime.now().isoformat(), "tool": tool_name, "args": tool_args, "result_status": result_status, # ok/timeout/empty_result/garbage/loop_detected "token_count": token_count, "duration_ms": duration_ms }

【深度研究面试题-03篇】
1. Q1:你的 Visit 工具，抓一个网页回来之后，到底给模型喂的是什么？A:返回网页的正文内容;Q2: 一篇新闻正文三千字，但导航栏、相关推荐、评论区、页脚版权加一块还有五千字，你这五千字也一起喂进去了？A: 应该是过滤过的，我用 BeautifulSoup 抓了正文;Q3: 那你的 Scholar 工具，搜回来的论文，你怎么确认它真的跟问题相关？就按 Semantic Scholar 返回的顺序直接拿前几篇？
【笔记】
- 我自己在第一版系统里栽过一次。有个用户问一个技术选型的问题，Agent 的 Visit 工具访问了一篇技术博客。那篇博客正文大概两千字，是真有价值的内容。但整个页面里还塞着：侧边栏的推荐文章标题加摘要（约八百字）、读者评论区（一千多字）、"作者其他文章"列表（五百字）、页脚的版权和导航（五百字）。这五千多字一起进了模型的上下文。下一步就出事了。模型开始推理"作者的其他文章是不是有更多信息"，还顺着一条读者评论里的观点分析了半天。整个推理跑偏了将近四步，白烧了一大把 token，最后那份报告质量很差。我排查了挺久，最后定位到根子上就是 Visit 返回的内容里掺了太多跟主题无关的东西。所以这篇我想先把一个观点立起来：工具最重要的职责不是"取回信息"，而是"过滤噪声"。
- Search 工具不能只做二传手，至少要加两层过滤：域名黑名单，加 snippet 质量打分。
  - 已知低质量域名黑名单。为什么要维护这个黑名单？很多 SEO 垃圾站排名不低，但内容是拼凑的、过时的，或者点进去就是付费墙，让模型看这些是白烧 token。
  - LOW_QUALITY_DOMAINS = { "zhidao.baidu.com", # 百度知道：答案参差，很多已过时 "wenwen.sogou.com", # 搜狗问问：同上 "wenda.so.com", # 360 问答：同上 "tieba.baidu.com", # 贴吧：非结构化，信噪比低 "mp.weixin.qq.com", # 公众号：抓不到原文，只有一段摘要
  - 为什么 num_results 默认 5 而不是 10？我们测下来，前 5 条基本覆盖了九成的有效信息。条数越多反而让模型分心，"哪条最重要"这个判断本身也吃 token。多取一点，过滤后留 5 条
  - 还有一个容易忽略的点：返回格式。别把原始 JSON 直接丢给模型。模型读自然语言比读 JSON 顺，而且 JSON 里那一堆 title、url、snippet 字段名，十条结果叠起来也占掉不少 token。整理成一段干净的结构化文本再喂：
    - lines = [f"搜索返回 {len(results)} 条结果：\n"] for i, r in enumerate(results, 1): lines.append(f"[{i}] {r.title}") lines.append(f" 来源：{r.domain}") lines.append(f" 摘要：{r.snippet[:200]}") lines.append("") return "\n".join(lines)
  - 段落级相关性过滤，我一开始就没用 embedding。 这点跟不少教程是反着来的。网上很多写法是把网页按段切开，每段算一次 embedding 跟 query 求余弦相似度，挑最高的几段。听起来更"准"，但 Visit 是高频调用的工具，一次深度研究可能访问十几个页面，每个页面再切成几十段，全量算 embedding，延迟和调用成本一下就上去了。我先用关键词重叠这种轻量方案扛着，它覆盖了大部分情况，省下的延迟在 Agent 这种连环调用的场景里很实在。当然它有失效的地方，得讲清楚：关键词重叠在 query 和正文语言不一致时基本歇菜。 用户用中文问，页面是英文正文，词对不上，过滤就退化成乱选。碰到这种跨语言场景，要么先把 query 翻译成目标语言再做重叠，要么这时候才值得上 embedding。把贵的方案留给真正需要它的场景，而不是一上来全场景套。
- Scholar 工具：学术文献的门槛比网页更高
  - Scholar 工具调学术搜索 API（比如 Semantic Scholar 或 arXiv），返回相关论文与普通网页过滤不一样。这里有个反直觉的点，别拿引用数当相关性排序。 引用数高的常常是奠基性工作，但对一个具体问题未必最有用。
  - 我们接 Semantic Scholar 的时候就踩过这坑。有个用户问某个模型架构的优化方法，Scholar 返回了五篇引用数很高的论文，结果其中三篇是这个架构的基础综述，跟"优化方法"关联度很低。模型把这三篇综述的摘要挨个看了一遍，一大把 token 全花在背景知识上，反而没集中在用户真正要的那点东西。你要的不是"关键词匹配上的论文"，是"真跟问题相关、来源可靠、时间也合理"的论文。直接按检索引擎排序拿前几篇，很容易抓回一堆引用数巨高、其实是相邻领域的论文。
  - 为了让 LLM 既能获取足量的学术背景，又不被冗余细节淹没，我设计了一个轻量级的学术检索与重排序模块。我们的设计理念是 ‘控制总量、严控质量、多维重排’：
    - 控制 Top-K 数量： 默认只向大模型输入 Top 3 篇 论文。因为一篇摘要约 300 字，3 篇就是 1000 字左右，这个 Token 量既能提供充足背景，又不会引入过多噪声。
    - 摘要截断： 将单篇摘要硬截断在 500 字以内，过滤掉实验细节，只保留核心结论。
  - 重排序的核心逻辑在于：不盲目依赖 API 默认排序，也不单看引用量（因为新出的好论文引用量还没跑出来），而是结合‘语义相关度 + 时效性 + 可获取性’综合打分：
    - 文本匹配度（权重 80%）： 标题关键词命中给予高权重（0.5），摘要命中给予中权重（0.3）。
    - 时效性衰减（权重 15%）： 快速迭代的领域极度看重近况，近 2 年发布的论文直接加 0.15 基础分，2–5 年的加 0.05。
    - 全文可读性（权重 5%）： 带有开放获取（Open Access PDF）链接的论文给予额外加分（0.05），方便 Agent 后续深入抓取阅读。
  - 为什么这里用关键词交集（Jaccard 思想）计算相关性，而不是用向量相似度（Embedding）这是一个工程上的性能与成本 Trade-off。学术搜索 API（如 Semantic Scholar）本身已经在粗召回阶段做过语义检索了。在二次重排序时，计算 10 篇候选论文的向量相似度需要额外的 Embedding API 调用，增加 200ms+ 的延迟和额外成本。对于短文本（标题/摘要）的二次精排，基于关键词的高权重匹配 + 时效性 + OpenAccess 规则的轻量级算法，在零延迟的前提下已经能取得非常理想的效果。
- Python 工具：安全沙盒是必须项，不是可选项
  - 你不能让 LLM 生成的代码直接在生产环境裸跑。LLM 写出来的代码，有可能调 os.system() 执行系统命令，用 open() 读写本地文件，import subprocess 起任意进程，甚至不小心写了个死循环把 CPU 跑满。这些在 Deep Research 任务里不常见，但一旦发生就是真事，等于把一台没人盯着的机器，交给了一段不可控的代码。
  - 做法是两关：执行前静态检查（白名单优先于黑名单），加子进程隔离里跑。
    - 白名单：允许的标准库。为什么用白名单不用黑名单？黑名单容易漏（禁了 subprocess 忘了禁 os.popen），白名单是明确的：只有这些算安全
    - timeout 为什么 10 秒？Deep Research 里的 Python 多半是数值计算或数据处理。正常 3 秒内出结果。10 秒上限能覆盖复杂计算，又能挡住死循环吃满时间片
    - 错误信息怎么回，这是个容易被忽略的细节。完整的 Python 堆栈通常二十来行，大半是框架内部的调用链，跟模型写的那几行逻辑没关系。你把整段堆栈喂回去，模型容易被中间那些层带偏，烧一堆 token 去分析其实无关的中间调用。只回最后五行（真正报错的地方），模型改代码的成功率反而更高。
    - 子进程加白名单这套，代价是每次执行都有子进程启动的开销，大概几十毫秒，比直接 in-process 跑慢。但这点延迟换的是安全，值。它能覆盖九成以上的需求。剩下那些更高安全要求的场景，比如要跑不可信的复杂代码，才需要上容器或者 gVisor、Firecracker 这类隔离，但它们冷启动有额外延迟，在 Agent 高频调用下开销不小，别无脑套
    - timeout 也别追求"永不超时"，就设短，10 到 15 秒。超时本身是个信号：一段正常的数值计算要是跑过 10 秒，多半是代码逻辑出了问题（数据量估错了，或者循环条件写错了），让模型重想一遍，比让它干等强

【深度研究面试题-05篇】
1. Q1：你说你的 Agent 支持深度研究，跑了 20 步，但问题是，到了第 15 步，模型还记得第 3 步找到的关键结论吗？怎么验证的？出现过'忘记'的情况吗？A：我把 Context 窗口开得比较大，32k，应该够了。Q2:32k 听起来不少，但 20 步每步平均 1000 个 token，就已经 20k 了，还要留 Prompt 和工具结果，很快就满了。而且就算没满，模型对 20k 之前的内容注意力也会衰减。你的解法本质上是靠'更大的窗口'撑着，不是真正解决了问题。那如果任务需要 50 步呢？
【笔记】
- IterResearch 框架要做的事情——用演进报告替换线性历史记录，把上下文从"越来越长的对话"变成"越来越好的研究报告"。
- 这个机制在任务步骤少的时候（5-8步）没有问题，历史不长，模型能处理。但当步骤数超过15步时，问题开始集中出现：
  - 问题一：Context 越来越长，注意力越来越稀薄。Transformer 的注意力机制是全局的，但在超长序列里，对早期 token 的有效注意力会下降。第 3 步找到的一个关键事实——"A 公司 2024 年的净利润是 12 亿"——到了第 20 步，可能已经淹没在大量中间步骤的噪声里，模型即使没有"忘记"这个 token，实际上它对这个事实的利用率已经很低了。这会导致一个很常见的现象：模型在后续步骤里重新搜索了已经找到的信息，因为它"感觉"自己还不确定。
  - 问题二：搜索结果大量重复，但 Context 不断增大。线性历史里有大量"冗余"信息——同一个事实被不同来源重复提及，对话历史里有大量"我接下来要……"这类推理过程文字。这些内容对推理没有额外帮助，但持续占据 Context 空间。
  - 问题三：上下文满了，只能截断，但截断会丢信息。当 Context 快满时，ReAct 只能把最老的历史截掉。但最老的历史里往往有最初的任务定义、关键的背景信息、早期发现的核心结论。一截断，模型开始在没有全局背景的情况下推理，更容易绕圈子。
- 在 IterResearch 里，Agent 的工作空间不是一个越来越长的对话历史，而是一个固定结构的"演进报告（Evolving Report）"，它包含：
  - 已确认的事实（Confirmed Facts）：每一步新发现的、经过来源确认的信息
  - 尚未解决的子问题（Open Questions）：还没找到答案的待研究问题
  - 信息缺口（Information Gaps）：发现了有某个方向的信息但还不完整
  - 当前研究方向（Current Focus）：下一步要研究的具体问题
- IterResearch vs ReSum：两种上下文管理策略的区别
  - ReSum（动态摘要模式）： 维持 ReAct 的线性历史结构，但在上下文即将溢出时，触发一次 LLM 摘要调用，把最老的一段历史压缩成摘要，腾出空间继续添加新内容。优点：改动最小，在现有 ReAct 框架上加一个摘要触发机制就够了，实现成本低。缺点：摘要是有损压缩，如果摘要质量不好，关键细节可能被压掉。而且摘要触发时机是被动的（Context 快满才触发），不是主动管理，在高频摘要的情况下，多次压缩会导致信息越来越失真。
  - IterResearch（演进报告模式）： 从一开始就不采用线性历史，而是用结构化报告作为工作空间，主动管理"哪些信息需要保留、以什么形式保留"。优点：信息的留存是主动选择的，不是被动压缩的。结构化报告让模型每次都能清楚地看到当前研究状态，不需要从大量历史里"找"信息。缺点：需要额外的 extract_findings 调用，每步多一次 LLM 调用；报告结构需要精心设计，否则结构化过度会丢失重要细节

#秋招/项目
【深度研究面试题-06篇】
1. Q1:你做过一个金融保险领域的 Deep Research系统，每轮搜索10条，整个任务平均跑15轮，总共大概150条原始结果。150条结果，你们去重了吗？A：他说去重了，用 URL 去重，同一个链接只保留一次。Q2:那我问你，同一篇新闻稿，36kr 发了一版，知乎专栏转载了一版，微信公众号也转了一版，CSDN 的爬虫站又爬了一版。这四个 URL 完全不同，你的 URL 去重全部保留。你的 Agent 以为它找到了4个独立的信息来源，实际上是同一篇文章，这个问题你怎么处理？Q3: 那你怎么判断一个来源可不可信？权威财经媒体和专门做 SEO 的内容农场，你的系统能区分吗？
【笔记】
- 在我们的金融保险 DR 项目里，有一次我专门做了一次抽样统计：从某个研究任务的150条原始结果里，手工检查其中随机抽取的50条，发现其中有19条在内容上与其他条目高度重叠，重叠率接近40%。这些重叠完全逃过了 URL 去重。URL 去重之外，还有两个层次需要做：内容指纹去重，和语义去重。
- 内容指纹去重用的是 MinHash（最小哈希）。思路是把每篇文章的正文转成一组哈希签名，相似的文章签名会有大量重叠。检查签名重叠程度，就可以快速判断两篇文章是否近似重复，不需要逐字对比全文
  - 把文章正文切成 3-gram 字符级 shingle。为什么用 3-gram 而不是词语？因为转载文章经常会改写标题、换个开头，词语级别的比较容易被微小改动干扰，字符 3-gram 对这类"语法改写型转载"更鲁棒。
  - num_perm=128：使用128次随机排列来估计 Jaccard 相似度。更高的 num_perm 精度更高，但内存和计算成本线性增加。128 是准确性和性能的经验最优点，业界用得最多。
  - threshold=0.8：Jaccard 相似度超过80%就认定为近重复，删除。为什么是0.8不是1.0？因为转载文章通常会有5-20%的内容修改。（换个标题、加个编者按、删掉作者信息），设0.8能覆盖这类情况。设太低（比如0.5）会误删真正独立的相关文章。
- 语义去重是更高一层的去重，用于处理"角度不同但说的是同一件事"的情况。MinHash 检测的是文字层面的相似性：两篇文章字面重叠够多才会被认定为重复。但有些文章内容几乎相同，只是改写程度较高，MinHash 识别不出来——比如A媒体原创报道"某公司Q3营收同比增长32%"，B媒体的转述"第三季度该公司营收实现32%同比增幅"，字面相似度可能只有40%，不触发 MinHash 阈值，但从知识角度看，这两篇给 Agent 的信息价值是完全相同的。
- 来源可信度：你凭什么相信一个网站说的话
  - 第一层：域名白名单和黑名单
  - 第二层：信号特征打分
  - 第三层：LLM 交叉验证：
    - 一个来源说了一件事，我们不把它直接写进报告。要求同一事实至少有2个独立来源支持——独立的意思是不同域名、原文不互相转载。只有单一来源的结论会被标注为'待核实'。
    - 这一步成本不低，每次研究任务会额外调用一次 LLM，平均增加约0.8秒延迟。但效果很显著。
    - 在我们的项目里，开启交叉验证之前，最终报告的幻觉率（报告中可追溯到虚假或无来源信息的比例）是14%。开启交叉验证之后，降到了3%。 这个数字是我们通过人工抽样标注100份报告得到的，不是理论值。14%到3%，是这套系统最重要的一组数字。
    - 如果面试官追问"你们的幻觉率怎么测的"，回答要点是：人工标注。我们抽样了100份不同主题的研究报告，每份报告里的结论性陈述逐条对照原始来源核查，判断是否有无来源支撑或与来源矛盾。这是目前业界最可靠的评估方式，自动评估做不到这个精度。
