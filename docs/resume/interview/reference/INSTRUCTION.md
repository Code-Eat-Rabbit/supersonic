对你的需求，我会把阅读优先级定为：**EntSQL** → DAB → InsightBench → DataSpace。不是因为它们都“最新”，而是它们分别能帮助你设计企业业务口径、端到端问数、结果洞察、自动判分这四部分。 [arxiv](https://arxiv.org/abs/2606.03363)

另外，先纠正前面的定位：你记忆中的“En Bench”，很可能是 EntSQL，而不是 EntBench。我之前没有准确定位。EntSQL 的核心正是：SQL 生成需要遵循企业私有的指标定义、报表惯例和组织规则，而不能只依赖数据库 Schema。 [arxiv](https://arxiv.org/abs/2606.03363)

结合你之前介绍的 SuperSonic 二次开发、SchemaMapper → Semantic SQL Parser → 执行 → 结果解读流水线，我建议构建的是“企业语义问数与分析 benchmark”，而不是泛化的 Python 数据科学 benchmark。

## 1. 第一优先级：EntSQL——决定你“应该出什么业务题”

论文：*EntSQL: A Benchmark for Grounding Text-to-SQL in Long-Context Enterprise Knowledge*  
时间：2026 年 6 月；编号：arXiv:2606.03363。

### 为什么最符合你的需求

它关注的不是“模型认识不认识字段”，而是“能否把企业业务知识落实到查询逻辑中”。数据集包含五个业务领域的 1,066 个中英文对齐语义样例，多数问题需要问题文本和 Schema 之外的领域知识。 [arxiv](https://arxiv.org/abs/2606.03363)

这与你关注的指标消歧、comment 规范、口径约束、Semantic SQL 生成高度一致。

### 你应该借鉴什么

我建议把它的“企业知识 grounding”思路转化为以下题型，而不是直接照搬公开题目：

| 企业题型 | 示例 | 要测的能力 |
|---|---|---|
| 相似指标消歧 | “销售额”指下单金额、支付金额还是确认收入？ | 是否遵循企业定义 |
| 隐含过滤规则 | 有效订单是否排除取消、测试、内部订单？ | 是否正确应用业务规则 |
| 时间口径 | “本月收入”按支付时间还是确认时间？ | 是否选对时间字段与窗口 |
| 聚合粒度 | 客单价是总金额/订单数，还是客户级均值？ | 是否正确落实指标公式 |
| 组织范围 | 某事业部是否包含下属团队、历史归属？ | 是否理解组织规则与生效时间 |

上述题型是针对你系统的设计建议，不是 EntSQL 官方分类的逐项复述。

你尤其应该借鉴“证据约束”：每道题不只保存标准 SQL，还保存决定答案的业务定义及其来源。这样才能区分：

- 规则没有提供；
- 规则提供了，但检索没找到；
- 规则找到了，但 Parser 没有正确应用；
- Semantic SQL 正确，但编译或执行出错。

## 2. 第二优先级：DAB——决定你“怎么从实际工作构建题库”

论文：*Can AI Agents Answer Your Data Questions? A Benchmark for Data Agents*  
时间：2026 年 3 月首发，10 月更新；编号：arXiv:2603.20576。 [arxiv](https://arxiv.org/html/2603.20576v3)

### 为什么值得读

DAB 不是先人为设计一批复杂 SQL，再找问题去匹配，而是通过企业调研提炼实际工作难点，再构造数据和任务。它重点覆盖多数据库整合、不规范关联键、非结构化文本转换和领域知识。 [arxiv](https://arxiv.org/html/2603.20576v1)

对你而言，最有价值的是它的 benchmark 构建方法和失败轨迹分析，而不一定是跨四种数据库的具体设置。 [arxiv](https://arxiv.org/html/2603.20576v1)

### 你应该借鉴什么

我建议沿用“真实工作 → 能力分类 → 任务构建”的路线：

1. 从脱敏后的真实问数记录、分析需求、历史事故中收集种子问题。
2. 让业务人员说明正确口径和常见误解。
3. 给题目标注能力标签，而不只标“简单/中等/困难”。
4. 保留执行轨迹，定位失败发生在哪个模块。
5. 按业务频率和风险报告成绩，避免复杂但低频的题目主导总分。

例如，“去年收入”被写成 rolling 365 days，就是非常值得进入企业回归集的真实错误；没有必要为了像公开 benchmark，就强行加入企业根本不存在的 MongoDB 跨库查询。

## 3. 第三优先级：InsightBench——决定你“怎么评结果解读”

论文/项目：*InsightBench*；项目由 ServiceNow 开源。 [github](https://github.com/ServiceNow/insight-bench)

### 为什么适合你的结果解读模块

InsightBench 包含 31 个业务数据集，每个数据集带有人工策划、植入的数据洞察。它不只测单个问题的回答，还评估提出分析问题、解释结果、总结洞察和行动建议，采用双向洞察评估机制。 [insightbench.github](https://insightbench.github.io/)

这比只检查“答案引用了几个数字”“文字是否流畅”更贴近你希望做的有价值 insight。

### 你应该借鉴什么

建议借鉴“可核验洞察集合”，但不要把一篇标准报告当作唯一答案。

例如，同一份业务数据可以有多个应被发现的事实：

- 总体销售额下降；
- 下降主要集中在某渠道；
- 该渠道下降主要来自订单量，而不是客单价；
- 其他渠道的增长抵消了部分下降。

然后分别评估：

| 维度 | 你要回答的问题 |
|---|---|
| 数值忠实度 | 引用的数字、比例、排名是否正确？ |
| 洞察覆盖率 | 找到了多少重要且有证据支持的发现？ |
| 无依据结论 | 是否编造原因、市场事件或客户行为？ |
| 业务相关性 | 是否回应用户关心的指标和范围？ |
| 建议可追溯性 | 建议是否能追溯到数据中的发现？ |

这套维度是我的企业化改造建议。尤其要明确：维度贡献分析不等于因果识别，不能因为某渠道贡献了下降，就判定它是下降的因果原因。

## 4. 第四优先级：DataSpace——决定你“怎么自动判分”

论文：*DataSpace: Benchmarking Data Agents for Verifiable Analytics over Heterogeneous Workspaces*  
时间：2026 年 8 月；编号：arXiv:2608.03451。 [arxiv](https://arxiv.org/abs/2608.03451)

### 为什么值得借鉴

它要求 Agent 返回完整结果表，并对列对齐、类型与精度归一化、行顺序等进行处理，再校验答案。这比仅匹配一个数值或比较 SQL 文本更适合分析型任务。 [arxiv](https://arxiv.org/abs/2608.03451)

### 你应该借鉴什么

对你的 S2SQL 架构，我建议将评分分成三层：

1. 语义意图：指标、维度、时间窗口、过滤条件、排序规则是否正确。
2. 执行结果：完整结果表是否正确，而不要求 SQL 文本完全一致。
3. 解释内容：结论是否与结果一致，是否存在无依据推断。

其中，第一层能发现“碰巧算对”，第二层允许等价 SQL，第三层防止“查数正确但解释错误”。

## 5. 如何组合成你自己的企业 Benchmark

下面是我建议的结构，不是任何一篇论文的原始方案。

### 题库分成四个子集

| 子集 | 评测对象 | 主要参考 |
|---|---|---|
| 业务语义集 | 指标消歧、口径、时间、组织范围 | EntSQL |
| 查询执行集 | 多步查询、关联、聚合、跨源处理 | DAB |
| 结果解读集 | 对比、趋势、贡献拆解、洞察与证据 | InsightBench |
| 交互与边界集 | 应澄清的问题、缺数据、不可回答、权限限制 | 根据企业产品要求自行补充 |

前三个子集分别借鉴上述论文的任务与评价思路；交互和权限不能因为这些论文覆盖不充分就省略，应当作为企业验收要求独立设计。 [arxiv](https://arxiv.org/abs/2606.03363)

### 每道题至少保存这些信息

```text
case_id
用户问题与必要的对话上下文
数据快照、语义模型版本、业务规则版本
必需的业务知识及来源
标准语义意图：
  指标 / 维度 / 时间 / 过滤 / 粒度 / 排序
参考 Semantic SQL 或参考执行方案
标准结果表与比较规则
必须满足的断言
允许与禁止的解释结论
能力标签、业务频率、风险等级
```

这里不必强制每道题都有唯一标准 SQL，但必须明确“什么情况下算对”。

### 同时跑端到端评测与模块隔离评测

针对你的流水线，我会特别保留三种运行方式：

- 正常端到端：测用户实际体验。
- 提供正确语义 Schema：隔离 SchemaMapper，测 Parser。
- 提供正确结果表：隔离查数链路，单独测结果解读。

这样，你优化指标 comment、Few-shot、Parser 或解读 Prompt 后，才能知道收益来自哪里，而不是只看到总准确率波动。

## 6. 第一版的落地范围

建议先做约 200—300 道经过业务审核的高质量用例，不追求一开始就上千题。这个数量是试运行建议，不是论文给出的最低要求。

优先覆盖：

- 高频真实问题；
- 高损失口径错误；
- 已发生过的线上 bad case；
- 相似指标和歧义表达；
- 应澄清、应拒答和无法回答的情况。

开发集可以用于 Prompt 和检索优化；隐藏测试集不能进入 Few-shot 或调试流程。同一题的改写版本应放在同一分区，另保留时间外的新问题测试集，避免表面分数很高、遇到新业务问题却失效。

阅读时，先把 EntSQL 的任务与业务知识设计、DAB 的题库构建与错误分析读透，再用 InsightBench 和 DataSpace 补齐解释评分与自动判分。这四篇比单纯选择一个最新排行榜，更能直接帮助你形成企业 benchmark 的设计文档和验收规范。 [arxiv](https://arxiv.org/abs/2606.03363)
