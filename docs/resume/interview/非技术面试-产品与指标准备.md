## 1. SchemaMapper LLM 语义映射（58% → 81%）

### 1.1 30 秒概括

> "研究员说'查一下净利润'，系统需要知道'净利润'对应数据库里哪个字段。原来的系统靠向量匹配找最相似的字段，但分不清'净利润'和'扣非净利润'——语义相近但业务含义完全不同。我引入了 LLM 做消歧，让它像人一样根据上下文选对字段。映射准确率从 58% 提升到 81%。"

### 1.2 功能实现类问题

**Q：为什么需要这个功能？用户痛点是什么？**

> "最大的痛点是'查不准'——研究员用业务术语提问，但数据库里字段是英文缩写（如 `net_profit`、`net_profit_excluding`）。原来的系统靠向量相似度匹配，遇到语义相近的字段就会混淆。研究员拿到的数据可能是错的——比如查'扣非净利润'结果返回了'净利润'，差了好几个亿。这是 Chat-BI 系统最危险的失败模式：**SQL 语法对、执行不报错、结果看似合理但语义错**。"

**Q：怎么解决的？产品思路是什么？**

> "三层漏斗设计：
> 1. **向量粗召回**——先用 embedding 找 Top-10 候选字段（快但粗）
> 2. **规则过滤**——去掉数据类型不匹配的（比如用户要数值，去掉文本类型）
> 3. **LLM 消歧精选** ⭐ 我做的——把候选字段的**四个维度信息**（字段名 + 中文注释 + 数据类型 + 所在表名）给 LLM，让它像人一样选最对的那个
>
> 关键洞察：**光给字段名（`pe_ttm`）LLM 区分不了，加上中文注释（"TTM 市盈率 / 滚动 12 个月"）才能选对**。"

**Q：为什么不直接用最强的 LLM 端到端生成 SQL？**

> "两个原因：
> 1. **可解释性**——分层设计能看到每一步在做什么（召回对不对、过滤对不对、消歧对不对）；端到端 LLM 是黑盒
> 2. **准确率上限**——业界实测端到端 LLM 生成 SQL 在 200+ 表规模下准确率只有 10-31%；分层设计利用确定性引擎（规则+Calcite）兜底，LLM 只做'选择题'不做'填空题'，准确率可控"

**Q：你是怎么排查定位到瓶颈在 SchemaMapper，而不是 SQL 生成或执行环节的？**

> "端到端查询有多轮改写、SchemaMapper、S2SQL 生成、语义校正、物理 SQL 翻译五个环节。定位到 SchemaMapper 分三步：
>
> **第一步：用户反馈 + ELK 日志看链路**
> - 研究员反馈'查比亚迪扣非净利润，返回的是净利润的值'
> - 在 Kibana Discover 里按 `traceId` 串联看完整链路：改写后的 query → SchemaMapper 候选列表 → LLM 生成的 S2SQL → 最终物理 SQL
> - 发现 SchemaMapper 召回的候选里，正确字段（`net_profit_excluding`）在 Top-10 但排第 3，错误字段（`net_profit`）排第 1——**embedding 把语义相近的字段排到了前面**
>
> **第二步：分层验证确认瓶颈位置**
> - 把 SchemaMapper 输出的错误候选**手动替换成正确字段**，后续 Parser/Corrector/Translator 生成的 SQL 就对了
> - 这证明后续管道是确定性的——**不纠正映射错误**。SchemaMapper 错了全链必错
>
> **第三步：小样本量化归因（定方向，不建大评测集）**
> - 从 ELK 导出**最近一周约 1000 次查询**（日均 ~150 × 7 天）
> - 在失败 query 里**随机抽约 50 条**人工拆链路看——样本量不大，目标是**定方向**而不是做统计显著性
> - 约 **60%（约 30 条）错在 SchemaMapper**，约 25% 是 SQL 生成错误（时间条件/聚合函数），约 15% 是值链接失败（公司名没匹配到代码）
> - SchemaMapper 错误的**具体表现**（50 条里反复出现的几类）：
>   - **选错近义字段**：'净利润'被映射成'利润总额' / '扣非利润'被映射成'净利润'——embedding 把语义近的字段排到前面，规则过滤分不清
>   - **营收口径混淆**：'营收'被映射成'营业总收入'而不是'营业收入'——总营收含其他业务收入，业务含义不同
>   - **一字之差**：'市盈率'被映射成'市净率'——字面极近、业务完全不同
>   - **召回遗漏**：'ROE'没进候选——ROE 是衍生指标（净利润/净资产），不在物理表字段名里；'扣非利润'没进候选——用户简称 vs 库里全称差太远
> - 结论：**优化 SchemaMapper 是提升端到端准确率的最高 ROI 路径**
>
> **评测集怎么来的**（和上面 50 条归因是两件事）：
> - 端到端自建测评集**在 SchemaMapper 优化之前就已经有了**（T0 的 45% 就是用它测的）
> - SchemaMapper 专属测评集是从这套端到端测评集**一一对应倒推**出来的——同一批 200 条 query，Schema gold 只是端到端 gold 里的字段映射部分（详见 § 1.3 / § 2）"

### 1.3 指标类问题

**⚠️ 前置澄清：同一批 200 条 query，两套 gold，测的层次不同**

| 指标 | 测什么 | 评测集 | 用什么方法测 |
|------|-------|-------|-----------|
| SchemaMapper 映射准确率 **58%→81%** | **字段映射**（query → 多个语义元素 ID 是否全对）| **200 条 SchemaMapper 专属测评集**（从端到端集一一对应衍生）| Recall + Precision + **Exact Match（EM）** |
| 端到端查询准确率 **45%→72%→87%** | **完整链路**（NL → SQL → 执行结果是否对）| **200 条自建端到端测评集**（先于 Schema 优化就有，详见 § 2）| 执行准确率 + 五维度语义评分 |

> "两套评测集是**一一对应**的——同一批 200 条 query。端到端 gold 看整条链路；SchemaMapper gold 只是其中的**字段映射那一层**。数字不能混谈，但 query 不是两套无关的题。"

**Q：SchemaMapper 的 200 条专属测评集怎么来的？**

> "不是从线上失败 case 现抽的——线上那 50 条只够**定方向**。专属集是从**已有的端到端测评集倒推**出来的：
>
> 1. 端到端测评集在 SchemaMapper 优化前就已经建好（T0 的 45% 用它测）——人工 + 多大模型交叉验证标注的完整过程详见 § 2
> 2. 每条端到端标注里本来就包含正确的语义元素集合（`gold_elements`：METRIC / DIMENSION / ENTITY…）
> 3. SchemaMapper 专属测评集 = **抽出这 200 条的 `gold_elements` 层**，只评字段映射，不跑 SQL
>
> 所以：**200 = 200，一一对应**；SchemaMapper 测评是端到端测评的**单步显微镜**——端到端错了，可以下钻看是不是映射层错了。"

**Q：58%→81% 具体怎么测的？**

> "一条 query 如'比亚迪去年的营收和净利润'的 Schema gold 不是单个字段，而是**一个字段集合**（就是端到端标注里的 `gold_elements`）：
> - METRIC: 营业收入 (id=101)
> - METRIC: 净利润 (id=105)
> - ENTITY: 比亚迪 (id=201, value=002594)
> - DIMENSION: 报告期 (id=301, value=2025)
>
> SchemaMapper 也输出一个**选中字段集合**。评测用信息检索的三件套：
>
> | 指标 | 公式 | 含义 | 58%→81% 用的 |
> |------|------|------|-------------|
> | **Recall（召回率）** | gold 中被选中的数 / gold 总数 | '该选的都选了吗' | T0 ~70% → T1 ~90% |
> | **Precision（准确率）** | 选中的字段里对的数 / 选中总数 | '选的有多少是对的' | T0 ~65% → T1 ~88% |
> | **Exact Match（EM，精确匹配率）** | 选中集合 == gold 集合 → 1 分，否则 0 分 | '**全对了吗**' | **58% → 81%** ⭐ |
>
> 58%→81% 测的是 **EM（精确匹配率）**——200 条里选中字段集合和 gold 集合完全一致的比例。这是最严格的指标：多选一个、漏选一个都算 0 分。
>
> **为什么要同时看三个指标**：
> - Recall 低 → **召回阶段漏了**（embedding 词典不够，该选的字段没进候选）
> - Precision 低 → **选了不该选的**（LLM 消歧过度召回）
> - EM 低 → **整体集合不对**（任何一个错了或漏了就算不对）
>
> 混淆矩阵按 **元素对**统计——比如'净利润'被误选为'扣非净利润'多少次、'营收'被误选为'营业总收入'多少次。
>
> **关键**：58%→81% 是 SchemaMapper 层的 EM——不执行 SQL，只看字段映射集合。跟端到端评测（要执行 SQL 比对结果集）是完全不同的评测方法，但用的是同一批 query。"

**Q：测 SchemaMapper 时遇到了什么困难？**

> "三个困难：
> 1. **gold 不唯一**——有些 query 正确映射不唯一（如'PE'可以是 TTM 也可以是 Forward）。规则在端到端标注阶段就定了（'默认选 TTM，标为 ambiguous'），Schema 层直接继承
> 2. **召回和排序要分开看**——要区分'召回阶段漏了'（embedding 词典不够）和'召回到了但选错'（需要 LLM 消歧）。所以同时看 Top-K 命中率和 EM
> 3. **单步准 ≠ 端到端准**——Schema EM 到了 81%，端到端还可能在 SQL 生成/时间条件上翻车；反过来端到端偶尔也对（简单 query），但映射集合并不 EM——所以两套指标都要看"

**Q：怎么迭代的？迭代节奏是什么？**

> "**每周 2-3 次迭代**。每次改 prompt 或加规则后，5 分钟跑完全量 200 条 Schema 评测 + 输出混淆矩阵。看混淆矩阵定位问题——是召回阶段漏了（embedding 词典不够）还是消歧阶段选错了（prompt 需要调）。针对性修 → 再跑评测 → 看数字提升。如果掉了回滚——**评测集是迭代的护栏**。端到端准确率的变化用同一批 200 条的完整链路评测跟踪（详见 § 2）。"

### 1.4 Prompt 调优与 bad case

**初始 prompt（SuperSonic 原版）：**

> SuperSonic 的 `EmbeddingMatchStrategy.java` 里的 `LLM_FILTER_PROMPT`：
> ```
> #Role: You are a professional data analyst specializing in metrics and dimensions.
> #Task: Given a user query and a list of retrieved metrics/dimensions through vector recall,
> please analyze which metrics/dimensions the user is most likely interested in.
> #Rules:
> 1. Based on user query and retrieved info, accurately determine metrics/dimensions user truly cares about.
> 2. Do not return all retrieved info, only select those highly relevant to user query.
> 3. Maintain high quality output, exclude metrics/dimensions irrelevant to user intent.
> 4. Output must be in JSON array format, only include IDs from retrieved info, e.g.: ['id1', 'id2']
> 5. Return JSON content directly without markdown formatting
> ```

> "**原版的问题**：只让 LLM 看 `retrievedInfo`（整体 JSON），没有显式引导它关注 COMMENT/中文注释。Reddit r/LangChain 社区的共识是：**'hallucinated columns 问题 rarely about retrieval, it's that the LLM only sees column names but not what they mean'**——LLM 会退化为字面匹配。"

**踩过的 4 个坑（按时间顺序）和修复：**

**坑 1：LLM 忽略 COMMENT，只看字段名（最大 bad case 来源）**

> - **现象**：用户问'扣非利润'，候选 rank 1 是'净利润'（COMMENT='合并口径净利润'），rank 2 是'扣非净利润'（COMMENT='扣除非经常性损益后的净利润'）。LLM 选了 rank 1——**只看字段名字面相似度，没看 COMMENT 里的'扣除非经常性损益'**
> - **业界对照**：LangChain GitHub Issue #5158 提出同样的观察——'Column names do not describe perfectly well what they contain. If the SQL agent can consider the table and column comments, it will help.'
> - **修复**：在 prompt 里加显式引导——'**优先对比每个候选的 name + description/COMMENT + dataType + 所属表，不要只看字段名做字面匹配**'
> - **效果**：这类 case 准确率从 ~40% 提升到 ~75%

**坑 2：过度自信——LLM 给的理由是事后合理化，不能作为正确性的证据**

> - **现象**：LLM 选了错误字段后还给了一段'看似合理的推理'——如'扣非利润最接近净利润的概念，因为扣非是一种净利润的衍生'。但实际选错了
> - **业界对照**：FinVerBench 论文（arXiv 2506）发现 GPT-4.1 在财务校验任务上 **95.3% 假阳率**——它把 41 个正确的报表全部判错，每一个都给了'看似合理的计算理由'。论文结论：**LLM 给的'理由'不能作为正确性的证据**
> - **评测 vs 运行的区分**（保持上下文一致的关键）：
>   - **评测/调试时**：prompt 里要求 LLM 输出 reasoning 字段——**保留**，用于人工分析 bad case（理解 LLM 为什么选错，是忽略 COMMENT 还是字面匹配）。JSON 格式里的 `llm_reasoning` 就是这个用途
>   - **实际运行时**：reasoning **不参与下游决策**——Corrector/Translator 看不到 LLM 的理由，只用 LLM 选出的字段 ID 列表。理由只是给人看的辅助信息，不是系统的判断依据
> - **修复**：不在运行时依赖 LLM 的理由做正确性判断。转而用**执行结果反向校验**——跑 SQL 后检查数值是否符合 FinVerBench 四类约束（Arithmetic / Cross-Statement / YoY / Magnitude），不齐就触发兜底
> - **效果**：评测时靠 reasoning 定位 bad case，运行时靠确定性校验做闭环——**不依赖 LLM 自评**

**坑 3：候选太多时 LLM 注意力首尾偏置**

> - **现象**：Top-10 候选拼进 prompt 时，中间 rank 4-7 的候选容易被 LLM 忽略——它倾向于选 rank 1 或 rank 10 附近的
> - **业界对照**：学术界 RSL-SQL（arXiv 2411.00073，Spider leaderboard SOTA）建议 Top-K=5 而非 10
> - **修复**：把 Top-10 限制为 Top-5，给每个候选定稳定编号（#C1, #C2...），prompt 里要求 LLM '逐个评估每个候选的 COMMENT 与 query 的匹配度'
> - **效果**：候选数从 10 降到 5 后，中间候选被忽略的问题基本消除

**坑 4：JSON 格式不稳定**

> - **现象**：原版 prompt 要求 JSON 输出，但实际约 5-15% 的输出会带 markdown fence（```json）、寒暄（'Sure, here are...'）、或 Python 集合格式（`{'id1'}` 而非 JSON `["id1"]`）
> - **业界对照**：业界实测纯 prompt 要求 JSON 只能拿到 80-95% 稳定性；Google Cloud 六大失败模式之一就是'Messy Output'
> - **修复**：① 开启 LLM 的 `json_format=true`（structured output）；② 加 callback 后处理用 regex 提取 `[...]` 段做兜底；③ parse 失败时 retry-with-error-feedback（把错误信息塞回 prompt 重试 1 次）
> - **效果**：格式失败率从 ~12% 降到 <2%

**调整后的 prompt（最终版本要点）：**

```
#Role: You are a data analyst experienced in financial data semantics.
#Task: 从向量召回的候选字段中，选出与用户 query 最匹配的字段。

#候选字段（已按 embedding 相似度排序）：
#C1: name=净利润, COMMENT=合并口径净利润（税后）, dataType=REAL, 表=利润表
#C2: name=扣非净利润, COMMENT=扣除非经常性损益后的净利润, dataType=REAL, 表=利润表
#C3: name=利润总额, COMMENT=税前利润总额, dataType=REAL, 表=利润表
...

#Rules:
1. **优先对比每个候选的 COMMENT 和 dataType，不要只看字段名做字面匹配**
2. 逐个评估每个候选的 COMMENT 与用户 query 的语义匹配度
3. 若有 2 个以上候选语义高度接近无法区分，返回全部（不要强行二选一）
4. 输出 JSON 数组，只含 ID，如: ["#C2"]
```

> "关键变化：① 显式强调 COMMENT 优先；② 候选编号 + 逐个评估；③ 不确定返回多个；④ 限制 Top-5。"

### 1.5 诚实边界

**LLM 消歧显著解决的问题（58%→81% 的 +23pp 主要来自这几类）：**

> 1. **语义相近但业务含义不同的消歧** ⭐ 最大贡献（约 +12pp）
>    - 之前 embedding 把'净利润'、'利润总额'、'营业利润'排到相似度前 3，规则过滤分不清
>    - LLM 看到 COMMENT 里的'税前利润总额' vs '税后合并口径净利润'后能正确区分
>    - 这类 case 从 ~30% 准确率提升到 ~85%
>    - **业界对标**：FinStat2SQL（arXiv 2506.23273）在金融报表 Text2SQL 里也用'向量召回 + LLM 二次判断'的两阶段消歧处理'Net Income (IFRS) vs Profit After Tax (VAS)'的术语差异——和我们的方案是同一个套路
>
> 2. **同义词 / 别名识别**（约 +6pp）
>    - 用户说'营收'，数据库里叫'营业收入'——在语义层注册别名后召回到了，LLM 理解'营收'='营业收入'选对了
>
> 3. **衍生指标识别**（约 +5pp）
>    - 用户说'ROE'，ROE 是衍生指标（净利润/净资产）不在物理表里——在语义层 measures 定义后 LLM 能选出来

**剩余 19% 的错误 case 归因分析（按严重程度排序）：**

> 1. **注释缺失导致 LLM 盲猜**（约 8%，最大瓶颈）
>    - 约 25% 的历史遗留字段没有中文注释（如 `fin_exp_intan` 只有英文名）
>    - LLM 只能靠字段名 + 数据类型猜——'fin_exp_intan'是'无形资产摊销'还是'金融支出'？猜不对
>    - **业界对标**：Reddit r/LangChain 共识——'column names do not describe perfectly well what they contain'；WrenAI 的方案是强制在 MDL 里定义每个字段的 description，我们部分字段缺失 description
>    - **改进**：正在推注释补全，优先补高频字段
>
> 2. **低频实体值不在词典里**（约 4%）
>    - HanLP 词典每天从数据库导 top 10 万高频值，但有些小众公司名/行业名排在 10 万以外
>    - **改进**：白名单机制 + 降低词典阈值
>
> 3. **LLM 过度自信 + 格式不稳定**（约 3%）
>    - FinVerBench 论文实测 GPT-4.1 在财务校验上 95.3% 假阳率——LLM 会给出'看似合理的理由'但其实选错了
>    - EMNLP 2025 论文（arXiv 2411.16742）证实直接让 LLM 给置信度**系统性偏高**，建议用 token-level 置信度做 rescaling
>    - **我们的应对**：不在 prompt 里让 LLM 自评置信度，改用执行结果反向校验
>
> 4. **跨主题域歧义**（约 2%）
>    - 'PE'在金融是市盈率，但在行为实验域可能是心理量表维度缩写
>    - **改进**：多轮改写补全主题域上下文
>
> 5. **隐式时间 / 多指标歧义**（约 2%）
>    - '去年'是自然年还是财年？'利润'是净利润、利润总额还是归母净利润？
>    - **改进**：返回多个候选让用户选

**评测集本身的短板：**
> - 200 条（与端到端同一批）不能完全覆盖线上长尾场景。业界如 Spider 2.0 有几千条
> - 目前只测了金融经济数据，行为实验数据还没进评测集
>
> **改进路线**：补注释 + 与端到端集同步扩到 500 条 + 引入 FinVerBench 四类约束做执行结果反向校验 + 行为实验数据进评测。"

## 2. 查询记忆复用（72% → 87%，800+ 条）

### 2.1 30 秒概括

> "SchemaMapper 优化完后端到端卡在 72%——字段常选对，Parser 仍因 **Few-shot 结构不对齐** 翻车。业界（DIN-SQL / DAIL-SQL）已证明 Text2SQL 高度依赖示范质量与示例选择；我们原来是 JSON **写死静态范文**（演示域『超音数』），对金融题甚至变成有害示范（如把『去年』教成滚动 365 天）。记忆复用：成功 SQL 过审入库，Parser 按相似度动态召回同构范文。端到端 72%→87%；Schema 已对子集上 Parser 条件准确率约 75%→90%。核心不是『存 SQL』，是 **按题选对示范，而不是堆死示例**。"

### 2.2 功能实现类问题

**Q：为什么会想到做记忆复用？最核心的痛点是什么？原来什么样？不做的替代方案呢？**

> "**核心痛点：Text2SQL 的准确率高度依赖 Few-shot 范文的『结构相似度』，而原来用的是对所有题一视同仁的静态范文——结构不对齐时，范文不但帮不上忙，还会教坏。**
>
> **产品价值（顺带说清『为什么值得做』）**：
> 1. 研究员查询**结构大量重复**（只换实体/时间），同构范文收益高
> 2. T1 后瓶颈在 **Parser**——字段对了仍可能时间/聚合写错
> 3. 成功经验要在 **同一 Agent 内跨用户沉淀**——甲做对的题，乙直接受益
>
> **业界背景（为什么必须较真 Few-shot）**：
> - DIN-SQL（NeurIPS 2023）：合适的 in-context 示例相对简单 few-shot 大约 **+10pp** 量级
> - DAIL-SQL：few-shot 相对 zero-shot 可到 **+11pp**；**精选示例显著优于随机示例**
> - 静态写死 demonstration 在范文与当前题差距大时会出现 **retrieval bias**——LLM 被不相关示例带偏
> - 该选的是 **SQL 意图/结构相近** 的题，而不是表名、公司名碰巧相似的题
>
> 结论：**Parser 不是缺『几条 SQL』，缺的是『跟当前题同构的成功写法』。**
>
> **原来的状态（T1：Schema 已优化，记忆库未上）**：
> - `#Exemplars` 主要靠配置里的**静态 Few-shot**（如 `s2-exemplar.json`）
> - 内容是开源演示域：『超音数近 12 个月访问人数按部门』等
> - **所有金融 query 共用这一小撮范文**——和真实题型的 SQL 骨架对不上
>
> **能说明痛点的例子（结构错位 / 有害示范）**：
>
> | 当前用户问题（需要的 SQL 骨架） | 静态范文在教什么 | 实际翻车 |
> |-------------------------------|-----------------|---------|
> | 「A 股去年 ROE 排名前 10」→ `ORDER BY` + `LIMIT` + 衍生指标 | 『查某用户访问次数』→ 简单 `WHERE` | 学不会排序/截断 |
> | 「比亚迪去年营收」→ 自然年区间 | 『超音数近 12 个月』→ **滚动 365 天** | **照着写成滚动窗口（有害示范）** |
> | 「比亚迪与宁德时代营收对比」→ `IN` / 多实体 | 单实体等值过滤 | 结构迁不过去 |
>
> **如果不做动态记忆，替代方案及为何否掉**：
>
> | 替代方案 | 做法 | 为什么不够 |
> |---------|------|-----------|
> | **一直堆静态 Few-shot** | 每种骨架手写进 JSON | 滞后线上；堆数量 ≠ 选得准；token/维护双爆 |
> | **每次 prompt 塞尽量多范文** | 几十上百条全进 `#Exemplars` | 超上下文；噪声大 |
> | **微调专用模型** | 用成功 SQL 微调 | 成本高、迭代慢 |
> | **动态检索同构范文（我们选的）** | 成功过审 → 向量库 → 按 query 召回注入 | 对齐 example selection；范文跟业务长 |
>
> **一句话**：业界证明 Text2SQL 拼的是 **选对示范**；我们原来是 **写死示范**；记忆复用是把『做过对的同构题』动态选进 Parser prompt。"

**Q：记忆复用作用在链路的哪一步？怎么起作用的？和 SchemaMapper / 相似推荐什么关系？**

> "准确落点是 **Parser 阶段**（Semantic Parser / `NL2SQLParser` → `OnePassSCSqlGenStrategy`）：
>
> ```
> 多轮改写 → SchemaMapper（字段映射 → 产出本轮 Schema）
>         → 【Parser：生成 S2SQL ← 记忆复用注入 #Exemplars】
>         → Corrector → Translator → SQL 执行
>                                      ↓
>                              成功且过审 → 写入记忆库
>                                      ↓（异步另一用途）
>                              相似问题推荐只取 question 文案展示
> ```
>
> **读路径（复用，同步）**：
> 1. SchemaMapper 选好字段后进入 Parser
> 2. 向量召回候选（最多 10）→ 筛成 few-shot（本仓库 5）→ 注入 `#Exemplars`
> 3. LLM 照着同构成功题写当前 S2SQL
>
> **写路径（沉淀）**：执行成功 → PENDING → LLM/人审 → ENABLED 才可被召回
>
> **和另外两个模块的分工**（常被追问，一次讲清）：
>
> | 模块 | 链路位置 | 给谁用 | 取什么 |
> |------|---------|--------|--------|
> | **SchemaMapper** | 映射阶段 | 系统选字段 | metric/dimension → 拼进 Parser 的 `{{schema}}` |
> | **记忆复用** | **Parser 阶段** | 给 LLM 当范文 | `(Question, Schema, SideInfo, SQL)` → `{{exemplar}}` |
> | **相似推荐** | **Parse 之后异步**（不堵主解析） | 给人点（行为实验期尤甚） | 只展示历史 `question`；**与记忆复用共用向量库**；写进该 `queryId` 的 `similarQueries`，前端展开再读 |
>
> **一句话**：SchemaMapper 选对字段；记忆复用教 Parser 写法；相似推荐把成功问法露给人——实验运维反复查时最省打字。"

**Q：怎么注入到 prompt 的？完整 prompt 长什么样？10 条候选怎么筛成 5 条？**

> "Parser 模板四个占位符：`{{exemplar}}` / `{{question}}` / `{{schema}}` / `{{information}}`（模板中英对照见下）。
>
> **模板原文（中英对照）**：
>
> ```
> #Role: You are a data analyst experienced in SQL languages.
> #角色：你是一位精通 SQL 的数据分析师。
>
> #Task: You will be provided with a natural language question asked by users,
> please convert it to a SQL query so that relevant data could be returned
> by executing the SQL query against underlying database.
> #任务：把用户自然语言问题转成可执行 SQL。
>
> #Rules: / #规则：
> 1. 列名和取值必须出现在 Schema 里，禁止幻觉。
> 2. 时间范围用 > < >= <= 写出。
> 3. Question 没提时间就不要擅自加时间条件。
> 4. 不要用函数推算日期区间。
> 5. 嵌套聚合用 WITH。
> 6. AS 别名用下划线包起来。
> 7. 别名语言与 Question 一致。
>
> #Exemplars: {{exemplar}}
> #Query: Question:{{question}},Schema:{{schema}},SideInfo:{{information}}
> ```
>
> **条数配置**：
>
> | 配置项 | 本仓库 | 含义 |
> |--------|--------|------|
> | `exemplar-recall.number` | **10** | 向量召回**候选池**上限 |
> | `few-shot.number` | **5**（参数默认 3） | **真正写入 `#Exemplars` 的条数** |
>
> **10 → 5 具体怎么筛（`PromptHelper.getFewShotExemplars`）**：
>
> 1. **组候选池（≤10）**
>    - 先放入本轮从记忆库召回的 **dynamicExemplars**（Agent 记忆）
>    - 若不足 10，再用系统预设 exemplar 集合按当前 query 向量补齐
> 2. **按相似度拆两桶**
>    - `same`：similarity **> 0.989**（几乎同题，必须进 prompt）
>    - `noSame`：其余候选
> 3. **砍掉过弱的尾部**（候选明显多于 few-shot 时）
>    - 对 `noSame` 按 similarity **升序**排序，丢掉最低的一截，只保留相对更像的一段（避免最差范文进 prompt）
> 4. **凑满 few-shot.number（5）条**
>    - 有 `same`：全部保留 `same`，再用 `noSame` 补到 5
>    - 无 `same`：从 `noSame` 取 5 条，但**强制保留相似度最高的那 1 条**（shuffle 后若被挤掉会换回来）
> 5. 若开启 self-consistency 多次推理，每一轮各自按上面规则组一份（本仓库 self-consistency=1，通常只组一次）
>
> **面试口径**：先召回最多约 10 条 → 近重复必留、最像必留、弱相似丢掉 → **最终注入约 5 条**。
>
> **记忆怎么塞进 `{{exemplar}}`**：每条一行 `Question:...,Schema:...,SideInfo:...,SQL:...`，多条拼接。范文是历史轮四元组；当前轮 Schema 在 `#Query`。
>
> **填好后的完整 prompt 示例**（问「宁德时代去年的营收」）：
>
> ```
> #Role: ...
> #Task: ...
> #Rules: 1....7....
> #Exemplars:
> Question:比亚迪去年的营收,Schema:...,SideInfo:CurrentDate=[2026-07-30],SQL:SELECT SUM(营业收入) ... WHERE 公司名称='比亚迪' AND 报告期 >= '2025-01-01' AND 报告期 <= '2025-12-31'
> Question:茅台去年营业收入,Schema:...,SideInfo:...,SQL:SELECT SUM(营业收入) ... WHERE 公司名称='贵州茅台' AND ...
> （最多再拼到约 5 条）
> #Query: Question:宁德时代去年的营收,Schema:...(本轮 SchemaMapper 产出),SideInfo:CurrentDate=[2026-07-30]
> ```
>
> **要点**：不是贴一句历史 SQL，而是 **四元组范文**；教写法，不替映射。"

**Q：LLM 自动审核怎么做的？prompt 和判定标准是什么？**

> "写路径的闸门在 `MemoryReviewTask`（定时约 60s 扫一遍）。**开源实现是 POSITIVE / NEGATIVE 二分类，不是打 1–5 分。**
>
> **触发与范围**：
> - 仅处理：尚未被 LLM/人审过的记忆（`llmReviewRet`、`humanReviewRet` 皆空）
> - Agent 需开启 memory review；对应 ChatApp `MEMORY_REVIEW` 需 enable
>
> **审核 prompt（代码 `MemoryReviewTask.INSTRUCTION`，中英对照）**：
>
> ```
> #Role: You are a senior data engineer experienced in writing SQL.
> #角色：你是一位擅长写 SQL 的资深数据工程师。
>
> #Task: You will be provided with a user question and the SQL written by a junior engineer,
> please take a review and give your opinion.
> #任务：下面是用户问题和初级工程师写的 SQL，请你评审并给出意见。
>
> #Rules:
> 1.ALWAYS follow the output format: opinion=(POSITIVE|NEGATIVE),comment=(your comment).
>   输出必须是：opinion=(POSITIVE|NEGATIVE),comment=(你的评语)
> 2.NO NEED to check date filters as the junior engineer seldom makes mistakes in this regard.
>   不必重点抠日期过滤（默认初级工程师在日期上较少出错）——注意：这是开源默认；我们业务上仍会靠人审兜时间口径问题。
>
> #Question: {用户问题}
> #Schema: {当时的 dbSchema}
> #SideInfo: {sideInfo}
> #SQL: {s2sql}
> #Response:
> ```
>
> **判定标准与后续状态**：
>
> | LLM 输出 | 含义 | 系统动作 |
> |---------|------|---------|
> | `opinion=POSITIVE` | 认为该 SQL 可作范文 | **直接 ENABLED**，写入向量库，可被 Parser 召回 |
> | `opinion=NEGATIVE` | 认为有问题 | **保持 PENDING**，进人工审核队列；人审通过才 ENABLED，否决则 DISABLED |
> | 解析失败（格式不对） | 正则抽不出 opinion | 本轮不改状态，下个调度周期可能重试 |
>
> **人审怎么接**：数据工程师/我看 PENDING；人审与 LLM 冲突时 **以人审为准**，冲突 case 进评测集回归。
>
> **和『语法成功就入库』的区别**：执行成功只进入 PENDING；**只有 POSITIVE（或人审通过）才能当 Few-shot**——否则错 SQL 会污染 `#Exemplars`。
>
> **诚实边界**：开源 prompt 默认『不重点查日期』，和金融场景『去年=自然年』的痛点不完全匹配——所以人审兜底仍然必要；若重做会把时间口径、字段是否覆盖用户意图写进 Rules。"

**Q：人工审核是谁在做？怎么保证效率？800+ 条是怎么攒出来的？有没有冷启动？**

> "**30 秒答法**：人审是我 + 数据工程师，**每周集中一次**；平时靠 LLM 自动 POSITIVE 放行。简历 **800+** = **冷启动 200**（4 个 Agent 分摊）+ **4–7 月线上约 600**（约 200/月，流量稳，不讲爬坡）。冷启动是为了上线就能召满约 5 条同构范文；飞轮看新题过审率，不是每次查询都变一条记忆。
>
> ---
>
> **① 谁在审、怎么保证效率**
>
> | 角色 | 节奏 | 做什么 |
> |------|------|--------|
> | **LLM** | 持续（约每 60s 扫 PENDING） | `POSITIVE` → 当场 ENABLED；`NEGATIVE` → 等人 |
> | **人工** | **每周一次**（约 0.5～1 小时） | 清 NEGATIVE/格式失败；**抽检**部分 POSITIVE；冲突进评测集 |
>
> - 人审单条 **30 秒～1 分钟**；周队列大约十几～三十条 NEGATIVE + 少量抽检
> - 效率靠三件事：**LLM 先筛**、**同 question 去重**、**只收 LLM_S2SQL 成功题**（规则 SQL 不入库）
> - 人不盯盘——日常放行交给 LLM，人做周批次兜底
>
> ---
>
> **② 800+ 怎么来的（构成 + 节奏）**
>
> - **4 月初上线** → 到 7 月约 **3 个月**
> - **800+ ENABLED** = 冷启动种子 **200** + 线上沉淀约 **600**
> - 月净增约 **200**（周约 **50**）；日均查询 ~150 稳定，**不讲爬坡**
>
> | 时点 | 净增 | 累计 |
> |------|------|------|
> | 4 月初 | 种子 +200 | 200 |
> | 4 / 5 / 6 月 | 各 +200 | 400 → 600 → 800 |
> | 7 月 | 少量补录 | **800+** |
>
> ---
>
> **③ 有没有冷启动？200 怎么分到 Agent？和 prompt 里 5 条什么关系？**
>
> **有，必须有。** 库空着时只能吃静态『超音数』范文，金融/实验题会被带偏。
>
> **两层数字不要混**：
>
> | 层级 | 条数 | 含义 |
> |------|------|------|
> | **每次注入 prompt** | **~5**（`few-shot.number`） | 业界甜点：DAIL-SQL（Gao et al., VLDB 2024 / arXiv:2308.15363）在 Spider-dev 上 1/3/5-shot 执行准确率约 80.2%→81.7%→82.4%，再往后边际变小 |
> | **每个 Agent 的库** | **远大于 5**（我们冷启动约 **40～60**） | 库要覆盖多种 SQL 骨架，才能**随时召到** 5 条同构范文——**40～60 是我们的工程定标，不是某篇论文的「飞轮阈值」** |
>
> **文献怎么说「记忆条数 vs 收益」（勿与 40～60 混为一谈）**：
>
> - 出处：Cook, Patel, Vellaichamy, et al.（JPMorganChase），***Continual Learning of Domain Knowledge from Human Feedback in Text-to-SQL***，[arXiv:2511.10674](https://arxiv.org/abs/2511.10674)（2025-11），§4.3 / **Figure 4**
> - 原文要点：在 BIRD Dev 上画了「memory store 里 online instances 数量 → 执行准确率」曲线；**非 procedural 的 memory baseline 在前约 10～20 条实例时早期学习更快**（faster initial learning within the first 10–20 instances）；实例继续增多后，更复杂的 Procedural Agent 才反超
> - 因此面试应说：**文献支持『同域记忆从大约十几～二十条起就开始有可见收益』**；我们定 **单 Agent 冷启动 40～60**，是在「已有早期收益」之上再留余量，保证多种骨架（自然年/排名/多实体/JOIN…）都能召满约 5 条，**不是论文写了 40～60**
>
> **4 个 Agent × 种子 ≈ 200**（按主题域隔离，飞轮在 Agent 内转）：
>
> | Agent | 种子 | 为何这个量 |
> |-------|------|-----------|
> | 公司研究 | **~60** | 问得最多：单/多指标、自然年、多实体、排名 |
> | 绿色经济 | **~50** | 跨表与口径相对多 |
> | 经济研究（宏观） | **~50** | 时间序列、同比环比 |
> | 行为实验 | **~40** | 表少、骨架少 |
>
> 种子来自 ELK 高复用成功题 + 端到端评测已验证写法，**上线前集中人审**后批量 ENABLED；系统静态 exemplar 仍作召回不足时的兜底。
>
> ---
>
> **④ 转化率（成功查询 → ENABLED）**
>
> 周漏斗（流量稳定时）：
>
> ```
> 周查询 ≈ 1050（150×7）
>   → 成功且 LLM_S2SQL ≈ 700～800
>   → 去重后新 PENDING ≈ 80～100（同问已有 ENABLED 则跳过）
>   → 新 ENABLED ≈ 50/周
> ```
>
> | 口径 | 约值 | 一句话 |
> |------|------|--------|
> | 全量查询 → 新 ENABLED | **~5%** | 低是正常的——大量重复不问不入库 |
> | 新 PENDING → ENABLED | **~50%～60%** | 才是闸门过审率 |
>
> **金句**：飞轮看『新结构过审』，不看『每次查询都变记忆』。
>
> ---
>
> **⑤ Agent 隔离（顺带答清）**：集合 `memory_{agentId}`；同 Agent 多用户共享范文；跨 Agent 不召回。
>
> **收束**：人周审 + LLM 日审；800 = 200 种子（4×~50，为召满 5 条）+ 3×200 月增量；转化报漏斗不要报单点。"

### 2.3 端到端测评集与指标

**⚠️ 时间线前提：端到端测评集先于 SchemaMapper 优化存在**

| 阶段 | 端到端准确率 | SchemaMapper EM | 说明 |
|------|------------|-----------------|------|
| **T0**（加入时） | **45%** | 58% | 端到端测评集已就绪；Schema 专属集从它倒推 |
| **T1**（Schema + LLM 消歧后） | **72%**（+27pp） | **81%** | 同一批 200 条 query 复测 |
| **T2**（记忆库上线后） | **87%**（+15pp） | 81% | Schema 已优化完，+15pp 全是记忆库 |

**Q：端到端 200 条测评集怎么构建的？**

> "这是**整条问数链路的基准集**，在我做 SchemaMapper 优化之前就建好了——T0 的 45% 就是它测出来的。为什么是 200 条？因为**人工一天深度标注的上限大约就是 200 条**——每条要定 query、字段映射、期望结果口径，快的 1 分钟、慢的几分钟。
>
> **覆盖范围**：金融经济三个子域——绿色经济、公司研究、经济研究
>
> **难度分布**（200 条按此比例，Schema 专属集继承同一分布）：
>
> | 难度 | 占比 | 条数 | 具体测什么 | 示例 query |
> |------|------|------|----------|-----------|
> | **简单单表** | 40% | ~80 | 单张表内查某个指标 + 单个实体 | "比亚迪去年的营业收入是多少？" |
> | **多表关联** | 35% | ~70 | query 涉及 2-3 张表的字段 | "比亚迪去年的营收和资产负债率" |
> | **复杂聚合** | 25% | ~50 | 排名/分组/筛选 + 衍生指标（ROE/毛利率） | "A 股去年 ROE 排名前 10 的公司" |
>
> **为什么要分难度**：不同难度的失败环节不同——简单单表错多在映射排序；多表关联错多在召回遗漏；复杂聚合错多在衍生指标或 SQL 生成。**按难度分层才能定位该改哪一层**。
>
> 标注在人工初标基础上，补了两步验证：
>
> **第一步：多大模型交叉验证**
> - 用 qwen-plus 和 deepseek 两个 LLM 独立对 200 条做字段映射 + 结果口径预测
> - 两个 LLM 一致 + 人工认可 → high-confidence（约 70%）
> - 两个 LLM 不一致 → 人工逐条复审（约 30%）——这些往往是真正的语义消歧难点
> - 标注规则文档化——如'PE 默认选 TTM 而不是 Forward'、'营收默认指营业总收入而不是营业收入净额'
>
> **第二步：固化评测集**
> - 输出标准 JSON：每条同时带**端到端 gold**（期望结果口径 / 关键约束）和**字段映射 gold**（`gold_elements`）
> - SchemaMapper 专属测评集 = **抽出同一批的 `gold_elements` 层**——一一对应，不是另抽一套题"

**端到端标注 JSON 示例：**

```json
{
  "id": 42,
  "query_text": "比亚迪去年的营收和净利润",
  "gold_elements": [
    {"type": "METRIC", "id": 101, "name": "营业收入", "bizName": "revenue"},
    {"type": "METRIC", "id": 105, "name": "净利润", "bizName": "net_profit"},
    {"type": "ENTITY", "id": 201, "name": "比亚迪", "value": "002594"},
    {"type": "DIMENSION", "id": 301, "name": "报告期", "value": "2025"}
  ],
  "gold_answer": {
    "entity": "比亚迪",
    "period": "2025",
    "metrics": ["营业收入", "净利润"],
    "result_check": "两列数值量级分别为百亿级营收、十亿~百亿级净利润；报告期为 2025 年报/年累计"
  },
  "difficulty": "medium",
  "domain": "corporate_finance",
  "ambiguous": false,
  "confidence": "high",
  "notes": "多指标查询，营收和净利润都在利润表"
}
```

```json
{
  "id": 78,
  "query_text": "比亚迪的扣非利润",
  "gold_elements": [
    {"type": "METRIC", "id": 106, "name": "扣非净利润", "bizName": "net_profit_excluding"},
    {"type": "ENTITY", "id": 201, "name": "比亚迪", "value": "002594"}
  ],
  "gold_answer": {
    "entity": "比亚迪",
    "metrics": ["扣非净利润"],
    "result_check": "返回扣非净利润而非合并净利润；数值应与净利润接近但通常更低"
  },
  "difficulty": "hard",
  "domain": "corporate_finance",
  "ambiguous": true,
  "confidence": "low",
  "notes": "用户说'扣非利润'——是'扣除非经常性损益后的净利润'的简称，靠别名匹配"
}
```

> "每条标注包含：query 原文、`gold_elements`（给 SchemaMapper 用）、`gold_answer`（给端到端执行核对用）、难度、主题域、是否歧义、置信度、备注。`confidence=low` 是两个 LLM 不一致后人工裁定的——往往是真正难点。
>
> **和 § 1 的关系**：§ 1 线上抽 50 条失败只负责**发现瓶颈**；真正回归用的 200 条是这套端到端集；Schema 专属集是它的字段映射切片。"

**Q：45% → 72% → 87% 怎么测的？**

> "全程用**同一套 200 条端到端测评集**，保证纵向可比：
> - **评测方式**：一条 query 进去，一个答案出来，**中间不允许任何人工干预**（无 human in the loop）
> - **判定**：执行结果是否满足 `gold_answer` 的口径约束 + 五维度语义评分（字段是否对、实体是否对、时间是否对、聚合是否对、数值量级是否合理）
> - 这跟线上不同——线上用户可以改 query、选候选字段、纠错反馈，所以线上体验准确率会高于 87%。我们的 45%/72%/87% 测的是**系统独立能力**
>
> **和 SchemaMapper 200 条的关系**：同一批 query。Schema 层只比对 `gold_elements`（不跑 SQL）；端到端跑完整链路比对答案。所以可以说 Schema 测评是端到端测评的**一部分 / 单步显微镜**。"

**Q：为什么简历/对外讲的是端到端指标，而不是 Parser 环节指标？Parser 本身提升了多少？**

> "**对外讲端到端，是因为记忆复用的产品价值是『整题答对了没有』；对内下钻才看 Parser。**
>
> **为什么主指标用端到端（72%→87%），而不是只报 Parser**：
> 1. **验收口径**：研究员只关心答案对不对，不关心中间 S2SQL 字符串是否和 gold 逐字相同
> 2. **简历一致性**：记忆库写在『端到端准确率』上；SchemaMapper 才单独报映射 EM
> 3. **T1 之后瓶颈已转移到 Parser**：Schema 已到 81%，再优化映射边际变小；记忆库上线后端到端 +15pp，**几乎都可以归因到 Parser 写法变好**（Schema 数字没变）
> 4. **Parser 单独 gold 更贵**：要标「标准 S2SQL」比标字段集合难（写法不唯一：等价 SQL 很多），所以日常回归以端到端为主，Parser 做**条件切片**分析
>
> **Parser 环节怎么报（面试深挖时用）**：
>
> 在同一套 200 条上，取 **SchemaMapper EM 已正确** 的子集，看最终答案是否对——这近似「映射对了的前提下，Parser（+Corrector/执行）有没有写对」：
>
> | 阶段 | 条件（Schema EM=对）下的成功率 | 说明 |
> |------|-------------------------------|------|
> | **T1**（静态 Few-shot） | 约 **75%** | 字段对了仍常栽在时间/同比/换实体 |
> | **T2**（动态记忆） | 约 **90%**（**+15pp**） | 同结构成功题被召回当范文 |
>
> 和端到端 +15pp（72%→87%）**量级对齐**——因为 T1→T2 Schema 没变，端到端提升主要由 Parser 条件准确率抬升贡献。
>
> **诚实边界**：75%→90% 是端到端集上的**条件切片**，不是另建一套 Parser 逐字 EM 评测集；若面试官追问『有没有 S2SQL Exact Match』，答：没做严格字符串 EM（等价 SQL 太多），用的是执行结果/语义口径，和端到端判定一致。"

**Q：记忆库的 +15pp 贡献怎么拆解？**

> "时间线很清晰（T0→T1→T2），且端到端数字都来自同一套 200 条：
> - **T0→T1**：SchemaMapper 优化（58%→81%），端到端 45%→72%（+27pp 是 SchemaMapper 的贡献）
> - **T1→T2**：记忆库上线，端到端 72%→87%（**+15pp 全是记忆库的贡献**，因为 SchemaMapper 在 T1 已经优化完）；Parser 条件准确率同步约 75%→90%
>
> 所以记忆库单独贡献端到端 15pp，SchemaMapper 单独贡献 27pp——**SchemaMapper 对端到端的贡献反而比记忆库大**；但记忆库是 Schema 优化之后的**下一瓶颈解锁**。"

**Q：测评集构建过程中遇到了什么困难？**

> "三个困难：
> 1. **gold answer 口径不唯一**——有些 query 正确映射/结果不唯一（如'PE'可以是 TTM 也可以是 Forward）。定义了'默认选 TTM，评测里标注为 ambiguous'
> 2. **端到端判定比字段映射更难**——字段对了 SQL 还可能时间条件错；要同时标 `gold_elements` 和结果口径约束
> 3. **评测集偏小**——200 条不能完全覆盖线上长尾。业界如 Spider 2.0 有几千条。后续在扩——但宁可 200 条标得牢，也不要几千条标得飘"

**Q：记忆库有没有帮倒忙的时候？**

> "有——这是真实的风险。如果记忆库里有一条**看似成功但实际错误**的 SQL，被召回后做 few-shot 会引导 LLM 犯同样的错。我们遇到过：
> - 某条 SQL 的时间范围识别错了（把'去年'理解成最近 365 天而不是自然年）
> - 被召回后，后续类似的 query 也跟着错
>
> 兜底机制：(1) LLM 评审 + 人工审核尽量挡住错误 SQL 入库；(2) 如果用户在线上反馈'答错了'，我们会回溯召回的记忆库 SQL，发现错的就标记为 DISABLED。"

### 2.4 诚实边界

> "记忆库目前没有**淘汰机制**——只进不出。长期来看这有两个问题：
> 1. **语义层改了之后旧 SQL 过时**（比如字段改名了）
> 2. **低质量记忆稀释高质量记忆**——如果库里 800 条里有 50 条是边缘 case，召回时可能命中低质量的
>
> 端到端测评集本身的短板：200 条偏小；目前主要覆盖金融经济三域，行为实验数据覆盖不足。
>
> 如果重做我会加：(1) TTL（30 天未召回的 SQL 降权）；(2) 召回后反馈闭环（被用户否决的 SQL 自动降权）；(3) 端到端集扩到 500–1000 条并补行为实验域。"

## 3. 推荐问题（内置 15% + 相似 11%）

> **本节主叙事（先背这四句）**
> 1. **反复查**主战场 = **行为实验开展期**的实验助理（兼职大学生 / 实习生），不是「所有研究员都不知道问什么」。
> 2. **相似推荐的产品意义** = 结果旁的**连续追问**：查完「未发报酬名单」→ 接着「预算花了多少 / 还剩多少 / 人均」或校准失败、样本结构——**不是输入联想**。
> 3. **金融经济（以绿色金融为例）** = **内置引导题**示范怎么开口，不是天天近重复。
> 4. 双通道共用记忆向量库；指标统一用**查询贡献率**（同分母）：内置 **15%**、相似 **11%**。

### 3.1 30 秒概括

> "推荐要拆场景。行为实验开展时，实验助理会反复问运维题——没发报酬有哪些人、校准失败要不要补招、场次结构、**实验预算花了/剩下/人均多少**。内置给 FAQ 清单；**相似推荐挂在查完结果旁，专门吃连续追问**（刚问完报酬名单，推预算/补招近邻），不是边输入边联想。绿色金融更偏探索，靠内置引导开口。贡献率同分母：内置 **15%**、相似 **11%**；和记忆复用共用 `memory_{agentId}`。"

### 3.2 真实问法样例（面试必背）

#### A. 行为实验 · 反复查（实验助理高频）

| # | 真实问法 | 业务含义 | 推荐怎么吃 |
|---|---------|---------|-----------|
| 1 | 「xxx 行为实验还没有发放实验报酬的人员有哪些」 | 发被试费清单 | 内置 FAQ + 相似近邻（换实验名） |
| 2 | 「注意力校准失败的被试有多少」 | **要补招被试**的信号 | 问完报酬常被相似推出 |
| 3 | 「xxx 行为实验现在所有场次中的男女比例是多少？男性中风险态度是厌恶风险的比例是多少」 | 样本结构 / 量表交叉 | 复合问法，适合固化进内置或被相似召回 |
| 4 | 「xxx 行为实验已经花费多少预算 / 还剩多少 / 人均多少」 | 实验经费进度 | **连续追问**：刚查完未发报酬名单 → 相似常推预算类 |

**连续追问（产品金句，相似通道核心价值）**：

> "相似推荐吃的是『查完 A 还要问 B』，不是『开始输入时联想』。例：刚问『信任博弈还没发报酬的人有哪些』→ 助理下一步常问『这笔实验花了多少 / 还剩多少 / 人均多少』，或校准失败人数、场次男女比×厌恶风险——都在**同一实验运维清单**上。记忆库里有过成功问法，向量近邻摊在结果旁，点一下继续查，**不用重新组织自然语言**。"

**面试金句**：

> "这些不是博导闲聊，是**实验助理排班时的刚需与连续追问**。骨架固定，变的是实验名、场次、人——所以相似推荐在行为 Agent、实验实施周特别值钱。"

#### B. 绿色金融 · 引导题（内置示范开口）

| # | 内置引导例题 | 示范什么 |
|---|-------------|---------|
| 1 | 「绿色金融改革试验区地级市 2010–2020 年碳排放、GDP、第二产业占比面板」 | 政策试点 × 面板口径 |
| 2 | 「A 股公司按 ESG 评级分组的平均 ROA / Tobin's Q，区分国企与非国企」 | ESG × 财务 × 所有制异质 |
| 3 | 「试点碳交易省市的碳配额成交均价与当地 AQI / PM2.5 的年度关系」 | 碳市场 × 环境指标 |
| 4 | 「绿色信贷余额占比最高的前 10 个省份，及其绿色债券发行只数」 | 绿贷 / 绿债区域对比 |

**面试金句**：

> "绿色金融侧不是助理每天换个省名重问一遍，而是**第一次不知道自然语言怎么起头**——内置题是研究开口模板，点下去走完整问数链路。"

### 3.3 功能实现类问题

**Q：为什么要做推荐问题？是用户反馈，还是看 ELK 发现的？**

> "**两边都有，但必须拆场景——别说成全站统一痛点。**
>
> **主场景：行为科学 · 实验开展期（反复查 + 连续追问）**
> - 谁在问：**实验助理**（兼职大学生、实习生）
> - 反馈：天天查报酬 / 校准 / 场次 / **预算**，问法骨架差不多，且**查完 A 还要连着问 B**（真实问法与追问链见 §3.2-A）
> - 实验实施约 4 周、数据 T+1，助理**高频、短间隔、换实体**
> - ELK：行为实验域约占全量 **~45%**，被试管理类近重复扎堆
>
> **次场景：绿色金融等金融经济研究（引导）**
> - 实证题一次一问、换假设就换结构，**不像实验运维那样近重复扎堆**
> - 痛点：『这套库自然语言怎么起头才问得出面板』→ **内置引导题**（§3.2-B）
>
> **结论**：相似 ← 行为**连续追问**；内置 ← 绿色金融**引导** + 行为运维 FAQ。"

**Q：相似推荐的产品意义是什么？是不是有助于连续追问？**

> "**对——相似的主价值就是结果旁的连续追问，不是输入联想，也不是替代内置开口。**
>
> **分工**：
> | 通道 | 解决哪一段 | 典型行为实验例子 |
> |------|-----------|-----------------|
> | 内置 | 还没开口 / FAQ 清单 | 进门就能点『未发报酬有哪些人』 |
> | **相似** | **刚查完一题，下一跳问什么** | 刚查完未发报酬 → 推『预算花了/剩下/人均』『校准失败多少人』『男女比×厌恶风险』 |
>
> **为什么挂在 parse 之后**：产品语义是『基于你刚问的那句，摊开历史上成功的近邻题』；技术上 `QueryRecommendProcessor` 用本轮 `queryText` 异步召回，结果区展开再读——时机和『查完还要追问』对齐。
>
> **条件（诚实）**：记忆库里要有过这些成功问法且向量够近才会出现；不是工作流引擎硬编码下一步，是**用历史成功题当下一跳**。
>
> **一句话**：内置教怎么开口；相似让助理在同一实验运维清单上**连着点下去**。"

**Q：数据埋点怎么设计的？15% / 11% 怎么算？**

> "**B 端不主报曝光点击率——两条通道统一成『查询贡献率』，分母都是总查询次数。**
>
> 每次真正提交问数打一条 `query_submit`，带归因字段 `source`：
>
> | `source` | 含义 |
> |----------|------|
> | `manual` | 手打提交 |
> | `preset` | 点**内置推荐**触发的查询 |
> | `similar` | 点**相似推荐**触发的查询 |
>
> | 指标 | 公式 | 简历值 | 日均 150 次时约 |
> |------|------|--------|----------------|
> | **内置贡献率** | `count(source=preset)` / `count(全部 query_submit)` | **15%** | ~23 次 |
> | **相似贡献率** | `count(source=similar)` / `count(全部 query_submit)` | **11%** | ~17 次 |
> | （对照）手打占比 | `count(source=manual)` / 全部 | ~74% | ~110 次 |
>
> **为什么不用 impression CTR**：这是实验室内部 B 端工具，关心的是『有多少查询真的从推荐进来』，不是资讯流式的『看了多少次点了多少次』。只看了推荐没提交，**不进这两个贡献率的分子，也不单独当主 KPI**（最多工程上留 version 防异步错挂，不进简历数字）。
>
> **加分**：11% 叙事抬**行为实验周·助理**；15% 叙事抬**绿色金融点引导题**。两数可同框横比（同分母），加起来约 **26%** 查询来自推荐。
>
> **注意**：`source` 必填，否则手打和点推荐分不清。"

**Q：整个作用链条是怎样的？**

> "两条链，汇合都是『点推荐 → 当新 query 再走 parse/execute』。
>
> **A. 内置（引导 + FAQ）**——进门就能看，**不依赖当前输入**
>
> ```
> 管理员按 Agent 配 Top-N（绿色引导题 / 行为运维 FAQ）
>   → 打开问数页拉内置列表 → 点击 → 当作新 query 提交（source=preset）
> ```
>
> **B. 相似——不是『开始输入时』召回，而是『本轮 query 已经提交、进入 Parse 之后』异步召回**
>
> ```
> 用户提交本轮问数（手打或点推荐）
>         │
>         ▼
> ChatQueryServiceImpl.parse()
>   ├─【同步】ChatQueryParser 做 SchemaMapper / S2SQL…
>   └─【Parse 结束后】ParseResultProcessor 链
>         └─ QueryRecommendProcessor.process()
>               └─ CompletableFuture.runAsync {   // 不堵 parse 返回
>                     ExemplarService.recallExemplars(
>                       memory_{agentId}, 本轮 queryText, topK=5)
>                     → 只取 question 文案
>                     → 写入该 queryId 的 ChatQueryDO.similarQueries
>                  }
>         │
>         ▼
> 前端结果区出现「推荐相似问题」；展开时若列表还空，
> GET /chat/manage/getChatQuery/{queryId} 再读库（等异步写完）
>         │
>         ▼ 用户点击某条
> 当作新 query 再走 parse（source=similar）
> ```
>
> **和记忆复用**：同一 `memory_{agentId}`；记忆在 Parser **同步**注入 SQL 四元组，相似在 Parse 后**异步**只给人看 question。
>
> **别和输入联想混淆**：输入框边打边出的联想是另一套 search/recommend，不是这条相似推荐。
>
> **一句话**：绿色内置 = 进门引导；行为相似 = **查完报酬名单后推预算/补招等连续追问**，**不是按键输入触发**。"

**Q：为什么两个通道？一个不行吗？**

> - **内置**：绿色金融要引导开口；行为要运维 FAQ——不依赖『当前刚问了什么』
> - **相似**：吃『查完 A 还要问 B』——助理问完未发报酬，立刻推预算花了多少、校准失败、样本结构最自然
>
> 只有内置盖不住换实验名 + 连续追问长尾；只有相似则第一次开口缺示范。**互补，权重不同**。"

**Q：这两个通道是同一个向量库吗？**

> "是，`memory_{agentId}`。相似只要 question、异步、容错；记忆复用整四元组进 Parser、同步、精度优先。简历拆两个模块：准确率 vs 提问体验（引导 + 少打字）。"

### 3.4 指标类问题

**Q：15% 和 11% 再强调一次？分域怎么讲？**

> - **同一套口径**：分母都是总 `query_submit`；分子分别是 `preset` / `similar`
> - **15%**：内置贡献——绿色引导题 + 行为 FAQ
> - **11%**：相似贡献——实验期近邻被点进去查的占比
> - 同分母，**可以横比、可以相加**（约 26% 来自推荐）；分域叙事仍是：**行为抬相似 11%**，**绿色金融抬内置 15%**
> - 诚实：简历是全站汇总；实验周切片若追问，可答分析时看过、日常看板未必按周拆

**Q：怎么证明推荐真帮到实验助理，而不只是占比好看？**

> "贡献率只说明『从推荐入口进来的查询占比』。更深一层：对这些 `source=similar|preset` 的 query 看执行成功率，以及同骨架手打是否下降（规范化 queryText 后的近重复率）。现状主报两个贡献率（§3.5）；『证明少打字』还可以做更深。"

### 3.5 诚实边界

> "1. 主 KPI 已统一为查询贡献率（B 端合理）；更深的『少打字 / 引导后首问成功率』还没系统做
> 2. 全站 15%/11%，**按 Agent / 实验周切片**不够系统
> 3. 还没严肃 A/B
> 4. 绿色内置多样性；引导例题若与线上清单有出入以当时配置为准
>
> 若重做：`source` + `agentId` 分开验收『助理少打字 / 绿色被引导』。"

## 4. 深度研究（GAIA-165 53%，双层解读）

### 4.1 30 秒概括

> "查到数据后有两种解读：默认的描述性解读（<2s，结构化摘要 + 关键指标解释）和可选的深度研究（多步联网交叉验证 + 归因分析，失败静默回退）。深度研究用 Main-Sub Agent 编排，在 GAIA-165 评测集上做到 53%（SOTA 80%）。"

### 4.2 功能实现类问题

**Q：为什么做双层解读？统一做深度研究不行吗？**

> "三个原因：
> 1. **延迟差异巨大**——描述性解读只需总结已有数据，深度研究还要多步搜索、工具调用和交叉验证，链路明显更长；具体耗时见[深度研究准备文档](三、深度研究-面试准备.md) §0.3/§4：n=3 可观测下界，临时超时 11 分钟，非正式 SLA
> 2. **失败率不同**——描述性解读几乎不失败（就是 LLM 总结已有数据）；深度研究依赖联网搜索 + 工具调用，失败率更高
> 3. **用户需求分层**——有些查询只需要看到数据，有些还需要理解原因，因此把描述性解读作为默认能力、深度研究作为按需能力
>
> 所以产品决策是：**默认走快的，可选走深的，深的失败静默回退**——永远不让深度研究阻断查数主链路。"

**Q：Main-Sub Agent 编排是什么？为什么这样设计？**

> "深度研究需要**多步推理**（比如'比亚迪 2024 年净利润变化的原因'需要：查财务数据 → 查行业对比 → 查政策变化 → 综合归因）。单 Agent 做多步推理有个致命问题——**上下文膨胀**（每一步的中间结果都塞进同一个 context，很快撑爆 LLM 窗口）。
>
> Main-Sub 设计：
> - **主 Agent**：任务拆解 + 结论汇总（轻量，不做事）
> - **子 Agent**：每个子任务一个独立会话，并发执行，**互看不到对方的上下文**
> - 子 Agent 回传**结构化报告**（不是原始数据），主 Agent 汇总
>
> 这样上下文是隔离的——每个子 Agent 的 context 只有自己的任务，不会膨胀。"

**Q：53% vs SOTA 80%，差距在哪？**

> "差距主要在 **Level 3（复杂多步推理）**——我们 19%，SOTA 约 60%+。典型失败 case：
> - 需要 5+ 步工具调用的任务，中间任何一步失败就全链失败
> - 需要跨多个信息源交叉验证的任务（如'对比 A 公司和 B 公司的 ESG 评级差异原因'）
>
> Level 1（简单问答）我们 68%，接近可用水平。**差距集中在多步推理——这是 Agent 方向的业界共性挑战**。"

### 4.3 指标类问题

**Q：GAIA-165 是什么？为什么选这个评测集？**

> "GAIA 是 General AI Assistants benchmark（Meta 发布），165 道题。选它因为：
> 1. **业界对标**——GAIA leaderboard 上第一名 h2oGPTe 是 80%，我们 53% 有明确的参照系
> 2. **分 Level**——Level 1/2/3 难度递增，能看到我们在哪个难度上掉链子
> 3. **任务类型多样**——不只是问答，还有多步推理、工具调用、网页浏览
>
> 53% 在一个单人、业余时间做的系统里是一个**真实的位置**——不是 SOTA，但也不差。"

**Q：MCP 工具调用 98% 成功率怎么测的？**

> "从 ELK 日志统计：
> - 分子：成功完成的工具调用次数（返回了有效结果）
> - 分母：总工具调用次数
> - 2% 失败原因：联网搜索超时、知识库 RAG 召回为空、网页解析失败
> - 降级链：工具失败 → 尝试备选工具 → 如果全失败，深度研究标记为'部分完成'，仍输出已有结论"

**Q：深度研究的失败率是多少？怎么处理？**

> "失败率需要基于统一评测口径和实际运行日志统计，当前不报未经实测的数字，详见[深度研究准备文档](三、深度研究-面试准备.md)。处理方式：
> - **静默回退**到描述性解读——用户看到的是基础解读，不会感知到深度研究失败
> - 在 ELK 里记录失败原因（超时/工具失败/推理错误），周期性回扫优化
>
> 产品决策是：**宁可降级也不报错**——内部系统用户不需要看到'深度研究失败'的红色提示，只需要拿到能用的答案。"

### 4.4 诚实边界

> "深度研究是这个项目里我最不满意的模块——53% 对 SOTA 80% 差距大。但它的价值不在绝对数字，在于：
> 1. **跑通了完整链路**（任务拆解 → 并发执行 → 汇总 → 归因）
> 2. **工程化做扎实了**（断点续跑、熔断限流、全链路追踪）
> 3. **有明确的改进路线**（多步推理的规划能力、工具调用的鲁棒性）
>
> 如果重做我会：换更强的 reasoning 模型、优化子 Agent 的任务分配策略、加 self-correction 机制。"

## 5. 高频通用问题速查

### Q：这个项目最大的挑战是什么？

> "**准确率 vs 延迟 / Token 成本**。问数主链里 LLM 可能出现在：Schema 消歧、S2SQL 生成、结果解读；记忆还有定时 Review。模型 **deepseek-v4-pro**，定价按 **输入 ¥0.025/百万、输出 ¥6/百万**——输出贵 **240 倍**，所以控成本关键是**压输出长度**（结构化短答、解读要 brief），其次才是 Few-shot 条数。"

### Q：一次查询消耗多少 token？一天多少钱？（deepseek-v4-pro：输入 0.025 / 输出 6）

> "**先对齐代码调用链，再拆输入/输出算钱——输出单价是输入的 240 倍，费用几乎全在 completion。**
>
> #### 0）调用链（读代码后的结论）
>
> ```
> parse
>   ├─ 规则 STRICT/MODERATE 出候选（无 LLM）
>   ├─ [可选] EmbeddingMatchStrategy LLM filter  ← Schema 消歧
>   ├─ [可选] rewriteMultiTurn                 ← 默认 ChatApp enable=false
>   ├─ ★ OnePassSCSqlGenStrategy               ← S2SQL，few-shot=5，self-consistency=1 → 通常 1 次
>   ├─ LLMSqlCorrector                         ← 默认 enable=false
>   └─ QueryRecommendProcessor                 ← 仅向量召回，无 LLM
> execute
>   └─ DataInterpretProcessor                  ← 描述性解读，ChatApp 默认 enable=false；Data Agent 打开
> 定时
>   └─ MemoryReviewTask @60s                   ← 默认 enable=false；Data Agent 打开后审 PENDING
> ```
>
> - **开源默认「一次成功问数」**：多数时候 **只有 S2SQL 1 次 LLM**（规则已带上 selectedParse 时常跳过 Mapping）。
> - **简历 / Data Agent 生产叙事**（Schema 消歧 + 解读 + 记忆审都打开）：按下面「全开」表估。
>
> #### 1）分环节：输入 / 输出拆开（估算，prompt+completion）
>
> | 环节 | 代码 | 输入 token | 输出 token | 单次费用（元） | 费用结构 |
> |------|------|-----------|-----------|---------------|---------|
> | Schema 消歧 | `EmbeddingMatchStrategy` LLM filter | **~2.0k** | **~80**（ID JSON） | **≈0.00053** | 输出虽短，但仍占大半（¥6） |
> | **S2SQL 生成** | `OnePassSCSqlGenStrategy` | **~6.0k**（模板+**5 条**范文+本轮 schema） | **~250**（thought+SQL） | **≈0.00165** | 输入大、输出短；费用仍主要在输出 |
> | 描述性解读 | `DataInterpretProcessor` | **~1.5k**（Question+结果表文本） | **~400**（自然语言摘要） | **≈0.00244** | **输出最长 → 单次最贵** |
> | 多轮改写 | `rewriteMultiTurn` | ~2.0k | ~40 | ≈0.00029 | 可选；多数 query 为 0 |
> | Corrector | `LLMSqlCorrector` | — | — | **0** | 默认关 |
> | 相似推荐 | `QueryRecommendProcessor` | 0 | 0 | **0** | 无 LLM |
>
> **公式**：`费用 = 输入/10⁶×0.025 + 输出/10⁶×6`
>
> **Data Agent 全开、无改写（中位）**：
> - Token：输入 **9.5k** + 输出 **0.73k** ≈ **合计 ~10.2k**
> - 费用：≈ **¥0.0046 / 次**
> - 其中输出贡献约 **95%**（0.00438 / 0.00462）
>
> #### 2）记忆定时 Review
>
> | 项 | 值 |
> |----|-----|
> | 代码 | `MemoryReviewTask`，60s 轮询，只审未 LLM/人审的 PENDING |
> | 单条 | 输入 **~1.2k**，输出 **~60**（`opinion=…,comment=…`）→ **≈¥0.00039/条** |
> | 日量 | ~10–15 条（对应月增 ~200 ENABLED、过审率 ~50–60%） |
> | **日费用** | 12×0.00039 ≈ **¥0.005/天**（可忽略） |
>
> #### 3）一天 150 次（全开叙事）
>
> | 项 | 输入 token | 输出 token | 费用 |
> |----|-----------|-----------|------|
> | 查询 150×(9.5k / 0.73k) | **142.5 万** | **10.95 万** | 142.5×0.025 + 10.95×6 = **3.56 + 65.7 ≈ ¥0.69** |
> | 记忆 Review | ~1.4 万 | ~0.07 万 | **≈ ¥0.005** |
> | **合计** | **~144 万** | **~11 万** | **≈ ¥0.70 / 天**（约 **¥21 / 月**） |
>
> **对照：若仅开 S2SQL（开源默认成功路径）**
> 150×(6.0k 入 / 0.25k 出) → 日费用 ≈ **¥0.25**（约 **¥7.5 / 月**）。
>
> #### 4）30 秒口述
>
> 「deepseek-v4-pro，输入百万 2 分 5、输出百万 6 块。一次问数输入大概九千五、输出七百多，钱几乎全花在输出上——尤其结果解读会写几百字。一天 150 次全开大约七毛钱；如果只跑 S2SQL 大概两毛五。记忆定时审一天几厘钱。」
>
> #### 5）诚实边界
>
> 1. Token 是按 prompt 模板 + 5-shot schema 长度**估算**，不是 tokenizer 逐票计量；字段多/结果表大时输入会涨。
> 2. 你给的 **输入 0.025** 对应官方 **缓存命中**档；若大量 **cache miss（官方约 ¥3/百万输入）**，输入成本会升两个数量级，但通常仍低于输出项。
> 3. 深度研究另计，不进这 150 次账单。"

### Q：你最大的收获是什么？

> "**用数字迭代**的方法论。在来之前我以为做 AI 就是'调 prompt'，来了之后发现：SchemaMapper / 记忆库每次改动都要用固定测评集看涨跌——从'凭感觉'变成'看数字'。这个思维方式跟 TDD 一脉相承。"

### Q：团队怎么协作的？

> "5 人正式团队 + 我 1 个实习生。组长（资深后端）负责架构决策和核心代码，我负责智能问数的体验优化模块。协作模式：
> - **每周 2-3 次迭代**——我改完跑评测，数字达标了提交 code review
> - **遇到选型问题先写方案文档**（如 pgvector 选型、DataSet 建模），组长审批后才动手
> - **线上 bug 通过 ELK 排查**——日志在 Kibana 里按 traceId 串联看完整链路"

### Q：如果重新做你会怎么改？

> "四个遗憾（诚实清单）：
> 1. **多轮对话改写深度不够**——只取最近 1 轮，改写后走单轮解析。应该实现真正的上下文继承
> 2. **权限粒度粗**——所有注册用户看所有表。应该做表级权限
> 3. **评测集规模小**——200 条不够，应该扩到 1000 条
> 4. **记忆库没有淘汰机制**——只进不出，长期会有过时 SQL"

### Q：这个项目的商业价值是什么？

> "对实验室来说，降低了研究员的数据使用门槛——**从'等 DBA 1-2 天排队取数'到'15 秒自助查询'**。按日均 150 次查询、每次节约 1 天等待时间算，每天节约 ~150 人天的等待。对类似科研机构/高校的可复制性很高——任何有'大量非技术研究员 + 复杂数据库'的场景都适用。"

### Q：为什么选这个实习？和你未来的方向有什么关系？

> "[个人方向题，按实际回答。建议从'AI 落地'、'数据民主化'、'Agent 方向'切入——这些是当前行业热点，且跟你做的 Data Agent 直接相关]"

### Q：你觉得自己最大的优势是什么？

> "**在技术和产品之间做翻译**。我的角色不是纯写代码——我要理解研究员的痛点（产品思维）、设计解决方案（架构思维）、用评测验证效果（数据思维）。这种跨领域能力让我能独立负责一个完整模块，而不是只做螺丝钉。"
