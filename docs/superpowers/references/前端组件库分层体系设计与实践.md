在中后台（ToB）业务研发中，组件库不仅是 UI 复用的基础设施，更是工程效率与系统稳定性的核心支撑。随着业务复杂度提升，单一组件库难以同时兼顾“稳定性、易用性与场景复用”，因此需要通过 分层体系设计 来解耦职责。  
本文基于一个在大厂内典型的组件体系实践，总结一套可落地的前端组件库分层方案，解决前端初学者对组件库类型不清晰的一个状态。  
整体分层设计思路  
该体系本质是一个“能力逐层抽象”的结构：  
● 基础组件层 ：解决“稳定性”问题（底层能力）  
● 业务组件层 ：解决“易用性”问题（业务封装）  
● 场景模板层 ：解决“开箱即用”问题（页面级复用）  
● 工具层 ：解决“研发效率与规范”问题（工程化支撑）  
核心思想可以总结为一句话：  
基础组件保证不出错，业务组件保证好用，场景模板保证能直接用。  
基础组件层：稳定性优先的设计基石  
1\. 职责定位  
基础组件层面向最底层 UI 能力，主要包括：  
● PC 基础组件（表格、表单等）  
● H5 基础组件（列表、表单等）  
● 可视化组件（图表、流程、组织结构等）  
其核心目标不是“功能多”，而是“ 长期稳定 ”。  
2\. 设计原则（重点）  
（1）API 一旦发布，不可破坏  
● 正式版本发布后，不允许删除或修改已有 API  
● 所有 API 在设计阶段必须“克制”  
● 不确定的能力，一律不提供  
本质是在做“接口冻结”，避免业务侧频繁适配。  
（2）优先采用受控组件设计  
● 所有状态尽量由外部控制（value / onChange）  
● 避免组件内部复杂状态机  
好处：  
● 行为可预测  
● 易于调试  
● 降低组件复杂度  
（3）单一用法原则  
● 一个组件只提供“最标准的一种用法”  
● 不做过度扩展（例如：同一个组件支持多种模式）  
这样可以：  
● 降低维护成本  
● 提高一致性  
● 避免分支逻辑膨胀  
3\. 版本策略  
基础组件应长期维持在：  
● 主版本稳定（1.x）  
● 禁止频繁 breaking change  
这是中后台组件库和 ToC UI 库的一个关键区别。  
业务组件层：易用性与业务抽象  
1\. 职责定位  
业务组件层是对基础组件的 二次封装 ，主要特点：  
● 面向具体业务场景  
● 提供更高层抽象能力  
● 降低业务开发复杂度  
可以理解为：  
基础组件 = 原材料 业务组件 = 半成品  
2\. 典型分类  
（1）通用业务组件（PC / H5）  
● 表单增强组件（复杂校验、联动逻辑）  
● 列表查询组件（筛选 + 表格组合）  
● 审批流组件等  
（2）可视化业务组件  
● 报表组件  
● 图表组合组件  
● 流程可视化封装  
（3）领域组件（按业务域拆分）  
例如：  
● 招聘域组件  
● 薪酬域组件  
● 财务域组件  
这些组件通常具备明显的领域特征。  
3\. 设计核心  
业务组件层的目标是：  
● 提升开发效率  
● 减少重复造轮子  
● 统一业务交互模式  
与基础组件的关系可以总结为：  
基础组件解决“能不能用” 业务组件解决“好不好用”  
场景模板层：从组件到页面的跃迁  
1\. 职责定位  
场景模板层是将业务组件进一步组合，形成：  
● 页面级模板  
● 系统级骨架  
● 标准业务流程  
它解决的问题是：  
不只是组件复用，而是“页面结构复用”。  
2\. 覆盖典型场景  
（1）通用后台场景  
● 列表页（筛选 + 表格）  
● 详情页（信息展示 + 操作）  
● 表单页（新增 / 编辑）  
● 审批流页面  
（2）系统级结构  
● 布局框架（导航、侧边栏）  
● 权限结构  
● 路由组织  
（3）富交互场景  
● 组织架构图  
● 流程图  
● 报表分析页面  
3\. 核心价值  
● 新项目可以“快速起步”  
● 保证 UI / 交互一致性  
● 降低设计与开发沟通成本  
本质是把“最佳实践产品化”。  
工具层：工程化与生态能力  
工具层不直接参与 UI 渲染，但决定整体研发效率。  
1\. 基础工具库  
职责：  
● 统一三方依赖（如工具函数库、时间库、请求库）  
● 收敛版本，避免重复依赖  
● 提供通用能力：  
○ 请求封装  
○ 错误处理  
○ 时间格式化  
○ 文件处理等  
2\. 脚手架工具  
能力包括：  
● 项目初始化  
● 本地开发服务  
● 构建能力（本地 / 线上）  
● Mock 数据代理  
设计原则：  
● 功能精简  
● 覆盖核心研发流程即可  
3\. API 类型生成工具  
● 将接口文档自动转换为 TypeScript 类型  
● 与接口管理平台打通  
价值：  
● 提升类型安全  
● 减少手写类型成本  
● 降低前后端联调错误  
4\. 设计与开发协同工具  
（1）设计侧插件  
● 提供设计组件与模板  
● 支持从设计稿生成代码结构  
（2）开发侧插件  
● 模板代码快速引入  
● 自动补全与提示  
目标：  
打通设计 → 开发 → 交付链路  
总结：分层体系的本质价值  
这套体系的核心不是“多做几层封装”，而是明确边界：  
| 层级 | 核心目标 | 关键词 |
| --- | --- | --- |
| 基础组件 | 稳定性 | 不变 |
| 业务组件 | 易用性 | 好用 |
| 场景模板 | 复用性 | 开箱即用 |
| 工具层 | 效率 | 工程化 |最终形成一个闭环：  
● 基础组件保证质量  
● 业务组件提升效率  
● 场景模板加速交付  
● 工具体系提供支撑  
很多团队组件库做不起来，本质原因是：试图用“一层组件库”解决所有问题。  
而成熟体系一定是：分层 + 解耦 + 明确职责边界  
这也是中大型前端工程体系走向成熟的标志。
