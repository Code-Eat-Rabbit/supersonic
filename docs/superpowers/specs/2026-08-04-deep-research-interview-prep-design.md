> 日期：2026-08-04  
> 状态：待用户审查

---

## 1. 背景与目标

### 1.1 问题

候选人需深入准备 Data Agent 简历中的「问数结果深度研究」模块。已有题纲追问链与部分产品侧话术（`非技术面试-产品与指标准备.md` §4），但缺少与「业务背景」同款的、可按题复习的工程向准备文档；同时对 Agent 工程细节有遗忘，需要有目标的回看。

### 1.2 目标

1. 产出 `docs/resume/interview/三、深度研究-面试准备.md`，使 L1 主题能讲清工程细节并指向代码标本。
2. 统一职责与指标口径，消除与「业务背景」等文档的矛盾。
3. 采用「面试问题驱动 + 按需回看标本」学习，而非通读整个项目。

### 1.3 非目标

- 不写完整 30–40 分钟模拟面试脚本（题纲附录仍待各模块确认后串）。
- 不把 MiroFlow / 开源 SOTA 说成「我发明的」或主动做框架对比（多数面试官不关心 MiroFlow）。
- 不编造无法核对的运营数字（如失败回退率、连续回退后的用户行为分析）。
- 不在本规格范围内改 Data Agent / miro-flow 功能代码；耗时实测是准备流程中的一步。

## 2. 约束与叙事口径（L0）

### 2.1 职责与来源

| 项 | 口径 |
|----|------|
| Owner | 候选人从 0-1 搭建深度研究服务（工程 harness：编排运行时、工具接入、服务化、追踪与熔断） |
| 算法博士后 | 咨询角色：Prompt 调优建议、测评集选取与跑法——不主导实现 |
| 起源 | 业余参加阿里云 Research Agent 比赛 → 魔改接入 Data Agent（双层解读、与 Java 查数主链路对接、领域知识库） |
| 复习标本 | `miro-flow-solution`：用于把工程细节摸熟；面试不主动对比 MiroFlow |

### 2.2 产品定位（与简历对齐）

- **默认**：描述性解读（&lt;2s）——仅基于查数结果做结构化摘要与关键指标解释。
- **可选**：深度研究——多步联网交叉验证与归因；失败或超时则**静默回退**描述性解读，不阻断查数主链路。
- **触发**：用户主动选择（非默认全开）。
- **通信**：独立 Python 微服务 ↔ Java 主链路（REST；深度研究为异步长任务）。

### 2.3 硬指标

| 指标 | 取值 | 说明 |
|------|------|------|
| GAIA-165 | 整体 53%（L1 68% / L2 47% / L3 19%）；SOTA ~80% | 简历已写，保留 |
| MCP 工具调用成功率 | ~98% | 简历已写；实现时核对「成功」定义 |
| 超时上限 | **待实测后填入** | 与端到端耗时相关，不预设 120s |
| 端到端耗时 | **待实测后填入** | 跑典型任务后再定话术（通常多久 / 分位数） |
| 失败/回退率 | **不写入、不主动交代** | 被追问只讲机制：最终结果不可用 → 静默回退 |

描述性解读 &lt;2s、默认关闭深度研究——仍作产品对比，不依赖未验证的「平均 90s」。

### 2.4 诚实边界

- 53% 是有参照的真实位置；短板在 Level 3 多步推理。
- 价值在跑通链路 + 工程化（追踪 / 熔断 / 断点续跑 / 不挡主链路），不是算法创新。
- Prompt / 评测方法有博士后建议；服务实现是候选人 owner。

## 3. 方案选择

| 方案 | 描述 | 结论 |
|------|------|------|
| A. 先通读源码再答题 | 细节扎实但耗时、易散 | 不采用 |
| B. 纯题驱动不看代码 | 快但易与实现不一致 | 不采用 |
| C. 题驱动 + 按需回看标本 | 有目标复习，产出即面试文档 | **采用** |

交付物组织采用**分层准备**（非全量无差别题海、非对练脚本优先）：

- **L0**：事实库（一处定义）
- **L1**：必答深挖（第一句 + 要点 + 易踩坑 + 回看标本路径）
- **L2**：够用即可（骨架 + 1 例）

## 5. 交付物结构

### 5.1 主文件

路径：`docs/resume/interview/三、深度研究-面试准备.md`

建议目录：

1. 元信息 / L0 事实库  
2. 30 秒开场 + 宽问/锥问第一句  
3. L1 追问链（按 A→G）  
4. L2 速查  
5. 待实测回填清单（超时、端到端耗时）  
6. 与题纲/简历对照表  

体例对齐 `一、业务背景-面试准备.md`，深度按 L1/L2 区分。

### 5.2 跨文档同步

| 文档 | 动作 |
|------|------|
| `一、业务背景-面试准备.md` | 「博士后主导」→「候选人 0-1 owner + 博士后咨询」；深度研究耗时/失败率与 L0 对齐 |
| `非技术面试-产品与指标准备.md` §4 | 去掉或弱化「平均 90s」「失败率 15–20%」；机制话术保留 |
| `面试题纲.md` | 可选：第一句中的超时数字待实测后再改；实现前不强行改 |

### 5.3 错误处理与一致性

- 凡未实测的耗时/超时：文档中明确写「待实测」，答题话术用定性描述，不假装精确。
- 凡与旧文档冲突：以本规格 L0 为准，同步改旧文，避免面试时两套口径。
- MiroFlow 仅作标本：答题用「我当时的设计/实现」，需要类比时再说「这类系统里常见做法是…」。

## 6. 验证方式

| 检查项 | 通过标准 |
|--------|----------|
| L1 覆盖 | 题纲 §三 A–G 中 L1 主题均有第一句 + 要点 + 标本路径 |
| 口径一致 | 业务背景 / 非技术面试 / 新文档对职责与指标无矛盾 |
| 数字诚实 | 超时与耗时要么实测填入，要么标注待测；无失败回退率 |
| 学习可用 | 候选人可按 L1 题打开标本文件完成一轮复习 |

耗时实测：在标本或可用环境下跑若干典型深度研究任务，记录耗时分布与合理超时配置，写回 L0 与相关答题（具体命令与任务集在实现计划中给出）。

---

## 7. 成功标准

- 能按 L1 主题把工程细节讲圆，并指出对应代码位置（标本）。
- 口径与简历一致，且与业务背景不再互相矛盾。
- 耗时类数字要么实测填入，要么明确「待测」。
