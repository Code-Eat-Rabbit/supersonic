# SuperSonic 金融 NL2SQL 测评 — 面试文档

> 项目周期: 2天 | 角色: 独立完成 | 数据: 沪深300 × 5期年报 | 84题

---

## 一、一句话概括

为 SuperSonic 搭建了端到端金融 NL2SQL 测评管线，覆盖数据采集→语义建模→测试集生成→双模型跑批→多维度评分全流程。核心发现：**语义建模质量是 NL2SQL 准确率的天花板，LLM 选型在当前配置下无差异。**

---

## 二、为什么做这个项目

SuperSonic 作为 Chat BI 平台，其核心价值在于**语义层**——将自然语言映射为结构化查询。面试中必然被问：

1. "语义层到底值多少钱？" — 需要量化建模质量对准确率的影响
2. "哪个 LLM 最好？" — 需要真实数据而非直觉
3. "怎么评估 Text2SQL 系统？" — 需要展示方法论

这个项目用 84 道金融场景题目给出了可量化的答案。

## 三、技术架构

```
akShare API (东方财富)
  → fetch_data.py: 沪深300 × 5期年报, 3张表各1500行
  → SQLite 存储 (csi300.db)
  → build_semantic.py: Domain + 6 Model + Dataset + 2 Agent
  → SuperSonic 语义引擎:
       SchemaMapper (embedding) → NL→指标/维度映射
       SemanticParser (LLM)     → 生成 S2SQL
       Corrector (规则)         → SQL 修正校验
       Translator               → 物理 SQL
  → run_eval.py: 84题 × 2模型跑批, 增量保存
  → calc_accuracy.py + calc_semantic.py: 精确匹配 + 语义评分
  → report.py: 双模型对比报告
```

### 关键技术突破

| 挑战 | 方案 | 深度 |
|------|------|------|
| SuperSonic 源码不支持 SQLite | 修改 `EngineType` 枚举 + 添加 `sqlite-jdbc` 依赖 + Maven 重建 | Java 源码级修改 |
| langchain4j 类冲突 | 自定义 `OpenAiChatModel` 与官方 JAR 同名类冲突 → classpath 优先级调优 | JVM 类加载机制 |
| 语义层聚合错误 | v1: 5期SUM=加总(错误) → v2: WHERE最新期=每公司1行(SUM=值本身) | 语义建模方法论 |
| Gold 日期不匹配 | SQLite `2023-12-31 00:00:00` vs Gold `'2023-12-31'` → LIKE 通配修复 | 数据精度处理 |
| 跑批输出缓冲丢失 | 后台 Python 无输出 → `-u` 标志 + 逐题增量保存 | 工程健壮性 |

## 四、核心发现

### 发现一: 语义建模是准确率天花板

| | DuSQL (Demo) | CSI300 v1 | CSI300 v2 |
|------|-------------|-----------|-----------|
| 建模方式 | 默认聚合 | 3 Model 全期 | 6 Model 最新期+全期 |
| 每实体行数 | 1 行 | 5 行 | 1 行 |
| SUM 语义 | = 值本身 | = 5期加总(错误) | = 值本身 |
| 对标 DuSQL | — | ❌ | ✅ |

**根因:** 同一个 `净利润` 指标在不同问题中语义不同——"茅台ROE"需要最新期值，"连续3年增长"需要全部5期。单个 Model 无法同时满足。

**解法:** 分层建模——按时间粒度拆分为"最新期 Model"和"全期 Model"，前者对标 DuSQL 的标量查询，后者支撑同比分析。

### 发现二: LLM 选型在当前配置下无差异

| 对比维度 | qwen3.7-plus | deepseek-v4-pro |
|---------|-------------|-----------------|
| SQL 输出 | 100% 一致 (84/84) | 100% 一致 (84/84) |
| 解析评分 | 14位小数完全一致 | — |
| 可用率 | 100% | 100% |
| 平均延迟 | ~3300ms | ~3200ms |

**根因:** SuperSonic 的 SchemaMapper 使用 embedding 检索（不调 LLM），Parser 在 `temperature=0` 下确定性输出。LLM 只参与自一致性评分环节，且 `self_consistency number=1` 时不重采样。

**结论:** 对于结构清晰的语义模型，选便宜的模型即可。LLM 差异只在以下场景体现:
- 复杂语义模型（几十个指标需 LLM 推理选择）
- 模糊 NL 问题（需消歧，如"表现最好的公司"）
- 增大 self_consistency number（多次采样看一致性）

### 发现三: 两种评分方法的适用场景

| 评分方法 | 手写 SQL | NL2SQL 风格 |
|---------|---------|------------|
| 精确匹配 | 26% | 100% |
| 语义评分 (5维) | 26% | 100% |
| 适用场景 | 评估系统整体能力 | 评估语义层一致性 |

手写 SQL 评分反映"人想表达的"和"系统能生成的"之间的差距，NL2SQL 评分反映系统的一致性。

## 六、方法论沉淀

### 语义层治理原则

1. **一个 Model 一个粒度** — 不要在一个 Model 里混不同时间粒度
2. **SUM 语义要自洽** — 每个公司的行数=1 时 SUM=值本身，>1 时需要最新期过滤
3. **维度值字典是关键** — 没有 `stock_name='贵州茅台'` 的字典值，就无法按公司过滤
4. **先治理后测评** — 语义模型质量决定了准确率上限

### 分层建模模板

```
最新期 Model: WHERE report_date = (SELECT MAX(...) FROM table)
  → 每个公司 1 行 → 标量查询 ("茅台ROE", "利润最高5家")
  → 衍生指标 (ROE/ROA) 可直接在语义层定义

全期 Model: 不带 WHERE
  → 每个公司 5 行 → 同比分析 ("连续3年增长")
  → 需窗口函数/自关联
```
