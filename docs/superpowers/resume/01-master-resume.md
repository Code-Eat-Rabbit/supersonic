## 简历 Bullets（精简版）

### 语义层建模引擎（SchemaMapper LLM 增强）

> 为 SchemaMapper 引入 LLM Filter 机制：在 HanLP 分词 + BGE embedding 粗排召回候选字段后，由 LLM 对候选做语义消歧精选；通过三步变量隔离实验将映射准确率从 52% 提升至 91%，剩余 9% 顽固 case 完成归因分析并制定改进路线

### Agent 记忆管理系统

> 设计 Agent 记忆管理系统：成功执行的 LLM 生成 SQL 自动存入 Memory 向量库，作为 Few-shot 样本注入后续 NL2SQL 的 prompt 中；引入 LLM 定期自动评审 + 人工审核双机制，实现记忆库的持续质量管控

### 数据结果解读增强

> 在 LLM 基础总结之上，接入联网搜索与业务知识库 RAG 服务，使解读结果不仅描述数据本身，还能关联外部信息（市场动态、业务背景），提升解读的深度和可信度

### 相似问题推荐

> 设计基于 embedding 向量检索的相似问题推荐系统：用户提问后异步检索历史成功问答并写入数据库，前端懒加载展示；实现 Agent 级 Memory 隔离与 LLM 自动审核机制

## 30 秒概括

"我在 SuperSonic Chat-BI 项目中负责 NLP 到 SQL 的链路优化和智能化增强。核心工作分四块：第一，为 SchemaMapper 引入 LLM Filter 做语义消歧，通过变量隔离实验把 NL→语义元素的映射准确率从 52% 提到 91%。第二，设计了 Agent 记忆管理系统，让每次成功的 SQL 自动沉淀为 Few-shot 样本，有 LLM 自动评审+人工审核的质量管控。第三，正在增强结果解读——接入搜索和知识库 RAG，让 LLM 不只是总结数据，还能关联外部信息做深度解读。第四，相似问题推荐系统，用户问完一个问题后自动推荐相关的历史成功问题。"

## 10 个高频问题速查

### 1. 为什么需要语义层而不直接 Text2SQL？

> 直接 Text2SQL 依赖表名/列名硬匹配——"客单价"需要 LLM 同时理解业务含义和表结构。语义层把 JOIN 逻辑、聚合公式、字段别名在确定性引擎中处理，LLM 只需要做"NL→语义元素ID"的映射，显著降低幻觉和复杂度。

### 2. Memory 状态机为什么设计 PENDING 状态？

> 写入立即生效有两个风险：SQL schema 过期（表结构变更后旧 SQL 失效）和 LLM 生成语义错误（语法对但意图错）。PENDING 作为审核关卡，用 LLM 自动评审 + 人工兜底做质量管控。

### 3. SchemaMapper 的 52%→91% 是怎么验证的？

> 自建 100 题金融场景测评集，gold 格式是 element ID 列表。评分：精确匹配（ID Jaccard，40%）+ LLM-as-Judge（五维语义评估，60%）。Judge 与被测 SchemaMapper 解耦（deepseek 做 Mapper，qwen-turbo 做 Judge）。

### 4. 为什么只测 SchemaMapper 而不是端到端？

> Parser/Corrector/Translator 是确定性管道——不纠正映射错误。Mapper 错了全链错。端到端测评无法区分"Mapper 错了"和"Parser 错了"——聚焦 Mapper 能精确归因。

### 5. 变量隔离在你的改进中怎么体现？

> Phase 1 只改 prompt、Phase 2 只改语义模型、Phase 3 只加 memory。如果同时改，你看不到提示词贡献了多少、治理贡献了多少，无法制定正确的下一步策略。

### 6. 结果解读的搜索和 RAG 是同步的还是异步的？

> 同步。因为需要等搜索和 RAG 结果回来才能交给 LLM 做最终聚合——如果异步，LLM 聚合需要等回调，复杂度上升而没有实际收益（整个解读过程本来就比 SQL 执行快得多）。

### 7. 相似问题推荐和 Memory Few-shot 是什么关系？

> 共用同一套向量库（agent_memory_{id}），但用途不同：相似问题只取 question 文本展示给用户，Memory Few-shot 取完整的 (question, s2sql, schema) 注入 LLM prompt。一个面向用户，一个面向 LLM。

### 8. 这四个模块之间有什么依赖关系？

> 结果解读增强的搜索和 RAG 部分独立运行，不依赖其他模块。相似问题推荐和 Memory 共用向量库但不互相依赖。语义层是底层基础设施，其他模块都建立在其之上。
